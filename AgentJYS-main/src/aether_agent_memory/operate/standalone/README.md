# Operate 独立演示：内存 P2 Mock

独立实现位于 `operate/standalone`。参考旧项目的热度、缓冲区和对账方案，重新实现不依赖公共 runtime 的运行路径。原来的 `operate/basic`、其他旧 Operate 实现、runtime、Remember、Recall 和项目启动入口均未修改。

这套代码可以直接运行，但原项目的服务入口不会自动切换到它。这里没有网页演示台，不需要 Redis、SQLite、模型服务或真实 P2。演示使用 Python 标准库。

## 1. 怎么运行

在 PowerShell 中执行（建议使用项目要求的 Python 3.13）：

```powershell
Set-Location 'D:\codex项目\捷运盛\AgentJYS-GitHub-20260924\AgentJYS-main'
$env:PYTHONPATH = Join-Path (Get-Location) 'src'
python -B -m aether_agent_memory.operate.standalone --scenario all
```

如果电脑没有配置 `python` 命令，可将上面的 `python` 换成已安装 Python 的完整路径。此次验证使用的是：

```powershell
& 'D:\codex项目\.agent-work\aether\workspace-support\operate-venv\Scripts\python.exe' -B -m aether_agent_memory.operate.standalone --scenario all
```

只看某个场景，例如提交响应丢失：

```powershell
python -B -m aether_agent_memory.operate.standalone --scenario lost_response
```

运行新实现的验证：

```powershell
python -B -m aether_agent_memory.operate.standalone.test_standalone
```

演示推进的是模拟时间。例如“600 秒后”会立即推进，不需要真的等待十分钟。每个场景使用全新的内存状态。成功时输出“场景检查：通过”；结果不符合预期时会报错退出。

## 2. 已提供的场景

| 参数 | 情况 | 应看到的处理 |
|---|---|---|
| promotion | M1 连续 12 次进入 Context | cold 基础副本保留，另建热副本 |
| cooling | M1 进入热层后不再访问 | 到期唤醒，热度衰减后移除热副本 |
| lost_response | P2 接受动作，但提交响应丢失 | 保留原动作编号，查询并确认，不重复执行 |
| unknown | 无法确认实际层级 | 不默认当作 cold，不提交动作；查询恢复后继续 |
| capacity | 热层剩余容量为 0 | 保留热目标、等待重查；容量释放后执行 |
| new_access | 旧计划运行时，M1 又进入 Context | 更新统计，先查完旧计划，再根据最新统计生成新计划 |
| eviction | 缓冲区达到预留水位 | 移除最久未有效访问的驻留项，保留统计并唤醒对账，可继续降温 |
| tenants | 两个租户都存在 M1 | 热度、队列和计划分别处理，不串数据 |
| warm_cooling | 已有热副本，目标降到温层 | 先迁移基础层到 warm 并核验，再移除热副本 |
| stats_reclaim | 冷层记录保留期结束 | 复查后回收统计与调度记录，保留 P2 数据 |
| access_during_retention | 保留期内再次访问 | 取消回收，原统计继续累计 |
| reenter_after_reclaim | 统计回收后再次访问 | 旧事件去重，新事件查询元数据后建立新统计周期 |
| reclaim_unknown | 回收时查询 Unknown | 暂停回收，恢复后重新开始完整保留期 |
| capacity_reclaim | 统计总量达到上限 | 保留活跃记录；安全回收后接收新的 Memory |
| duplicate_delayed | 重复和延迟的访问事件 | 重复只计一次；延迟事件按发生时间衰减 |
| action_failure | P2 明确执行失败 | 明确失败后释放所有权和预留，再生成新计划 |
| false_success | 返回成功但实际结果不正确 | 副本缺失或损坏均不确认；外部修复后核验原计划 |
| capacity_race | 多条 Memory 争抢容量 | 先预留容量，其他记忆等待，外部扩容后继续 |
| same_memory_concurrency | 同一 Memory 被并发调度 | 10 次并发调度只提交一个计划，重复通知不计访问 |
| access_during_verification | 回收核验期间收到访问 | 保留原统计、重新入队，按新访问完成温层调整 |

主要输出字段：

- `access_count`：当前统计周期的累计有效访问次数，重复事件不重复计数；统计回收后为 null，再次建档从新周期计数。
- `heat` / `desired`：最近一次评估的热度和目标层；未评估时为 null。不是每次打印都会重新计算。
- `evaluated_at`：该评估发生的模拟时间。
- `base` / `hot_replica`：Mock 查询的实际基础层和热副本状态；Unknown 时不展示为已知层级。
- `in_buffer`：是否仍驻留在缓冲区0，不代表 P2 中是否有数据。
- `pending_action`：该 Memory 尚未确认结束的计划编号。
- `tracked` / `tracked_memories`：是否仍有统计记录，以及当前统计表记录总数。
- `cold_since` / `reclaim_at`：确认冷层收敛的时间、最早回收检查时间；不是最近访问时间，到期仍要复查。
- `timer_scheduled`：是否还有逻辑定时任务。
- `actions` / `effects`：本场景所有 Memory 的动作总数和成功执行次数。

## 3. 处理流程

```text
模拟 Context 信号
  → 有效访问去重
  → 更新对应 Memory 的统计，合并缓冲区记录
  → 将 Memory 放入去重唤醒队列
  → worker 处理一次对账
      ├─ 有未完成计划：查询原计划
      │    ├─ running / Unknown / not_found：保留原编号，稍后继续查询
      │    ├─ 明确失败：结束旧计划，延迟后重新判断
      │    └─ 成功：核对实际状态及读取证据，确认后重新处理最新统计
      └─ 无未完成计划：查询实际状态、评估热度
           ├─ 状态不明：等待重查
           ├─ 已达目标：验证可读；温/热安排降温或巡检，冷层进入保留期
           │    └─ 保留期到期：再次核验且无新输入/未完成计划，回收统计及调度记录
           └─ 未达目标：查容量，登记计划，再提交 P2

到期定时器 / 缓冲区淘汰检查 → 同一个去重唤醒队列
```

同一 Memory 的身份由 tenant、application、user、agent、memory_id 共同确定。版本更新仍共用该身份的计划所有权。不同 Memory 可以由多个异步 worker 并发处理；同一个 Memory 始终先处理未完成计划。

准备提交期间如果又收到输入，会丢弃尚未提交的旧判断，再读取新统计。已提交的计划不会因为新输入而随意取消或换一个编号重新提交。

## 4. 热度如何计算

沿用旧方案的指数衰减思路，不保存每次访问时间的完整列表：

```text
衰减访问累计值 = 旧累计值 × exp(-经过时间 / 衰减常数)
                + 本次事件按延迟时间衰减后的贡献

频次分数 = 1 - exp(-衰减访问累计值 / 5)
最近访问分数 = exp(-距离最后一次有效访问的时间 / 衰减常数)
热度 = 0.6 × 频次分数 + 0.2 × 业务重要性 + 0.2 × 最近访问分数
```

业务重要性由输入元数据提供，默认 0.5，当前没有接重要性模型。

升入 hot 使用 0.70 阈值，已处于 hot 时降到 0.55 以下才离开；升入 warm 使用 0.25，离开 warm 使用 0.15。这种不同的升降阈值用来减少边界附近反复切换。

默认衰减常数为 3600 秒。演示为了便于观察设为 60 秒。重要性不随时间衰减，较高重要性的记忆可能长期保持 warm，这是当前公式的行为。

降温不是每次循环重算所有 Memory。完成对账后，估算下一次跨越降温阈值的时间，或者安排有限间隔的巡检；定时器到期后才唤醒。定时器使用有界的到期堆，每轮只检查有限条目，过期的替代条目会定期压缩。

## 5. 驻留淘汰与统计回收

缓冲区驻留、统计记录和 P2 数据有不同的生命周期：

- 默认驻留硬上限 1000，达到 800 开始淘汰，降到 600 停止。
- 淘汰驻留前计算热度、登记对账通知；保留统计、计划和定时器，继续完成降温。
- 确认目标为 cold、实际基础层为 cold、没有热副本、读取核验通过且没有未完成计划，才开始统计保留期。默认 3600 秒。
- 保留期结束，重新查询状态、评估热度并核验读取；检查没有新访问、新版本、待处理通知和未完成计划，才删除统计、残留驻留项及逻辑定时器。
- 即使记录一直没有被淘汰出缓冲区，满足上述条件也会回收，避免低流量时永久驻留。
- 回收不删除 P2 正文、副本或事件去重记录。定时堆中的旧引用会失效，并按有界规则压缩。
- 新有效访问取消保留计时，统计尚在就继续计数；Unknown、读取失败也取消本轮计时，恢复后重新确认并开始完整保留期。

统计表默认最多 10000 个 Memory。满时拒绝新建档输入，调用方保留事件稍后重试；不会为腾位置强制删除仍有热副本、温层目标、未完成计划或 Unknown 的记录。如果所有记录都不满足回收条件，容量仍可能用完。

去重表独立保留，默认上限 100000 条、期限 24 小时，按批清理过期项。它不会随某条统计回收一起删除。重试必须保持事件编号、版本和原始发生时间；超过接收时间范围的旧事件被忽略。去重表满时也会明确拒绝输入。

访问入口推荐使用 `await controller.receive_access(key, event_id, version=..., event_at=...)`。统计已经回收时，该入口先从 P2 查询可信元数据，再建档计数；不复制旧计数，不补造 P2 数据。旧事件重试被去重拦截时，不重新建统计。同步 `access()` 只适用于已经注册且仍被跟踪的记录。

入口返回 true 表示接受；false 表示重复或不符合计数条件；抛出异常表示未接受，例如容量不足或查询失败。调用方负责保存并重试未接受的事件，当前 Demo 没有外部消息积压存储。

单条统计只存衰减累计值、最近时间等字段，不存完整事件时间列表。`access_count` 在一个活跃统计周期内仍会随访问增加；本次解决的是闲置统计记录积压，不把计数伪装成固定窗口。长期累计审计不属于该表职责。

回收后 Operate 不再定时巡检该冷层对象，后续新访问或显式元数据注册可重新加入。若正式 P2 能独立改变副本状态，未来还需接入变更通知或冷层清单巡检；此处尚未实现。

## 6. P2 Mock 如何工作

P2Port 只描述 Operate 需要的五种能力：查询实际状态、查询容量、提交动作、查询原动作、校验读取。这是 Demo 的接口假设，还需要和 P2 负责人确认，不能当作已经确定的真实 P2 协议。

Mock 维护对象表、动作表、容量和容量预留，均在内存中。示例正文也是内存里的少量字节，只用于校验 hash，不代表正式 P2 的存储方式。

- `seed()`：演示程序预置假设数据，Operate 不会在查询失败后调用它补造数据。
- `submit()`：登记动作和容量预留；同一个编号重复提交不重复执行，改变意图则拒绝。
- `query()` / `observe()`：只查询，不改变动作进度。
- `advance()`：由演示驱动单独调用，执行假设的动作效果；不属于 P2Port。
- `verify_read()`：读取模拟对象字节并校验 hash，不直接返回固定 true。

cold/warm → hot 是建立热副本，基础副本保留。hot → warm/cold 会先保证目标基础层存在，再移除热副本。动作成功响应本身不算闭环，Operate 还会查询实际状态并核验保留的基础副本和目标数据。

Mock 动作记录默认上限 10000，不随意清理幂等编号。满后明确拒绝新的提交；需启动新的隔离演示或以后增加经确认的动作记录保留策略。对象总量也有上限。容量目前是全局共享值，不含租户配额和公平调度。

## 7. 故障边界

- 接口超时、提交响应丢失：保留原计划，查询原编号，不盲目生成新编号。
- 动作 not_found：无法证明“从未执行”，仍保留原计划等待，不擅自认定失败。
- 明确失败：释放旧计划；Mock 同时释放容量预留，再按最新情况重试。
- 返回成功但副本缺失、正文 hash 不匹配：不确认成功，保留计划并重查。
- 未知状态长期不恢复：保持等待。尚未实现人工处置界面、最终超时裁决或自动修复策略。
- 单次对账有等待上限；演示驱动也有最大推进次数，不能悄悄无限等待。
