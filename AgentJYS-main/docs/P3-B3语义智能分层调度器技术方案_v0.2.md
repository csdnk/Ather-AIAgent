# P3-B3 语义智能分层调度器技术方案文档

**版本**：v0.2  
**适用范围**：P3-B3 语义智能分层调度器算法设计、P3 内部联调、P2/P1 调度执行接口对接、异常降级与后续策略演进  
**设计重点**：以 B3 调度算法为核心，同时覆盖 B1/B2/B3、Redis、Milvus/P2、Celery、P1/P2 Executor 等依赖异常下的识别、降级、重试、熔断和回退机制。  
**修订说明**：v0.2 对 v0.1 的组织结构进行了技术方案化重组，将内容从“流程说明型”调整为“目标约束—架构设计—接口设计—算法设计—容错设计—部署测试—演进设计”的常规技术方案结构；同时重点扩展 V2 Contextual Bandit 与 V3 Deep RL + GNN 的后续演进设计。

---

## 1. 背景、目标与设计原则

### 1.1 背景

P3 是语义层与智能调度模块，B3 是其中的语义智能分层调度器。B3 不负责 Embedding 计算、不管理用户可见记忆、不保存对象或向量主数据，也不直接执行底层物理迁移；B3 的核心职责是消费 B2 的 memory signal、P2 的 Segment/Object/Access 状态、P1/P2 的 TierState 与执行反馈，计算调度价值并输出标准化调度动作。

P2 当前接口对账文档已经指出：B3 所需的不是单个 `SegmentStat` 字段，而是围绕 Agent/RAG 语义资源形成的可追溯、可召回、可调度、可反馈的接口闭环，即 `object_id -> chunk_id -> vector_id -> segment_id`，并进一步关联 `memory_id/source_id/tier/action_id/feedback`。

### 1.2 建设目标

B3 第一阶段目标是完成 **V1 Heuristic MVP**，形成以下最小闭环：

```text
状态输入
  B2 memory signal
  P2 SegmentStat / ObjectStats / AccessStats
  P1/P2 TierState
        ↓
调度对象视图构建
        ↓
Heuristic 评分与动作选择
        ↓
TierAction 输出
  Keep / Promote / Demote / Pin
        ↓
P1/P2 Executor 或 mock executor 执行
        ↓
TierActionFeedback 返回
        ↓
action_log、异常回退、策略统计
```

### 1.3 设计原则

1. **边界清晰**：B3 负责决策，不负责向量化、记忆生命周期、对象存储、物理迁移和底层路由更新。
2. **默认安全**：状态不可信、字段缺失、执行不可用时，默认 `Keep`，避免错误迁移。
3. **异步调度**：B3 不阻塞 Agent/RAG 主链路，不阻塞 P2 写入或检索主链路。
4. **可解释优先**：第一阶段每个动作必须输出 `score`、`reason`、`policy_version` 和 `trace_id`。
5. **闭环可追溯**：必须形成 `action_id -> feedback -> action_log` 的幂等闭环。
6. **演进兼容**：V1 的 action_log 和 state snapshot 应为后续 Bandit、Deep RL、GNN 预留 state-action-reward 数据结构。

## 2. 总体技术架构

### 2.1 B3 在 P3 内部的位置

```text
B1 Embedding 下推
  负责 chunk/vector/embedding_ref 生成
        ↓
P2-E1/E2 保存向量、对象、chunk 元数据
        ↓
B2 Agent 记忆管理器
  负责 Working/Episodic/Semantic Memory、Context Pack、memory signal
        ↓
B3 语义智能分层调度器
  聚合 memory signal + P2 状态 + TierState，生成调度动作
        ↓
P1/P2 Executor
  负责真实迁移、Freeze/Unfreeze、路由更新、反馈回调
```

### 2.2 逻辑组件划分

| 组件 | 职责 | 第一阶段实现方式 |
|---|---|---|
| Signal Collector | 拉取 B2 memory signal、P2 状态、TierState、历史 feedback | 周期拉取 + 离线回放，事件触发可预留 |
| Scheduling View Builder | 构建统一调度对象视图 | 基于 segment_id/object_id/memory_id 对齐 |
| Rule Engine | 预过滤、评分、动作选择 | V1 Heuristic |
| Action Manager | 生成 TierAction，保证 action_id 幂等 | 支持 Keep/Promote/Demote/Pin |
| Feedback Handler | 接收 TierActionFeedback，更新日志和 cooldown | 真实 feedback 或 mock executor |
| Action Log Store | 保存 state、score、action、feedback、reward 预留字段 | 本地 WAL + 统一日志平台 |
| Fault Controller | 降级、重试、熔断、回退 | 依赖级故障矩阵 |
| Policy Config | 权重、阈值、冷却窗口、灰度开关 | 配置化 + policy_version |

## 3. 模块边界与接口依赖

### 3.1 P3 内部模块边界

| 模块 | 主责 | 向 B3 提供 | B3 不应做的事 |
|---|---|---|---|
| B1 | Embedding 下推、chunk 向量化、embedding 写入 | chunk/vector/object 引用间接进入 P2 | 不由 B3 触发重向量化，不由 B3 选择 embedding 模型 |
| B2 | 记忆管理、Context Pack、用户可见态 | memory signal、memory_id、importance、context_used_flag、ttl、status | B3 不决定记忆是否用户可见，不删除或压缩 B2 记忆 |
| B3 | 调度评分、动作生成、反馈闭环 | action_log、资源侧状态提示 | 不保存主数据，不执行真实迁移 |

### 3.2 外部模块边界

| 模块 | B3 依赖内容 | 主责方 |
|---|---|---|
| P2-E1 | SegmentStat、VectorMeta、SegmentMembership、IndexStatus、AccessStats | P2-E1 |
| P2-E2 | ObjectMeta、ObjectStats、ObjectStatus、ChunkMeta | P2-E2 |
| P2-E3 | RelationStats、最小关系图、共同访问关系 | P2-E3；MVP 可 mock |
| P1/P2 Executor | TierAction 接收、Freeze/Unfreeze、迁移、路由更新、TierActionFeedback | P1/P2 |
| Redis | B2 Working Memory 和短期状态，不由 B3 直接依赖 | B2/运维 |
| Milvus/P2-E1 | 向量检索和 Segment 状态，不由 B3 直接检索主链路 | P2/B1/B2 |
| Celery | B2 异步归档、压缩、重试任务 | B2 |
| 监控/Trace | request_id、trace_id、latency、status、error_code、action_id | 全模块 |

## 5. V1 Heuristic 算法设计

### 5.1 算法目标

V1 不追求全局最优，而追求可运行、可解释、可回退、可对比：

- 高频访问、近期命中、语义价值高、迁移成本低的对象或 Segment 倾向 Promote；
- 长期低访问、语义价值低、占用热层资源的对象或 Segment 倾向 Demote；
- 用户显式记忆、高重要性记忆、近期进入 Context Pack 的对象倾向 Keep 或 Pin；
- 状态异常、字段缺失、依赖不可用时默认 Keep；
- deleted、disabled、expired、failed 对象不得 Promote、Pin 或 Prefetch。

### 5.2 调度对象视图

```text
SchedulingObjectView =
    SegmentStat
  + ObjectStatsForB3
  + MemorySignal
  + TierState
  + ActionHistory
  + TraceContext
```

构建流程：

```text
segment_id 聚合 Segment 状态
  -> 通过 top_hit_objects 或 SegmentMembership 对齐 object_id
  -> 通过 object_id/chunk_id/memory_id 对齐 B2 memory signal
  -> 通过 current_tier 对齐 TierState
  -> 通过 action_id/object_id/segment_id 对齐历史反馈
  -> 生成可评分视图
```

### 5.3 预过滤规则

| 条件 | 处理方式 |
|---|---|
| 对象或记忆状态为 deleted/disabled/expired/failed | 不允许 Promote/Pin/Prefetch |
| Segment 处于 Growing/Migrating | 默认 Keep |
| current_tier 缺失 | 不执行 Promote/Demote |
| TierState 不可用或目标层不可写 | 默认 Keep |
| B2 signal 缺失 | 降级为 access-only，禁用 Pin |
| ObjectStats 缺失 | 降级为 Segment 级调度 |
| Executor 不可用 | 只生成建议，不提交真实动作 |
| action_log 不可写 | 不提交真实动作 |
| 重复失败或刚迁移过 | 进入 cooldown |

### 5.4 评分函数

#### 5.4.1 访问热度分数

```text
score_access = normalize(
    0.4 * log(1 + hit_count)
  + 0.3 * recent_hit_score
  + 0.2 * top_object_hit_score
  + 0.1 * hit_density_score
)
```

其中：

```text
hit_density_score = hit_count / max(object_count, 1)
```

若没有窗口统计，则通过本轮快照与上一轮快照差值估算近期热度。

#### 5.4.2 语义价值分数

```text
score_semantic =
    0.4 * importance
  + 0.2 * context_used_flag
  + 0.2 * user_defined_flag
  + 0.1 * business_priority
  - 0.2 * correction_penalty
```

对象类型基础权重：

| 对象类型 | 权重建议 |
|---|---:|
| Memory | 0.90 |
| RagEvidence | 0.80 |
| LongTermKnowledge | 0.75 |
| DocumentChunk | 0.60 |
| Unknown | 0.30 |

#### 5.4.3 时间衰减分数

```text
score_recency = exp(- elapsed_hours / half_life_hours)
```

MVP 可先使用 24 小时或 72 小时半衰期，后续通过回放数据调优。

#### 5.4.4 成本惩罚分数

```text
score_cost = normalize(
    size_bytes * tier_cost_weight
  + estimated_migration_latency
  + target_tier_load_penalty
)
```

成本越高，越抑制 Promote，防止大 Segment 因少量对象命中而被整体升温。

#### 5.4.5 综合评分

```text
score_total =
    0.35 * score_access
  + 0.30 * score_semantic
  + 0.20 * score_recency
  - 0.15 * score_cost
```

所有权重和阈值必须配置化，并通过 `policy_version` 标识。

### 5.5 动作选择

| 条件 | 动作 |
|---|---|
| `score_total >= promote_threshold` 且目标层可写 | Promote |
| `score_semantic >= pin_threshold` 或用户显式记忆 | Pin / Keep |
| 当前在热层且 `score_total <= demote_threshold` | Demote |
| 状态异常、依赖异常、日志不可写 | Keep |
| Segment 热但对象映射缺失 | Keep 或 Segment 级 Promote，reason 标记 `semantic_mapping_missing` |
| 混合 Segment 只有少量对象热且 size 很大 | Keep 或对象级调度建议 |
| Executor 连续失败 | Keep + cooldown |

建议初始阈值：

```yaml
promote_threshold: 0.70
demote_threshold: 0.35
pin_threshold: 0.85
cooldown_minutes: 30
max_retry_per_action: 3
```

## 6. 混合 Segment 与颗粒度对齐策略

一个 Segment 可能同时包含 Memory、DocumentChunk、RagEvidence、LongTermKnowledge 等不同对象类型。B3 不能仅使用整段 `access_count/hit_count` 判断热度，否则可能出现“Segment 分得过大，啥都相关，全调过来”的热层污染问题。

处理策略：

| 情况 | B3 处理 |
|---|---|
| Segment 热度主要来自 Memory/RagEvidence，且 top_hit_objects 能与 B2 signal 对齐 | 允许 Promote 或 Pin 建议 |
| Segment 很大但 Top-K 热对象很少 | 不直接 Promote 整段，输出 Keep 或对象级调度建议 |
| Segment 内 DocumentChunk 多但命中低 | 降低 Segment 级 Promote 权重 |
| Segment 内存在 deleted/expired/disabled 对象 | 不作为 Promote/Pin 理由，记录状态同步告警 |
| ObjectStats 缺失 | 降级为 Segment 级 Heuristic |
| segment_id 到 object_id 映射缺失 | reason 标记 `membership_missing`，降低动作激进度 |

当前 `object_type_stats` 和 `top_hit_objects` 能支撑 MVP 的混合 Segment 判断，但后续对象级调度仍需要 `SegmentMembership` 或 `ObjectStatsForB3.segment_id` 稳定可查。

    pub target_tier: Option<StorageTier>,
    pub action_type: TierActionType,
    pub score_total: f64,
    pub score_access: f64,
    pub score_semantic: f64,
    pub score_recency: f64,
    pub score_cost: f64,
    pub reason: String,
    pub policy_version: String,
    pub input_snapshot_version: String,
    pub execute_status: Option<ExecuteStatus>,
    pub execute_latency_ms: Option<u64>,

日志原则：

5. reward 字段第一阶段可为空，但结构必须预留。

## 8. 故障识别、降级、重试与熔断设计

### 8.1 总体容错原则

B3 不能成为主链路阻塞点。所有异常按以下原则处理：

1. 状态不可信时默认 Keep；
2. 依赖短暂失败时使用最近一次稳定快照；
3. 快照超过 TTL 后停止 Promote/Demote，只保留 Keep；
4. 连续失败触发熔断，暂停对应依赖调用；
5. 调度动作必须幂等，重复 feedback 只更新一次；
6. B3 异常不阻塞 Agent/RAG 主链路和 P2 主链路；
7. action_log 不可追溯时不执行真实迁移。

### 8.2 模块级故障矩阵

| 故障模块 | 故障表现 | B3 识别方式 | 降级策略 | 重试策略 | 是否拖死核心服务 |
|---|---|---|---|---|---|
| B1 | embedding 失败、向量写入延迟 | P2/B2 状态为 pending_embedding/embedding_failed | B3 不重试 B1，不将缺向量对象作为 Promote 理由 | 由 B1/B2 异步重试 | 否 |
| B2 | memory signal 超时或过旧 | signal_version 过旧、接口超时、字段校验失败 | 使用上一快照；超 TTL 后 access-only；禁用 Pin | 指数退避，连续失败熔断 | 否 |
| B3 | 策略服务异常、配置错误 | 健康检查、policy_version 异常、日志失败 | 全局 Keep，暂停真实动作 | 服务重启，配置回滚 | 否 |
| Redis | Working Memory 延迟或不可用 | B2 报错、Redis P99 超阈值 | B3 使用已落地 signal，不等待 Redis | B2/运维处理 | 不直接拖死 B3 |
| Milvus/P2-E1 | SegmentStat/索引状态不可用 | P2 状态接口超时、index_state 异常 | 使用最近 Segment 快照；超 TTL 后 Keep | 有限重试，熔断 | 否 |
| P2-E2 | ObjectStats 不可用 | BatchGetObjectStats 失败 | 降级为 Segment 级调度 | 批量拉取重试 | 否 |
| P2-E3 | RelationStats 不可用 | RelationStats 超时或为空 | 关闭 Prefetch/GNN 相关逻辑 | 低频重试 | 否 |
| Celery | B2 异步归档积压 | queue length、worker heartbeat 异常 | B3 使用已有 signal，不等待异步压缩 | Celery 自身重试/DLQ | 否 |
| P1/P2 Executor | 动作提交失败、反馈超时 | SubmitTierAction 失败、feedback timeout | 标记失败，cooldown，回退 Keep | 同一 action 最多 3 次 | 否 |
| 监控/Trace | 日志平台不可用 | 写入失败、本地队列积压 | 写本地 WAL；无法写 WAL 则停真实动作 | 异步补传 | 不拖死主链路 |

### 8.3 降级级别

| 等级 | 触发条件 | B3 行为 |
|---|---|---|
| L0 正常 | B2/P2/P1/日志均可用 | 完整语义调度 |
| L1 语义信号缺失 | B2 signal 不可用 | access-only，禁用 Pin |
| L2 对象状态缺失 | ObjectStats 不可用 | Segment 级调度 |
| L3 Segment 状态缺失 | SegmentStat 不可用 | 仅 Keep |
| L4 执行侧不可用 | Executor 不可用 | 只生成建议，不真实执行 |
| L5 日志不可追溯 | 本地 WAL 不可写 | 停止真实动作 |

### 8.4 重试、熔断与幂等

```yaml
retry:
  max_attempts: 3
  initial_backoff_ms: 500
  max_backoff_ms: 10000
  multiplier: 2.0
  jitter: true

circuit_breaker:
  failure_threshold: 5
  window_seconds: 60
  open_seconds: 120

cooldown:
  action_failure_cooldown_minutes: 30
  migrated_object_cooldown_minutes: 60
```

幂等建议：

```text
action_id = hash(policy_version + target_id + action_type + target_tier + time_bucket)
```

## 11. 后续演进方案设计

后续演进不是简单替换算法，而是在保持接口闭环不变的前提下，将 V1 的固定规则逐步升级为“反馈驱动”和“图结构预测”的调度策略。演进分为 V2 Contextual Bandit 与 V3 Deep RL + GNN 两条主线。

### 11.1 演进前提

V2/V3 不应在 V1 闭环不稳定时启动。至少需要满足：

1. `MemorySignal + SegmentStat + ObjectStats + TierState + TierAction + TierActionFeedback` 字段稳定；
2. action_log 能稳定记录 state、score、action、feedback、reward 预留字段；
3. mock executor 或真实 executor 能返回可复现的反馈；
4. 至少有一套回放数据集支持 LRU/LFU/Keep-only/Heuristic 对比；
5. B3 已具备 shadow mode、policy_version、cooldown 和回滚机制。

---

### 11.2 V2：Contextual Bandit 反馈驱动调度

#### 11.2.1 设计目标

V2 的目标是从固定权重 Heuristic 升级为轻量在线学习策略，使 B3 能根据执行反馈自动调整不同场景下的动作偏好。例如，在某些 workload 中访问热度更重要，在另一些场景中语义价值或迁移成本更重要；Bandit 通过反馈学习不同状态下 Promote、Demote、Keep、Pin 的收益。

#### 11.2.2 状态、动作与奖励设计

状态特征：

```text
x_t = [
  score_access,
  score_semantic,
  score_recency,
  score_cost,
  object_type,
  current_tier,
  size_bucket,
  hit_density,
  tier_load,
  user_defined_flag,
  context_used_flag,
  failure_history,
  cooldown_state
]
```

动作集合：

```text
A = {Keep, Promote, Demote, Pin}
```

第一阶段不建议将 Evict/Prefetch 纳入在线 Bandit 主动作空间，避免安全风险；可先作为建议式动作或 shadow action。

奖励函数建议：

```text
reward_total =
    w_hit     * reward_hit
  + w_latency * reward_latency
  - w_cost    * reward_cost
  - w_move    * reward_migration
  - w_fail    * penalty_failure
```

其中：

| 奖励项 | 含义 |
|---|---|
| reward_hit | 动作后对象或 Segment 是否继续被命中 |
| reward_latency | 动作后访问延迟是否下降 |
| reward_cost | 热层资源占用和迁移成本 |
| reward_migration | 迁移次数惩罚，防止频繁震荡 |
| penalty_failure | 执行失败、回滚、超时惩罚 |

#### 11.2.3 策略形态

V2 推荐先采用：

```text
LinUCB / Thompson Sampling + Heuristic Guardrail
```

设计方式：

1. Heuristic 仍作为安全基线；
2. Bandit 只在 Heuristic 允许的动作集合内选择；
3. 如果 Bandit 输出动作与安全规则冲突，以安全规则为准；
4. 对 `deleted/disabled/expired/failed` 对象永远不探索 Promote/Pin；
5. 对高价值用户显式记忆不探索 Evict。

#### 11.2.4 训练与上线流程

```text
V1 action_log 积累
    ↓
离线回放构造 state-action-reward
    ↓
训练 Bandit 初始参数
    ↓
Shadow Mode：只记录 Bandit 建议，不执行
    ↓
与 Heuristic/LRU/LFU 对比
    ↓
小流量灰度：低风险对象启用 Bandit
    ↓
失败率、震荡率、收益稳定后扩大范围
```

Shadow Mode 是 V2 必须阶段。Bandit 在 shadow mode 中只输出 `candidate_action` 和 `estimated_reward`，不直接影响真实 TierAction。

#### 11.2.5 接口增量

V2 不应修改主接口，只增加日志字段：

```text
bandit_policy_id
bandit_selected_action
bandit_estimated_reward
exploration_flag
exploration_rate
baseline_action
actual_action
reward_total
```

#### 11.2.6 风险控制

| 风险 | 控制方式 |
|---|---|
| 在线探索导致错误迁移 | 先 shadow，再低风险灰度 |
| 奖励延迟导致学习偏差 | 使用固定观察窗口，如 1h/24h |
| 热层被探索动作污染 | 热层容量水位保护和迁移次数上限 |
| 动作震荡 | cooldown + migration penalty |
| Bandit 失效 | policy_version 回滚到 V1 Heuristic |

---

### 11.3 V3：Deep RL + GNN 预测式调度

#### 11.3.1 设计目标

V3 的目标不是简单把 Heuristic 换成神经网络，而是解决 V1/V2 难以处理的两个问题：

1. **关联预取问题**：对象之间存在 session、task、memory、chunk、evidence、vector、segment 的关系，单对象特征难以预测未来访问。
2. **长期收益优化问题**：一次 Promote/Demote 不只影响当前命中，还会影响未来热层占用、迁移成本、调度震荡和多轮 Agent 任务质量。

因此 V3 设计为：

```text
GNN 负责对象/记忆/Segment 关系表征
Deep RL 负责长期动作策略优化
```

#### 11.3.2 图建模设计

构建异构图：

```text
Node Types:
  Memory
  DocumentChunk
  RagEvidence
  LongTermKnowledge
  Object
  Vector
  Segment
  Task
  Session

Edge Types:
  memory_from_object
  object_has_chunk
  chunk_has_vector
  vector_in_segment
  session_has_memory
  task_has_memory
  rag_has_evidence
  evidence_from_chunk
  co_access
  semantic_similar
```

节点特征：

```text
access_count, hit_count, recent_hit_count,
last_access_time, importance, context_used_flag,
user_defined_flag, object_type,
current_tier, size_bytes, status,
score_access, score_semantic, score_cost
```

边特征：

```text
relation_type, weight, co_access_count,
last_co_access_time, semantic_similarity,
task_dependency_strength
```

GNN 输出：

```text
node_embedding
future_access_probability
related_prefetch_candidates
segment_value_embedding
```

#### 11.3.3 RL 环境设计

RL 状态：

```text
s_t = {
  hot/warm/cold tier state,
  candidate object/segment features,
  GNN embedding,
  recent access window,
  previous actions,
  failure/cooldown state
}
```

动作空间：

```text
A = {
  Keep,
  Promote(object/segment),
  Demote(object/segment),
  Pin(object),
  Prefetch(object/related set)
}
```

第一版 RL 不建议真实执行 Evict，可将 Evict 保留为建议动作或离线仿真动作。

奖励函数：

```text
R =
  + α * hit_improvement
  + β * latency_reduction
  + γ * semantic_quality_gain
  - δ * migration_cost
  - ε * hot_tier_pressure
  - ζ * failure_penalty
  - η * oscillation_penalty
```

约束：

- deleted/disabled/expired 不可 Promote/Pin/Prefetch；
- 用户显式记忆不可 Evict；
- 热层容量超过阈值时限制 Promote；
- 迁移失败对象进入 cooldown；
- action_log 不可写时不执行真实动作。

#### 11.3.4 训练流程

```text
构建 state-action-reward 日志
    ↓
构建异构图快照
    ↓
训练 GNN 表征模型
    ↓
离线环境中训练 RL 策略
    ↓
离线策略评估：与 V1/V2/LRU/LFU 对比
    ↓
Shadow Mode 输出动作但不执行
    ↓
小范围建议式 Prefetch
    ↓
灰度执行低风险 Promote/Demote
```

#### 11.3.5 推理部署方式

V3 不建议一开始在线训练。推荐：

1. 离线训练 GNN/RL；
2. 周期性发布模型版本；
3. 在线只做轻量推理；
4. Heuristic Guardrail 始终保留；
5. 模型异常时回退 V1 或 V2。

在线推理输入为 `SchedulingObjectView + GNN embedding`，输出候选动作和置信度。若置信度低或违反约束，则回退 Heuristic。

#### 11.3.6 资源需求

V3 需要 GPU 训练资源，但不属于第一阶段 MVP 必需条件：

| 阶段 | 资源需求 |
|---|---|
| 小规模 GNN/RL 验证 | 单卡 ≥32GB 显存 |
| 中等规模图训练 | 单卡 ≥64GB 显存 |
| 较完整 RL/GNN 实验 | ≥64GB 显存，建议可扩展至 2 张 GPU |

GPU 建议作为项目共享训练资源申请，不建议写成 B3 个人独占硬件。

#### 11.3.7 风险控制

| 风险 | 控制方式 |
|---|---|
| 模型输出不可解释 | 输出 top features、近邻关系、reason template |
| 图关系数据不稳定 | E3 可 mock 起步，关系 schema 先冻结 |
| RL 策略过激 | Heuristic Guardrail + shadow mode |
| 训练反馈延迟 | 固定 observation window 与离线 OPE |
| 线上效果回退 | policy_version 一键回滚 |
| 成本过高 | 仅对热点候选集合做模型推理 |

## 12. 当前关键结论与修改建议

1. 文档结构应按常规技术方案组织：背景目标、架构设计、接口设计、算法设计、容错设计、部署测试、演进设计，而不是只按算法流程展开。
2. 当前 SegmentStat 已能支撑 B3 MVP，但建议补充或通过其他接口提供 `status/updated_at/movable`。
3. `object_type_stats` 与 `top_hit_objects` 能解决混合 Segment 的基础颗粒度问题，但对象级调度仍依赖 ObjectStats 或 SegmentMembership。
4. V1 的重点是 Heuristic 闭环，不应宣称真实迁移收益，除非 P1/P2 真实 Executor 就绪。
5. 后续 V2/V3 不应写成简单“引入 Bandit/RL/GNN”，而应明确 state、action、reward、训练方式、上线方式、接口增量和回滚机制。
6. 任何依赖异常时，B3 必须默认 Keep、异步降级、有限重试、熔断隔离，保证 Agent/RAG 主链路和 P2 存储主链路不被拖死。

---

## 13. 最终结论

B3 技术方案的第一阶段核心是：以 `MemorySignal + SegmentStat + ObjectStats + TierState + TierAction + TierActionFeedback + Trace` 为主接口，完成可解释 Heuristic 调度、动作反馈闭环和故障降级机制。后续演进不应脱离第一阶段日志和接口基础，而应在 action_log 与 state-action-reward 数据稳定后，逐步升级到 Contextual Bandit，再进一步基于 SegmentMembership、RelationStats 和对象关系图实现 Deep RL + GNN 的预测式调度与预取。整个过程中，B3 必须始终保持“调度决策者”边界，不越权承担 B1 向量化、B2 记忆生命周期、P2 存储引擎和 P1/P2 物理迁移职责。
