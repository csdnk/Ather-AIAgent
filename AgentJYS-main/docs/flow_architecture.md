## 运行入口和数据职责

当前入口为 `python -m aether_agent_memory`，子命令使用 `--config <service.yaml绝对路径>`。运行配置来自仓库外目录；不再使用旧 `--db` / `--cache-root` 服务入口。

```text
python -m aether_agent_memory check-config --config /absolute/deployment/service.yaml
python -m aether_agent_memory serve --config /absolute/deployment/service.yaml --require-profile development
```

`check-config` 只检查结构和身份配置。`serve` 必须连接明确的 PostgreSQL、Redis、Milvus、Ceph、原生 BGE、结构化模型和独立 Temporal。数据库保存权威元数据、幂等回执、任务、身份和日志；Ceph 保存原输入和正文；Redis 保存可重建热副本；Milvus 保存版本绑定的向量。运行数据、证书、模型及密钥放仓库外。

健康就绪、Worker 运行、保存/长期化/召回、原结果重取及恢复分别验证。现有 AKS 服务正在运行不代表它已部署本次源码；完整测试、正式 Temporal/HTTPS、HA 和灾备结论见[源码清理与部署就绪验收](../../交付成果/测试与验收/P3_源码清理与部署就绪验收_20261004.md)。

## 业务边界与仍有效的契约

Remember 拥有正文、来源、生命周期和候选资格；Recall 消费这些接口并提供共享 Embedding 和上下文；Operate 根据当前事实执行及核对原动作；RF 与 Temporal 共同保持身份、准入、事务、幂等、任务和恢复边界。`saved` 与向量 `ready` 分别取证，持久化成功不自动等于可召回。

顶层 Recall 受理/执行契约与 `examples/recall_admission.py` 仍有有效消费者，属于组件示例。它使用真实 PostgreSQL 和部署方提供的可信授权快照，只推进受理与执行状态，不生成 ContextPack；不会恢复已删除的生产 mocks。当前服务装配走 `runtime.flows`，不把组件示例当作服务启动方式。

旧 Python app、Sidecar、Celery、SQLite 适配和重复实现已退役。Rust P2 原型与生成协议仍属其他组件；正式 P2 adapter 和 Nginx gateway 另行联调，不能从 Ceph 测试推导 P2 已验收。

## Operate：Ceph 原文 + Redis 热副本（2026-10-07）

当前策略只有两种状态；冷、热描述的是**有没有 Redis 副本**，不会移动或删除 Ceph 原文。PostgreSQL 保存记忆元数据、统计、任务和动作回执，不充当温层；业务删除与生命周期清理仍走原有独立流程。

| 情况 | Operate 的处理 | 为什么这样做 |
|---|---|---|
| 新记忆、低热度 | 保留 Ceph 原文，不建立 Redis 副本 | 避免每次读取或评估都先占用热层 |
| 热度达到 0.70 | 从 Ceph 核验并读取原文，建立 Redis 副本，读回确认 | 热层可重建，Ceph 始终保留原文 |
| 已是热目标，热度处于 0.55～0.70 | 继续保持热目标 | 两个阈值避免边界附近反复升降温 |
| 热度低于 0.55 | 确认 Ceph 原文可读且哈希正确，再移除 Redis 副本 | 防止原文故障时误删仍可用的热副本 |
| Ceph 未查到、不可读或校验失败 | 不把 Unknown 当冷层，不执行依赖该证据的降温；已提交动作保留原 ID 等待恢复 | 请求失败不能证明原文或动作不存在 |
| Redis 容量不足 | 延后升温；降温仍允许执行 | 移除副本不需要空闲缓存容量 |
| 写入或删除响应丢失 | 查询并恢复原动作，再核验目标状态和读取证据 | 不以“请求已发出”冒充完成，不盲目生成第二个动作 |
| 同一记忆处理时又被访问 | 成功读取统计照常更新；同版本的未完成评估任务合并通知 | 减少任务堆积，同时保留最新热度输入 |
| 历史温层记录/未完成动作 | 页面标为历史记录；运行中的旧温层动作返回不支持，不解释为新降温操作 | 升级时不篡改历史，不误删副本 |

### 缓冲区与任务触发机制

热度仍按衰减访问量、业务重要性和最近访问衰减计算，默认衰减时间常数为 3600 秒。本次调整的是**何时发起评估**：记录有效访问仍逐次进行，创建评估任务则按窗口和到期时间合并。不是每秒重算全部记忆，也不是把一分钟内的多次访问只记成一次。

| 情况 | 新处理方式 | 解决的具体问题 |
|---|---|---|
| 同一记忆连续被访问 | 首次可在下次周期轮询时评估；评估后 60 秒内的新访问更新统计，合并成一个到期通知 | 避免一个任务刚结束，下一次访问又立即创建任务 |
| 一直有新访问 | 下次时间以最近一次评估为准，不随每次访问向后顺延 | 避免持续访问让任务一直无法执行 |
| 旧计划尚未完成，又有新访问 | 保留统计和水位；普通任务不重复下发；完成时发现新输入，再按窗口安排评估 | 既不丢访问，也不并行生成同一记忆的新计划 |
| 热记忆尚未降到阈值 | 根据当前统计预测何时低于 0.55，只登记那个到期时间；新输入到达可提前重算计划 | 避免固定每 300 秒进行无意义复查 |
| 已确认冷层、Ceph 可读、无新输入 | 停止该记忆的周期热度评估；默认 3600 秒后只清理衰减统计，不调用存储、不生成评估任务 | 避免冷记忆长期占用计算与查询资源 |
| 执行器不支持所需调度 | 停放通知，等待执行器能力或暂停配置发生变化；其间访问仍记入统计 | 避免不断提交注定不支持的动作 |
| 临时失败、容量不足或状态尚未确认 | 依次等待 60、300、900、3600 秒，随后维持 3600 秒；成功后重置 | 避免故障期间快速重试；新访问不能绕过失败退避；仍受任务预算限制 |
| 原动作结果 Unknown | Temporal 按上述间隔查询/恢复原动作，不生成新动作 ID，达到查询预算后交给现有恢复/人工处理 | 防止网络失败导致重复副作用 |
| 删除、归档、过期清理 | 独立准入，绕过普通访问窗口、调度能力门槛和评估退避 | 生命周期清理不被普通热度窗口延迟；仍遵守任务资源与权限限制 |

例如：M1 在第 0 秒完成一次评估。第 1～59 秒又发生 12 次有效访问，累计访问数为 13；只保留一个第 60 秒到期的通知。到期后取最新统计重新评估。如果此时旧任务还没完成，则先等待完成，不重复下发。**通知合并，统计不合并丢失。**

当前有效访问沿用 `recall.access` 且 `stage=read`、`outcome=succeeded`；同一次访问的重复事件不会重复计数。每次有效访问仅更新衰减总量、最近时间和计数等紧凑统计，不为热度计算保存每次访问的完整时间列表。冷态统计到期删除后，新访问会重新建立衰减统计；累计水位和历史任务仍保留。

### 持久化与升级

- `operate_views` 保存当前版本、访问/存储水位、最近评估时间、唤醒原因和调度状态；`operate_heat` 保存热度输入；`operate_due` 保存按时间排序的到期通知。以上通过现有 PostgreSQL 元数据接口落库，不增加另一种数据库。
- 每个租户作用域下的记忆只保留一个当前到期通知。更新通知、统计及相关元数据使用原有事务边界，服务重建后从数据库恢复。
- 日常周期扫描改为按索引读取到期队列；首次升级或能力配置变化时，才分批检查已有视图。每页最多 64 条；冷记忆的到期统计清理仅操作元数据。
- 旧周期任务若执行到一半，先用其已记录的路由列表结束当前轮，下一轮切换到新队列。Temporal 退避使用版本补丁，历史工作流回放继续保留原定时行为；不改写已存在任务的期限和重试预算，也不改变幂等重放的签名。
- 新的自主对账任务默认最多执行 24 小时，使分钟级退避不受原访问请求 300 秒期限限制。新建普通对账任务的执行次数上限至少为 32 次，由 Operate 注册自己的任务类型预算，其他任务仍沿用公共上限（默认 3 次）；清理任务沿用公共上限，动作查询沿用公共查询预算（默认 6 次）。每一步仍重新检查身份、权限与版本，单个任务超出次数或执行/查询期限进入现有失败、恢复或人工处理流程。容量不足等已确认没有成功执行动作的情况，可按退避时间登记下一次评估；这不代表无限重试同一个结果未知的动作。
- 完成通知重复执行不会再次递增退避或延长冷态统计保留期。事件发起者已撤销的旧通知会停放，需要新的有效授权事件来唤醒。

### 配置与边界

| 配置 | 默认值 | 含义 |
|---|---|---|
| `operate_evaluation_window_seconds` | 60 | 普通访问触发的最短评估间隔 |
| `operate_evaluation_timeout_seconds` | 86400 | 新建自主对账任务的执行期限，单位秒 |
| `operate_decay_seconds` | 3600 | 热度的衰减时间常数 |
| `operate_stats_retention_seconds` | 3600 | 已确认冷态后保留衰减统计的时间 |
| `operate_audit_seconds`、`operate_retry_seconds` | 兼容旧配置 | 仍允许旧配置文件包含，新的持续调度不再使用；退避固定为 1/5/15/60 分钟 |

周期工作流仍需轮询数据库，以便发现新到期项；实际评估可能因轮询、积压或正在执行的旧计划晚于到期时间。这里减少的是 Operate 评估与无效存储检查，公共事件投递和其他业务任务依然存在。

搬迁沿用现有任务并发控制和 Redis 容量配额，并在清除热副本前核验 Ceph 原文。本次增加到期任务批量限制，**尚未实现跨 Worker 的每秒搬迁字节限速**；Redis 容量上限不能等同于搬迁带宽上限。任务历史、访问去重键和累计视图的全局归档仍需容量管理，不能据此声称数据库不会增长。

停止固定审计后，Redis 副本意外消失需要下一次有效访问、既有维护机制或其他到期通知来触发检查；本次不承诺所有漂移即时发现。没有同负载 CPU 前后对照，因此不提供资源下降百分比。

普通 Remember/Recall 的缓存写入路径不再自动给冷记忆创建 Redis 副本。冷记忆仍可直接从 Ceph 读取；只有热度策略升温才创建副本。Redis 缓存自身仍有 TTL、容量限制和故障回退，热目标与此刻实际存在的副本需要持续对账。

生产装配在 `runtime/storage/azure.py` 中注入 `RememberPipeline.read_authority`，读取路径会检查权限、当前版本/状态以及 Ceph 正文哈希，并在读完后再次检查元数据。策略在 `operate/`，真实 Redis 动作与 PG 回执在 `runtime/storage/redis_executor.py`，因此两层调度需要同时调整这三个边界。
