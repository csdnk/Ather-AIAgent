# Remember 历史能力退出说明

本文说明现行代码与兼容执行器的边界。历史字段出现在结构定义中，不代表新请求仍启用历史流程。

## 新请求保留的流程

- Working 保存完整文本。文件入口先核验原始文件并解析，将解析文本作为 Working 正文；来源身份与文件地址另行保留。
- 正文与元数据提交后尝试首次 Redis 准入。成功且正文版本仍有效时登记热地址；缓存不成功不撤销正文，也不阻塞向量化或整理。
- 原文向量化与长期整理分别调度。后者不等待前者完成，LLMLingua 派生物不替换原文或原文投影。
- 单条长 Working 按 `compression_min_bytes` 判断，默认路线为 LLMLingua → 压缩派生物 → LangMem 候选提取 → 相关旧记忆检索 → LangMem 动作判断。`direct` 是显式可选路线，失败不能静默切换。
- 新到长文件单独整理，不夹带待处理短消息。短消息只汇总未处理的完整消息，在数量、字节数或等待时间达到条件时整理；不重叠上一批已处理消息。
- 5X 统计原始 Working 与其全部块最终长期结果正文总和之比，不是 LLMLingua 单步指标，也不是删除事实的强制条件。
- 反思保留为独立雏形，不作为上述整理流程的前置或后置步骤。
- Working 是不可更正的原始记录。新信息另存 Working，由长期整理决定长期记忆的版本动作；显式更正接口只接受长期记忆。
- 普通删除 Working 只撤销自身可用性、停止尚未提交的整理并清理自身投影/缓存，不删除已形成的长期记忆，也不撤回独立保留的来源。来源撤回/删除使用单独入口。
- 短消息先完整提取；容量不足时，可在同一 Working 内按段落或句子分段恢复。不可安全分割的单句明确失败，不能按字符切碎或丢弃超出的候选。所有部分完成后才消费整条输入。
- 长期结果、待投影清单及相关事件一起登记；提交后按公共任务容量接收事件投递和投影任务。容量不足时，通过现有 Temporal 的 Remember 待处理表继续投递，不增加公共周期路线或调整限额。正文已保存不等于向量已就绪。

## 本次退出和明确停用的内容

| 内容 | 处理 | 原因 |
| --- | --- | --- |
| Working 摘要阈值判断、引用描述生成、摘要登记入口 | 删除无调用的 `needed` / `descriptor` / `register` | 新请求保存全文，不能重新制造引用说明正文 |
| 旧策略开关 | 在策略 schema 标记 deprecated，说明实际作用 | 保留字段、默认值和序列化结构，避免历史任务的检查点绑定失效 |
| “P2 负责所有解析”的说明 | 改为文件入口负责解析、正文提供方负责存储读取 | 内置 Documents 已实际执行 PDF/DOCX/text 解析 |
| 历史评测的 Celery hook 和额外 LLM 审查说明 | 改为归档及重新适配要求 | 旧脚本不是当前流程验收入口 |
| Ruoyi P3 镜像的长路线依赖遗漏 | 显式安装 LLMLingua extra 和 CPU PyTorch | 默认长路线不能依赖基础镜像偶然预装的包 |

弃用字段包括 `working_summary_*`、`summary_*`、`precompression_enabled`、`compression_quality_sample_rate`、`memory_support_sample_rate`、`consolidation_tokens`、`consolidation_overlap_messages`、`compression_require_ratio`。其中部分仅供已持久化摘要/压缩任务恢复，其余对新请求无效。新配置使用 `long_memory_route`、`compression_min_bytes`、`consolidation_bytes` 等实际生效字段；不加入额外审查或消息重叠。

## 暂不能直接删除的兼容内容

| 保留项 | 保留理由与后续退出条件 |
| --- | --- |
| 已持久化摘要任务的终结入口 | 只按任务栅栏标记过时，不调用模型、不发布摘要、不改写 Working。准备、发布、提交及恢复阶段均拦截；保留阶段名称用于收敛旧 Temporal 历史 |
| 旧独立压缩任务、旧表示记录的恢复读取 | 新入口不创建；历史任务和源记录仍可能引用它们，不能清表后让任务悬空 |
| 旧内联正文及旧地址读取 | 新写入用完整正文存储地址；删除兼容读取前需迁移旧数据并验证 hash、权限与版本 |
| MemorySnapshot 中的正文 | 是调用阶段的已加载内容，不能误当作数据库旧内联存储而删除 |
| 来源清单、正文地址、证据范围和向量片段身份 | Recall 和审计需要这些真实身份，不属于“来源引用描述”正文 |
| 元数据 DTO 和现有版本/生命周期字段 | 本次不增加 is_current，不改变 Recall/Operate 的读取或生命周期策略 |

彻底删除兼容执行器需单独完成存量清点：确认相关任务无 pending/running/retry，历史正文和表示已迁移，冻结策略仍能恢复，最后移除处理器和表读取。不能仅凭新请求测试通过就推断生产历史存量为零。本次不改变公共周期计划，不替换 Temporal，也不清理 Azure 历史数据。

## 2026-10-09 恢复与判别修复

- 旧 Working 更正不能从已准备的持久化或恢复阶段继续写入正文；已经完成的历史回执不重新加热缓存。旧版本记录只保留读取身份，不自动重写历史数据。
- 旧摘要状态不再阻塞完整原文向量化。历史引用描述或摘要正文若与来源原文 hash 不同，仍不得冒充原文建立新投影；需显式重新导入经核验的原文。
- 原来“完整短消息重试两次后永久阻断”的计数只作历史兼容读取，新任务使用有界的语义分段检查点，并区分候选超量、输出截断和输入预算不足。
- 两阶段 LangMem 均要求保留数量上下界、否定、条件与例外。阶段二利用已绑定的原文证据修复同一断言遗漏的限定，不增加审查调用。提示绑定升级后，旧任务不会静默套用新提示。
- 记忆删除与压缩派生物失效不等于源对象物理擦除；已有存储保留政策仍有效。
- 百条结果不能在同一正文事务内逐条申请后台任务。事件投递本身也会创建任务，因此保存/更新及投影就绪事件保留原始身份和顺序，使用可恢复的投递清单；已有消费者和公共 Outbox 不变。
- 生成内容的类型字段不符合 schema 时，交回官方 LangMem/Trustcall 的有界结构修复；未修复结果不能当作零候选成功。阶段二漏处理候选时按已有分组边界缩小批次，全部候选覆盖后再提交；不会把同一旧记忆的相关候选拆开分别更新。
