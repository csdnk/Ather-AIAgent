# ADR-P3-003：独立日志存储与基于事实的检测恢复

> 2026-10-02：租户、日志与 Trace 复用项目已有 PostgreSQL；节点日志使用同库 node_logs。P2、executor 和旧 Demo 迁移不在本次 PR 范围，详见 development/16_PostgreSQL接入与数据迁移.md。下文 SQLite 描述仅适用于原开发配置。

## 背景与目标

三个流程已经共用事务、任务和事件，但阶段记录不足以解释一次请求在 Worker 重启、依赖中断或响应丢失后的完整过程。当前目标是搭建可开发、可定位问题的系统，暂不部署容器或指标平台。

## 决策

1. 采用独立 SQLite 结构化节点日志，记录开始、返回、异常、取消和实际事务提交/回滚。独立存储使失败日志不随业务回滚消失。
2. 在 Task 与 Outbox 中持久化生产 Span 上下文，同一 trace_id 贯穿派生处理；每次重试有新 Span。独立入口请求通过业务对象关联，仍分别建 Trace。
3. 默认记录有界、脱敏的输入输出摘要与错误堆栈位置。原文经已有对象授权接口读取，技术日志不增加正文副本。
4. 追溯查询检查当前授权，并返回独立的持久任务/事件事实。日志缺失或节点结束不构成业务效果证明。
5. 健康探测分开报告 liveness、readiness、依赖和业务能力。探测不执行恢复；恢复沿用领域 Handler 和持久状态。
6. 设置时间及数量保留上限，查询声明保留范围，日志写入异常暴露为健康降级；不因此盲目重试外部副作用。

## 采用方式与替代方案

初始实现借鉴 OpenTelemetry 的 Trace/Span 设计并提供本地日志。2026-10-01 增量将其接入真实 OTel SDK：HTTP Server Span 提取 W3C 上下文，业务子 Span 与 SQLite 节点日志共享 ID，并提供可选的 OTLP/HTTP protobuf 导出。structlog 输出独立的 JSON 请求摘要，不替换授权节点查询。独立 SQLite 继续复用 P3 现有日志库，不增加 P2 存储，也不要求部署日志服务集群。导出是可替换的技术出口，不能替换业务事实与 Temporal 恢复依据。

未采用纯 print/文件散落方案：缺少稳定结构、保留策略和权限查询。未将技术日志与业务事实全部写入同一事务：回滚会同时失去错误证据。未通过日志扫描触发外部重试：日志可能丢失、截断、被清理，无法证明副作用未发生。

## 代价与边界

独立日志与业务提交不是跨库原子操作；查询须结合持久事实，明确允许日志缺口。全量记录增加磁盘写入，当前无吞吐承诺。保留清理可能截断 Trace。初版查询采取发起主体隔离，比跨主体共享对象权限更保守。注入提供方需要可装饰的 Python 实例；新适配器须接入测试验证。

HTTP 入站 W3C 传播和本机 OTLP 收发已有测试；所有出站服务传播、持久化完整 tracestate/sampling flags、Azure 集中采集、日志加密/防篡改存储、生产保留策略和多主机查询仍待后续实施或部署验收。共享 Collector 的权限隔离需要部署方另行配置，不自动继承 P3 本地 Trace 查询权限。

本轮新增 PyJWT 负责外部 JWT 验签，主体/租户/权限仍来自 P3 服务端配置；不提供登录或 Token 签发平台。身份、日志和追踪的具体配置及测试边界见 [租户入口与可观测性接入](../development/12_租户入口与可观测性接入.md)。详细节点规范见 [日志追踪与健康检测](../development/06_日志追踪与健康检测.md)。
