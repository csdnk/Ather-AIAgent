# P3/P4 原结果读取与执行状态恢复实施计划

沿用已授权的 T06/T07，在现有隔离工作树串行使用 executing-plans 和 TDD；不重复请求执行授权，不提交、合并或部署。正式数据库能力仍由 P2 提供，当前元数据/缓存参考组件只作为开发测试证据。整体上线要求保持原范围。

## 目标与实现边界

保存一次业务调用前后的可恢复信息：原输入、原 operation/job、原结果与其绑定、当前引用映射和执行位置。恢复不得重新生成 operation ID、重取事件时间或以当前结果替换原结果。先补齐持久证据与读取，再实现所有权转移和安全续跑；本计划的中间交付不自动开放接管。

代码核对发现：StoryRun 的 refs/sources/receipts/episodes/recalls 和若干跨步骤局部变量仍在内存；基础 library runner 也有独立 receipts。一个步骤可能上传后保存、连续归档再恢复，或者分别删除来源。现有 prepared/observed 记录只证明 HTTP 意图和回执，不能证明业务结果已验证或引用状态已消费。

## 设计决策

1. 同步变更的原结果从已有不可变 MutationRecord 读取，新增只读结果接口。返回原 MutationReceipt 和存储时的 response；校验身份、当前目标读取权与 result_hash。生命周期的原存储结果明确是 metadata_without_content，不能把正文重新写回元数据或以当前 MemorySnapshot 替代原状态。需要正文的消费者另按原引用、现行权限读取。
2. P4 的恢复状态区分业务权威结果与调用方状态。前者来自原任务/原变更回执；后者记录语义名称到原引用的映射、原操作列表、定义绑定、步号和消费阶段。浏览器进度不是恢复状态的唯一来源。
3. 执行状态使用版本化 P2 对象和不可变父链，元数据只保存绑定和 head。保存前后检查 run/owner/revision/active/定义，P2 写入后读回摘要再发布 head。同序号冲突拒绝；丢回执可核对同一 head，不能新建另一条父链掩盖未知状态。
4. 状态只保存必要元数据、结果引用和回执；旧 Recall 正文不得借由新状态读取接口绕过删除/撤权。跨步骤的 old recall、episode 基线、提炼任务和清理任务也要显式保存；只持久化五个 dict 不足以恢复完整故事。
5. 新 P4 请求版本化状态策略，发送下一个业务效果之前必须持久保存当前状态和原操作前缀；P3 对采用该策略的运行在准入中核对。旧登记不自动升级策略，缺失历史状态不凭当前代码补造。
6. 状态读取/解析不执行业务请求。复原之后仍需检查原任务状态、版本和现行权限；自动继续留到所有权转移和逐效果恢复逻辑完成后。

接口：GET /p3/mutation-receipts/{operation_id}/result?kind=… 返回 receipt 与 response；缺失记录为 COMMIT_UNCONFIRMED，不能据此重发。P4 校验 operation、kind 与规范化 result_hash。接口不重新提交业务、不创建任务、不改原回执。

## Task 2：版本化执行状态对象与父链

文件：新增 runtime/contracts/client_states.py、foundation/client_states.py、flows/client_state_routes.py；扩展 client_runs 契约及准入；测试 tests/integration/test_client_states.py。

接口：PUT/GET /p3/client-runs/{run_id}/states/{sequence}。保存返回更新后的原 ClientRunRecord；读取返回原字节与 X-P3-State-Hash。绑定格式固定 p4_state_v1；sequence 从 1 连续增长，上限 1024；每份原 JSON 最多 262144 字节，且不超过配置的对象输入上限。绑定包含父 hash、内容 hash/大小、定义摘要和规范化原操作列表摘要。head 的发布与 run 修订在同一事务中完成。同一 head 的相同字节重试允许核对原保存，其他旧修订或分叉拒绝。新 state_policy 必须同时具有 p4_task_v1 与原定义。

- [x] RED：缺失端点、错父链/错原操作/旧 owner/P2 损坏/丢回执/竞争不能取得新 head；拒绝新策略的无状态准入。补充审查复现已有日志可重排、读取未核对 head 与接口清单缺项。
- [x] GREEN：复用当前事务、身份和 P2 对象契约，实现 pending→ready→head，不增加数据库驱动；已有操作顺序不可重排，读取前后核对发布绑定。
- [x] 验证：同序号幂等、原字节读回、IO 前后身份/owner/revision/active 变化、重启、双写竞争、终态历史读取和旧策略拒绝通过。最终专项 61 项、合并回归 1328 项通过，Ruff/Mypy 通过；批次有重叠，不累计。

Task 2 完成的是 P3 状态对象及准入能力。后续 Task 3 已将 state_policy 接到新版 P4，并实现引用映射、跨步骤变量和逐次结果消费；完成状态以 Task 3 的验证记录为准。相同原字节的 PUT 回执核对要求原 writer/revision、当前相同 head 且 run revision 尚未发生后续变化；后续修订之后应通过 GET 核对历史状态，不以新序号覆盖不确定性。

## 审查和证据

重点：生命周期原响应与当前版本不同；空合并后出现新数据；P2 成功但元数据提交未知；旧 Recall 被撤权后不能借状态恢复读取正文；页面单步骤有多个效果；原定义和执行版本不兼容；终态 head 与容量清退。

逐项保留红测试和失败；最终合并回归、Ruff/Mypy、源文件摘要与 P2 engine/proto 边界检查通过后记录局部证据。正式 P2、完整恢复/迁移、生产身份/模型/镜像/Azure/Temporal、故障/灾备/长稳继续按整体上线计划执行，导学会话仍待完整验收。
