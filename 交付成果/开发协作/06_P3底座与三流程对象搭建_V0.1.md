## 对象分组

| 模块 | 新增对象 | 用途 |
|---|---|---|
| RF 公共底座 | ResourceLocation、NodeLogRecord、HealthObservation、RuntimeHealthSnapshot | 统一资源地址、日志关联与健康证据 |
| RF 监测与恢复 | SignalDefinition、SignalObservation、WorkerHeartbeat、OperationDefinition、DispositionRule、IncidentRecord | 信号→规则→维护执行→业务复核的基础定义 |
| RF 任务与运行 | TaskWaitRecord、CheckpointRecord、ConfigurationSnapshot、BackupManifest | 挂接既有任务、等待、断点、配置和恢复证据 |
| B 来源与加工 | SourceRecord、DerivedArtifact、ProcessingRecord、ExtractionDecision | 保存原件、登记加工产物、跟踪阶段、处理候选事实 |
| B 记忆与索引 | ChunkDescriptor、ProjectionManifest、MemoryRecord | 正文权威、预期块清单、索引批次和 Ready 发布 |
| B 正文与资格 | GuardStamp、FullBodyReadResult | 完整正文、来源、对象与关系修订 |
| B/C 交接 | ReferenceHandoff、ReferenceHandoffReceipt、ProtectionReference、CleanupRequest、CleanupTargetResult、CleanupReceipt | 地址更新、保护持有者、释放和清理回执 |
| A 共享计算 | EmbeddingSpace、ChunkProjectionRequest、ChunkProjectionResult、ChunkSearchRequest、ChunkSearchResult、ChunkHit | 兼容编码空间、精确批次写入与取块 |
| A 记忆候选 | MemorySearchRequest、MemoryCandidate、MemorySearchResult | 块命中聚合为记忆候选，独立限制 K 与取块工作量 |
| A 正文组包 | RecallPlanRequest、RankingEvidence、ContextPackUnit、ContextAssemblyPlan、ContextCommitRequest | 记忆级排名、完整冲突组、整包预算和最终核验 |
| C 调度迁移 | SchedulingRound、BufferEntry、MigrationPlan | 事件水位、驻留热度、保护与迁移后地址交接 |

交接对象集中放在 B 的契约模块，避免 B 与 C 循环依赖。文件位置不改变事实归属：保护引用由 C 维护；地址权威与交接确认由 B 维护；清理请求由 B 发出、回执由 C 返回。

## 三流程的数据交接

| 提供方 → 消费方 | 输入与输出 | 实现时的完成条件 |
|---|---|---|
| B → A 共享编码 | 既有 EmbeddingRequest/Result，配合 EmbeddingSpace | Query与Passage模型、维度、前缀和归一化兼容 |
| B → A 索引写入 | ChunkProjectionRequest → ChunkProjectionResult | 精确记忆版本、正文指纹、批次、块指纹均匹配且可搜索；超时仅查询原操作 |
| A → B 发布索引 | ProjectionManifest → MemoryRecord | 当前对象修订与正文仍匹配；全部预期块核验后，在事务内发布 Ready |
| B → A 内部检索 | MemorySearchRequest(purpose=extraction) → MemorySearchResult | 只提供候选ID、精确版本、排名与命中证据；不运行完整Recall组包 |
| A → B 读取正文 | MemoryRef列表 → FullBodyReadResult列表 | 每个请求项恰好一个结果；授权后读完整正文，核验指纹，返回出处与GuardStamp |
| A → B/RF 最终提交 | ContextCommitRequest → 结果RecordRef | 同一事务重新读取资格、授权和关系修订，原子写Recall结果及outbox |
| C → B 地址交接 | ReferenceHandoff → ReferenceHandoffReceipt | 旧地址、类型、代次、指纹、预期修订和Provider读证据匹配，B条件更新 |
| B → C 保护释放 | protection_id、expected_revision → ProtectionReference | 核验保护的所属任务/动作；确认无在途副作用后释放，不把到期当成自动释放 |
| B → C → B 删除清理 | CleanupRequest → CleanupReceipt | B先逻辑阻断；C处理保护和每个目标；完整回执返回B后再确认清理完成 |

接口方法均位于各模块 `contracts/ports.py`。新加入 `MonitoringPort`、`MemoryFoundationPort`、`GenerationVectorPort`、`MemoryCandidatePort`、`ContextAssemblyPort`、`LifecycleCleanupPort`。

## 必须保持的规则

1. **身份不补默认值。** `MemoryRef`携带完整作用域、记忆ID与版本。范围选择只是限制，服务必须与TrustedContext授权求交；模型可解析不代表有权限。
2. **正文与索引批次分开。** 正文地址和缓存使用正文资源代次；向量地址使用索引批次。向量地址的content_hash表示被投影正文的指纹，不是序列化向量文件的指纹。不能把正文代次和索引代次混成一个全局计数器。
3. **Ready针对完整批次。** 预期块从0连续编号、向量ID唯一、全部核验通过、已有发布时间。索引必须指向同一记忆版本及正文指纹。
4. **Top K按记忆计数。** 合格记忆按最佳有效命中块得分排序。一个记忆的多个块/多个版本不能占多个位置；并列时使用作用域与ID稳定排序。取块页大小、总取块量、轮数和期限单独受限。
5. **块命中不提供完整内容。** B返回完整权威正文，并校验UTF-8 SHA-256。缓存只能覆盖相同正文指纹与代次；回源失败必须逐项说明，不返回部分正文冒充成功。
6. **完整组装包。** 一条记忆或必需冲突组整体接纳/跳过；关系补全成员与Working不占长期主候选K，但都占token预算。完整正文原样进入渲染文本，不能静默截断或换成摘要。
7. **计数使用最终文本。** ContextAssemblyPlan声明实际token数，服务必须对含分隔符、说明和出处的最终渲染文本调用context tokenizer；Pydantic只检查数值范围，不执行真实分词器。
8. **最终核验必须在提交事务内执行。** GuardStamp记录对象修订、关系修订、授权代次、正文指纹。传入的stamp只是证据，不能代替B重新读取权威状态；有变化需重新规划，不能直接保存旧计划。
9. **访问热度只计成功正文读取。** chunk hit不是read；packed不再加热。消费AccessObserved时按原事件/访问键去重，BufferEntry保存归并后的计数与水位。
10. **确认地址后再清旧副本。** C必须取得B的applied回执并释放保护，旧副本才可清理；unknown回执保留旧副本。清理回执必须逐项覆盖原清单，未知不能写completed。
11. **日志、健康和业务事实分开。** 日志只允许受控元数据；健康探测不做恢复动作；过期/未知证据不能判定ready；维护完成还要有业务验证证据，才能关闭异常。

## 兼容与接入顺序

新增定义分别位于以下文件；原 `models.py` 保持兼容：

- [RF foundation.py](../../AgentJYS-main/src/aether_agent_memory/runtime/contracts/foundation.py)
- [B foundation.py](../../AgentJYS-main/src/aether_agent_memory/remember/contracts/foundation.py)
- [A foundation.py](../../AgentJYS-main/src/aether_agent_memory/recall/contracts/foundation.py)
- [C foundation.py](../../AgentJYS-main/src/aether_agent_memory/operate/contracts/foundation.py)

开发时从具体模块导入类型，例如 `aether_agent_memory.remember.contracts.foundation.MemoryRecord`。跨网络/持久化数据使用 `model_validate_json`；输出使用 `model_dump_json`。Schema由既有工具发现 `models.py` 和 `foundation.py` 后自动生成，不手工编辑。

建议按以下依赖接入，每步都需要实际消费者与失败路径测试：

1. RF补新健康/日志适配和操作、信号、规则注册；保留现有Task、UoW、事件、诊断与维护入口。注册时验证操作名、信号名和验证操作引用存在，采集时执行标签组合上限。
2. B接持久MemoryRecord、来源与加工记录，提供逐项完整正文读取；把现有内联MemorySnapshot明确适配为读DTO。旧地址无法可靠确定批次时需迁移/重建，不能随意填一个generation冒充旧数据。
3. A共享向量适配器接精确批次对象，B接全部块核验与索引发布；随后实现内部MemoryCandidatePort。
4. A接RecallPlanRequest、记忆聚合、完整组、实际token预算和条件提交。仅Working时旁路Embedding/Vector/RRF；历史重取也重新核验资格。
5. C接轮次、Buffer、保护、地址交接与清理回执；维持既有ActionRecord与Provider证据链。

现有日志使用schema_version=1与字典健康响应。新增NodeLogRecord使用`p3/log/2`，RuntimeHealthSnapshot使用`p3/health/2`；需要显式适配，不能直接替换现有日志数据库或HTTP响应。

旧RecallRequest/ContextPack继续服务原实现。新RecallPlanRequest与ContextAssemblyPlan明确完整正文模式，并能表达“无内容且存在降级原因”。旧ContextPack的压缩表示和空结果约束不同，接入时需增加明确映射或版本化结果协议，不应强行转换后丢失语义。
