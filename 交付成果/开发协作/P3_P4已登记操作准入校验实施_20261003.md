# P3/P4 已登记操作准入校验实施计划

本项继续全系统 T06/T07，在既有隔离工作树串行实施。沿用 P2 的对象与事务端口，不修改 P2 引擎和共享协议，不提交、发布或部署。全系统上线验收及导学交接条件保持不变。

**目标：**已经通过 P3 checkpoint 保存的原操作，只有当前执行者携带当前修订号、使用已保存的原请求字节，才能进入 HTTP 任务准入或同步业务变更事务。省略执行者请求头不能绕过已登记操作的校验。

## 设计与边界

- 新 prepared 操作与“身份、原操作 ID → 原运行、原绑定摘要”索引在同一事务内提交。原操作 ID 不能被后续运行重新绑定；历史记录不自动补造索引。
- HTTP 边界读取 `X-P3-Run-ID`、`X-P3-Run-Owner`、`X-P3-Run-Revision`。三项必须齐全且唯一；请求头只是待验证声明，P3 以事务内原登记为准。
- 在四类 Temporal 命令准入及十类同步 mutation 的业务事务中，检查原运行、当前身份、owner、revision、active、running、prepared、原字节 ready、method/route/target/content-type/hash。一并保存通过检查的 HTTP 声明，供原结果回查。
- Remember/更正/文档在写入不可变命令输入前先检查一次，防止旧执行者占用原操作 ID；P2 IO 之后的准入事务再次检查，前置检查不替代最终事务检查。Recall 在同一事务内回滚未接纳记录。
- 已接纳 Temporal 任务继续按原 job/workflow ID 和原 Activity fence 执行；请求者登记变化不撤销已接纳的业务。已观察、已结束和旧执行者通过 GET 查询原结果，不能再次 POST 创建效果。
- P4 顺序为 prepared checkpoint → 原字节保存确认 → 获取此时的本地登记修订号 → 携带执行者声明发送业务 HTTP → observed checkpoint。不会把鉴权令牌写入 snapshot 或对象库。
- 本项只覆盖已登记的操作。尚未登记的新操作、不同操作 ID 下的跨作用域写入，仍需要后续的权威作用域隔离。不会为了补齐这一项而限制同一用户的全部业务 API，也不会把此项称为完整执行权隔离。
- 执行者标识用于协作实例的并发隔离，不代替正式用户/服务身份。自动接管、动态结果重建、旧记录迁移仍保持未开放。
- 原操作索引和最终准入依赖事务的原子性与隔离；当前验证使用既有参考元数据组件，不把普通 P2 Put/Get 当成分布式 CAS，也不推定正式 P2 已提供所需隔离能力。

## 实施和验证

- [x] 红测试：漏头/旧 owner/旧 revision/改变原字节或路由不能准入；原字节未 ready 不能准入；原索引提交失败不留下 checkpoint。
- [x] 实现原操作索引及统一事务内准入检查，覆盖 Temporal 与同步 mutation 两条路径。
- [x] P4 使用完成原字节保存后的最新登记修订号，验证失败不发送业务请求。
- [x] 验证原任务不因登记变化丢失、GET 可查原结果、普通无登记调用兼容、HTTP 字段与索引跨 Service 重建保持一致。
- [x] 运行相关回归和静态检查，保留失败及当前 P2/参考元数据组件证据层，更新正式验收报告。
