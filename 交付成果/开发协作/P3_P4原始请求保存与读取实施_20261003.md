# P3/P4 原始请求保存与读取实施计划

本项沿用全系统计划 T06/T07 和已确定的 P3/P2 存储职责。使用 executing-plans 在当前隔离工作树串行实施；不新增审批步骤，不提交或部署，不修改 P2 引擎/proto，不新增 P3 数据库驱动。

**目标：**每次 P4 业务请求在发送前已有可从 P3/P2 读取的原始 HTTP 字节，丢回执或重启后按原运行、原 operation 和原绑定核验，不从摘要反推正文。

**架构：**P4 先保存 prepared 意图，再通过 P3 的受认证接口保存原始字节，确认回执后才发送业务请求。P3 复用运行登记的事务端口和现有 P2 对象 Put/Get；原始字节不进入浏览器 snapshot、P4 本地文件或第二份权威数据库。

**依据：**[运行登记与重启恢复设计](../架构设计/P3_P4运行登记与重启恢复补充_20261003.md)。版本化运行定义、尚未生成的后续步骤输入、结果映射恢复、所有权转移、API 准入隔离和中断续跑仍属于完整 T06/T07 后续必做范围，不因原输入保存完成而取消。

## 接口和不变量

- `PUT /p3/client-runs/{run_id}/inputs/{operation_id}` 接收原始二进制正文，以 `X-P3-Run-Owner` 和 `X-P3-Run-Revision` 绑定原登记所有者和版本。请求意图必须已存在、带完整 binding，正文 SHA256 必须等于原 request_hash。
- `GET` 同一路径按当前身份读取已确认的原始字节；P4 再核对原 hash。未保存、未确认、缺少旧绑定、正文丢失或损坏均明确失败，不改写原意图，不据此判断业务没有执行。
- 输入元数据使用 `client_request_input` 引用，与 Temporal `command_input` 分开。对象键由原作用域/运行/操作引用和正文摘要确定，正文实际经过 P2。
- 写入顺序：当前身份/owner/revision/active 校验 → 原子保存 pending 元数据 → 事务外 P2 Put/Get 字节复验 → 再校验当前身份/owner/revision/active → 同一输入记录变为 ready。外部写失败保留 pending，不制造成功回执。
- 同一原输入的 ready 回执可在当前身份和同一 owner 下原样重取；新输入须仍是 prepared、运行 queued/running 且占有 active。旧 observed/unbound 行不能补造历史输入。
- 每次输入受现有 max_input_bytes 限制；空正文合法，因为 reprocess 等请求可以没有 HTTP body。每轮操作数量仍受现有 256 条上限约束。
- 元数据 CAS 来自既有事务端口，普通 P2 Put/Get 只承担内容存储和复验。正式 P2 事务适配缺失时，生产入口继续拒绝启动。
- P4 的保存调用不携带业务 operation header，避免把保存动作再登记为新的业务请求。用户凭据只由 HTTP 客户端发送，原输入回执和 snapshot 不保存 Authorization/Cookie。

## 审查重点

空请求不能被误认为没有输入；同一操作的不同字节不能覆盖原对象；P2 作用后身份/owner 变化不能提交 ready；ready 重试不得增加记录或释放 active；保存失败不得发业务请求；缺失历史字节不得从当前故事常量补造。以上分别由对应任务的定向测试覆盖。
