# P2 对象同键并发写问题与验收要求

日期：2026-10-03。结论：当前 P2 的同键并发对象写入存在已复现错误，P3/P4 的合并验收暂不签通过。本文给出消费需求、复现证据和验收条件；没有修改 P2 引擎或共享 proto，具体修复方案由 P2 决定。

## 已观测到的失败

| 证据 | 环境及触发 | 结果 |
|---|---|---|
| FG-84 | P3/P4 合并回归；当前 P2，测试 Temporal，参考元数据/缓存 | 1367 项中 1366 通过、1 失败。失败为两个写入者并发保存同一运行、同一 operation、同一份原输入，一个 HTTP 200、另一个 HTTP 503 |
| FG-85A | 同一用例独立复现，增加 P2 调用错误采集 | P2 写调用返回 gRPC INTERNAL；P3 保留依赖未确认，没有把异常写成成功 |
| FG-85B | 排除 P3 调用链，直接使用现有 P2 ObjectService；独立测试命名空间、20 个新 key，每个 key 两个同步开始的 PutObject | 40 次写中 20 次成功、20 次 INTERNAL。错误为 `io error: No such file or directory (os error 2)`；20 次最终 GetObject 的 SHA-256 均与原始 163840 字节一致 |

原输入并发用例后续有 6 次独立通过，说明普通请求时序下存在间歇性，不能据此删除原失败。原始日志、调用回执、命名空间、输入摘要和运行 ID 保存在外部工作区，正式报告引用证据编号即可。

## 源码定位与边界

仓库 `AgentJYS-main/engine/engines/e2-object/src/backend.rs` 的 `LocalFsBackend::put` 第 44—46 行对同一目标使用 `full.with_extension("tmp")`，随后 `fs::write` 和 `fs::rename`。并发调用共用同一个临时路径，一个调用完成 rename 后，另一个调用可能找不到其临时文件。这段逻辑与直接 RPC 的错误吻合，P2 应核对实际运行构建并在其职责内修复。

本次验证针对当前开发用 P2 对象服务，不能推断 Azure Ceph 集群发生同样故障；正式 P2 在 Ceph 上的实现也应验证下述消费契约。最终字节读回正确，仅证明本次测试结束后的数据内容；不能由此声称每次写入已正确确认，或已经完成故障/灾备验收。

## P3 的消费需求

1. 同一不可变输入的 run、operation、内容摘要和原字节保持不变，多个并发调用不能因共享临时资源产生偶发内部错误。
2. 成功回执必须对应可读取、完整且摘要相符的对象；不能在部分写入或尚未发布时返回成功。
3. 明确错误、条件冲突、提交结果未知应可区分。结果未知时能够根据原对象/原操作核对，不能要求 P3 改 key、重生成 operation ID 或换一条数据覆盖原不确定性。
4. 不同字节竞争同一权威对象时，必须有 P2 明确的原子写入/条件写入语义，不能靠 P3 单进程锁冒充跨实例一致性。
5. 进程中断不能破坏已确认的原对象；临时数据的隔离和清理策略由 P2 实现，不能影响其他写入者。

## 复核与验收

- 重跑 `tests/integration/test_client_inputs.py::test_concurrent_original_input_writers_keep_same_receipt_and_run`，保留两个成功回执一致、原字节读回一致、原 run 不变的断言。
- 重跑直接 ObjectService 并发探针：新 key 和已存在 key、相同与不同 payload、多线程与多客户端均须覆盖；记录每个写入结果和最终对象摘要。
- 加入写入中断、rename/发布失败、返回成功后重启、读取与写入并发的检查，区分确定失败和未知提交。
- 在 P2 确认的正式 PG/Redis/Milvus/Ceph 组合中验证相同契约，再执行 P3/P4 合并回归。开发后端的一次绿色结果不能代替正式后端验收。

P3 当前保留原 input/run/operation 和失败信息，继续拒绝越过不确定状态执行后续业务。本次没有通过吞掉 INTERNAL、降低断言或改用新对象路径消除失败。P4 自动接管、逐项原结果核对和安全续跑仍需后续实现。
