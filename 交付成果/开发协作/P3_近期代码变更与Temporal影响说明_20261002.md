## 2. 最新 PR #14 的存储变化

### PostgreSQL

新增 [postgres.py](../../AgentJYS-main/src/aether_agent_memory/runtime/foundation/postgres.py) 和 [postgres_telemetry.py](../../AgentJYS-main/src/aether_agent_memory/runtime/foundation/postgres_telemetry.py)。配置通过 `metadata_backend: postgresql` 和 `postgres_dsn_env` 选择 PG；DSN 从环境变量读取。

业务状态仍使用统一的记录契约，原始值按 TEXT 保存，部分队列状态投影为 JSONB 并建立索引。PG 事务使用数据库 advisory lock 保持此前串行读写的语义，继续执行版本、授权和提交前 guard。这个实现优先保留正确性，不代表已经获得多实例并行写吞吐或完成 AKS 多副本验收。

PG 运行路径会在 PG 中提交，不会在 PG 故障时切回 SQLite；但实现仍继承原 `SQLiteTransaction`/`SQLiteUnitOfWork` 复用契约逻辑，代码层面的 SQLite 耦合尚未全部移除。

新增 [migrate_remember_postgres.py](../../AgentJYS-main/scripts/p3/migrate_remember_postgres.py)，只读复制已停止服务的 SQLite 元数据，核对记录数量和摘要并保存迁移标记。它不迁移 Ceph 正文，也不迁移 Temporal Server 的历史数据库。PG 下原 SQLite 快照备份/恢复 API 会明确拒绝，需要使用 PG 备份恢复工具并补齐运行方案。

### Ceph

新增 [ceph_p2.py](../../AgentJYS-main/src/aether_agent_memory/remember/basic/ceph_p2.py)，配置 `ceph` 时由 P3 装配 Python `CephP2`，通过 boto3、S3 SigV4 和 path-style 访问 RGW。账号、密钥来自明确指定的环境变量，bucket 由部署预先准备。

对象写入使用 `If-None-Match: *`；已有对象必须与预期字节一致。整对象读检查 SHA256，范围读检查响应范围和长度。写入确认丢失时，Temporal Activity 查询原对象；确认缺失且适配器声明不可变重写安全后，按原意图进行有次数上限的恢复。

这是一条 P3 直接使用 Ceph RGW 的正文适配路径；原 P2 gRPC 路径仍保留，配置拒绝同时设置两者。它不证明 P2 Rust 服务已经完成 Ceph 后端，也不替代完整 P2 解析、来源和放置契约的联调。

### 配置仍未达到已讨论的最终方案

当前 [config.py](../../AgentJYS-main/src/aether_agent_memory/runtime/flows/config.py) 仍是 `profile: local/production`，`metadata_backend` 默认 SQLite，开发配置仍可使用 lexical；Milvus Lite 和本地正文后端仍在源码及配置中。Operate 仍装配 [LocalCacheExecutor](../../AgentJYS-main/src/aether_agent_memory/operate/basic/executor.py)，创建 `executor.db` 和本地副本目录。

生产配置增加了 PG、真实正文端口和 Milvus URI 校验，但尚未完整落实三个环境固定后端、独立数据范围、Redis 环境前缀和私网接入。现有生产示例也未补齐新增的 PG/Milvus 必需项，不能直接按旧模板启动新版。

## 3. 最新 Remember 处理变化

- 压缩从一次生成/验证增加到最多三轮质量修复，并分别持久保存生成结果和验证结果。重启可复用已保存输出；压缩比仍是可见目标，关键事实质量必须通过，不会靠删掉条件或否定词达到比例。
- 抽取要求证据唯一且准确绑定原文。模型中的换行表示可以映射回原文 CRLF/CR/LF，重复引用必须提供足够上下文；改写事实需要独立支持验证，拒绝结果有持久记录。
- 语义去重、同一事件判断和追加信息更严格：标点规范化和模型生成的 event_key 仅用于发现候选，同一事件需要原文上下文支持；不确定或会丢失旧条件的修改保留为冲突。
- 比较过程持久保存逐候选决策和游标，绑定输入、来源、空间版本及处理器身份。恢复时复用有效检查点；来源或版本变化后重新核对。
- Working 摘要按解析后的正文长度判断，短附件不再仅因是文档就强制摘要。处理状态会显示失败原因及符合权限的 `reprocess`/`reindex` 操作提示，不自动把失败标记成成功。

## 4. Temporal 受到哪些影响

| 位置 | 改之前 | 改之后 | 实际影响 |
|---|---|---|---|
| [保存入口](../../AgentJYS-main/src/aether_agent_memory/runtime/temporal/ingress.py)与[索引任务](../../AgentJYS-main/src/aether_agent_memory/remember/basic/service.py) | 保存/文档/纠错、模型处理、投影/清理共享 `remember` 类别 | 新请求走 `remember_ingress`，投影/清理走 `remember_index`，模型仍走 `remember` | 长模型任务不会占满保存和索引的类别配额；租户、scope 等共同容量约束仍成立。旧任务保留已有类别 |
| [Activity 心跳](../../AgentJYS-main/src/aether_agent_memory/runtime/temporal/activities.py) | 获取本地容量及业务执行资格后才启动心跳 | Activity 在等待本地 slot 时已发心跳，仍受原超时限制；取得 slot 前不消耗业务尝试 | 减少等待容量时的无谓 heartbeat timeout，并保持业务提交 fence |
| [启动/控制意图转发](../../AgentJYS-main/src/aether_agent_memory/runtime/temporal/bridge.py) | 先处理一批 start，再处理 control | start/control 交替处理；每轮约 2 秒预算，到 RPC 边界让出调度 | 大量文档子任务不会持续挤压取消等控制请求；已发出的 RPC 仍按原超时完成和核对 |
| [Worker 配额](../../AgentJYS-main/src/aether_agent_memory/runtime/temporal/worker.py) | 共享 8 个 Workflow 执行线程，各队列可预留 8 个并发 Workflow task | 每队列预留 2 个，线程数按队列数乘 2 分配 | 调整资源占用和跨队列竞争；不是业务并发性能提升的验收结论 |
| [周期状态核查](../../AgentJYS-main/src/aether_agent_memory/runtime/temporal/periodic.py) | 周期遍历历史绑定，逐一请求 Temporal 状态 | 已核对且一致的终态缓存 900 秒；历史终态每 tick 最多刷新 16 个；活跃、未知副作用和已知异常不走该限额 | 减少历史增长造成的 RPC 压力。终态外部变化可能到下次核查才发现，不能把缓存理解为永久免查 |
| [正文确认丢失恢复](../../AgentJYS-main/src/aether_agent_memory/remember/basic/temporal_stages.py) | 缺失对象主要进入 query/retry/unknown 路径 | Ceph 不可变对象允许在确认缺失后保留原意图、有限重写并记录确认；超过预算转 attention | 改变 Activity 的恢复行为，保留原 operation/object 身份 |
| [Remember 检查点](../../AgentJYS-main/src/aether_agent_memory/remember/basic/pipeline.py) | 绑定策略、模型空间和 tokenizer | 另绑定任务种类、处理规则版本与相关模型/provider 身份 | 旧未完成任务的 `remember_task_binding` 可能与新版不匹配，Activity 会拒绝继续，需要受控处理 |
| [PG 启动绑定检查](../../AgentJYS-main/src/aether_agent_memory/runtime/flows/application.py) | 启动前主要核查 SQLite 的迁移与执行后端标记 | PG 中也检查 deployment ID、namespace、队列前缀和未完成任务/投递/Recall 的绑定 | 迁移元数据后不能随意更改 Temporal 身份或留下未绑定任务 |

PR #14 没有修改核心 Workflow 定义、TemporalConfiguration、Temporal Server 容器或其持久化部署。改动集中在 P3 的 Activity、Worker、意图转发和业务账本。把 P3 元数据切到 PG，不会自动把 Temporal Server 自己的历史持久化切到 PG。

旧任务仍能被相应队列的 Worker 接收，但还需检查其业务检查点。特别是新旧 `checkpoint_binding` 的计算规则不同，不能只凭 Workflow 定义未改或历史回放通过，就断言升级前的所有未完成 Remember 任务可原样续跑。
