# P3/P4 版本化运行定义实施计划

本项继续全系统 T06/T07 与已确认的原输入恢复方案，使用 executing-plans 在既有隔离工作树串行实施。数据库能力仍由 P2 提供；不修改 P2 引擎或协议，不提交、合并或部署，不提前创建导学会话。

**目标：**一轮 P4 执行在业务请求之前，已有不可替换的运行定义；后续步骤使用原场景输入及原事件时间，重启读取不会用当前常量补造历史。

**架构：**登记契约增加可选定义摘要、大小和格式标识，旧记录原样可读。原始定义通过独立 PUT/GET 端点及既有 P2 对象/事务端口保存，复用当前身份、owner、revision、active 检查。P4 把固定故事的数据、每步事件时间和执行实现摘要封装为版本 1 定义；从 P3/P2 读回并验证后执行。正文只在对象服务中保存，浏览器 snapshot 继续保存展示内容与有限证据。

## 不变量与设计取舍

- 新 P4 定义在登记前生成，摘要随首次登记固定。同 UUID 再次开始只读取原登记；新候选定义不会替换原数据。
- 定义存储先 pending，事务外 P2 写入与读回复验，再重新鉴权及检查 owner/revision/active 后 ready。正文超限、摘要不同、缺少注册绑定、已开始但未存原定义都拒绝。
- 带定义绑定的运行，在定义 ready 前不能变为 running 或登记业务操作。原登记不带定义时不补造历史；它不能由新版 P4 自动接管。
- ready 的重试和读取均检查原 P2 字节。损坏或丢失不能通过重新保存来掩盖；回执丢失保留原 UUID、原定义绑定与 active 占用。
- 固定场景的步骤文本、上传原文、额外写入文本、查询文本、更正与删除原因、保留/反思参数、事件时间在定义内明确保存。来自先前结果的 ID、版本和动态范围不预先猜测，继续由原结果和逐副作用 checkpoint 方案恢复。
- 每步虚构事件时间在定义生成时固定为同一 UTC 基点加步骤毫秒序号，用于当前固定演示故事；不把恢复时钟当作历史发生时间。
- 执行实现摘要绑定固定故事、构造/解析请求所用代码与契约。运行时改变版本须显式迁移或使用对应旧版本；摘要不一致时停止执行，不动态执行保存在对象库中的代码。
- 这一步提供运行定义和后续固定输入。原结果恢复、执行权转移、旧 P4/P3 准入隔离、完整中断续跑和正式 P2 验收仍是全系统必做项。
