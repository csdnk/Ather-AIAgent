你现在不要修改任何代码。你的任务是作为这个项目的“原作者 + 代码导师”，带我彻底理解当前代码仓库。

我的目标不是得到一个简单的项目总结，而是做到：以后我自己修改、扩展、排查这个项目时，能够像自己亲手设计和编写过一样理解它。

请严格按照“由整体到局部、由设计到实现、由静态结构到运行时”的顺序带我学习。

第一阶段：建立项目全景

1. 先扫描整个仓库，但不要急着解释代码。
2. 给出完整的项目目录树，并标记：
   - 核心目录
   - 核心文件
   - 配置文件
   - 启动入口
   - API/接口层
   - 业务逻辑层
   - 数据访问层
   - 外部依赖
   - 测试代码
   - 脚本和工具
3. 找出项目真正的入口点：
   - 程序从哪里启动
   - 第一段代码在哪里执行
   - 初始化顺序是什么
   - 第一个核心业务流程是什么
4. 用一张“项目架构关系图”的文字形式描述：\
   用户/调用方 → API → Service → Core → Storage/External Service\
   并根据当前项目实际情况替换这些名称。
5. 明确指出哪些目录/文件是核心代码，哪些只是辅助代码。

第二阶段：理解项目为什么这样设计

不要只告诉我“这个文件负责什么”，还要解释：

- 为什么需要这个模块？
- 它解决了什么问题？
- 为什么放在这里？
- 它和其他模块是什么关系？
- 如果删除它，会发生什么？
- 有没有其他实现方式？
- 当前实现有什么设计取舍？

对于重要设计，请明确区分：\
“业务需求”\
“架构设计”\
“代码实现”\
“第三方框架行为”

不要把框架自动完成的事情说成项目自己的逻辑。

第三阶段：追踪核心业务链路

找出这个项目最重要的 3\~5 条业务链路。

对于每条链路，从入口开始，一直追踪到最终结果。

例如：

HTTP Request\
↓\
Router\
↓\
Controller\
↓\
Service\
↓\
Core Logic\
↓\
Repository\
↓\
Database\
↓\
Response

对每一步告诉我：

1. 谁调用了谁
2. 调用的具体函数/方法
3. 输入是什么
4. 输出是什么
5. 中间的数据结构是什么
6. 有没有状态变化
7. 有没有异常处理
8. 有没有异步操作
9. 有没有缓存
10. 有没有数据库/网络访问

不要只给文件名，要尽可能定位到具体类、函数和代码位置。

第四阶段：理解核心数据结构

找出项目中最重要的数据结构，包括：

- class
- struct
- interface
- DTO
- Entity
- Model
- Request/Response
- 配置对象
- 状态对象
- 数据库表
- Redis Key
- 消息结构

对每一个核心数据结构解释：

它是什么 → 谁创建 → 谁修改 → 谁读取 → 生命周期是什么 → 最终在哪里被消费。

如果存在同一个概念对应多个数据结构，也要解释为什么需要多个结构。

第五阶段：理解状态和生命周期

重点检查：

- 对象生命周期
- 请求生命周期
- 任务生命周期
- 数据生命周期
- 缓存生命周期
- 数据库记录生命周期
- 工作流状态
- 重试机制
- 超时机制
- 错误恢复机制

如果项目使用了 Redis、数据库、消息队列、Celery、Temporal、Kafka、Milvus、Ceph、对象存储等基础设施，要解释它们在当前项目中到底承担什么职责，而不是泛泛介绍这些技术。

第六阶段：理解配置和环境

找出：

- 所有配置文件
- 环境变量
- 密钥/API配置
- 数据库配置
- Redis配置
- 服务地址
- Docker配置
- 启动参数
- 开发/测试/生产环境差异

告诉我：

“一个新开发者拿到这个项目以后，到底需要配置什么，项目才能跑起来。”

同时区分：

代码中写死的配置\
环境变量\
配置文件\
外部服务提供的配置。

第七阶段：理解异常和边界情况

不要只讲正常流程。

找出：

- try/catch
- error handling
- retry
- timeout
- fallback
- circuit breaker
- validation
- transaction
- rollback
- 并发控制
- 幂等性
- 数据一致性

告诉我这个项目遇到异常时到底怎么走。

最好给我几个真实的异常场景：

“如果数据库挂了，会发生什么？”\
“如果 Redis 挂了，会发生什么？”\
“如果第三方 API 超时，会发生什么？”\
“如果请求重复提交，会发生什么？”\
“如果服务重启，中间任务会不会丢？”\
“如果某个核心函数返回错误，错误最终在哪里被处理？”

第八阶段：理解测试

分析现有测试：

- 测试覆盖了什么
- 哪些核心逻辑没有测试
- 测试是单元测试、集成测试还是端到端测试
- 测试数据从哪里来
- Mock 了什么
- 为什么要 Mock

然后告诉我：

“如果我要修改这个项目，哪些测试是我必须先理解的？”

第九阶段：给我建立“修改地图”

这是最重要的一部分。

请建立这样的映射：

需求/修改目标\
→ 应该修改哪个模块\
→ 哪些文件可能需要修改\
→ 哪些接口会受到影响\
→ 哪些数据结构会受到影响\
→ 哪些测试需要修改\
→ 哪些地方容易产生副作用

例如：

“我要增加一个新的 Memory 类型”

应该告诉我：

1. 类型定义在哪里
2. 创建逻辑在哪里
3. 分类逻辑在哪里
4. 存储在哪里
5. 查询在哪里
6. Embedding 在哪里
7. API 是否需要修改
8. 哪些测试需要增加
9. 哪些地方存在潜在兼容性问题

第十阶段：最终建立我的项目知识库

最后不要再给我一个普通 README。

请生成一份“开发者脑内模型”，至少包括：

1. 项目一句话定义
2. 项目解决的问题
3. 核心架构
4. 核心模块
5. 核心业务流程
6. 核心数据结构
7. 核心依赖
8. 数据流
9. 控制流
10. 状态流
11. 配置体系
12. 异常处理
13. 测试体系
14. 常见修改入口
15. 高风险代码
16. 当前技术债
17. 当前设计中你认为最容易误解的地方

非常重要：

不要一次性把所有内容全部输出。

先完成第一阶段“项目全景”，然后停下来问我是否继续。

后续每个阶段都采用“讲解 → 举例 → 我回答问题 → 纠正我的理解”的方式。

在讲解过程中，如果发现我对某个模块理解错误，不要直接继续，而是指出：

“你的理解是 X，但代码实际是 Y，原因是 Z。”

如果某个结论无法从代码确定，请明确说“代码中无法确定”，不要猜测。

所有涉及代码的结论，都尽量给出具体文件路径、类名、函数名以及调用关系。

最终目标是让我真正理解这个项目，而不是让我记住一份项目总结。
