| 组成 | 必须回答的问题 | 负责方 |

这些材料应相互引用同一操作编号、信号编号和处置编号。不能只靠一张大流程图，也不能只有文字规范而没有契约样例和运行测试。

## 4. 统一规则怎样适用于不同操作

统一的是责任和结果表达，不要求每个函数都创建持久任务，也不把同步读取强制改成后台队列。

| 操作类型 | 统一接入要求 | 失败与恢复方式 |
|---|---|---|
| 有截止时间的请求，如 Recall | 可信上下文、阶段与结果、来源状态、最终资格核验、查询原请求 | 有已提交结果则核验后获取；未提交且不能安全继续则明确失败；新请求显式发起 |
| 后台加工，如 Remember 投影 | 使用公共 TaskHandler、持久输入、租约、尝试与成果提交 | 领域 recover 查原结果；可补交、有限续作或转人工 |
| 外部动作，如 Operate 迁移 | 调用前保存稳定 action_id、目标和版本；记录外部效果 | 结果不明查询原动作；核验实际位置和地址交接后完成 |
| 事件消费 | Outbox/Inbox、原事件身份、事务与消费者去重 | 重复事件不重复生效；需要外部副作用时登记后续任务 |
| 只读查询与健康探针 | 当前授权、超时、数据范围及新鲜度；无业务副作用 | 明确失败/未知/部分结果；健康查询不直接改变任务 |

所有适用操作都遵守：业务事实与待办可靠交接；成功必须有证据；提交前复核权限、版本及处理权；未知效果不能当作未执行；恢复保留原操作关联；日志不是恢复事实。

现有短请求、后台任务、维护操作和业务能力的状态各有模型。不能将它们全部压成一套“成功/失败”，也不能因维护脚本退出成功就标记业务已恢复。

## 5. 每项业务操作的接入卡

接入卡是评审记录，不是新建另一套业务数据模型。字段及枚举引用原 contracts；不适用项要说明原因。以可独立确认结果和副作用的业务操作为单位，例如保存、提取、投影、召回、删除、迁移及地址交接。

| 必填项 | 需要写清楚的内容 |
|---|---|
| 标识与责任 | 操作编号、业务名称、Owner、契约版本、调用方、适用运行类型 |
| 输入与授权 | 原请求/任务/对象引用、版本、内容绑定、可信身份、期限和允许范围 |
| 成功定义 | 哪些持久事实和外部证据同时成立才算成功；对应查询入口 |
| 执行边界 | 事务内写什么，事务外调用什么，哪些副作用可能在超时后发生 |
| 幂等与重入 | 哪个 ID 不变，同 ID 不同输入如何处理，重复请求返回什么 |
| 依赖与降级 | 必需依赖、可选依赖、影响能力、允许继续的路径 |
| 状态与失败 | 引用正式模型；无效果、未知、业务失效、不可继续如何表达 |
| 恢复规则 | 查什么证据；能否补交/重试；次数和期限；撤权/删除/迟到结果如何处理 |
| 观测输出 | 阶段、耗时、结果、错误码、受限关联信息、指标和探针 |
| 维护边界 | 允许的自动/人工动作、操作权限、幂等键、冷却、并发和预算 |
| 恢复验收 | 检查原结果的方式、稳定条件、未决事项、负责人和升级路径 |
| 测试与状态 | 正常及故障样例、对应测试、真实环境范围、尚未覆盖项 |

### 5.1 Remember 投影接入卡示例

- **编号/Owner/类型：** ROP-B-PROJECTION；B，复用 A 的向量接口；持久后台任务。编号为本文评审引用，不替代运行 task_id。
- **输入：** 当前 memory/version、正文摘要及模型空间，关联原 task_id 与原发起人；提交前复核资格。
- **成功：** 精确投影经核验、当前版本满足就绪条件；业务成果、Task 完成和必要事件可靠提交。向量调用返回“已受理”不足以成功。
- **副作用：** 向量写入发生在本地事务外；超时后远端仍可能已经写入。
- **恢复：** 按原投影身份查询。证实成功且仍有效则补交；确认无效果且有执行资格才续作；仍未知则有限查询；删除/更正/撤权阻断旧结果生效。
- **观测：** 保存至就绪时间、最老投影任务、向量能力、查询失败、未知和人工任务；业务 ID 留在受控日志。
- **维护：** Azure 可诊断依赖、触发受控评估；不能直接把 Memory 改为 ready。
- **验收：** 长于普通重试窗口的 Milvus 故障；远端写成功但丢响应；处理中删除；恢复后当前授权下真实检索与准确正文核验。
- **当前状态：** 原投影查询和基础恢复存在；长故障唤醒、人工接续、Azure 与真实 Milvus 演练未完成。

### 5.2 Recall 请求接入卡示例

- **编号/Owner/类型：** ROP-A-RECALL；A；带截止时间的请求，不强制创建后台 Task。
- **输入：** query、来源和预算、可信调用范围、原 recall_id/request_id。
- **成功：** 当前有权且有效的材料形成已提交 ContextPack，并如实表达可用、正常空或降级；没有可用结果时按正式契约返回失败。
- **依赖：** 由指定来源及重排策略决定必需项；长期依赖故障不能被编码为正常空，允许降级的情况必须写明。
- **恢复：** 先查原结果；已提交的旧结果再次获取仍重验资格。当前 `recover_expired()` 将到期未完成请求标失败；如需在期限内安全续作，需另补方案与实现。不能擅自延长旧请求或自动创建新用户请求。
- **观测：** 来源状态、排除原因、总耗时、各阶段结果、提交和传输交付分别记录。
- **维护：** Azure 处理服务/依赖故障；不替用户重放任意查询或绕过历史结果授权。
- **验收：** 依赖超时与正常空区分；结果已提交但响应丢失；结果获取前撤权；进程中断后原请求状态可说明。
- **当前状态：** 基础流水线、持久阶段和历史资格核验存在；正式 HTTP/传输交付、完整目标及云端验证仍需落实。

### 5.3 Operate 迁移与地址交接接入卡示例

- **编号/Owner/类型：** ROP-C-MOVE；C；具有外部副作用的持久任务。
- **输入：** 当前 Memory/版本、固定目标、原计划及 action_id、Provider 能力与资源证据。
- **成功：** 原动作达到可确认终态，实际层和目标一致、内容可读，并完成 Remember 所有者的元数据交接；迁移成功与地址写入成功分别核验。
- **恢复：** 超时或回执丢失查询原 action_id；元数据交接失败只恢复交接步骤。有效租约、同对象互斥、当前权限和删除屏障仍有效。
- **观测：** 等待资源、在途、Unknown、目标差异、地址待确认及原动作关联。
- **维护：** 可受控核查原动作及请求恢复；不能通过清空任务或新建迁移动作消除告警。
- **验收：** 动作成功但回执丢失、位置与终态矛盾、地址提交失败、处理中删除、更换 Provider 后原历史不可查。
- **当前状态：** 本地执行器与原动作查询存在；图中完整串行/等待/地址交接目标及真实 P2 行为须逐项实施验证。

上述三张卡是已填内容的设计示例，尚不等于全部正式操作完成登记；保存、提取、删除、事件消费等应按同一格式补齐。

## 6. 将监测与处置设计成可执行契约

### 6.1 每条监测信号必须登记

信号编号、Owner、采集来源、统计口径、单位、采样周期、有效期、有限标签、授权范围、缺失时表现、影响业务能力、关联处置编号。涉及比例时明确分母与统计窗口；没有请求和没有采集数据分开。

首批信号覆盖：Worker 心跳与任务推进、任务数量与最老等待时间、依赖和业务能力、Unknown 持续时间、attention 数量、日志/遥测丢失、备份新鲜度。

轻量存活不跑深度探针；详细探测有时间上限。数据库故障不能让所有外部故障报告一起消失。汇总状态同时携带新鲜度，不能把最后一次健康结果无限复用。

### 6.2 每条故障处置必须登记

处置编号及版本、触发信号、条件与持续窗口、缺失数据策略、影响范围、诊断步骤、前置条件、允许动作、权限、幂等、互斥、冷却与预算、停止条件、业务验证、人工升级、结案依据。

示例 **RUL-VECTOR-OUTAGE：向量依赖故障**：

1. 由连续失败或请求错误触发，并区分监测失联；具体窗口由环境配置维护。
2. 核查向量服务和 P3 当前能力，保留可独立运行的保存/Working。
3. 应用保留待办并退避，Azure 不重复提交投影；依赖稳定恢复后只唤醒仍有效的工作。
4. Worker 按原投影身份执行恢复判断；已到期或人工终态的任务交明确处置流程。
5. 依赖健康、实际读取核验和任务收敛共同决定业务恢复；剩余人工事项单独登记。
6. 达到预算或证据矛盾时停止自动动作并升级；告警消失不自动抹去未完成业务。

每次事件处理保留：异常依据、采用的规则版本、执行人/自动化身份、处置 operation_id、原任务关联、执行结果、业务验证、残留事项和结案人。日志帮助解释；Task/Operation/领域证据承担正式结果。

## 7. 现有契约应怎样收敛

以下是本次发现的具体设计工作，不应通过另建同名文档字段绕开。

| 项目 | 已有定义/实现 | 建议落实方式 |
|---|---|---|
| 健康报告 | `HealthReport` 为能力列表及配置版本；`Health.report()` 返回本地详细字典，两者形状不同 | 明确公开能力报告、受限诊断、轻量探针的边界；实现映射与契约测试，未知/过期有明确语义 |
| 维护请求 | `RecoveryRequest` 只有 operation_id、task_id、expected_revision、reason | 先复用现有模型；规则版本放维护审计或经评审扩展，不向严格模型随意增加字段 |
| 维护操作状态 | `OperationRecord` 为 accepted/running/completed/failed/unknown | 保持正式枚举；“业务已验证”作为证据或版本化扩展，不能在文案中虚构已支持 verified 状态 |
| 人工任务接续 | `attention_required` 为终态，无出边；`request_recovery` 只接受规定未决状态 | 设计显式处置协议：以原证据创建关联后续工作或评审新增状态边；始终重验业务资格，不直接清零次数/改状态 |
| 依赖长故障 | 有固定等待、期限及次数，缺完整等待/唤醒策略 | 定义等待原因、预算、退避、稳定恢复条件和限额唤醒；需要持久新字段时更新 models/rules 与样例 |
| HTTP 接入 | 现有 p3/1 路由表标为 design_only；受控恢复尚无正式 HTTP 映射 | 先补正式运行接口契约、认证/授权、错误映射和幂等样例，再接新 Host；Azure 方案中的路径只是候选 |
| 逐操作一致性 | TaskHandler 等机制已存在，但不是所有类型都走 Task | 为每张操作卡声明运行类型，分别验证短请求、后台任务、事件和外部动作 |

实施顺序：共同确认语义 → 修改唯一来源的模型/规则/接口 → 生成 Schema → 增加正反契约样例 → 接提供方与消费方 → 更新状态和验证证据。本文不直接修改或冻结这些代码契约。

## 8. 设计完成与运行完成的判定

| 阶段 | 完成条件 |
|---|---|
| 设计可交付开发 | 操作清单完整；每项有成功依据、异常/恢复分支、信号和维护边界；提供方与消费方接口明确；未决问题有 Owner |
| 本地实现可集成 | 正式契约与实际输出一致；正常、重复、失效、超时、未知效果等适用场景通过；日志和健康输出可核查 |
| Azure 接入完成 | 新 Host/Worker 真正运行；身份、网络、云端采集、缺失告警、受控处置和结果回查已连通 |
| 可交代维 | Worker 中断、长依赖故障、回执丢失、删除/撤权、重复告警、VM 不可达及备份还原等适用场景有真实证据；权限、升级与结案责任明确 |

本地性能指标达标与上述机制正确性分开。生产恢复目标由环境和业务负责人确认、实测，不沿用样例时间冒充承诺。
