# P3/P4 中断运行核对与安全续跑实施计划

沿用已授权的全系统计划 T06/T07 和运行恢复设计，使用 brainstorming、writing-plans 梳理本次续项，随后按 executing-plans、TDD 串行实施；不重复请求执行授权。源码在既有隔离工作树，证据留在外部工作区。本计划不改变 P2 职责与整体上线范围。

**目标：** 使中断运行在保持原 run/operation/job、原输入和作用域的前提下，先核对已发生的效果，再经版本与所有权控制继续尚未完成的流程；不重复已提交业务。

**架构：** 原登记、定义、输入和状态仍由 P3 契约提供并经 P2 保存。P4 通过只读核对取得原结果证据；所有权转移必须在 P3 原子事务中隔离旧执行者；六个场景随后改为明确的逐效果续跑。查询结果本身不授予执行权。

**依据：** [全系统实施计划](P3_全系统闭环与固定后端上线实施计划_20261002.md)、[原结果与状态实施](P3_P4原结果与执行状态恢复实施_20261003.md)、既有 ClientRun/ClientState/MutationResult/OperationLookup 契约。

## 约束与设计判断

- 正式数据库操作仍通过 P2；不修改 P2 engine/共享 proto，不另写 P3 数据库驱动替代。当前 P2 并发写错误继续是未通过门禁，不能用单进程锁、换 key 或吞错掩盖。
- 未找到原准入/结果不代表没有效果。HTTP 状态、任务完成、结果可读、结果已被消费、步骤完成分别表示；失败或待核对任务不能变成成功。
- 原状态只含元数据。旧 Recall/生命周期正文不能由恢复状态绕过当前读取权限；生命周期摘要基准仍是 metadata_without_content。
- 现有六个故事不能简单从页面步号或整段重放：一个步骤有多个效果，读到当前版本也不等于当时的局部变量。因此选择原操作核对→所有权事务→显式效果续跑的顺序；保留完整目标，不把只读核对当作安全续跑验收。
- 不提交、创建 PR、合并、部署或发布 Azure。没有独立发布审查前，作者自查只作为工程证据。

## Task 2：受版本控制的执行权转移

在 Task 1 的报告基础上，明确 P3 原子转移与旧 owner 准入失效规则、原所有者历史和幂等转移标识；具体事务契约和竞争测试在实施前结合当前代码补入本计划。不能通过“进程看来不在”或报告时间戳推断旧实例失去执行权。需要同时覆盖旧请求正在准入、原 Temporal 任务仍在执行、接管回执丢失和双实例竞争。

实施契约（2026-10-03）：

- 新登记的托管状态运行保存所有者起始修订及连续转移历史；旧无历史记录保持可读，不能凭当前 owner 补造过去历史，须经独立迁移后转移。历史按修订区间匹配原 HTTP 准入。
- `POST /p3/client-runs/{run_id}/transfers/{transfer_id}` 使用原 owner、原 revision、完整原记录摘要和新 owner 作为不可变意图。`GET` 同路径核对原转移结果；未找到保持 unconfirmed。相同 transfer ID/意图返回原结果，不同意图拒绝。
- P3 在同一 UOW 事务中校验当前身份和 RECOVER 权限、原 active 占用及完整预期记录，更新 owner/revision，追加所有者历史，设置待恢复标记，并保存包含转移前后记录的原回执。后续读回还需当前身份授权。并发转移只能一个提交；回执保存失败必须回滚 owner。
- 转移不修改 snapshot、原操作、定义或执行状态 head，不释放 active，也不创建/取消 Temporal 任务。待恢复期间拒绝新的业务准入及普通进度/状态写入；旧实例已经受理的原任务按原提交边界继续执行。

### Task 2 续项设计与实施顺序（2026-10-03）

目标仍是保留原运行身份、输入和效果完成安全恢复。沿用已授权的 T06/T07 与串行执行方法；本节明确实现决策，不扩展 P2 职责。

**状态链设计。** 在状态 envelope/binding 中增加可选 `stream_id`、`parent_stream_id`。初始存储沿用原空标识及原对象 key；转移后的标识固定为当前所有权历史的 transfer ID。序号继续沿已发布 head 加一，父 hash 和父存储标识明确指向该 head。不同标识的同序号预约相互独立，旧 pending 原记录与原字节不覆盖、不跳过或冒充发布。读取携带目标标识，并从当前 head 沿连续父引用核对真实祖先，最多 1024 项。空标识不加入序列化结果，避免改变旧记录的规范化摘要和转移回执。备选的覆盖原 pending 或直接跳号会破坏不可变预约/历史父链，因此不采用。

**显式激活。** `POST/GET /p3/client-runs/{run_id}/recoveries/{transfer_id}` 分别提交和查询原恢复激活。请求固定当前 owner/revision/完整记录摘要、目标 queued/running 与可选恢复状态。queued 仅允许原 queued、无操作、无状态 head；running 必须提交完整原日志的状态且定义已确认。状态不改写原操作的 HTTP 阶段、输入或结果消费结论；P4 后续按原效果核对并推进。新状态经 P2 保存并读回，再在同一事务内确认状态、切换 head、解除 hold、更新运行修订并保存不可变激活回执。只改变 snapshot.state，原错误和其他字段保留在当前记录及原回执。所有权、状态保存和激活竞争均复验 RECOVER、身份、原 transfer/owner/revision/hash/active。丢回执按原 transfer ID 查询；不同意图拒绝，旧激活重试不改写后续 owner 或状态。

**原 pending 字节。** 后续给原定义/输入/状态读取增加显式恢复查询，绑定当前 recovery transfer 并要求 RECOVER；只读取并校验原 binding 对应的 P2 字节，响应区分 pending/ready，不确认发布。不存在或损坏的原字节不能由摘要还原。定义仍缺字节时保持待恢复并要求可核对的原输入；业务状态可使用最后一个已确认状态加原日志重建新的状态链，旧预约留存。普通 GET 的 pending 拒绝规则和普通写入围栏保留。
