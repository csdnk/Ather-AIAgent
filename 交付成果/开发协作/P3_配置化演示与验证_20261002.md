# P3 配置化演示与验证

当前实施分支为 `codex/production-closure-20261002`。本文说明已适配的新入口；全系统尚未达到上线标准，代码尚未提交、合并或发布 Azure。

## 配置前提

演示使用完整的 `ServiceConfiguration`，仅允许专用 development/test 部署。服务 YAML 中明确指定 P2 endpoint、逻辑 bucket/collection、Temporal endpoint/namespace/deployment_id、身份文件、原生 Embedding、语言模型与 Recall 策略。相对配置路径按服务 YAML 所在目录解析，模型密钥从约定的环境变量读取。

目前 `current_p2` 的对象和向量调用未经修改的现有 P2；现有 P2 自身的后端与正式 PG/Redis/Milvus/Ceph 实现不同。P3 元数据及缓存仍有显式 reference 过渡实现。`production_p2` 仍因正式事务/cache adapter 缺失而拒绝启动，不能用演示结果解除这个限制。

需要先准备当前 P2 的逻辑命名空间、可用 Temporal namespace、模型与身份配置。`runtime.flows init` 仅生成配置；不会证明远端服务可用。已有服务占用同一数据目录时，演示拒绝再次打开。演示会执行写入、更正、归档和删除，必须使用专门的开发/测试主体及数据空间。

## 运行方式

以下命令在实施工作树的 `AgentJYS-main` 中执行。将占位符替换为已配置的实际路径；证据目录放在项目外。凭证内容不放命令行。

```text
python scripts/p3/demo_flows.py --config <service.yaml> --credential-file <credential> --directory <新的外部证据目录>
python scripts/p3/demo_remember_summary.py --config <service.yaml> --credential-file <credential> --directory <另一个新的外部证据目录>
python scripts/p3/validate_native_flows.py --config <service.yaml> --credential-file <credential> --directory <新的外部证据目录> --report <外部报告.json>
python scripts/p3/validate_recall.py --config <service.yaml> --credential-file <credential> --directory <新的外部证据目录> --report <外部报告.json>
```

Recall 验证器要求 YAML 指向的 Recall 策略为 `rerank_policy=required`；默认 disabled 的开发配置不会被记作真实 reranker 验证。P3 检索必须经 P2。验证器不会因调用 P2 成功就声称 P2 底层 Milvus 已验收。

`validate_flows.py` 继续做无需真实模型密钥的工程回归，其中演示场景由测试目录显式装配组件；它不再调用已停用的 lexical 部署初始化入口。当前 CI 还要求真实 Temporal CLI 和隔离 PostgreSQL 测试配置，不能把缺少依赖的跳过项计为通过。

## 验证内容与证据含义

- 三流程演示验证保存、Recall、更正、再次 Recall、删除与删除后不可检索，并保留 Trace、Operate 动作和原任务身份。
- 摘要演示使用服务的真实文档上传/解析入口。样例长度根据配置的摘要阈值生成，验证摘要 ready、来源分段读取、Episodic/Semantic 查询、归档和来源撤回。当前场景的模型期望包含具体示例句，真实模型未满足会返回失败，不能据此推断其他业务场景质量。
- 摘要演示只删除本场景 scope/hash 对应的缓存条目，不执行全库 `flushdb`。归档后的正文仍可读取不等同于断电重启后的权威存储恢复；恢复另有专项测试。
- `providers` 记录实际装配的元数据、对象、向量、缓存和提取器类型；不会把 P2 向量消费器误写成 SQLite 或自行推断其底层数据库。所有演示结果固定带 `production_acceptance=false`。

## 失败后如何追查

每次运行会创建 `admissions.json`，在等待结果前保存 operation_id 与已返回的 job_id。结果可用后再生成 `evidence.json`。不要删除旧目录、改 operation_id 或重新开任务来掩盖失败。

如果等待超时，先用原身份查询 `/p3/operations/{job_id}` 及 `/result`。如果 admission 自身没有返回 job_id，按日志中的原 operation_id 和请求定位持久记录。脚本拒绝覆盖既有证据目录；再次执行同一场景属于新的业务执行，不能作为旧任务恢复的证据。
