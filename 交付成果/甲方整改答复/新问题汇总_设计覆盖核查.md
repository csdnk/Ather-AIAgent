# 甲方新问题汇总：现有设计覆盖核查

核查日期：2026-09-19。依据：[甲方原件](../../项目资料/甲方要求/AetherStore项目现存问题汇总.docx)及本次五张问题截图。范围为现有方案与交付材料，不评价人员能力，不代替甲方评审，不把附件中的整改要求视为本次自动实施指令。本次没有重新运行测试，引用的是现有证据及其明确限制。

**结论：五类问题都有不同程度的设计依据，但目前不能答复“已经全部满足”。主要缺口是 Feature 级材料追溯、真正的回归测试方案、统一测试日历，以及双方可复现的接口与测试环境。**

此前的整改台账依据上一份阶段评审文件，强调“关键 Epic 五件套”。新文件明确要求“每个 Feature 全套材料”，并把 TCR 定义为“回归测试方案”。旧台账中的“材料已补”不能直接当作这次要求已经满足。

## 二、最容易误判的三个地方

### 1. 有 Feature 文档，不等于每个 Feature 配套完整

V1.4 明确将多数 Epic 对应一个汇总 Feature；C 组另保留原子子功能。因此不能说“没有 Feature 设计”，但这种汇总口径还需要核对是否适合一次迭代独立交付。

例如，现有 [EP-P3-03 更正、生命周期与删除](../EPIC/EP-P3-03.md)把更正、归档、重新激活和删除合在一份评审材料中，引用 D02/D03 和 TC-P3-04/05/09/15。它能说明一组能力，但尚未逐项说明各个 Feature 的交互、验收及改动后必须回归的关联场景。

建议先按可独立验收的迭代范围细化，并保留旧编号映射。每项只需有一张索引，准确链接 PRD 条款、Mock 场景、交互状态、主 ADR 决策和测试即可，不必复制六份相同内容。

**主 ADR 可以继续只有一份。** 每个 Feature 引用其中适用的 Dxx 决策及特定补充，便于核查即可；甲方原文要求配套 ADR，没有明确要求每个 Feature 单独一个 ADR 文件。组织方式仍需在联合评审中确认。

后端 Feature 的原型可以展示调用输入、输出、状态变化、失败与恢复；没有业务界面时，应明确调用者的交互方式和无界面的适用说明，不必为了交材料新增管理后台。

### 2. 当前 TCR 是结果记录，甲方要的是回归方案

[TCR 当前证据](../测试与验收/TCR当前证据.md)回答“跑了什么、结果怎样、哪些没跑”，是必要的执行记录，但没有完整回答“这个 Feature 改动后，应重跑哪些测试、为什么、何时运行、什么条件阻断发布”。

需补回归触发条件、受影响功能、必跑 TC、环境/数据、执行频率、失败处理及通过标准。例如更正逻辑改动，应覆盖新版召回、旧 Context 失效、迟到加工、隔离等关联风险。这里是建议的回归范围，尚未新增为正式测试方案。

已有 264 项本地测试及独立真实向量验证的记录可继续复用；数量不能证明每个 Feature 已验收，更不能证明真实 P2/P3 联调或 UAT 通过。

### 3. “只留 5 天”已有修订，但计划仍有冲突

V1.4 开头的统一计划已把基础联调前置至 10 月、首轮主要真实接口安排在 11-06，并安排两个连续工作周用于集中验收和复验。因此，不能再笼统说整个项目仍然只有最后 5 天测试。

但同一文档仍保留以下不同口径：

- Recall 的项目窗口说明仍将真实接口、性能与故障联调放在 11-23～27；Operate 和 SRF 也在该周集中验收。
- 多处“环境搭建与验收”最晚为 11-23，而统一计划的集中验收从 11-16 开始。需要说明不同环境的适用范围，并把各轮开测环境的就绪时间提前落实。
- 向量恢复、容量诊断在 11-20 才交接，11-23～27 同时承担首次验证与缺陷复验，不能全部算空闲缓冲。
- 文档提到 72h 长稳，但完整失败重跑未包含在当前基准估算中；P2 最终性能 Gate 在 11-28，距 11-30 交付很近。

这些是日历与依赖安排问题，与人员能力评价无关。当前两周整改计划 W01～W10 只是整改工作单元，也不能替代完整项目测试日历。

## 三、接口与独立测试应补到什么程度

已有 EI-P2 对接计划和接口需求汇总，不能从零重写。应在现有基础上提供一张统一表：场景步骤、调用方/被调用方、实际接口与版本、输入输出、前后依赖、超时重试、幂等/原操作查询、关联 TC、当前支持状态。

特别是 EI-P2-11 已明确指出完整动作执行链尚未找到直接对应的 P2 交付项。这是需要双方落实的能力缺口，不能仅靠画出时序图解决。新 P3 的 `/api/v2` 映射目前也属于接口设计，不能当作已注册运行的 HTTP 入口。

独立测试应分别交代三种模式：

| 模式 | 需要明确的内容 | 现有证据边界 |
|---|---|---|
| P3 独立 | 本地/模拟 Provider、模型模式、持久化、固定数据、故障注入、启动及重置方式 | 本地后端和自动化测试已有；不证明 P2 物理行为 |
| P2 独立 | 真实服务及必要底座、测试客户端、对象/向量/图数据、版本、恢复步骤 | 当前交付记录仍为源码核查，尚缺真实运行证据 |
| P2/P3 联合 | 双方固定版本、鉴权、端点、适配、数据、调用追踪和端到端故障用例 | 有设计与交接计划，TC-INT-01 尚未执行 |

V1.4 的模拟器设计已覆盖反馈丢失、超时、重启等情形；这些可用作假设和故障集的基础。仍需将它们收敛为同一套可部署、可复现的测试说明，并明确模拟不覆盖的真实性能、物理状态和恢复保证。

## 四、全文中另外需要回应的事项

- **PRD 冻结**：现有 G1/G2 和 Proposed 状态已保留审查要求，但没有实际统一评审通过记录。
- **提前 2 个工作日送审**：旧台账只写“约定提前时间”，需在日历中明确材料截止日、会议日、版本和送达记录；本次没有向外发送材料。
- **Feature PR 与 CI/CD 追溯**：仓库已有契约、基础、三流程、原生模型等工作流，其中三流程配置含 PR 触发。尚未据此证明每个 Feature 有 PR、审查、合并、远端 CI 成功与发布对应记录。
- **阶段总结与固定会议**：已有 Gate 所需记录字段，尚缺落实到日历的例会、总结和签收证据。测试统筹可指定责任角色，不需要评价个人能力。
- **工时与知识库**：现有目录提供资料入口，但未据此核实甲方指定工具的启用或统一统计；大量人天表仍在历史详细计划中，应明确其参考性质，避免继续用人天替代交付验收。

## 五、建议的补齐顺序

1. 先统一当前 PRD 范围、旧 Feature 与评审 Epic 的映射，避免两套计划各自成立却无法追踪。
2. 补 Feature 配套索引与回归方案，复用现有主 ADR、Mock 和测试，优先选择一条保存—更正—召回链验证完整性。
3. 将分批联调、环境就绪、功能/性能/长稳、缺陷复验、UAT、提前送审和发布安排合并成同一张日历。
4. 落实实际 P2 接口和三种测试模式，取得首条真实跨模块链路证据，再扩展覆盖。

本次新增的是核查结论，并未把以上建议标记为已实施。冷热实际分层范围仍需依据[范围决策单](冷热分层范围决策单.md)解决；设计材料、实际实现、测试通过和甲方签收应继续分别记录。
