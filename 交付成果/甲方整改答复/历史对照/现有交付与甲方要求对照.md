# 现有交付与甲方两周整改要求对照

日期：2026-09-19。判断对象为当前可读取的 P3 PRD V1.2、仓库 docs/p3 正式设计入口、外置原型与 ADR、需求及验收文件，以及本轮对话上一轮的代码核查。甲方依据为《南信大 P2/P3 项目阶段评审及两周整改要求》，会议日期 2026-09-17。本文仅评价交付内容，不评价参与人员能力。

结论：当前修改已经回应了项目主线不清、缺少总体架构、设计缺乏依据等问题；仍不足以直接宣布两周整改达标。主要差距是阶段范围尚有冲突、关键 Epic 五件套没有集中贯通、Gate 缺少项目级证据绑定、UAT 计划及统一汇报尚不完整。P3 的改进不能直接证明 P2 的专项整改已完成。

## 甲方真正要求的效果

纪要开头指出，重点是把目标、架构、Epic、测试和交付标准讲清楚、做清楚、验收清楚。第八节给出的检查方式是随机抽取 Epic 和技术方案，并检查里程碑证据及 MVP 之后的交付过程。

因此，判断标准是能否从一个业务目标连续找到原型、架构、实现、测试及当前结果，而非是否已经分别存在 PRD、ADR、测试代码和演示页。两周内需要形成可评审、可验证的体系；纪要并未要求两周内完成所有生产功能或全部性能验收。

## 首要范围差异 冷热分层

甲方纪要第九节原文：

> 冷热数据分层是否纳入当前阶段：暂定为待确认项。在没有明确业务价值、数据规模、分层收益、实施复杂度和工期影响之前，不建议直接扩大P2/P3当前范围。

而当前 PRD V1.2 §4.2 规定 MVP 包含基础调度和完整执行，§4.4 要求实际执行与确认，FR13/FR14 将升降层和执行列为 P0。当前主 ADR 及架构也沿用该要求。

这是尚未消除的范围口径差异。不能因为 PRD 日期较新，就推断甲方已经批准该范围；也不能仅凭这份纪要就自动删除此前已确定的调度需求。需要核对“当前阶段”指两周整改、MVP 还是新增物理分层，以及是否存在后续已确认的范围记录。

建议先写清三层：P3 内部状态观察与基础决策；本地缓存闭环验证；真实 P2/P1 物理层级迁移。逐层列业务价值、规模、预期收益、复杂度和工期，记录当前纳入哪层、剩余哪层待定。此结论形成之前，不把真实冷热分层写为已获甲方确认的本期承诺。

## 用一个 Epic 检查当前差距

以“跨会话使用当前有效记忆”为例，现有材料已能找到 PRD 的更正和召回要求、Mock 的预算 20 万改成 15 万、Remember/Recall 版本核验实现，以及更正后旧 Context 失效的测试。

还应将这些收敛到同一行或同一张卡：Epic ID、业务 Story、对应 FR、Mock S02、核心流程、架构节点及相关 ADR、具体源码、test_correct_filters_old_vectors_and_invalidates_old_pack、当前测试结果及环境、目标 Gate、仍未完成的真实 Provider 验证。

其中“旧值不出现”还需给出明确输入与预期：先保存 20 万并生成上下文，更正为 15 万后新召回采用新版，再取旧上下文返回失效；依赖故障时不得回退交付旧值。甲方随机抽取时应直接看到这条完整链，而不用从多份文件中临时拼接。

## Gate 应如何对齐

| 甲方关卡 | 本轮应明确的证据 | 当前不能直接声称的结论 |
| --- | --- | --- |
| G1 需求冻结 | 一页目标、范围结论、PRD/Mock 版本、Review 问题与结论 | PRD 写完不等于 G1 已过，冷热范围差异尚需闭合 |
| G2 设计冻结 | 主架构、ADR/TDR、接口与依赖、评审结论 | Proposed ADR 或契约静态检查不等于设计获批 |
| G3 MVP | 已约定范围内的真实流程、关键 TC/TCR、限制清单 | 本地工程原型不能自动代表全部 P0 完成 |
| G4 UAT Ready | 功能、集成、适用性能结果，UAT 环境/数据/方案及进入条件 | 当前先搭系统的优先级不能替代后续 UAT 准备 |
| G5 Release Ready | UAT 结论、遗留问题处置、发布回退与运行准备 | 有部署设计不等于已演练或已交接 |

内部 F1/B1 继续用于研发安排；在对外表中映射到甲方关卡，无需为了同名而更改全部工程文件。正式验收仍为 not_run 的条目不能因局部测试通过而批量改 passed，应区分工程实测和产品验收。

## 最小补齐方式

不建议继续扩写 PRD 或增加一批 ADR。保留现有技术材料，集中补齐四个入口：

1. 一份 10–15 页项目主汇报，包含一页目标、主流程、主架构、Epic 全景、当前进度、Demo、质量、风险、里程碑和下一步。
2. 一张关键 Epic 五件套与实现测试对应表，复用现有内容，补足具体 TC 与 TCR 链接。
3. 一张 G1–G5 与甲方问题关闭台账，绑定版本、评审结论、证据和状态；不代填甲方通过结论。
4. 一份紧凑的测试与 UAT 安排，明确各阶段如何验、以什么条件进入下一关，保留暂缓执行的性能项目。

PRD 和主 ADR 只围绕范围结论、版本和关键方案做必要修订。就当前交付而言，技术设计方面已具备继续评审的基础，项目级交付追踪仍需补齐，尚不宜原样提交并宣称整改完成。
