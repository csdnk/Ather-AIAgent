## 1. 用户意图与本次决定

用户明确要求：“我们目前也用接口调用来做存储，但是真实的存储可以用现有的资源先去做，等我们完成了之后……这些接口整出来给 P2。”

据此，当前阶段采用以下边界：

- Remember、Recall、Operate、P4 及 Temporal 活动通过明确的接口获取存储能力。
- 我们先实现这些接口背后的真实后端，使用 Azure 现有 PostgreSQL、Redis、Milvus、Ceph 完成业务和故障验收。
- 接口定义、数据结构、错误语义、幂等与一致性规则及契约测试形成交接包；后续 P2 按双方确认的契约接管实现。
- 本实现是 P3 需求驱动的真实后端实现，不代表 P2 已经交付或认可这些契约。P2 引擎和共享 proto 继续由 P2 负责。
- 当前阶段的真实数据库验收不再以正式 P2 已完成为前置条件。正式 P2 联调、迁移和切换单独验收。
- 生产交付仍需业务恢复、身份、迁移、镜像、Azure 部署、故障灾备和长期运行等验收。改变存储实现方不豁免这些条件。

本设计调整此前“当前运行只允许 current_p2，正式接入必须等待 production_p2”的装配限制。历史测试、旧失败与旧报告作为原阶段证据保留，不改写为新架构的完成证明。

## 2. 结构和职责

```text
P3 业务 / Temporal 活动
        │ 仅依赖有类型、有语义的存储接口
        ▼
元数据事务接口 / 对象接口 / 向量接口 / 缓存及执行接口
        │
        ├─ 当前：我们提供的 Azure 实现
        │          ├─ PostgreSQL：权威记录、任务意图、版本、回执
        │          ├─ Ceph：正文、上传输入、恢复所需原始对象
        │          ├─ Milvus：带作用域与版本的派生向量投影
        │          └─ Redis：有期限的热缓存、容量与失效管理
        │
        └─ 后续：P2 客户端适配器 → P2 服务 → P2 管理的真实存储
```

业务含义、可信作用域、最终权限复核、saved/ready 和 Temporal 编排由 P3 保持。SQL、S3、Redis 命令和 Milvus SDK 仅存在于存储实现层。

优先复用现有接口和适配器。现在以项目内类型化接口承接业务调用；交接契约还必须描述可以序列化的请求、响应和原子操作边界。Python Protocol、数据库连接、上下文管理器或回调本身不是已经可交付的跨服务协议。后续 P2 远程适配需要映射并验证这些语义，不能承诺只换地址。

备选方案：现在新建独立存储 RPC 服务会增加一套部署、认证与事务协议，当前需求尚不要求；将 SDK 调用散布到业务模块会增加 P2 接管成本。因此选择“稳定接口 + 独立真实后端实现 + 后续 P2 适配器”。

## 5. 必须明确的契约语义

每项接口写明输入、输出、授权、前置状态、幂等标识、超时、失败、查询和版本兼容规则。

- 身份：使用已有 TrustedContext/Scope 等契约；环境标识独立于业务租户/会话作用域。调用方提供的范围不能自动形成授权。
- 标识：保留原 operation/job/workflow/run ID、对象 ref、hash、bytes、版本、auth_epoch、fence。
- 事务：单次 PG 原子事务覆盖必要的多记录检查与修改、任务意图、outbox/inbox 和回执。当前 Python transaction 上下文需要完整接口；后续远程事务需要原子请求或受控事务会话，不能逐条 RPC 后宣称等同于原事务。
- 外部作用：Ceph/Milvus/Redis 调用不能放在长期持有的 PG 写锁内。先预约原意图，执行后独立读回并在新事务中校验版本与所有权，最后发布。
- 模糊结果：超时或响应丢失保持待确认；查询原操作/原对象，不换 ID 掩盖重复。无法证明成功时不返回成功。
- 向量：saved 表示保存已确认，ready 表示对应版本投影已确认；搜索结果还要经过正文、版本、来源和权限复核。向量依赖故障不能悄悄改用词法结果。
- 缓存：允许过期与重建；持久任务和唯一正文不能只存在于 Redis。明确 cache miss、内容损坏、依赖不可用和配额不足，禁止把任意故障都报成 miss。
- 删除：区分逻辑不可见、缓存失效、向量删除确认和物理对象清理；迟到任务不能恢复已删除版本。
- 存储层级：当前仅声明经过验证的 Redis 热副本与 Ceph 权威副本；没有实际配置和验证的 warm/cold 等能力必须返回不支持，不能以标签变化表示已迁移。
- 错误：复用项目已有错误契约，并明确版本冲突、权限拒绝、依赖不可用、待确认和不支持能力；驱动错误需脱敏，不泄露 DSN/凭据。
- 健康：只读就绪探针与写入验收分开；实际资源、provider、契约版本和未验收范围可观察。

## 异步调度与 PostgreSQL 事务执行边界（2026-10-03 补充）

远端数据库调用会等待网络。Temporal 心跳、超时和 HTTP 调度需要事件循环持续运行，因此不能在这些异步入口中直接执行同步 psycopg 事务。当前已将控制器、桥接、周期游标、任务计划/领用/结果记录，以及保存、正文读取和 Recall 阶段的已识别同步操作移至后台线程；完整事务在同一个工作线程中开始、执行和结束。外部模型、向量及对象的异步调用仍在事务外等待。

线程交接复制 Python contextvars，继续携带原 TrustedContext、任务执行 epoch、business_write_guard 和追踪上下文。原始输入摘要、权限与版本检查、提交前复核、周期 epoch/游标原子提交，以及丢失回执后的原操作查询均保留。线程任务取消并不证明数据库没有提交，调用方仍须按照原 job/operation 记录确认结果。循环中的回调显式绑定本次参数，避免后续迭代改变正在执行的目标。

阶段性验证：四个慢元数据用例先复现调度回调阻塞，修正后连同任务、周期、桥接、Remember、Recall、远端正文及服务生命周期回归共 73 项通过。真实 Azure 联调的第二轮诊断中，观测的 143 个元数据事务均在事件循环之外，readyz 为约 4 毫秒；首次保存仍超出原观察上限，数据库往返与排队开销继续诊断。此处不宣称完成生产性能或业务端到端验收。

### PostgreSQL 事务内读取复用

PG 适配层在共享 advisory lock 持有期间，按 namespace、tenant、key 复用本事务已读到的原始字符串和缺失结果。每次新事务重新建立读取集合，不复用解析后的可变领域对象；所有 put/delete 先使对应读取失效。后续读取会收到数据库结果，原有 pipeline 退出确认、COMMIT/ROLLBACK 和提交前检查仍执行。所有协作写入必须经过相同事务锁与记录接口；直接 SQL 管理操作不能与已缓存记录的业务读改混用。

这是减少同一事务重复网络查询的局部优化，不是跨请求缓存。范围查询与原生队列查询继续通过 PG，并刷新此前排队的命令。当前完整业务延迟仍须实测，不能据此宣称吞吐或高可用验收。
