核对日期：2026-09-21。产品依据为 [PRD V1.3](../../PRD版本/AetherBrain_P3_PRD_租户补全版_V1.3.docx)，重点是 FR18（7.19）、租户授权（7.16）、日志与删除（11.3）和异常恢复验收（12.7）。[总体 ADR](../../ADR版本/ADR-P2P3-001_总体架构决策.md)仍为 Proposed。本次完成设计说明与静态源码核对，未修改业务代码，未运行产品验收。

## 1 四种职责如何协作

| 能力 | 实际回答的问题 | 输入与输出 | 谁负责 |
|---|---|---|---|
| Trace | 这次请求经过哪些步骤，在哪一步变慢或失败 | 上下文、父子 Span、业务 ID → 可关联的处理过程 | RF 建立与传播；领域和适配器上报阶段 |
| 日志 | 这个步骤具体发生了什么 | 受限输入摘要、结果、错误码、栈位置 → 结构化节点记录 | RF 存储与查询；领域提供安全字段 |
| 健康检测 | 当前哪些能力可用，哪些工作停滞 | 探针、心跳、任务和事件状态 → 能力及影响报告 | RF 调度和汇总；领域与 Provider 提供探针 |
| 恢复 | 这项未完成业务接下来能做什么 | 持久事实、租约、版本、原执行证据 → 继续、补交、查询、取消、失败或人工 | RF 管处理权与预算；领域决定业务动作 |

一次 Milvus 故障会同时产生四种不同信息：Trace 指到投影调用，日志解释失败，健康报告说明长期能力受损，任务和投影记录决定下次能否重试。日志缺失时，Task 和原执行证据仍是恢复依据；只看到一个未结束 Span，不能确定工作仍在运行，也不能判定它没有执行成功。

业务库与日志库是两个独立文件。前者保存事实、待办和恢复证据；后者帮助定位。独立事务可以保留业务回滚时的错误记录，但同机同盘仍有共同故障风险，不代表高可用。

## 2 P3.3 可靠交接与恢复

### 2.1 保存后为什么不会丢后台待办

领域服务在同一个业务事务中写入主事实、Task 和 Outbox。提交失败则一起回滚；提交成功后即使进程停止，待办仍可被后续 Worker 发现。网络模型调用、Milvus 写入和 P2 动作在事务外执行，不能假设它们与 SQLite 一起提交或回滚。

提交后分成两条支线，图中 P3.3a 已显式分开：

| 支线 | 正常推进 | 中断后如何处理 |
|---|---|---|
| Task | 领取并登记 Lease、Attempt → 调用领域 Handler → 成果和 Task 完成一起提交 | 过期租约或不明结果进入恢复；旧 Worker 无有效处理权就不能提交 |
| Event | 按消费者领取 Delivery → 消费效果与 Inbox 同事务提交 → 单独确认 ACK | 消费失败整体回滚；ACK 丢失先查 Inbox，已消费则补确认，不重复生效 |

Task 是需要执行的工作，Event 是已经发生事实的交接；两者不要求相互串行执行。Inbox 的唯一性绑定消费者和事件，同一个事件可以被多个消费者各自处理一次。消费回调只提交本地事实或后续 Task，外部副作用交给 Task。

### 2.2 谁真正触发恢复

目前三流程入口是 `ThreeFlows`。持续运行的 Worker 调用 `tick()`，它更新心跳、检查到期 Recall、投递事件，并处理 Remember、Operate 任务。`Tasks._claim()` 会先 `sweep()` 过期租约，`run_once()` 优先领取恢复任务，再领取正常任务。没有持续运行 Worker 时，持久待办不会自己执行。

`Health.report()` 只查看依赖和状态，**不调用恢复、不重新迁移、也不重启进程**。未来可以由外部检测或受控维护发出恢复信号，但仍必须回到同一任务机制，不能直接绕过租约调用领域操作。

P3.3b 的判断顺序是：发现未决工作 → 检查处理权 → 领取新租约并重验授权 → 领域查询当前对象与原结果 → 根据证据选择下一步 → 提交前再次核验 → 复查业务结果。有效租约不能被随意抢占；版本、删除、撤权和期限仍然约束恢复。

| 执行证据 | 公共机制如何承接 | 领域的责任 |
|---|---|---|
| 已确认原结果成功 | 允许在有效租约下补交成果和完成状态 | 核对对象、版本、实际可用性；不能只相信“受理成功” |
| 证实没有效果，仍可执行 | `RESUME` 转 `retry_wait`，仍受执行次数与原任务期限限制 | 证明可安全继续；保留原幂等身份 |
| 在途或无法查证 | `QUERY_ONLY` 留在 `recovery_wait`，消耗查询预算 | 查询原动作或原投影，不能另建冲突动作 |
| 对象已失效或业务不能继续 | 取消、失败或 `attention_required` | 阻止旧结果生效，保留必要清理及核查 |

默认执行预算为 3 次、恢复查询预算为 6 次，租约 30 秒、等待 1 秒；这是当前配置默认值，不是产品承诺，也不保证长故障后自动恢复。当前没有完整的依赖恢复唤醒、指数退避或人工结案流程。受控 `request_recovery()` 只接受规定的未决状态，不能视为对所有失败或人工状态的“万能重试按钮”。

租约和 CAS 保护的是本地提交。进程暂停、请求超时之后，远端调用仍可能完成；远端正确性还需要稳定操作身份、可查询证据和删除屏障。不能把本地租约当作对 Milvus 或 P2 的自动回滚。

## 3 P3.4 Trace 与日志

### 3.1 一个 trace_id 如何串起后续工作

当前入口通过 `Identity.context()` 生成 trace_id、request_id、operation_id 和 span_id，并绑定可信主体与截止时间。方法进入时创建新 Span；同一上下文中的调用形成父子关系。入队 Task 或写 Outbox 时，保存当前生产者 Span 的上下文；后台恢复该上下文后，每次执行或查询都创建新的 Span。

因此，原请求结束后，可以继续查到同一个 trace_id 下的后台处理。这里不是一个 Span 从请求开始一直挂到恢复结束，而是一个请求关联许多各自有开始和结束的 Span。当前 `attempts` 保存尝试事实，`runtime.tasks.invoke` 等节点记录尝试过程；它们还没有完整的专用跨 Trace 尝试关联模型。

查询过程是先验证 DIAGNOSE，按原 trace_id 读保留日志，再关联 Task、Delivery 和 Recall 阶段，返回前再次授权。当前查询限制到原发起人及相应 scope；知道 trace_id 或获得某条 Memory 的共享授权，不等于可以查看整条他人的 Trace。

当前查询的边界也需要直说：日志分页；关联 Task、Delivery 和 Recall 阶段各有 100 条上限并标识截断；不是一次返回全部历史。`task_evidence()` 可进一步查看单项任务的尝试与恢复记录。日志库读取失败时，`Diagnostics.trace()` 当前没有完整的降级返回，业务库可用时应保留独立 Task 查询路径。

长周期设计需要增加持久关联：根请求 trace_id → 任务 / 事件 → 后续 attempt 的 trace_id 和 span_id。后续可为新恢复阶段创建新 Trace，再用 Link 和持久关联索引连接原根请求。原入口仍能发现后续阶段，同时返回保留范围和缺失区间。此项是设计建议，**现有代码没有跨 Trace Link 和完整关联索引**。

### 3.2 当前日志到底记录了什么

`Telemetry` 是自有 SQLite 节点日志实现，没有通过 Python logging 或 structlog 构建这条日志链，也没有启用 OTel SDK 导出。依赖声明中存在 `opentelemetry-*` 和 `structlog`，不等于这些包已进入当前运行调用链。

每个受观测方法记录 started、returned、failed 或 cancelled；业务事务另记 committed、rolled_back。`returned` 只表示方法正常返回，例如方法可以正常返回 `unknown`，它不代表业务成功。

| 数据 | 当前记录方式 |
|---|---|
| 关联信息 | trace、span、parent span、request、operation、服务与进程标识 |
| 业务信息 | 受限的任务、事件、记忆、版本、阶段及结果摘要 |
| 输入输出 | 递归受限摘要；非白名单字符串隐藏，只保留长度等信息 |
| 错误 | 错误码、异常类型、文件名、函数与行号；不保存异常消息、源码行或局部变量 |
| 体积控制 | 字符串、层数、集合长度有界；过大记录移除输入输出摘要 |

默认不采样，保留 14 天及最多 20 万条的清理目标。清理在初始化、每 100 次写入和查询时触发；没有独立的持续清理器。删除数据库行不等于立刻回收磁盘文件空间，也不是按文件大小轮转，不能写成“磁盘使用严格有上限”。

日志写入失败时，`emit()` 累加进程内 dropped，第一次向 stderr 输出固定错误码；不会因此把已完成的外部动作再执行一遍。健康查询据此把 logs 标为 degraded。但 dropped 跨重启不保留，缺失起止区间和外部告警尚未接通；初始化日志库失败也可能直接阻止 Host 启动。后续要把运行中写入失败、启动失败、读取失败分别设计，不能用一条“日志非关键”概括全部情况。

## 4 P3.5 健康检测如何表达影响

现有 `Health.report()` 有界并行调用已装配探针：业务数据库和日志库尝试写入后回滚；模型、向量、执行端、tokenizer 和重排按当前 Provider 检查。自定义 Provider 没有对应探针时可能返回 unknown；禁用的可选能力应显示 disabled。一次探测成功只能证明所探测的能力在该时刻可用，不保证所有用户请求都会成功。

| 层次 | 目标含义 | 当前状态 |
|---|---|---|
| startup | 启动准备是否完成，尚未完成时不按常规存活失败处理 | 尚未形成正式 HTTP 探针与部署接入 |
| liveness | 进程能否响应，是否需要按进程故障策略处理 | 本地函数返回 alive，不能据此证明外部请求能到达服务 |
| readiness | 当前是否应接受对应服务流量 | 现有汇总主要看业务库和日志；尚未接入新 Host 的正式 HTTP 路由 |
| 业务能力 | 保存、当前读取、长期检索、上下文及调度是否可用 | 已有部分依赖映射；上下文仍需按来源、tokenizer、重排策略更完整地汇总 |
| 未决工作 | 是否积压、租约过期、投递未确认或动作 Unknown | 已能从持久状态查询；持续采集、故障起止和告警跟进待补 |

Milvus 不可用时，长期能力可以是 degraded，同时 readiness 仍为 ready，保存和 Working 仍可用。这符合按能力表达影响的方向，但接入方必须读取能力字段。另一个现状是：日志曾丢失会导致当前进程的 readiness 为 not_ready；正式接入时应明确不同业务的接流量策略，避免把可用能力一并长期关闭。

现有健康细节查询依赖业务库中的诊断授权。数据库完全失效时，授权步骤本身可能失败，不能承诺一定能返回完整故障报告。正式轻量探针应使用与部署匹配的身份和响应边界，外部检测负责发现“服务连报告都无法返回”的情况；不暴露租户内容，也不新增独立管理产品。

仓库现有 `/health` 和 `/api/status` 通过 `MemoryRuntime.health()` 返回旧入口的状态，包含演示相关快照；本次核对的新链路是 `runtime.flows.ThreeFlows`。这两个入口必须区分，不能看到路由存在就把新链路 HTTP 接入标为完成。

## 5 Milvus 故障时间线

下面的 T0—T7 是按源码推导的相对步骤，不是真实事故时间或本轮测试记录。前提是保存已提交、提取已完成、Worker 持续运行，故障发生于后台投影。若失败在模型阶段，应定位到相应模型节点，不能全部归因于 Milvus。

| 时点 | 业务与持久事实 | Trace 和日志能看什么 | 检测与恢复如何配合 |
|---|---|---|---|
| T0 | `Remember.save()` 同事务保存来源、Working、提取 Task、saved 事件和原请求结果 | 入口 trace、remember.save 与事务提交 | saved 只确认保存；当前有效 Working 不等长期投影 |
| T1 | 提取任务提交派生记忆及 `remember.project`；派生投影尚未 READY | remember.run、extraction、入队节点，沿用原 trace | 后台投影仍是待办，不能把已提取当作可长期检索 |
| T2 | 领取投影任务并登记 Attempt；适配器先保存投影写入意图，再调用 Milvus | embedding 与 vectors.project；错误抛出会记 failed，正常返回 unknown 则在输出摘要体现 | 准备或查询异常进入 `record_failure()`；写入回执不明可返回 uncertain；两者均保留未决状态 |
| T3 | 已保存事实没有因远端故障回滚；任务处于 `recovery_wait` 等状态 | 原 trace 可查当前 Task、失败节点及后续尝试 | 显式健康查询报告向量不可用、长期受损及积压；当前没有后台自动告警 |
| T4 | Worker 重新领取恢复工作；B 核对权限、版本、删除和当前资格 | 新的 invoke / remember.recover / vectors.inspect Span | 查询原 memory/version/hash/model_space 对应的 vector_id，operation_id 沿用原 task_id |
| T5a | 精确投影已存在且核验通过 | inspect 返回 verified | 复核处理权与资格，直接补交正式结果；不再做一次迁移或生成新投影身份 |
| T5b | 确认投影不存在，且原任务仍允许执行 | inspect 返回 absent | 恢复决定 RESUME；公共层在期限和次数内安排原任务重试，之后仍须再次核验 |
| T5c | 查询仍失败、投影未就绪或证据不符 | 失败或非 verified 的查询结果 | 继续按原身份核查；当前不明或证据不符可能持续查询至人工状态，不能画成必然恢复成功 |
| T6 | 投影核验通过后，READY、processing_result、Task 完成及 projection_ready 事件同事务提交 | 业务提交记录与新状态 | 迟到结果遇更正、删除或撤权不能恢复旧资格；保留必要清理与核查 |
| T7 | 用当前授权实际检索并读取准确正文，确认剩余待办 | 新验证请求可有新 trace，通过业务 ID 对照原工作 | 这是业务恢复验证；端口通、探针绿或 Task 成功都不能单独替代此项 |

若故障期间进程崩溃，原租约到期后由新 Worker 接手；旧进程晚到的本地提交受租约屏障拒绝。若故障持续超过当前次数预算，任务可能进入人工状态，后续依赖恢复不会自动把所有终态任务重新激活。若业务已撤权，后台基础设施身份也不能替用户继续提交旧结果。

本轮还核对了配置示例 `configs/recall.milvus.json` 指向的本机 `127.0.0.1:19530`，TCP 连接在检查时未成功。该结果只覆盖这个示例地址，不代表不存在其他可用 Milvus；没有登录服务、执行真实模型投影或进行端到端恢复验收。

### 5.1 同一机制在 Recall 和 Operate 中有何不同

| 场景 | 共用的公共机制 | 领域决定的部分 | 当前边界 |
|---|---|---|---|
| Recall 来源中断 | 可信上下文、节点记录、请求阶段持久化、当前授权 | 指定来源是否必需，是否允许降级，空与失败区分；旧结果再取必须复核 | `recover_expired()` 目前把到期未完成请求置为失败，不是完整的断点续跑 Handler |
| Operate 执行成功但响应丢失 | Task、恢复预算、原操作关联、租约与日志 | 查询原 action_id，核对层级、版本与可读性；确认交接而非重复迁移 | 有本地执行器及原动作查询；真实 P2 和最新地址交接目标仍需逐项落实、验证 |
| Remember 投影不明 | Task、Attempt、恢复状态和原身份 | 核对精确投影、当前记忆资格；必要时补交 READY 或取消旧工作 | 有对应基础代码；本轮未做真实 Milvus 演练 |
