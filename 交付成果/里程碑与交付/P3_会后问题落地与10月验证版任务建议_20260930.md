# P3 会后问题落地与 10 月验证版任务建议

> 当前任务以用户确定的[P3 任务分配](../开发协作/15_会后五项整改任务分配与验收_20260930.md)为准。下文保留此前建议，不作为当前派工清单。

日期：2026-09-30。性质：会议行动建议，供范围确认和排期使用。负责人沿用会议记录；具体开发、测试和 P2 提供方按既有责任落实。本文未变更正式 PRD、ADR、接口契约或交付承诺。

## 一、总体判断

九项议题围绕三个目标展开：明确架构取舍；把验证环境接到真实依赖；形成 10 月能够复现验证的系统版本。

建议主线为：**先确定最小业务链路及 P2 能力边界，再接真实对象库和向量库，用大文件、更正、删除、撤权和故障恢复验证完整链路。** 2026-09-30 用户进一步确定 Working 必须通过向量召回，采用先保存、异步向量化；本项据此从可选评估调整为实施任务。GraphDB 先交付场景与架构设计。

现有 [MVP 总体落地方案](P3方案与进度评审_20260929/MVP完整交付计划_20260929.md) 以 2026-12-01 为完整 MVP 目标，真实 P2 按 10/10 可接入作排期假设。这次会议提出的 10 月可验证版本，建议新增为工程验证里程碑；是否同时调整完整 MVP 日期，需要另行明确。

本次阅读了现有方案、接口清单、代码中的 Working-only 路径和验收报告。9 月 26 日报告记录了本地统一服务验证；9 月 29 日报告进一步记录了加工阶段进度恢复和本地缓存修复。本次未重跑这些测试，不能将历史本地证据扩大为真实 P2、生产存储或产品验收结论。

## 二、九项问题怎样逐一落地

### 01 工作记忆向量化与架构优化｜陈凯

**要解决的问题：** 当前任务内容增多时，单靠最近记录或词法检索是否漏掉相关信息；向量化带来的检索收益是否值得额外延迟、成本和一致性维护。

**已确定方案：Working 写入向量库并通过向量进行召回，先可靠保存，再异步向量化。** Working 仍是当前任务/会话记忆，进入向量库不改变业务类型。按 ID 查看已保存正文与语义召回分开。

落地步骤：

1. 确定当前任务必须保留的信息，例如目标、约束、最新更正和未完成事项；这些内容不能因为相似度低而被遗漏。
2. 保存时登记独立的 Working 向量任务，经过编码、投影和当前版本完整核验后发布可召回状态；不等待长期事实提取的批量阈值。
3. 同时测相关信息命中、最新更正覆盖、保存到可用时间、召回 P95、编码开销和索引清理成本。数据量、查询集和环境保持一致。
4. 工作记忆向量投影绑定租户、任务/会话、正文版本、模型空间和有效期；更正、删除、到期同步使旧投影失去交付资格。使用同条件数据验证语义命中、延迟和成本。

原 `working_only` 契约绕过 Embedding 和向量检索，需随 PRD、流程图和实现一起修订：该模式只限制为 Working 来源，仍执行向量检索。未就绪或向量服务故障时明确提示，不静默用词法路径冒充成功；按 ID 查看已保存正文仍按当前资格执行。

**交付物：** PRD V1.4、整体及 Remember/Recall 流程图、契约与实现、补索引入口和回归证据；详见 [Working 变更设计](../架构设计/Working记忆向量召回变更设计_20260930.md)。

**关闭条件：** 保存不等待编码，索引未就绪不假报正常空，Working 纯语义查询经过向量库，范围/版本/权限、摘要、更正删除、重启恢复和历史补索引均有验证。Working 向量召回纳入最小任务集。

### 02 元数据与正文分离的性能瓶颈｜杨鹏通

**要解决的问题：** 召回是否因多次查元数据、逐条读对象、重复鉴权或大正文传输变慢；分离存储不能仅凭直觉判为瓶颈。

**推荐方案：保留事实管理与正文存储分工，先测量，再减少无效读取和串行等待。**

落地步骤：

1. 分段记录向量查询、候选资格检查、正文读取、哈希/版本核验和结果组织耗时；补充对象请求数、传输字节数、缓存命中率及并发量。
2. 用小文本、长文档和大对象比较缓存冷/热、单请求/并发条件，记录 P50/P95/P99；报告样本量和环境。
3. 先批量筛选允许使用的候选，再按需要读取正文；按实测瓶颈评估批量元数据查询、连接复用、受限并发读取和缓存。P2 没有批量接口时，需要明确扩展或受控并发方案。
4. 原始大文件按固定版本保存，加工产物保留准确的正文引用和来源映射；召回读取被选中记忆的准确正文，不必每次下载整份原始文件。字节范围必须与所引用的对象版本、编码一致。
5. 采用“元数据事实与待办同事务提交、异步发布索引、发布后核验”的方式处理跨库写入。对象已上传而元数据提交失败时，登记待核对/孤立对象，按规则回收，不能提前宣布就绪。

缓存键至少区分租户、对象/记忆版本及内容校验；缓存命中后仍复核当前资格。向量索引和缓存承载派生信息，不能成为版本、删除和权限的唯一权威。

业界可参考对象存储保存大内容、索引保存引用的组织方式，以及 [Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) 对事实与事件双写的处理。Outbox 本身不提供元数据库、对象库和向量库之间的原子事务。

**交付物：** 分段性能基线、瓶颈排序、优化前后对照、跨库一致性时序设计。

**关闭条件：** 在约定文件规模和负载下达到双方冻结的指标，同时保持内容、版本、授权一致。首周先确定指标，不能事后用测得的结果反写验收线。

### 03 版本冲突规则库与模型边界｜杨鹏通

**要解决的问题：** 并发写入冲突、明确更正和语义矛盾容易混为一谈，造成旧结果覆盖新事实或模型擅自判真。

**推荐方案：规则控制是否可以提交，模型提出语义判断候选。**

| 情况 | 规则负责 | 模型可以参与 |
|---|---|---|
| 重复请求 | 按幂等键及请求指纹识别，返回原结果 | 无需参与 |
| 同一版本并发更新 | 比较期望版本再提交；冲突后重新读取并重新判断 | 可重新分析内容，不得绕过版本检查 |
| 用户明确更正 | 核实来源、身份、对象及权限，建立替代关系并保留历史 | 辅助识别被更正的事实和原文证据 |
| 相似、等价或补充 | 按批准策略处理，不能只凭相似度覆盖 | 提议等价/补充关系，并给出证据位置 |
| 无明确更正依据的矛盾 | 保留未决冲突及适用条件，不按“最新文本必为真”裁决 | 识别冲突、解释分歧 |
| 删除、撤权、版本过期 | 硬性阻断不再允许的交付与迟到提交 | 不得推翻规则 |

每条规则记录编号、版本、适用范围、条件、动作、优先级、失败分支和正反案例。每次决策留存输入版本、命中规则、模型候选、证据引用及最终动作，支持回放。

先用可读决策表及现有代码规则实现，暂不因“规则库”三个字就增加独立规则引擎。多条规则同时命中时，先执行资格与版本屏障，再处理事实关系。

**交付物：** 规则决策表、模型输入/输出契约、冲突样例集及自动化回归用例。

**关闭条件：** 重复写、并发写、更正、补充、未决矛盾、删除后迟到提交均有确定预期；真实模型的误判与规则执行正确性分别统计。

### 04 断点续传、故障恢复与开源框架｜陈凯

**要解决的问题：** 大文件上传中断、后台加工中断和存储故障是不同层次的问题，需要各自的恢复依据。

| 层次 | 建议实现 | 候选与适用边界 |
|---|---|---|
| 文件上传 | 保存 upload_id、分片号、校验值及已完成分片；重连后查询并续传，完成后校验对象 | 优先复用 P2 已列出的分片接口及对象库 SDK；独立 HTTP 上传入口可评估 tusd |
| 加工流程 | 持久化阶段结果引用、输入版本、模型版本及分片进度；从已提交阶段恢复 | 优先复用现有 RF；复杂长流程和跨服务编排再评估 Temporal |
| 模型工作流 | 持久化图状态与检查点，明确任务重放边界 | LangGraph 适用于模型图流程，不能单独承担全系统跨库存储恢复 |
| 跨库故障与还原 | 元数据、正文、向量投影对账；确认备份范围、可重建内容及恢复次序 | 用真实环境演练确定恢复时间和允许数据损失窗口 |

当前接口清单已经列出创建上传、上传分片、查询分片、完成上传和终止上传五个方法。落地重点是 P2 的实际支持情况及异常语义，而非再定义一套同义接口。

现有 RF 报告记录了阶段恢复和缓存修复，可作为扩展起点；恢复已完成分片，不等于模型生成过程可在任意字节处续接。任何框架都不能替代副作用幂等、权限/版本复核和最终业务验证。

必须覆盖：进程重启、网络中断、对象库/向量库长故障、远端成功但响应丢失、恢复期间删除或撤权。远端结果未知时保留原操作编号查询，不能换新编号盲目重做。

**交付物：** 分层恢复方案、RF/tusd/Temporal/LangGraph 选型对照、故障矩阵与真实演练记录。

**关闭条件：** 不重复产生正式副作用，已完成分片可复用，内容校验一致，过期结果不复活；无法自动恢复时有明确状态及接续入口。框架新增与否由缺口和验证结果决定。

### 05 Mock 改为真实对象库和向量库测试｜陈凯

**要解决的问题：** 现有替身验证了部分协议与业务规则，但不能证明真实相似度检索、网络行为、索引可见性和存储故障处理。

**推荐方案：建立真实依赖集成测试环境，并保留可控的故障注入。**

1. 对象库优先采用 P2 计划交付的同类实现；暂不可接入时使用经版本、许可和接口兼容性确认的 S3 兼容对象库。向量库优先与现有适配方向一致，采用真实 Milvus。
2. 将统一 P3 服务接到对象库和向量库，实际保存原文、计算向量并检索；不能只用预设编号模拟向量命中。
3. 固定环境版本、模型空间、数据集、启动配置、测试入口和清理范围，使其他人能复现。
4. 在真实服务前注入断网、延迟和丢响应；需要模拟“写成功但回执丢失”时，必须确认远端已落盘再丢弃响应，不能用写入前抛错替代。
5. 同一套业务预期在真实 P2 可用后重跑，记录具体经过的 P2 接口和部署版本。

测试证据分三类登记：纯替身契约测试；P3 加真实对象/向量库的集成测试；经真实 P2 的联合测试。绕过 P2 直连数据库只能证明第二类。

Milvus 有不同一致性级别。功能测试可以用强一致帮助定位，但还需按拟部署的一致性配置验证就绪判断、读后可见和删除传播，不能仅靠固定 sleep 宣布完成。

**交付物：** 可复现的测试环境配置、真实依赖运行入口、故障注入用例和环境说明。

**关闭条件：** 原文可读回、真实语义检索有效、持久化重启后可继续使用、更正/删除和故障场景可复现。原型展示与工程证据分别标注。

### 06 GraphDB 场景与架构规划｜陈凯

**要解决的问题：** 明确哪些业务依赖关系查询，以及图数据库相对现有关系表能带来什么收益。这里按通用图数据库理解 GraphDB。

先定义三个场景：

1. 来源追溯：某条记忆来自哪份文档、哪个版本和哪段证据。
2. 更正与冲突：一条事实替代了哪些旧事实，哪些分歧仍未解决。
3. 多跳关联：例如“某作者的图书中，哪些章节涉及同一主题”，同时返回关系路径与原始依据。

设计节点可包括来源、来源版本、记忆版本和业务实体；边可包括 derived_from、supersedes、conflicts_with 和领域关系。节点与边必须绑定租户、版本、证据及有效性；关系本身的存在也可能泄露信息，遍历前后都需控制权限。

建议查询链路为：向量找到候选 → 受限图遍历补充关系候选 → 统一资格审核 → 读取准确正文 → 交付前复核。约束跳数、候选数和预算，避免无边界扩展。

P3 维护事实关系的业务语义，P2 提供底层图存取与查询能力。现有 P2 架构材料包含图引擎规划，但不能据此判定远程接口已交付。需要单列关系写入、删除/失效、批量查询、有界遍历和版本核对契约。

**交付物：** 三个可验证业务场景、图模型、查询样例、P2 接口差距表及架构图。

**关闭条件：** 每个场景能说明图查询的必要性和预期结果。10 月先完成设计；基础更正/冲突关系可以由现有可靠存储承载，完整图服务不建议成为首条闭环的前置依赖。若首个业务必须多跳查询，则需重新核定最小范围。

### 07 真实大块业务数据端到端测试｜陈凯

**要解决的问题：** 用实际业务内容验证容量、读取与加工路径，并验证结果正确性，避免只有几句话的演示。

建议以图书馆长文档作为首个主场景，气象结构化文件作为补充场景。数据必须有明确来源、使用许可、版本和 SHA-256；合成边界数据单独标识。

| 场景 | 完整操作 | 核对结果 |
|---|---|---|
| 图书馆长文档 | 导入真实馆藏资料/公版图书 → 上传 → 固定版本解析分块 → 向量化 → 跨会话提问 | 命中正确章节，正文及页码/章节出处与原件一致 |
| 图书更正与权限 | 更新可控测试副本 → 重新加工 → 召回 → 删除/撤权 → 旧结果重取 | 新版生效；旧版、删除正文和无权正文不再交付；加工中的旧结果不复活 |
| 气象大文件 | 导入真实站点时序 CSV 或已支持的 NetCDF → 记录变量、单位、时间与区域 → 按条件检索和读取 | 指向正确文件版本、站点/时空范围；数值与原文件核对 |
| 大文件中断恢复 | 上传、加工、发布索引的不同阶段中断；恢复后重复原请求 | 复用已完成工作，结果不重复，哈希一致，状态收敛 |

气象场景中的数值计算交给明确的数据处理模块；P3 保留数据引用、语义描述和处理结果依据。不把全部网格数值直接当自然语言向量化，也不将气象预测质量纳入本次记忆系统验收。尚不支持的格式应明确列为能力缺口，不能只保存文件名就算解析成功。

首周冻结单文件大小、总数据量、文档/分片数、向量数、并发量、缓存状态和指标。按小/中/大三个规模档设计，具体数值取决于真实数据与环境容量。大对象传输和大量小对象两种负载分别测量。

**交付物：** 数据清单、业务问题及人工核对答案、端到端用例、性能与正确性报告。

**关闭条件：** 从公开业务入口触发，经过真实依赖，用独立原件/答案校验结果；用例需包含正向、更新/删除/权限及至少一种真实故障。

### 08 节后首周与 P2 排期对齐｜陈凯

**要解决的问题：** 将“预计可以接”转成双方能够执行和验收的交付安排。

以现有 [P3 向 P2 接口清单 V2.0](../开发协作/P3向P2接口清单_V2.0_20260929.md) 为输入，首周完成一张共同确认的矩阵，每项记录：

- P2 提供方、P3 适配方、测试负责人。
- 具体方法与契约版本、支持/不支持范围、租户与认证方式。
- 可调用环境、部署版本、样例数据、就绪日期和联调时段。
- 幂等、更正、删除、版本绑定、索引可见、未知操作结果查询的语义。
- 首链必需项、可后移项、阻塞影响及最晚决策时间。

安排一次实际连通验证：写入并读回对象、写入并查询向量、核对当前版本，再记录一项失败路径。会议纪要或接口声明不能代替连通记录。

原方案中的“10/10 P2 可接入”仍需 P2 确认。若首周不能提供核心接口，应当立即记录 10 月真实 P2 闭环风险，明确实际可交付的证据范围并更新计划。

**交付物：** 双方排期矩阵、核心接口连通记录、阻塞清单和延期处理方案。

**关闭条件：** 接口、人员、环境、日期和共同验收用例都有记录；不是只有一个总体日期。

### 09 节后形成最小任务集合｜陈凯

**要解决的问题：** 把研究议题转成可交付范围，避免多个新基础设施同时进入关键路径。

建议 10 月版本至少包含六个工作包：

| 工作包 | 必交能力 | 可检查的证据 |
|---|---|---|
| M1 真实依赖与入口 | 统一服务可启动，经适配连接真实对象库、向量库；P2 联调状态明确 | 配置、环境版本、连通及启动记录 |
| M2 真实数据主链 | 大文档保存、当前任务可用、后台加工、长期就绪、跨会话召回及来源 | 一条完整业务用例及独立内容核对 |
| M3 事实与隔离 | 幂等、更正、基础冲突处理、删除/撤权、租户隔离 | 正反例、并发及处理中失效用例 |
| M4 上传与加工恢复 | 分片上传、阶段检查点、原操作查询和重启恢复 | 断网、重启及丢回执的演练记录 |
| M5 最小内部维护 | 延续现有 Operate/RF，验证一个约定动作及实际读回，例如缓存准备/修复 | 动作状态、原文校验及恢复记录 |
| M6 可复现交付 | 测试数据说明、用例、指标基线、运行手册、已知限制与验收报告 | 他人依说明复跑；候选版本固定 |

M5 的具体动作必须在首周确认底层支持范围。真实介质迁移只有实际效果经过验证时才能计入完成，控制回执或本地缓存动作不能替代迁移证据。

Working 向量召回依据用户补充决定纳入代码版本；完整 GraphDB 本月先交付设计结论，再按业务必要性与产能排实现。基础版本关系与恢复属于必需正确性，不能随完整图服务或工作流框架一起后移。

**交付物：** 冻结的任务清单，每项包含负责人、前置依赖、规模估算、交付物、验收条件和风险。

**关闭条件：** 六个工作包有可复现证据，高风险的数据错乱、越权、旧版本复活和不可判定副作用问题关闭；未完成能力明确列出，不以演示通过替代验收。
