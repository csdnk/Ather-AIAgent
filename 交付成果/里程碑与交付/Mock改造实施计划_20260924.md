# Mock 改造实施计划

日期：2026-09-24。状态：计划已形成，代码改造尚未开始。

依据：[Mock 产品原型审查与改造建议](../测试与验收/Mock产品原型审查与改造建议_20260924.md)、PRD V1.3、当前完整流程图及现有需求覆盖清单。

## 1. 改造目标与完成标准

将当前工程行为模拟台改造成以业务任务为入口的 P3 服务交互原型，让评审者看清：谁发起请求、提交了什么、P3 返回什么、结果为何如此、下一步如何继续。

保留平台式视觉风格及已有有效的模拟规则，覆盖完整 PRD 和关键流程。把入门体验、完整需求评审、工程诊断组织成递进层次。入门任务保持简短，完整性由全套任务和分支共同保证。

完成标准分三层记录：

1. **交互实现完成**：主任务可实际操作，输入、结果和状态一致；8 项已知问题逐项关闭或明确登记剩余项。
2. **模拟行为验证通过**：每个覆盖项有具体操作、预期和实际判定；原有关键规则无回退。
3. **业务理解验证通过**：目标评审者能够根据任务描述操作并解释结果；未经真实参与者验证，不能宣称本层通过。

本次范围为原型及说明、覆盖和验收材料。PRD、正式接口与后端能力以既有工程基线为准；发现需求歧义时记录具体差异，不在原型中悄悄新增产品承诺。上层应用外壳用于示例，明确区分 P3 返回材料与上层应用生成的最终答案。

## 2. 修改后的入口和页面组织

| 层次 | 主要内容 | 默认展示 |
|---|---|---|
| 业务任务体验 | 保存并使用、跨会话复用、更正后再次使用 | 进入原型首先看到此层 |
| 完整需求评审 | 文档处理、删除、共享、冲突、降级、恢复等专题；PRD与流程对应 | 从具体业务问题或需求条款进入 |
| 处理过程与诊断 | 调用参数、候选与块、后台任务、调度、追踪及演示控制 | 按需展开，并绑定当前任务/请求 |

每个业务任务采用同一结构：

- **情境**：正在处理什么业务，当前应用/Agent、会话和授权范围是什么。
- **输入与操作**：可见正文、来源和目标；明确哪个按钮会提交什么。
- **P3 返回**：内容、来源、有效版本、业务状态以及缺失或失败原因。
- **后续动作**：使用结果、等待加工、查看原请求、修正条件或重试等当前可行操作。
- **历史回顾**：已执行操作和当时结果可回看；更正、删除及授权变化支持前后对照。
- **展开过程**：需要时查看内部步骤、调用字段和模拟条件。

## 3. 六个阶段，按顺序执行

### 阶段一：确定任务结构和低细节线框

对应 M01、M02、M06。

工作内容：

1. 记录当前文件和模拟规则基线，在项目外保留改造前备份，保护已有用户改动。
2. 建立“PRD条款 → 业务任务 → 触发动作 → 预期结果 → 对应流程节点”的映射。
3. 把 S01 拆解为三个入门任务，共享、越权、停用及恢复进入后续专题。
4. 设计首页、任务操作页、结果页/区域、历史回顾和过程展开区的低细节线框。先落实内容与路径，再细化视觉。
5. 统一界面用语：主体、会话、来源、当前可用、长期可检索、结果缺失、操作未完成等；工程术语在需要时附解释。

阶段产物：任务与需求映射、页面结构和低细节线框，保存到 `交付成果/原型Mock/`。

检查门槛：三个任务都能明确指出起点、输入、结果、结束条件；应用与 P3 边界清楚；原有需求没有因页面重组丢失。此时只判断设计可实施，不声称用户已看懂。

### 阶段二：修复支撑交互的状态和执行逻辑

对应 M03、M04、M05、M07。

工作内容：

1. 为引导任务定义前置条件、输入、操作、预期结果和后续依赖，实际返回符合预期才继续依赖步骤。
2. 允许场景的预期结果是拒绝或降级；区分“动作已执行”“符合预期”“偏离场景”，不以勾号代替判定。
3. 定义“引导演示”和“自由试用”：引导偏离时停在失败处，说明原因并提供恢复入口；自由试用跟随实际状态。
4. 保存任务历史：每步输入、身份/会话、对象版本、实际结果及预期判定。历史回看仅供解释，原结果再次交付仍执行当前权限和有效性核验。
5. 将刚刚完成的操作与下一步分开显示，结果始终带具体操作名称。
6. 为入门任务定义可控的语义样例和同义问法，支持“项目预算”“我们最多能花多少钱”等任务内表达。区分支持范围外输入与正常业务空结果。
7. 明确重置、刷新、切换任务的状态规则，避免历史标签页把旧剧情或旧判定带入新状态。

主要修改位置：`platform-model.js`、`platform-content.js`、`platform-app.js`，必要时调整 `review-content.js`。新增结构只属于原型内部数据，不作为正式 HTTP 接口承诺。

检查门槛：审查中的同义查询、未开通身份推进、标题/结果错位均有针对性回归；故障不能推进成功分支；历史记录不能因后续操作被覆盖。

### 阶段三：完成三个业务任务的连续交互

对应 M01、M02、M05、M06、M07。

| 任务 | 操作过程 | 用户应观察到什么 |
|---|---|---|
| 保存并使用 | 填写预算20万元和来源 → 提交 → 查询预算 | 已保存的正文及来源；适用当前记忆立即可用；长期加工状态单列 |
| 跨会话复用 | 观察后台加工 → 明确创建/切换到另一会话 → 查询历史 | 当前任务范围确实变化；已加工历史仍可取回；返回来源和版本 |
| 更正后再次使用 | 选中原预算 → 更正为15万元 → 再次查询 → 回看旧结果 | 新旧值并排可辨；当前只采用有效版本；旧结果失效有原因说明 |

工作内容：

1. 首页直接提供上述任务入口和简短业务背景；默认展示一个清晰的开始动作。
2. 每次动作实际操作当前模拟对象，表单与结果关联，避免用“下一步”代替全部业务输入。
3. 基础表单只保留必要输入，K、表示、预算等进入调用参数展开区；参数仍可用于接入评审。
4. 后台加工用状态变化表达；如提供暂停/推进，标为演示控制，避免暗示业务调用者必须编排后台。
5. 实现任务历史和前后对照；失败后给出当前适用的恢复入口。
6. 保留平台风格，统一信息层级、按钮文案及状态颜色，检查桌面和窄屏可读性。

阶段产物：可操作的新版主入口及三个完整任务。这是第一版可以交给用户实际体验的成果，尚不表示全量改造完成。

检查门槛：真实改变会话与对象版本；任务中每个主按钮有可观察效果；结果完整对应输入；退出、返回、重置不丢失或串用其他任务的数据。

### 阶段四：迁移完整需求与异常专题

对应 M02、M04、M06，并维持全量需求范围。

按以下顺序迁移现有专题，逐组检查后继续：

1. **信息维护**：文档处理、当前与长期关系、稳定事实、更正、到期、归档和删除。
2. **取用质量与状态**：无相关材料、来源故障、预算不足、压缩表示、冲突组、索引未就绪及不完整内容。
3. **身份与共享**：未开通、跨租户拒绝、只读共享、撤权、在途交付及旧结果重新获取。
4. **后台运行与恢复**：未知保存结果查原请求、任务中断、租约和断点、维护与独立复验、调度迁移及正文引用交接。
5. **后续能力**：预测预热继续标为后续 P1，与 MVP 状态明确区分。

原有23个专题允许调整入口、分组和步骤数。每项保留或替代关系必须登记，不能用原来的“161步”作为重构后的固定完成指标。

阶段产物：全量专题、新旧入口对应及更新的覆盖矩阵。旧链接尽量保留兼容跳转，过时说明同步更新。

检查门槛：FR01—FR18 和现有关键流程分组逐项有入口、操作、预期和验证记录；失败与拒绝分支体现业务原因及可行下一步；原有规则没有被视觉简化删除。

### 阶段五：工程与交互验收

对应 M03—M08。

执行内容：

- 执行既有模型回归；针对执行器前置条件、预期拒绝、同义问法和历史记录增加必要测试。
- 浏览器执行三个主任务、迁移后的各专题及重要扰动：改变身份、改变会话、处理中更正/删除、刷新和重置。
- 核对界面内容、对象版本、任务状态和最终返回一致；单独检查旧结果回看与重新交付的区别。
- 检查导航、表单反馈、键盘基本操作、桌面/窄屏、相对链接和浏览器错误。
- 更新使用说明、覆盖矩阵、正式验收报告，逐项关闭 M01—M08；尚需真实用户验证的 M08 保持待验证。

阶段产物：新版 Mock、使用说明、覆盖矩阵、工程与交互验收报告。原始日志和截图留在项目外工作区。

检查门槛：已知严重交互问题修复；全量覆盖有实际记录；不以“能点完”代替预期判定。只在新改动或失败需要时重复测试。

### 阶段六：验证业务理解并迭代

对应 M08，复核 M01、M02、M06、M07。

先完成可体验版本，再安排未参与实现的目标评审者试用。建议首轮至少包含业务评审者与接入开发者两类视角，人数和时间按实际可用人员安排，不预设统计代表性。

任务只描述目标，例如“预算改成15万元，请确认下次不会使用旧值”；不预先给按钮路线。记录完成情况、停顿位置、错误理解、求助和提示。随后提供引导演示，其效果另行记录。

理解检查至少包括：P3负责什么；返回内容来自哪里；保存与长期就绪有何区别；更正后旧内容怎样处理；哪些控件仅用于演示。

阶段产物：真实试用记录、问题修复和更新结论。若尚无参与者，则完成可运行交付并明确“业务理解待真实验证”，不以助手自测替代。

退出条件：已发现的阻断任务问题和错误产品理解得到修复；受影响任务重新验证。真实后端、模型质量、性能与生产验收继续按独立工程计划进行。

## 4. 执行规则与交付位置

- 按阶段一至六串行推进；每阶段报告完成内容、检查结果、证据层级和剩余项。常规实现和检查通过后继续推进，不在每一阶段重复设置许可门槛。
- 第一阶段完成可审阅的任务和页面设计；第三阶段交付可体验主线；第五阶段交付完整模拟版；第六阶段补充真实用户理解证据。
- 用户可读的计划、设计、Mock和正式报告放在 `交付成果/` 对应分类；源码及成品必需资源随 Mock 保留。
- 备份、脚本、草稿、截图和原始检查记录统一放在 `E:/projects/codex/.agent-work/aether/workspace-support/`。
- 实施前核对现有工作区改动；保留正在使用的旧成果，不强行覆盖用户打开的文件。遇到源需求冲突时给出具体差异与建议，不擅自修改 PRD 或他人负责的业务代码。

## 5. 预计用户看到的变化

进入页面后先知道“今天要完成什么”；提交前能看到输入，提交后能看到对应结果；更正前后能直接对照；遇到失败能知道接下来怎么处理；需要审查技术实现时，再展开内部流程和工程证据。

本计划本身不代表上述改造已完成。后续实施以各阶段产物和验收记录更新状态。
