# 甲方评审沟通指南：PRD、ADR 与 Mock

日期：2026-09-20。用途：项目负责人会前准备、现场讲解与追问答复。本文不替代需求和技术决议，不代填甲方批准。

按用户最新指示，本轮执行与评审基线为 [PRD V1.3](../PRD版本/AetherBrain_P3_PRD_租户补全版_V1.3.docx)，租户开通、身份映射、停用与撤权均纳入当前需求。原文仍是产品评审稿，采用为开发依据不代表甲方已验收。主 [ADR](../ADR版本/ADR-P2P3-001_总体架构决策.md)目前为 Proposed。现有 [Mock](../原型Mock/index.html)未连接后端。

## 一、先讲什么

会议重心是产品行为、设计依据及可讨论的原型。不要逐页朗读框架介绍。先让甲方判断“我们要的结果是不是这个”，再说明“为什么采用这个方案”。

| 材料 | 现场作用 | 本次希望得到的结论 |
|---|---|---|
| PRD | 约定服务对象、输入输出、边界、异常和验收 | 行为与范围是否准确，有哪些需修订 |
| Mock | 把产品条款变成可观察的操作和结果 | 正常、纠错、删除、降级及未知结果是否符合预期 |
| ADR | 解释方案、备选、取舍、风险与验证方法 | 责任边界和技术路线是否可接受，哪些决策有条件接受 |
| 测试证据，作为附件 | 回答已经做到什么 | 分清设计、模拟、本地运行、真实联调与产品验收 |

建议35分钟：2分钟讲业务目标，6分钟核对PRD，8分钟走记忆主线，8分钟走租户主线，8分钟解释关键ADR，3分钟记录结论。租户主线是V1.3必讲内容，不留到追问环节。技术负责人追问时再展开源码或协议；业务负责人重点看结果和异常处理。

### 可以直接使用的开场

“我们要解决的是Agent在多轮、跨会话任务中，能够持续保存和使用当前有效、当前有权访问的信息。以公司A的项目Agent A1为例：预算最初是20万元，更正为15万元后，后续上下文不能继续把20万元当作当前事实。同公司的协作Agent A2只有获得共享许可才能读取；只读共享不允许删除；公司B的Agent不能跨公司取用。

V1.3进一步要求我们说明：身份通过认证后，怎样映射到已开通的业务租户；共享撤销、租户停用或任务重启后，权限为什么不会沿用旧状态。删除或撤权后，旧结果也不能重新交付失效内容。

今天先用PRD确认这些行为和范围，用Mock展示输入、状态与结果，再用ADR解释三流程如何配合、哪些能力复用开源、哪些保证由我们负责。本次评审是在确认方案，模拟演示和已经运行验证的内容会分别说明。”

## 二、PRD 怎么讲

先讲四个确定边界：对外是Remember和统一Recall；Operate自动运行；P3交付材料、来源和状态，上层生成最终答案；本期不新增独立Web管理端、角色系统、身份系统或审计平台。

接着按V1.3新增要求讲清下面的对应关系。条款是产品要求；表中待确认的是落地参数和双方责任，不能把必需行为改成可选项。

| PRD位置 | 必须讲清的产品行为 | 对应ADR | 会上需明确的落地内容 |
|---|---|---|---|
| 3.3、5.4 | 业务租户有稳定标识；改显示名称不改变归属；同租户也不等于共享全部记忆 | D01/D07 | 租户划分、主体归属及资源范围 |
| FR15、8.2 | 认证成功、映射到启用租户、获准执行具体操作是三次不同判断 | D07 | 认可的身份来源、映射规则及接入责任 |
| FR15、12.8 | 共享区分读取与删除；撤权影响新请求、在途交付和原结果重新获取 | D02/D03/D07 | 共享对象、操作、有效期和授权版本 |
| FR15、9.3 | 开通与停用使用受控配置；更新失败不能部分开放权限；停用不等于删除 | D07 | 配置维护方、版本记录、失败处理 |
| FR15、11、12.8 | 恢复旧数据或配置不能复活已失效权限；外部身份撤销及P2隔离需要联调证据 | D05/D07 | 撤销检测、缓存规则、凭证寿命及最大传播窗口 |
| 14.2 | 联调前确认身份与停用规则；生产前确认停用数据保留、删除和恢复规则 | D08 | 每个待确认项的Owner、确认节点和证据 |

然后讲六组容易误解的状态：

| 区别 | 面向甲方的解释 |
|---|---|
| 已保存 / 长期就绪 | 原始内容已经可靠保存，并不代表后台提取和索引全部完成 |
| 已受理 / 实际生效 | 底层接到调度请求，并不代表目标内容已经可读 |
| 正常空 / 降级 / 失败 | 没有相关材料、部分来源故障、完全不可用是不同结果 |
| 已阻断 / 已清理 | 删除先影响后续使用，后台物理清理可能尚未结束，需可查询 |
| 已认证 / 已开通 / 有操作权限 | 知道来者是谁，不代表已为其开通服务；租户已开通，也不代表可读或删除所有资源 |
| 已停用 / 已删除 | 停用阻断新的业务使用和未经许可的后台提交，数据保留与后续清理由约定决定 |

不要承诺模型永远正确。应承诺来源、版本、授权和失败状态可检查，并通过约定样本验证提取与召回质量。

PRD V1.3沿用并明确：MVP包含基础自动调度、实际执行及结果确认；MVP长稳不少于24小时，Final为72小时。当前暂缓指标门禁是开发优先级安排，不等于已经修改产品验收。若甲方希望调整阶段范围，形成明确版本决议，不能口头把模拟调度当产品验收。

## 三、Mock 怎么演示

2026-09-20已按V1.3重做[统一Mock](../原型Mock/index.html)。下面描述新版实际演示。浏览器里运行同一套记忆、授权、任务、动作及追踪模型；不连接真实后端。

### 3.1 必讲主线：同一记忆走完20步

打开S01，按步骤推进：A1保存20万元预算→立即使用Working→后台加工并取得长期资格→跨会话Recall→A2未共享时不可读→授予只读共享→A2可读但不可删→A1更正为15万元→旧Context失效→在途Recall期间撤权→最终交付阻断→保存快照→停用A→恢复旧快照仍不恢复许可→旧任务受阻→受控对账→运行检测。

每步讲四件事：调用者做了什么、看到什么结果、内部状态为什么这样改变、哪个PRD/ADR约束该行为。顶部切换“追踪与证据”和“检测与恢复”不会清空主线；专题之间独立预置并保存进度。

### 3.2 按问题展开专题

| 甲方问题 | 新版入口 | 重点 |
|---|---|---|
| 改错或删除后是否还能用旧内容 | S02/S05 | 原结果复核、迟到加工阻断、使用阻断与清理分开 |
| 断线重试会不会重复保存或计热 | S03 | 同键不同内容拒绝；Outbox重投与消费去重 |
| 检索失败和确实没有材料怎样区分 | S04/S08 | 来源覆盖、四种结果、完整冲突组及预算 |
| 调度是否自动，失败怎么确认 | S06 | 升降层、容量暂缓、明确失败、原动作对账和证据丢失保持Unknown |

| 租户开通和共享到底怎么管 | S09 | 当前身份、受控映射、资源与操作许可、撤权和外部传播窗口 |

### 3.3 按PRD 12.8六组核对

| 验收组 | 新版模拟走查 | 正式验收还需什么 |
|---|---|---|
| 合法映射与未绑定 | S09开通、未绑定拒绝及无效配置整批拒绝 | 真实身份验证与受控映射 |
| 跨租户与编号伪造 | S09范围伪造、B查询A任务；自由试用检查读写和旧结果 | 真实P2/P3各访问路径隔离，无敏感信息泄露 |
| 同租户共享与操作区别 | S09共享可读、删除拒绝 | 真实候选发现、来源和派生内容范围 |
| 撤权后旧结果与在途处理 | S01/S09可暂停交付，再撤权、继续并观察阻断 | 并发竞态和缓存的真实测试 |
| 停用、后台与旧配置恢复 | S01/S11实际操作模拟快照，当前许可覆盖旧状态 | 权威配置恢复、失联处理及真实重启证据 |
| 外部撤销与P2隔离 | S09以虚拟30秒窗口演示传播前后；不伪造真实认证结果 | 双方批准窗口内的实际传播及真实P2隔离 |

本次可说“产品行为已有可操作模拟”，不能说“对应后端已完成”。模型、身份、存储、执行效果和时钟均是模拟。完整实现状态仍见工程证据。

### 3.4 追踪与恢复的现场讲法

在S11记住第一次保存的trace_id，再模拟Worker退出、推进租约过期、执行恢复扫描和原任务重试，点击原trace查看节点输入、输出、状态与原因。检测记录、恢复判定和业务完成分别展示；旧Worker迟到提交明确被拒绝。

恢复旧快照使用“当前授权和有效性记录独立保留”的模拟假设，不沿用旧许可；正式配置与撤权记录怎样备份和恢复仍需在ADR落实。演示控制按钮不代表新增管理平台，也不让普通调用者获得维护权限。

## 四、ADR 的讲法

每项决策都按“需求约束 → 选择 → 备选 → 代价 → 验证”讲。技术选择由我方负责提出和举证，不要求甲方替我们决定Python库。甲方重点确认产品行为、集成边界、部署限制和验收条件。

| 决策 | 可直接使用的解释 | 代价与验证 |
|---|---|---|
| D01 三流程 | “事实维护、一次上下文交付、持续访问调整的完成条件不同，所以拆成三个责任模块；当前不要求三个微服务。” | 接口和事件多了，靠共享契约及跨流程测试控制 |
| D02 事实与派生分开 | “索引可能滞后，但更正和删除要及时影响使用，所以由Remember统一决定当前版本资格。” | 召回必须多做资格核验；用旧索引、在途加工和删除竞争测试验证 |
| D03 上下文流水线 | “相似的内容不一定有权使用或仍然有效，不能把向量TopK直接当答案材料。” | 增加筛选、预算与最终检查；验证来源故障和更正后结果 |
| D04 有边界地采用框架 | “复用成熟的提取、推理和检索机制，把授权、版本与业务结果保留在我们的契约中。” | 需要维护适配器；以输入输出与故障测试决定是否采用 |
| D05 Provider接口 | “P3决定业务资格，P2或约定执行端提供真实存储和状态证据。” | 需要共同冻结协议；Milvus验证路线不自动替换P2交付范围 |
| D06 状态核对循环 | “执行响应可能丢失，系统持续查询原动作，把已知结果与未知状态区分开。” | 需要持久动作及查询能力；执行后丢响应时检查没有重复冲突动作 |
| D07 授权与运行保障 | “身份先映射到已开通租户，再按资源和操作授权；新请求、后台提交、旧结果重取都复核。Trace帮助定位，持久事实决定恢复。” | 要管理配置及授权版本；验证共享撤销、租户停用、旧快照恢复、外部撤销窗口及迟到结果 |
| D08 阶段边界 | “目标能力全部保留，分阶段交付、逐项留证；范围变化经决议后修订。” | 未确认的底层能力不能假装具备；评审必须明确依赖和阶段结果 |

### 完整答法示例：为什么只用 LangMem 的局部能力

“PRD要求记忆能更正、删除、追溯来源，还要求保存后后台任务不丢。LangMem适合提供结构化记忆候选，所以我们把它接到提取接口。正式记忆的身份、版本和提交仍由Remember管理。

如果直接采用框架自带存储路径，我们仍要证明它能同时满足事实、任务和事件的一致性交接，目前没有这样的验证结论。局部适配的代价是多维护一层转换，但后续可以替换提取模型而不改整个记忆协议。是否正式使用，要通过中文否定、引述、假设、重复输入和失败恢复实验。当前默认提取还不是实际LangMem模型，这一项没有报为真实联调完成。”

## 五、框架相关追问与回答

### 1. 为什么不直接用一个现成AI记忆产品？是不是重复建设？

“我们会优先复用成熟能力。这个项目同时要求事实生命周期、受授权的上下文交付、两侧轨迹驱动的自动调度，以及与P2的接口协作。单个框架能覆盖其中一些环节，仍需证明整个组合满足这些约束。自研重点是业务契约和一致性边界，不是重新写向量数据库或模型推理引擎。”

如对方点名Mem0、Zep等，不说它们不能用：“可以按同一需求矩阵评估。目前没有完成所有备选的实测比较，所以不宣称当前选择是行业最优。如果备选在适配成本和验证结果上更好，可以在端口边界内替换。”

### 2. 这些框架是不是都会装进系统？

“不是。LangMem是提取适配候选；LlamaIndex和Controller模式主要参考设计；FastEmbed/ONNX Runtime和可选Sentence Transformers参与真实推理。Temporal、OpenFGA、TEI目前是研究或后续候选，不是当前运行前提。”

### 3. LangMem是大模型吗？模型提取错了怎么办？

“LangMem是记忆处理库，调用配置的模型形成候选，本身不是一组模型权重。候选需要通过结构、来源和范围校验；不允许模型自己决定租户和正式版本。质量不满足时保留原输入与失败/未就绪状态，不把不可靠候选包装成稳定事实。模型质量需要样本验证，不能由结构校验完全保证。”

### 4. LlamaIndex不直接使用，为什么还写进ADR？

“ADR记录采用的设计依据和取舍。我们借鉴Retriever、融合和后处理分层，运行接口仍由P3维护。没有把完整Query Engine接入，因为P3负责上下文材料，上层才负责生成答案。参考对象不等于运行依赖，文档中会明确标注。”

### 5. Embedding和重排序是不是做了两遍相同工作？

“Embedding让大量材料能通过向量快速找候选；CrossEncoder再一起看问题和少量候选，做更细的相关性判断。后者计算较重，所以可配置，并且需要验证质量收益与额外延迟。它不替代权限、版本和来源核验，也不承诺一定提升所有样本。”

### 6. BGE为什么适合？换模型会怎样？

“目前选择了可本地运行并已经验证Query/Passage链路的中文BGE模型，便于先完成可复现实现；这不等于完成了全模型质量比较。换模型要重新验证输入预处理、向量空间与索引绑定，必要时重建投影，不能因为维度相同就混用。”

### 7. 用Kubernetes Controller，是不是现在就要上K8s？

“目前借鉴的是‘读取当前状态—判断差异—执行—核验’的控制循环，用Python实现。没有直接运行Go的controller-runtime，也没有把每条记忆建成K8s资源。以后部署到AKS是另一项工程决策。”

### 8. 为什么先用SQLite？能支撑正式系统吗？

“SQLite是当前单机验证阶段的事实存储，帮助我们验证事务、任务和故障边界；没有把它作为多主机共享数据库承诺。多副本前需要明确存储方案，例如PostgreSQL，并重新验证并发领取、CAS、幂等和数据迁移。是否足够取决于部署和负载证据，不以品牌判断。”

### 9. Milvus和P2是什么关系？会不会做了两套存储？

“Milvus适配用于向量能力的独立实现与验证。目前仍需与P2 E1的联合交付接口统一，不能未经确认就把它替换为正式唯一方案。P3依赖的是VectorPort和资格规则，正式由哪个Provider承担，要明确一个部署路径和数据归属。”

当前事实：SDK适配及协议故障测试已完成，真实Milvus服务联调尚未执行。

### 10. 为什么不直接使用Temporal，自己写任务可靠吗？

“目前任务规模和流程复杂度受单机阶段约束，复用已有SQLite事务和持久任务以减少基础服务数量。我们承担租约、幂等、有限重试和领域恢复的测试责任，但没有宣称实现了Temporal全部历史重放能力。若长流程、复杂补偿或多主机协调超过当前能力，会评估替换；不会长期叠加两套权威任务系统。”

“即使采用Temporal，流程恢复也必须重新检查当前租户和授权。历史里保存了当时许可，不代表现在仍能提交；恢复引擎不能替我们定义V1.3的停用和撤权规则。”

### 11. 有Trace是否就能恢复？日志丢了怎么办？

“Trace帮助查过程；数据库中的任务、租约、版本和动作证据决定恢复。日志丢失要报告缺口，不能据此推断动作没执行。业务变更和待办同事务提交，外部效果不明查原动作；这是恢复依据。”

### 12. 你们已经接了OpenTelemetry和Azure Monitor吗？

“当前有自有本地Trace/Span、独立日志库和健康检测，借鉴OpenTelemetry的关联模型。OTel SDK/OTLP、跨HTTP传播和Azure集中采集尚未接通。下一阶段会接标准采集体系，不把目前的本地查询描述为完整分布式监控平台。”

### 13. 健康检测成功，是不是能保证业务正常？

“探测有深度区别。进程响应、数据库可读写、模型能推理，以及最终业务结果正确，不是同一结论。我们分别报告依赖和业务能力；真正的业务正确性由结果校验和场景测试证明。”

### 14. 为什么不直接用Azure身份或Namespace实现租户隔离？

“Azure目录验证身份来源，Namespace管理集群资源；业务租户和记忆访问权仍要由服务确认。同一目录下可以服务多个客户，同一租户内也有未授权用户。当前已有本地范围授权，外部身份映射、租户停用与撤权传播还需真实接入。”

### 15. 框架停止维护、升级不兼容怎么办？

“业务模型不直接继承框架内部对象，通过适配器接入并固定版本。升级先跑同一契约和故障样例，再验证真实依赖；涉及模型/索引变化还要迁移数据。可替换降低影响范围，但替换仍有适配、迁移和回归成本，不能承诺零成本。”

### 16. 数据会不会上传到外部？开源授权是否有问题？

“要按实际部署回答。当前已验证的BGE推理在本地CPU运行；LangMem未来是否走外部模型取决于接入配置，不能承诺所有模型路径都天然不出域。正式引入包、模型权重和外部服务前，分别核对版本、许可证及数据流，按甲方环境要求选择。框架开源不等于所有权重和服务条款都相同。”

这是部署和依赖核验事项，本文件没有完成许可证法律审查，也没有代填甲方数据出域许可。

### V1.3对框架选型增加了什么约束？

“LangMem生成的候选不能决定租户和授权；LlamaIndex的过滤机制只能帮助缩小候选，最终资格仍由P3复核；Controller模式要求重新读取当前状态，所以旧事件不能带着旧权限直接执行。数据库、队列及未来Temporal保存执行依据，身份设施验证来者身份，P3仍负责业务开通、共享和停用规则。选用任何框架，都要通过同一套12.8场景。”

## 六、产品与进度追问

### “V1.3增加租户，是不是要做一套账号和管理平台？”

“本期通过受控部署或开通配置，登记稳定租户编号、启停状态、认可的身份来源和主体映射，并记录配置版本与结果。不新增登录、邀请、计费或租户管理页面。需要双方明确谁维护配置、怎样验证更新，以及失败时怎样保证不会部分开放权限。”

### “我们已经用Azure登录，为什么还会被拒绝？”

“登录成功说明身份得到验证。P3还要确认该身份已映射到启用的业务租户，并获准对目标资源执行这次操作。业务租户、Entra目录和Kubernetes Namespace是不同边界。内部记录可以区分未认证、未开通、已停用和无资源权限；对外响应仍要避免泄露其他客户的数据存在情况。”

### “同一个客户的Agent为什么不能互相读？共享后为什么不能删除？”

“归属同一客户不代表负责同一个项目或具备相同职责。共享要明确主体、资源、操作、有效期和授权版本；授予读取只开放读取。删除、纠错等写操作按独立许可判断，服务基础设施凭证也不能代替调用方业务许可。”

### “撤权时已经在查询，或者以前拿到过结果，怎么办？”

“新请求、在途最终交付以及向P3重新获取原结果，都要检查当前授权与有效性。不能仅凭旧缓存、旧结果编号或任务创建时的许可重新交付正文。已经交付到调用方系统的内容无法靠P3撤权自动收回；下游保留和清理责任需要在接入约定中说明。”

### “停用客户会删数据吗？已经执行的动作要回滚吗？”

“停用不等于删除。先阻断未经许可的新使用与后台提交，保留业务归属和记录。已经发生的外部效果需要查询和对账，不能假设停用就撤销了动作，也不能由公共重试器继续盲发。保留期限、后续删除及恢复规则按14.2在生产前确认；必要对账使用受控维护权限。”

### “从备份恢复后，原来撤销的权限会不会又回来？”

“按FR15，不能回来。恢复设计必须有识别当前停用与撤权状态的依据，并在恢复后重新核验；无法确认时不能沿用旧许可开放业务。具体权威配置、授权版本或撤权记录怎样恢复，需要在ADR中落地并注入旧快照验证。当前Mock已提供旧快照恢复实验，但其权威配置是模拟保留的；正式系统仍需实现和真实证据。”

### “在身份平台禁用账号，是不是马上全部失效？”

“本地共享撤销与外部身份撤销是两条链路。外部撤销受凭证有效期、验证方式和缓存影响，不能口头承诺所有已签发凭证瞬间失效。按FR15和14.2，联调前确认检测机制、凭证寿命及最大传播窗口，再测试窗口内的阻断效果。Mock预设过期凭证不能证明真实传播时间。”

### “底层P2保证隔离，为什么P3还要检查？”

“P2需按契约隔离真实存储访问；P3负责调用方范围、当前版本、共享许可和最终交付。两侧分别验证，任何一侧的服务凭证都不能扩展用户权限。12.8要求真实P2多路径联调，单测或浏览器模拟不能替代。”

### “Mock都能点通了，为什么还不算开发完成？”

“Mock确认的是产品行为，当前数据、模型、身份和执行反馈是模拟的；真实后端另有本地验证。真实模型、远程存储、权限和故障都要有相应证据。比如S08能演示冲突组、S11能演示安全恢复，不代表后端已完整实现这些能力。”

### “不是说系统已经搭好了吗？”

“公共基座与三流程的本地基础实现已搭好；后续是在这个基础上完善真实提取、完整冲突处理和生产Provider。当前有408项自动测试及上一批真实本地Embedding/重排序链路证据，但不能换算成整个PRD的完成百分比。”

### “为什么不先做所有业务，最后加日志、隔离和恢复？”

“这些要求影响接口、数据归属和提交方式。后加容易出现身份传不下去、旧任务覆盖新版本、外部动作重复执行。我们先建立最小公共闭环，随后业务与异常一起实现；不先建设完整运维平台。”

### “调度优化到底能节省多少、快多少？”

“目前能说明策略输入、执行及核验机制，还没有生产负载下的收益结论。需要同一数据、资源和负载比较基础方案与调度方案，同时观察对在线业务的影响。不能用Mock容量和本地目录复制数据来宣称生产收益。”

### “这些决策是不是都已定了？”

“主ADR是待联合评审。当前已有实现证明部分方案可运行，但是否接受生产Provider、部署边界及阶段安排，要记录本次评审结论。接受某项设计也不等于该功能已经验收。”

## 七、会上需要形成什么结论

不要只记录‘整体认可’。至少逐项记录：

| 议题 | 需要明确的内容 |
|---|---|
| 需求版本 | 确认所有评审材料按V1.3，后续变化形成版本决议 |
| 产品行为 | 更正与冲突区别、删除阻断与清理、来源故障结果、旧结果复核 |
| 租户开通 | 业务租户划分、稳定编号、认可身份来源、主体映射、配置维护方；失败更新不得部分开放 |
| 共享与停用 | 读取/写入范围、有效期、在途及旧结果复核；停用不等于删除，外部已执行动作如何受控对账 |
| 撤销与恢复参数 | 外部撤销检测、凭证寿命、缓存和最大传播窗口；旧配置/数据恢复不得复活失效权限 |
| 接入范围 | P2/其他Provider承担的具体能力、协议、测试环境和双方交付责任 |
| 调度承诺 | PRD既定基础调度仍保留；本阶段实际执行对象、介质范围及验收路径 |
| 安全与部署 | 身份来源、业务租户映射、数据出域约束、Azure环境及密钥管理 |
| V1.3验收安排 | 12.8六组逐项指定场景、实施方和证据；旧快照恢复、外部身份及真实P2隔离列为待验证 |
| 待办 | 每项问题对应Owner、补充材料、确认节点和验证方式；没有证据不承诺日期 |

建议会议记录逐行填写：议题/PRD条款/ADR编号/Mock场景/结论（接受、附条件接受、待补充、拒绝）/条件与理由/Owner/计划确认日期/所需证据。参与人和日期由实际会议填写，文档作者不能自行把Proposed改成Accepted。
