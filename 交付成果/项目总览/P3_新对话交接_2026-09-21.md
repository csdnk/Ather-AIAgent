## 5. 已确认的三流程边界与最近完成内容

### 5.1 Remember（B）

LangMem 用于候选提取，不负责我们的全部业务事实和可靠性。可信身份、来源、正式 ID、版本、幂等提交、显式纠错、删除屏障、投影资格及事务由 Remember 与公共底座负责。

Remember 是权威记忆事实的 Owner，为 Recall／Operate 提供精确读取、来源与关系读取及最终资格核验。有效 Working 不必等待长期提取或向量投影完成。

### 5.2 Recall（A）

结果是获授权、当前有效、符合预算的 ContextPack，不是必须由 Query Engine 直接生成自然语言回答。

已完成的图形更新：

- **A.1 主流程：**来源选择、读取与资格、融合或直接通过、筛选排序、冲突与替代关系、完整组预算、最终核验、保存与交付。
- **A.1a 编码与向量检索：**Query 检查 → Query 用途与模型空间绑定 → 模型 tokenizer → FastEmbed 调 BGE／ONNX 推理 → 按配置池化／归一化与向量检查 → 服务端 scope 及模型空间过滤 → Milvus → 候选 ID、版本、分数、来源。
- **A.1b 权威正文读取：**长期候选或 Working 引用 → B 权限核验 → 当前版本、删除、到期及来源检查 → 按 MemRecord 存储引用读取正文、来源及关系 → 逐项读取结果 → 访问事件与后续交付。
- **仅 Working 的显式分支已经画入 A.1：**直接向 B 按授权范围和会话读取并核验，跳过 Embedding、Milvus、RRF，进入筛选排序、冲突处理、预算、最终核验及交付。
- 只查 Working 时，读取成功且无合格记录返回 Empty；读取失败返回 Failed；不能自动转查长期。权限拒绝不算空；材料因冲突完整性或预算无法交付时仍按主流程报告不可用。

其他重要约定：

- Passage 在记忆建库／投影阶段编码，不在每次 Recall 中重编码所有正文。Query 和 Passage 要绑定兼容模型空间；同维度不代表兼容。
- BGE 是编码模型，FastEmbed 是调用适配，ONNX Runtime 是推理运行时。图里采用已有可选本地适配方案，不表示唯一后端或已联调验收。
- Embedding tokenizer 与 ContextPack 预算 tokenizer 作用不同。
- RRF 是排名融合，只有多路候选需要；示例是名次从 1 开始的 `Σ 1/(60+rank)`。不是向量与关键词混合索引。
- `read` 和 `packed` 是访问阶段；当前策略给成功 read 去重计热，packed 不再重复计热，重复事件也不重复生效。
- 原结果重取必须重新核验当前授权和有效性，不能直接返回已经失效的历史正文。

### 5.3 Operate（C）

最近一次更新仅参考用户附件《P3_整体架构与完整流程(1).excalidraw》里的 Operate，未采纳附件其他模块的改动。最新正式图已包含所需流程，无需从临时微信路径重新取附件才能继续。

已画入 C.1—C.5：

1. 缓冲区0按 Memory 聚合、去重；原子取走一批，新输入进入下一批。
2. 同一 Memory 的准入和本轮登记串行；键需包含租户与授权范围。已有未完成工作时，后续需求进入缓冲区1。
3. 本轮目标固定；查询 P2 实际层，一致则 No-op，不一致再规划。
4. 资源不足进入等待队列，由资源更新唤醒重查；查询失败不等于不一致。
5. 动作意图先持久保存，固定 action_id；Running／Unknown 保留原动作并查询，不盲目重发。
6. 实际层与动作状态分别核验；层级一致且动作成功后，核验新地址、对象、版本及可读性。
7. 通过 Remember Owner 的授权接口条件更新 MemRecord，写入确认后才结束本轮并放行下一轮。元数据写失败重试交接，不重新迁移。
8. 资源不足、位置冲突、P2 不可用、终态矛盾、删除与清理有各自处理分支。无法查证时不画成成功。

缓冲区／等待区是持久业务状态的逻辑角色，不是要求重建多套独立公共队列。参考 Kubernetes Controller 的当前状态对账机制；不是直接把 Go controller-runtime 嵌进 Python，也不默认把每条记忆建成 CRD。

## 6. 下一步：公共底座怎么讲、怎么展开

### 6.1 必须先解释的四种职责

| 能力 | 回答什么 | 依据 |
|---|---|---|
| Trace | 一次请求经过哪里、卡在哪一步 | trace_id、Span、父子关系或异步关联、阶段耗时与结果 |
| 日志 | 一个节点具体发生什么、为何失败 | 结构化记录、输入输出摘要、错误详情 |
| 健康检测 | 能否接请求、依赖是否可用、任务是否停滞 | 主动探测、心跳、队列及持久状态 |
| 恢复 | 中断后下一步做什么，怎样避免破坏状态 | 任务、租约、版本、动作状态和执行证据 |

**日志和 Trace 帮助定位，但不能单独作为恢复依据。** 日志可能缺失、Trace 可能采样；权威状态和执行证据需独立持久化。进程重启、依赖恢复和业务完成也不是同一件事。

用户希望一个 trace_id 能查到完整处理过程。需进一步设计入口上下文、跨任务／事件传播、每次尝试的独立 Span、长时间恢复的关联方式。不能承诺所有重试永远挤在一个无限长 Span；应支持从原 trace_id 联查相关任务、事件和后续尝试。

### 6.2 建议展开的公共子图

在现有 P3 整体内展开，保留 P3.1—P3.6 主编号并按需加子编号：

- **追踪：**入口建上下文 → 同步调用 → 持久任务／事件交接 → 后台处理 → 结束或恢复尝试 → 授权关联查询。
- **日志：**节点开始 → 输入摘要 → 结果或异常 → 脱敏 → 存储 → 轮转／保留／清理 → 检索；补充写入失败如何发现与记录缺失。
- **检测：**启动、进程与依赖探测 → 实际能力汇总 → 任务停滞和未确认事件扫描 → 判断影响 → 告警或受控恢复触发。
- **恢复：**发现未决工作 → 取得处理权 → 查询当前事实／原动作 → 领域判定重做、继续、对账、终止或人工 → 条件提交 → 业务复查。

每张图写明触发方、处理方、输入输出、数据落点、失败分支与真实边界；不要只罗列 OpenTelemetry、Azure Monitor 等产品名称。

### 6.3 用一个贯穿案例讲清楚

建议案例：Remember 已提交输入，后台构建投影时 Milvus 不可用。

1. Trace 能定位到后台投影与失败的向量调用。
2. 日志记录任务 ID、记忆版本、耗时和错误，默认不泄露完整敏感正文。
3. 数据库保留未就绪投影、任务尝试、失败原因和待处理状态。
4. 健康检测报告向量能力受损及积压影响，不盲目触发整个服务重启。
5. 恢复取得有效处理权，Remember 重验记忆是否已删除、版本是否改变、动作能否继续。
6. 按可安全重试或查询原结果的规则处理，确认投影写入后更新正式状态。

随后再对照 Recall 来源中断、Operate 执行成功但响应丢失，说明公共机制共用、领域判断不同。

### 6.4 框架研究范围

| 对象 | 重点 | 采用边界 |
|---|---|---|
| OpenTelemetry + W3C Trace Context | Span、传播、异步关联、采样与导出 | 标准接口与接入参考；先核对现有代码是否真正使用 SDK |
| Python logging / structlog | 结构化字段、异常栈、上下文、脱敏 | logging 与 structlog 是待比较的实现选择，不声明两者均已接入 |
| Kubernetes 探针规范 | startup、liveness、readiness | 进程存活与接流量资格分开，依赖抖动不应造成重启风暴 |
| Outbox/Inbox、租约、CAS | 原子交接、重复消费、过期处理权 | 现有持久任务与恢复设计的核心机制 |
| Temporal | Activity、History、Retry、Heartbeat、Replay | 学习恢复机制；不未经决策增加第二套权威任务系统 |
| Azure Monitor / Application Insights / AKS | 采集、查询、身份与部署接入 | 先定义应用产生哪些记录，再决定接到哪里 |

指标体系可暂缓，但用于定位未决工作的任务状态、尝试记录、租约期限等基础事实不能省略。
