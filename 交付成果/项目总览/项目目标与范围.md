# P2 / P3 项目目标、范围与现状

版本：评审稿 1.0；日期：2026-09-19。对应甲方 §5.1、§7。角色安排只说明结果责任，不评价人员能力。

| 问题 | P2 AetherEngine | P3 AetherBrain |
|---|---|---|
| 为什么做 | 为向量、对象与图提供可关联、可恢复的存储能力，减少各引擎独立接入的复杂性 | 让 Agent 跨会话可靠复用记忆，并在更正、删除和依赖故障后仍给出可信结果 |
| 为谁做 | P3、P4 和需要三态数据的应用接入方 | 应用、Agent 与 P4 接入方 |
| 解决什么 | 候选、正文、图关系难以关联，内部状态与控制结果难以核实 | 保存不等于可检索、旧事实误用、检索故障伪装空结果、后台动作不可追溯 |
| 最终交付 | E1/E2/E3 引擎与接口、持久恢复、跨引擎引用和联调证据，约定范围的状态与控制能力 | Remember、统一 Recall、内部 Operate，以及调用契约、部署运行与验收证据 |
| 当前不做 | E4 文件/E5 块/E6 时序仅调研；不凭 P3 本地替身宣称 P2 完成 | 不新建独立 Web 管理、RBAC、身份或审计平台；预测优化属于 P1 后续阶段 |
| 什么算完成 | 真实服务完成对象精确读写、向量检索、图关联、恢复及约定接口用例，达到共同确认的验收基线 | 核心场景真实运行，隔离、版本、删除、降级正确；完成集成、质量/性能、UAT 与发布准备 |

## 一条可以讲清楚的业务主线

应用提交“预算 20 万元、每周五汇报”。Remember 可靠保存来源，当前会话先可用，后台加工和投影成功后可跨会话召回。预算更正为 15 万元后，Recall 必须过滤旧候选并复核旧结果。删除来源后，迟到加工不能复活旧内容。Operate 消费存储和读取事件，自主判断是否需要动作，并核对执行结果。

P2 提供候选、正文、关系和物理状态；P3 决定记忆是否有效以及可以交付什么。分层涉及的物理执行依赖 P2/P1 和联合确认的契约。

## 截至本次评审的真实状态

- P3：本地后端原型已能运行。SQLite 持久基础、Remember/Recall/Operate、原生 BGE ONNX 向量计算有代码与测试证据。
- 限制：默认记忆提取仍为原文事件，向量检索为 SQLite 逐条相似度计算；Context 已按实际 tokenizer 计量（默认 o200k_base），支持真实 CrossEncoder；Milvus适配已有、服务联调待环境。真实语义冲突组、文档加工/压缩、下游模型预算校准及真实 Provider 联调尚需完成。当前状态见[协作基线](../开发协作/01_当前实现与待办.md)。
- Mock：展示业务行为与期望状态，未连接后端。P2 Mock 同样只是消费方评审样例。
- P2：对象、向量、图、WAL 和 gRPC 有实质源码；本机未完成 Rust 编译与现场联调，因此仅列源码核查。
- 冷热：本地目录复制已验证动作协议的一部分，不能证明真实分层收益。甲方 §9 与现 PRD FR13/FR14 存在范围待决项。

## 本轮成功标准

两周整改的目标是可评审、可追溯、可验证：抽取任一评审 Epic，能定位 Story、Mock、Flow、Architecture、Test、代码与缺口；抽取一个决策，能解释备选、代价与验证办法。G1/G2 仍需联合评审通过。G3–G5 不能以材料齐全替代实际运行与验收。

产品/项目角色负责目标和范围；架构角色负责方案和契约；各 Epic 角色负责结果；测试/交付角色负责证据与 Gate。具体姓名及评审日期待团队安排，未代填签字。
