## 4. 已确定的职责和关键设计

### 4.1 RF / B / A / C

- RF 提供身份授权、事务、持久任务、事件投递、日志、健康与恢复机制；领取任务后调用业务处理器，不代替业务处理器完成加工。
- B / Remember 负责来源、记忆、正文、版本、生命周期、资格判定、向量投影写入/核验/清理和索引发布。
- A / Recall 负责 Query 编码、向量搜索、候选聚合、排序和 Context 组包，同时向 B 提供 Passage Embedding 能力。
- C / Operate 消费事实、形成放置决策、执行迁移/清理并核验。它主要在内部运行，不是第三个用户业务入口。

代码已拆开 B 的 `ProjectionPort`、`GenerationProjectionPort` 与 A 的 `VectorSearchPort`、`GenerationSearchPort`。旧组合接口和导入仅为兼容；当前目录为 118 个对象、68 个正式方法、24 组 Protocol。部分旧入口仍写 22 组，不能据此判定当前目录数量。

### 4.2 召回的目标顺序

**A 获取块命中 → 调 B 审查资格 → A 聚合为合格记忆候选并占 Top K → 调 B 读取完整正文 → A 排序组包 → B 最终复核 → RF 条件事务提交。** Working-only 走受控读取，不经过长期向量检索。

- Top K 按作用域内的 memory_id 计数，同一记忆的多个块不重复占名额；只使用有效版本、已发布批次内的合格块计分。
- 正文由 B 的接口提供，不用向量库命中片段冒充全文。候选审查、正文读取、最终提交是三个核验时点。
- 当前基础代码：A 调 `MemoryReadPort.load`，B 内先执行 `final_guard`，只返回允许读取的正文；审查与读取合在一次调用里。
- 新多块读取 `load_bodies`、完整候选与组包流程尚未完整接入。
- 拟新增 `MemoryQualificationPort.qualify`、`CandidateQualificationTarget`、`CandidateQualificationResult` **目前只有文档设计，没有 Python 契约、Schema 或服务实现**，不计入上述 118/68。
- 新审查结论区分 allowed、excluded、unverifiable；资格审查通过不代表正文读取成功，不产生访问热度。请求结果缺项或错配不能默认允许。

### 4.3 EmbeddingSpace

它描述模型、固定版本、维度、分词器、Query/Passage 前缀、归一化、距离规则和输入 token 上限，不存储模型本体或向量数据。当前编码使用 model_space 标识；EmbeddingSpace 的集中配置管理仍待服务接入，不能说注册与解析服务已经实现。

当前单模型通常使用一个空间。Query 与 Passage 使用模型规定的配套方式；更换不兼容模型或配置不能直接搜索旧向量，需规划重新编码及空间切换。三种距离算法不是不同的语义理解能力；两侧均单位归一化时 cosine、内积和 L2 的排序等价，但数值与阈值不同。

## 5. 租户、鉴权及后台的真实实现边界

| 图中模块 | 当前机制 | 未完成或容易误解的地方 |
|---|---|---|
| 应用 / Agent | HTTP Remember、Recall；任务状态/进度查询；请求幂等 | “两个业务入口”不代表仅两个 HTTP 路由；查询原处理不等于重新提交 |
| 可信身份与业务租户 | Identity.provision 受控配置凭据摘要与 Principal；Bearer 凭据认证后建立 TrustedContext；按 Scope 和操作权限检查 | 当前不是 Entra JWT 验证；外部身份映射待接。selection 只能限制范围，不能扩权 |
| 租户内共享与撤权 | 同租户应用/用户/Agent 默认隔离；AuthorizationGrant 授予具体资源操作；停用主体、提高 auth_epoch、移除授权后重验 | 不支持跨租户共享；具体授权已实现，但共享记忆完整检索尚未完成；独立租户启停和管理接口未齐备 |
| 持久任务 | SQLite 任务记录、租约、幂等、状态机、截止时间、重试/恢复及执行配额 | 任务按执行类别、租户和 scope 限制；不代表所有 HTTP 请求都有租户限流；多副本生产能力未验收 |
| 可靠事件 | 业务事务写 Outbox，按消费者投递；Inbox 去重；确认丢失可恢复 | 可重复投递，不重复提交受保护的本地消费效果；外部动作仍需任务、幂等和原动作核验 |

授权区分 `memory:read/write/correct/delete/history` 与维护诊断、恢复、配置。具体资源共享仍要求接收主体具备对应操作权限。普通租户维护权限不自动获得全库配置和备份权限，部署运维需额外授权。

后台任务保留原发起人上下文，执行时复核；事件携带发起人和授权版本，领域消费重验；Worker 自身的运行身份不扩大业务授权。旧 Recall 结果再次获取也需要复核。

## 6. 监测与日志：下一轮需要补什么

现有 NodeLogRecord、SignalDefinition / SignalObservation、HealthObservation / RuntimeHealthSnapshot，以及基础调用日志、依赖探针、任务积压和 Worker 检查均有基础。AccessObserved 是业务访问事实，不能用普通日志代替。

缺口是：各节点怎样产生数据、谁负责记录、统计单位及窗口、重试去重、信号如何采集汇总、健康能力如何由证据推导，还没有统一到足以供三方独立完整实施的程度。通用对象存在，不等于所有业务指标已经采集。

若用户要求继续这项工作，按下面顺序执行：

1. 逐节点覆盖 B/A/C 的正常、排除、故障、超时、取消、重试及恢复分支，登记唯一记录责任方。
2. 定义公共口径：节点标识、追踪关联、结果/原因分类、开始结束边界、调用数/尝试数/块数/记忆数、缺失及重复处理。
3. 核对日志、指标、业务事件的真实接收接口；缺失的契约明确补齐，不凭空宣称已有指标上报方法。
4. 在每个业务流程段落下面写上报时机、对象字段及例子；已有公共字段只在首次定义，后续引用。
5. 明确健康能力与依赖/业务信号的映射、采样窗口、配置阈值、有效期和未知状态。正常权限排除不算系统故障；无法核验不能当作普通空结果。
6. 补采集系统自身故障：日志丢失、采样缺失、进程中断无结束记录，如何留证、告警及影响业务。
7. 配套验收用例，同时核对业务结果、日志、指标、事件、健康状态，验证关联正确、不重复计数。

责任建议：RF 提供统一封装、采集汇总和健康判断机制；A/B/C 提供各自业务事实和能力规则；测试验证同一套口径。A 调 B 时，两侧均可留调用记录，但不能把两条日志误算成两次逻辑审查。
