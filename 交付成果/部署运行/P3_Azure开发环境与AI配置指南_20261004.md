# P3 Azure 开发环境与 AI 配置指南

适用日期：2026-10-04。适用源码：`AgentJYS-main` 的 Azure 存储接口版本。此文可以交给开发者及其 AI 助手，按下面的检查点创建独立环境。账号、数据库密码、Token、私钥和 kubeconfig 由维护者通过团队的受控渠道提供，本文不包含这些值。

## 1. 当前代码与运行方式

P3 使用一套源码，通过 `service.yaml`、环境变量、证书和独立数据范围切换本机、AKS 开发、测试及生产环境。入口为：

```text
python -m aether_agent_memory
  → runtime/flows/cli.py
  → runtime/flows/application.py
  → Service：HTTP + Temporal SDK Workers
```

PostgreSQL 保存权威元数据、任务、幂等回执和诊断记录；Ceph 保存正文、原始输入与版本化对象；Milvus 保存向量投影；Redis 保存可恢复的热副本；独立 Temporal Server 编排持久任务。P3 自身不再使用旧 SQLite 存储或旧 RF 调度器。旧数据迁移已取消，新开发环境使用新的数据范围。

Redis 的正文准入按完整 scope 原子计算字节配额，有效上限为 `min(cache_capacity_bytes, remember.cache_scope_bytes)`。执行器和普通正文缓存共享这一上限；它不是整个 Azure Redis 实例的内存上限。多人使用不同 namespace 隔离，实例总容量、eviction 策略与监控由维护者配置。

现有 AKS 演示服务仍在运行。本次源码在独立 AKS 测试 Pod 中验证，不能据此声称现有 Deployment 已升级到本次 Git 提交。现有演示 Temporal 使用 development server；正式 PostgreSQL Temporal 部署需要另行完成第 10 节的权限与资源事项。

本次候选镜像在本机启动、Worker 就绪及原回执/正文/召回结果的重启恢复已验证；经桌面 relay 的一次新保存仍出现 `EXECUTION_INTERRUPTED`，未完成完整新业务验收。开发者应先按本文搭好个人环境，再实际验证新保存与召回；不能只凭连接成功或 `/p3/readyz` 为 200 就认定全部业务通过。具体失败和最终 AKS 回归结果见本次验收报告。

正式 P2 接管接口及 Rust `engine` 继续保留。公开 Azure 服务不接受旧 `current_p2` 装配，也不会在缺少正式适配器时偷偷降级运行。

## 5. 数据库连接、TLS 与数据隔离

### PostgreSQL

DSN 必须保留真实服务域名、显式数据库、账号、密码、`sslmode=verify-full` 和存在的 CA 路径。以 `psycopg.conninfo.make_conninfo` 生成 DSN，避免手工拼接密码。密码从受控私密文件读取，不放命令行或日志。

```python
import json
from pathlib import Path
import certifi
import psycopg
from psycopg.conninfo import make_conninfo

private = json.loads(Path('E:/p3-dev/alice01/private/backend-inputs.json').read_text('utf-8'))
dsn = make_conninfo(
    host='postgresp3.postgres.database.azure.com', port=5432,
    dbname=private['postgres_database'], user=private['postgres_user'],
    password=private['postgres_password'], sslmode='verify-full',
    sslrootcert=certifi.where(), connect_timeout=10,
)
with psycopg.connect(dsn) as connection:
    database, user = connection.execute('SELECT current_database(), current_user').fetchone()
    tls = connection.execute(
        'SELECT ssl, version FROM pg_stat_ssl WHERE pid=pg_backend_pid()'
    ).fetchone()
    print({'database': database, 'user': user, 'tls': tls})
```

若经已分配 PostgreSQL relay 连接，可在 `make_conninfo` 中加 `hostaddr='127.0.0.1', port=<转发端口>`，仍保留 `host='postgresp3.postgres.database.azure.com'` 做证书名称校验。容器里的 CA 路径必须改成容器挂载路径，例如 `/certificates/azure-ca.pem`。

优先给每位开发者分配独立 database。当前 PG 实现通过同库 advisory lock 串行化事务；仅分 schema 能隔离数据，但不能隔离锁竞争，多人同时运行或并行回归会争用同一锁。若暂时只能共用 database，应由维护者安排串行测试。服务配置的 `azure_storage.postgres.schema_name` 必须在启动前创建；本实现的 `search_path` 只含该 schema，缺失时失败，不落入共享 `public`。管理员用正确数据库连接执行 `CREATE SCHEMA <个人schema> AUTHORIZATION <个人role>`，并授予所需权限。保留角色最小权限；不要改共享默认 schema。

### Redis、Milvus 与 Ceph

```python
import certifi
import redis
from pymilvus import MilvusClient

# private 沿用上文读取的外部文件。
cache = redis.Redis(
    host='redisp3.redis.cache.windows.net', port=6380,
    password=private['redis_password'], ssl=True,
    ssl_cert_reqs='required', ssl_check_hostname=True,
    ssl_ca_certs=certifi.where(), socket_timeout=5,
)
print({'redis_ping': cache.ping()})
cache.close()

vectors = MilvusClient(
    uri='https://milvus.internal:19530', secure=True,
    server_name='milvus.internal',
    server_pem_path='E:/p3-dev/alice01/certificates/milvus-ca.crt',
    token=private['milvus_token'], db_name=private['milvus_database'],
)
print({'milvus_collections': vectors.list_collections()})
vectors.close()
```

私网地址只在获准网络或现有 relay 上可达。Redis relay 应保留真实 host 的 DNS/SNI 校验；Milvus relay 应使用真实 `server_name=milvus.internal` 与团队 CA。优先在 AKS 执行以上连接检查，或使用管理员提供的 TLS 透传入口。不要把 `127.0.0.1` 当证书身份，也不要用 `ssl_cert_reqs=none`、不可信证书跳过或明文 Redis 解决连接问题。

本项目已有 `交付成果/部署运行/Azure数据库连接/` 桌面连接成品，可由维护者另行提供给有权限的团队成员；其外部私密配置不能随本文公开分发。本指南的 AKS 测试不依赖该工具，数据库 GUI 连上也不能替代 P3 服务验证。

Ceph 使用 S3 兼容凭据及 RGW endpoint；需要 bucket 已存在、精确前缀内的读写删除权限。`azure_storage.namespace` 驱动 Redis 的 `aether:<namespace>:...`、Ceph 的 `aether/<namespace>/v1/` 和 Milvus 的实际集合绑定。Milvus 实际集合由 namespace/database/logical collection 指纹生成，查看运行的 provider binding 获取实际名称。

| 隔离项 | 每位开发者的示例 | 必须保持的关系 |
|---|---|---|
| PG database / schema | `p3_dev_alice01` / `p3_alice01` | 账号仅访问自己范围 |
| 测试 PG database | `p3_test_alice01` | runner 强制 `p3_test_` 前缀；测试在其中创建/清理独有 schema |
| Azure namespace | `dev-alice01` | Redis/Ceph/Milvus 使用同一环境绑定 |
| Milvus database | `p3_alice01` | 预置 database；有自己的集合创建/删除权限 |
| Ceph bucket | 管理员分配的开发 bucket | 只清自己 namespace 的对象前缀 |
| Temporal namespace | `p3-alice01` | 管理员预置；不要抢其他服务的队列 |
| Temporal deployment_id | `p3-alice01-dev` | 同环境重启保持稳定，换环境必须换绑定 |
| 业务身份 scope | `tenant_alice01` + application/user/agent | 与身份文件和请求授权一致 |

将上述完整模板保存在 deployment 目录外，再初始化新的空目录：


服务密钥保存在仓库外的 `private/service-environment.json`，它是 `AETHER_*` 到实际值的扁平 JSON，包括 `AETHER_POSTGRES_DSN`、`AETHER_REDIS_PASSWORD`、`AETHER_MILVUS_TOKEN`、`AETHER_CEPH_ACCESS_KEY`、`AETHER_CEPH_SECRET_KEY`、`AETHER_LLM_API_KEY`。在 AI 的子进程中加载这个文件到环境，再运行下面命令；不要把密码拼进 PowerShell 参数或复制到成品文档。可把以下启动器保存为外部 `$P3Work/start-p3.py`，确认 `P3_CODE` 与 `P3_WORK` 是自己的实际路径：

```python
import json
import os
import subprocess
import sys
from pathlib import Path

P3_CODE = Path('E:/dev/aether/AgentJYS-main')
P3_WORK = Path('E:/p3-dev/alice01')
values = json.loads((P3_WORK / 'private/service-environment.json').read_text('utf-8'))
required = {
    'AETHER_POSTGRES_DSN', 'AETHER_REDIS_PASSWORD', 'AETHER_MILVUS_TOKEN',
    'AETHER_CEPH_ACCESS_KEY', 'AETHER_CEPH_SECRET_KEY', 'AETHER_LLM_API_KEY',
}
assert required <= values.keys()
assert all(isinstance(k, str) and isinstance(v, str) and v for k, v in values.items())

environment.update(PYTHONDONTWRITEBYTECODE='1', HF_HUB_OFFLINE='1',
                   TIKTOKEN_CACHE_DIR=str(P3_WORK / 'assets-01/tiktoken'))
raise SystemExit(subprocess.call(
    [sys.executable, '-B', '-m', 'aether_agent_memory', 'serve', '--config',
```


```powershell
Invoke-RestMethod http://127.0.0.1:18090/p3/readyz
& $P3Python -B scripts/p3/smoke_service.py --url http://127.0.0.1:18090 --credential-file (Join-Path $P3Work 'private/credential') --timeout 180
```

冒烟写入一条唯一测试记忆，并验证长期化、召回和原结果读取。只对自己的环境运行；该条数据会保留。健康检查通过不代表全部业务或灾备通过。

个人环境的恢复验证应先记录原 `operation_id`、`job_id`、`memory_id`、正文哈希和 Recall 结果 ID，再只重启自己的 P3，保留 PG、Ceph、Temporal 持久文件与 runtime 目录。重启前后保持 `deployment_id`、namespace、task queue 以及已持久化的 `periodic_seconds` 一致。运行中的周期计划拒绝直接换间隔；本次候选验证曾把已绑定的 30 秒改成 60 秒，导致 `/p3/readyz` 返回 503，恢复原间隔后 Worker 与原回执恢复。`request_timeout_seconds` 是请求预算，不能替代周期计划的一致性检查。需要调整周期计划时先制定明确的停用/新环境方案，不直接改共享运行配置。

### 使用 Docker Compose 的开发者

`compose.p3.yaml` 使用相同源码与后端，额外挂载外部 deployment、runtime 和 models 三个目录。先把配置路径转换成容器路径：身份、Recall、Embedding JSON 和公有 CA 位于 `/deployment`，运行目录为 `/runtime`；将已准备的 `model/`、`tiktoken/` 放在挂载的 models 目录内。Embedding 设 `model_path: /models/model`，可写缓存设 `/runtime/embedding-cache`；`HF_HUB_OFFLINE=1` 和 `TIKTOKEN_CACHE_DIR=/models/tiktoken` 作为容器环境变量设置。模型挂载只读，不能把需写入的缓存指向 `/models`。

设置 `AETHER_DEPLOYMENT_DIR`、`AETHER_RUNTIME_DIR`、`AETHER_MODELS_DIR` 三个实际绝对路径，六个服务密钥由上述私密文件传入 Compose 子进程。服务配置必须是 `host: 0.0.0.0`、`port: 8080`、`data_dir: /runtime`，Temporal endpoint 必须从容器可达；Windows 主机的 loopback development CLI 不能直接作为容器的 Temporal 地址。

先执行 `docker compose -p p3-alice01 -f compose.p3.yaml config --quiet`，再只启动自己的 Compose 项目 `docker compose -p p3-alice01 -f compose.p3.yaml up -d --build`。用个人宿主机端口变量 `AETHER_HOST_P3_PORT` 和 `AETHER_HOST_WEB_PORT` 避免占用现有服务。检查 `/p3/readyz`、Worker 与业务后再按原 ID 验证恢复；个人服务停止使用同一 `-p p3-alice01`，保留外部数据，不使用 `down -v` 清持久卷。正式 Compose 入口 `compose.production.yaml` 使用经验证的镜像摘要和 `production` profile。

新环境的 Milvus 集合由第一次投影或查询通过真实适配器创建并校验结构。此前 `/p3/ready` 中 vectors 可以显示 unknown；探针只读，不负责创建集合。先确认 `/p3/readyz` 与 Worker，再执行首次业务冒烟，随后检查完整 `/p3/ready`。缺少集合创建/加载权限时补齐数据面权限，不把 unknown 改成 ready。

HTTP 返回 `400 REQUEST_IN_PROGRESS` 时，保存 `Location`、`X-P3-Job-ID`、原 operation ID，轮询原 job/结果；不要更换 ID 重发原 POST。停止/重启自己的 P3 后，应再次读取同一 operation/recall 结果，并确认 Worker 接回已有任务。

## 8. 部署个人 AKS P3 或准备正式发布

源码模板为 `deploy/azure/p3.yaml`，包含 ClusterIP Service、单副本 Deployment、Secret 注入、探针及模型/运行 PVC。先复制到外部目录，把 namespace 和镜像摘要换成自己的值。生产还需把 profile 改为 production，并同步 `--require-profile production`。单副本 `Recreate` 有更新期间的短时停机；本次未对常驻服务执行该更新。

1. 管理员准备个人 namespace、网络策略、PG database/schema、Milvus database、Ceph bucket/prefix、Temporal namespace，以及 `p3-models`、`p3-runtime` PVC。模型 PVC 预载 BGE、必要分词缓存并给予 UID/GID 1000 可读权限；runtime PVC 可写。PVC 名称在个人 namespace 内独立。
2. 把容器配置改为 `host: 0.0.0.0`、`port: 8080`、`data_dir: /runtime`、`identity_file: /deployment/identities.yaml`、`embedding_config: /deployment/embedding.json`、`recall_config: /deployment/recall.json`。Embedding `model_path=/models/model`、`cache_dir=/runtime/embedding-cache`；模型与分词器只读，runtime 缓存可写。Redis/Milvus CA 位于 `/certificates`，Temporal TLS 位于 `/temporal-tls`。
3. 创建 `p3-configuration` ConfigMap，包含 service.yaml、embedding.json、recall.json、identities.yaml；创建 `p3-public-certificates` ConfigMap，包含 azure-ca.pem、milvus-ca.crt 和所需 Ceph CA。原凭据不进入 ConfigMap。
4. 创建 `p3-runtime` Secret，包含上文六个 `AETHER_*` 值；PG DSN 的 trust root 是 `/certificates/azure-ca.pem`。创建 `p3-temporal-client` Secret 保存 TLS CA/客户端证书/私钥。个人无 TLS 的 development Temporal 可在自己的模板中删去该 Secret volume/mount，或建立无数据的占位 Secret；正式 TLS 配置必须真实存在。
5. 使用个人 AcrPush 身份构建和推送镜像，固定 Git SHA 和镜像摘要；配置 AKS 拉取身份。只在个人 namespace 执行 apply 与 rollout。

示例命令中的路径、namespace 和 SHA 都要替换为已核验值：

```powershell
$P3Namespace = 'aether-p3-alice01'
$P3Deployment = Join-Path $P3Work 'aks-deployment'
$P3Revision = git rev-parse HEAD
$P3Registry = 'aetherp3acr-a0bne7gpetbpdcbq.azurecr.io'
az acr login --name aetherp3acr
docker build -f Dockerfile.p3 -t "$P3Registry/aether/p3:$P3Revision" .
docker push "$P3Registry/aether/p3:$P3Revision"
# 将实际推送摘要填入外部 p3.yaml 的 image。
kubectl --kubeconfig $P3Kubeconfig -n $P3Namespace create configmap p3-configuration `
  --from-file=service.yaml="$P3Deployment/service.yaml" `
  --from-file=embedding.json="$P3Deployment/embedding.json" `
  --from-file=recall.json="$P3Deployment/recall.json" `
  --from-file=identities.yaml="$P3Deployment/identities.yaml"
kubectl --kubeconfig $P3Kubeconfig -n $P3Namespace create configmap p3-public-certificates `
  --from-file=azure-ca.pem="$P3Deployment/certificates/azure-ca.pem" `
  --from-file=milvus-ca.crt="$P3Deployment/certificates/milvus-ca.crt"
kubectl --kubeconfig $P3Kubeconfig -n $P3Namespace create secret generic p3-runtime `
  --from-env-file="$P3Deployment/private/runtime.env"
kubectl --kubeconfig $P3Kubeconfig -n $P3Namespace create secret generic p3-temporal-client `
  --from-file=ca.pem="$P3Deployment/private/temporal-ca.pem" `
  --from-file=client.pem="$P3Deployment/private/temporal-client.pem" `
  --from-file=client.key="$P3Deployment/private/temporal-client.key"
kubectl --kubeconfig $P3Kubeconfig apply --dry-run=server -f "$P3Deployment/p3.yaml"
kubectl --kubeconfig $P3Kubeconfig apply -f "$P3Deployment/p3.yaml"
kubectl --kubeconfig $P3Kubeconfig -n $P3Namespace rollout status deployment/p3 --timeout=300s
kubectl --kubeconfig $P3Kubeconfig -n $P3Namespace port-forward service/p3 18090:8080
```

首次 create 前检查同名资源；后续修改个人资源走受控 apply，不覆盖共享 Secret。不要输出 `kubectl get secret -o yaml`。公网访问另配 HTTPS 网关、Bearer/JWT 和网络策略；Temporal、数据库、维护写接口保持私网。

部署验收依次核对镜像摘要、backend binding、`/p3/readyz`、Worker 心跳、保存→长期化→召回、原操作结果重取、个人服务重启恢复，以及恢复演练。需要回滚个人 Deployment 时可 `kubectl rollout undo deployment/p3 -n <个人namespace>`；数据库/对象的状态兼容和备份由发布方案单独保证，镜像回滚不能自动回滚数据。

## 9. 持久化、备份和恢复

### 正式 Temporal 的镜像与初始化

`deploy/azure/temporal.yaml` 需要同时含 `temporal-server` 和 `temporal` CLI 的镜像，因为 startup/readiness 使用带 TLS 的 `operator cluster health`。模板的 `REPLACE_WITH_REVIEWED_TEMPORAL_SERVER_CLI_IMAGE_DIGEST` 必须替换成实际推送到 ACR 的摘要。仓库已提供 `deploy/vm/Dockerfile.temporal`，固定 Server 和 admin-tools 来源并只复制 CLI；不要直接换成 server-only 镜像。

```powershell
# 在 AgentJYS-main，沿用第 8 节的注册表和已核验 SHA。
$P3TemporalImage = "$P3Registry/aether/temporal:$P3Revision"
docker build -f deploy/vm/Dockerfile.temporal -t $P3TemporalImage .
docker run --rm --entrypoint /bin/sh $P3TemporalImage -ec 'command -v temporal-server; temporal --version'
docker push $P3TemporalImage
# 将 push 返回的 sha256 摘要填入仓库外 temporal.yaml，再做 server dry-run。
```

管理员先准备实际 namespace、`p3-temporal-database` Secret、`p3-azure-ca` ConfigMap、`p3-temporal-config` Secret 和 `p3-temporal-server-tls` Secret。数据库 Secret 包含 `SQL_HOST`、`SQL_USER`、`SQL_PASSWORD`，密码通过文件或 stdin 注入；服务器配置、客户端证书和 CA 的 SAN/SNI 必须匹配实际私网服务名。`p3-temporal-initialization` ConfigMap 应由当前 `deploy/azure/initialize-temporal.sh` 创建。脚本按字面密码脱敏并保留 SQL 失败退出码，禁止把 Secret 展开在命令参数。

schema Job 模板默认 `P3_SCHEMA_MODE=upgrade`，仅用于已经安装过 Temporal schema 的目标。完全新环境由管理员先创建 `agent` 库内的 `p3_temporal` 和 `p3_temporal_visibility` schema，将仓库外 Job 中的模式改为 `initialize`，再安装/升级。已存在环境不得重复 initialize，不使用 create/drop-database。`BTREE_GIN` 扩展 allowlist、schema 安装授权、TLS Secret 与正式服务的可达性均须先补齐；本次没有对现有演示 Temporal 执行此切换。

旧 SQLite 数据不迁移。新环境需要对 **新产生的 PostgreSQL 数据**保留离线 `pg_dump`/`pg_restore` 能力，并在独立目标 database/schema 做恢复演练。连接参数与密码通过受控环境或 `PGPASSFILE` 注入，不放 shell 参数；保留 verify-full TLS。

P3 在线维护接口不能直接用旧 SQLite 文件覆盖正在运行的 PG：备份/恢复请求会明确返回契约拒绝。验证该拒绝和数据不变只是安全边界，不能替代实际 PG 恢复演练。

完整灾备还需同步 Ceph 对象版本、Milvus 投影或重新构建方案、正式 Temporal persistence、身份/JWT 配置、模型绑定和必要 runtime anchor。Redis 是热副本，不能当正文备份。先在独立环境恢复并核对原 operation/recall ID、版本与授权，确认后再计划正式切换；不对常驻共享库执行 DROP、TRUNCATE、flushdb 或全 bucket 清空。

### 已知超时的诊断约束

本次本机候选的同一原保存 job 在 commit 与 admit_cache 路径出现 30 秒 StartToClose 超时，也出现 10 秒 heartbeat 超时；最后仍需人工处理。只读对比中，同一 Azure PostgreSQL 的简单 `SELECT 1` 在候选容器经 relay 约 75–82 毫秒，在 AKS 直连约 1 毫秒；这说明访问开销不同，但没有证明 relay 是唯一根因。应比较阶段、事务与日志等待，保留已有授权、版本和提交 guard，完成回归后才关闭该问题。`request_timeout_seconds` 是 HTTP/请求预算，`StageRegistry` 的阶段预算独立；单纯调大前者不能解决该失败，也不能成为验收证据。未知写入只查询和处理原 job，不换 operation ID 再提交相同意图。

最终应交付自己的 `service.yaml`（无原凭据）、身份配置、可执行的启动/测试命令、部署绑定与测试结果摘要。私密文件仅存受控外部目录；原始日志留外部供追溯。本文中的占位值不是有效账号，不能直接当作完成配置。
