## 恢复内容与隔离方式

若依已接管原 P3 数据卷、数据库 schema、对象及向量命名空间和 Temporal 执行绑定。因此没有直接将旧 worker 启动到原状态上，而是恢复了独立副本。

| 层次 | 旧系统现在使用 | 若依侧处理 |
|---|---|---|
| HTTPS 网关 | 新增 `legacy-public-web`，独立公网 IP、域名和证书卷 | 保留 `public-web` 的配置与运行 Pod |
| 网页、身份与后台 | 恢复 `aether-platform`、`aether-keycloak`、`aether-budibase` | 保留 `aether-ruoyi-*` |
| 平台数据库 | 恢复原 `aether-platform-db` 与原持久数据；更新旧域名对应 issuer | 若依继续使用自己的平台数据库 |
| P3 文件 | 新卷 `aether-legacy-p3-data`，复制旧源码、依赖、模型和必要配置 | 原 `aether-agent-p3` 卷继续由若依 P3 使用 |
| P3 PostgreSQL | 独立数据库 `aether_legacy_20261006`，从接管后原 schema 取得一致性快照 | 原业务数据库只读作为复制源 |
| Ceph 与 Redis | 命名空间 `aether-legacy-20261006`；Ceph 对象复制到独立前缀，Redis 使用独立键空间 | 保留原命名空间 |
| Milvus | 独立集合，保留同一嵌入模型与向量维度 | 原集合只读作为复制源 |
| Temporal | 新增 `legacy-temporal`，使用独立卷及 SQLite 在线一致性备份 | 原 `temporal` 服务保持运行 |
| 工作流身份 | 在独立 Temporal 服务中保留原 namespace、workflow ID 和执行绑定 | 两个 worker 不连接同一个 Temporal 服务 |
| 运维页面 | `temporal-ui` 指向 `legacy-temporal`，通过旧平台管理员身份鉴权 | 若依管理入口保持原样 |

旧平台的会话和目录来自其保留数据库；旧 P3 的记忆及任务状态来自本次复制时的状态，包含若依接管后已经写入的历史。恢复后，两套系统继续各自写入，**不会自动双向同步**。

复制源和目标经过显式区分。对象、向量与身份绑定仅在旧副本中迁移；未通过修改任务终态来制造成功。旧系统保留原应用打包方式，即基础镜像加持久卷内校验后的应用文件，本次未重新构建旧版本应用镜像。

## 运行边界与后续维护

- 两套应用共享 AKS 与部分云基础服务，但使用隔离的数据库、数据前缀、集合和工作流服务。不同数据库并不代表不同 PostgreSQL 服务器；本次没有为所有基础设施建立独立物理集群。
- 新增一个公网 IP、三个持久卷（声明容量合计 31 GiB）、独立数据库与存储副本，并恢复旧工作负载，会增加资源用量；具体费用以 Azure 账单为准。本账号没有节点级指标权限，本次未作容量或负载验收。
- 此次验证了实际登录、权限、历史读取及一条新业务保存/召回闭环。没有重放验收全部历史任务，没有进行全链路负载、长稳或 HA 测试；各存储的一致性副本不等于跨所有存储的统一时间点灾备验收。
- 旧平台的登录会话仍在进程内，重启后需重新登录。Temporal 延续开发服务加持久卷的原部署形态，不应视为生产高可用。
- 若要停用本次恢复，先处理旧系统正在执行的任务，再停用旧应用和独立旧网关；保留新卷和数据库供恢复。**不得将 `aether-agent-p3` 的卷重新指回若依正在使用的原卷，也不得套用旧整体网关清单覆盖 `public-web`。**
- 后续发布若依时保留本报告列出的旧资源；更新旧系统时只操作旧服务与 `legacy-*`，不重跑旧迁移生成器覆盖现有目录或云资源。
