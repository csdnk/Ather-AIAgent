## 4. Temporal 的数据库处理边界

现有 `agent.p3_temporal` 主 schema 已到 `1.19`，`p3_temporal_visibility` 已到 `1.1`。解除扩展限制后执行 **upgrade**，保留已完成结构和数据，不重新 initialize，不新建数据库。仓库续跑 Job 已改为 `p3-temporal-schema-upgrade-1-32-0` 与 `P3_SCHEMA_MODE=upgrade`。

Azure 参数允许扩展与数据库内 `CREATE EXTENSION` 是两个动作。当前已保存的数据库管理员凭据用于必要结构升级；若组织改为管理员代执行，请其在 `agent` 内按 Temporal visibility 的既有 `search_path` 安装 `btree_gin`，核对扩展所属 schema。运行时 `p3_temporal_runtime` 保持普通应用角色，不需要超级用户、建库或建角色权限。参数本轮报告为动态配置，无需主动重启 PostgreSQL；若 Azure 保存操作返回具体待重启要求，再按实际结果处理。

## 6. 管理员完成后的核验顺序

1. 读回扩展允许列表及账号有效权限，核对目标 VM 与实际 FQDN。
2. 从 VM 核验主机指纹、cloud-init、私有 DNS 和四个既有存储的认证连接。
3. 按现有进度完成 Temporal schema 升级，启动持久化 Temporal 和 mTLS，验证 namespace、历史与重启。
4. 构建包含本轮修正的最终镜像，核对摘要和配置，再加载离线包，启动 P3、网页和 HTTPS。
5. 使用正式服务账号验证记忆写入、异步 ready、召回、更正、删除、恢复和权限撤销；形成最终部署验收。

管理员只需反馈“BTREE_GIN 已保存，VM 已创建”或“资源组 Contributor 已授予”。名称不同时附上订阅、资源组、VM 名称、实际域名即可。资源创建成功与最终应用上线分别核验。
