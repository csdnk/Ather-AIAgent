# 任务处置闭环设计与实施计划

目标：运维无需编写代码即可从调度异常进入关联工单，认领、检查、记录处理、执行被授权的任务控制、核验并关闭；恢复整体运行图表。

实现复用 Vue、Python 运维服务、PostgreSQL 和既有 Java 网关。用户已要求直接实施，不再逐项请求设计批准。

## 设计

- 历史任务统计与处置工单统计分开。恢复排队/运行/恢复/重试卡片和两张总览图，保留异常清单和 8 行队列。
- 独立 ops_task_cases 记录以任务编号唯一关联，保存原始作用域、诊断快照、负责人、状态、处置方案、核验及追加式时间线。复用 support 资源权限和命令审计，不修改旧工单。
- 状态：待认领、处理中、转研发、待核验、已核验、已关闭；支持重新打开。并发认领和更新使用版本校验；不同任务不能共用同一工单。
- 可执行操作：重新检查原任务/执行器与用户启用状态；正在运行的任务提交取消或核对原执行；处理记录、转研发、关联后续成功任务、人工结案和重新打开。
- 外部控制先持久保存原操作编号，超时只查询原操作，不发第二个控制。取消或核对受额外 tasks:execute 权限限制，禁止用工单权限绕过。
- 已结束任务不直接重写终态或复制输入。完成闭环有三种明确结果：原任务后来成功、同作用域同业务的后续任务成功、负责人明确核对后无需继续执行（人工结案，不宣称业务成功）。结果未知时不允许人工结案。
- 核验由服务端读取原任务及后续任务，检查状态、业务回执、工作流及作用域；关闭前再检查版本和核验时效。人工结案需另一名有权限的管理员复核。
- 不创建任意命令执行入口，不自动扩大权限或重启共享基础服务。缺少具体失败步骤时明确显示缺少证据。
