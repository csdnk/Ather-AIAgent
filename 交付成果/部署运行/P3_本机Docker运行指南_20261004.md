在 Windows PowerShell 中运行：

```powershell
# 启动 Docker Desktop，选择 Linux containers，然后启动本套服务。
& 'E:/projects/codex/aether/交付成果/部署运行/P3_本机Docker.ps1' -Action Start

# 查看容器和 P3 就绪状态。
& 'E:/projects/codex/aether/交付成果/部署运行/P3_本机Docker.ps1' -Action Status

# 实际认证连接 PG/Redis/Milvus/Ceph，并发送真实模型请求。
& 'E:/projects/codex/aether/交付成果/部署运行/P3_本机Docker.ps1' -Action Verify

# 把控制台 operator 凭据复制到剪贴板，再在页面的凭据框粘贴。
& 'E:/projects/codex/aether/交付成果/部署运行/P3_本机Docker.ps1' -Action CopyCredential

# 需要通过 API 提交业务时，复制 application 凭据。
& 'E:/projects/codex/aether/交付成果/部署运行/P3_本机Docker.ps1' -Action CopyCredential -Principal p3_application

# 只停止本套容器和本套 Azure 转发，保留数据。
& 'E:/projects/codex/aether/交付成果/部署运行/P3_本机Docker.ps1' -Action Stop
```

`Start` 会按依赖顺序启动，包含 schema 检查和容器健康等待，冷启动需要时间；最终以 `Status` 和 `Verify` 为准。`Verify` 现在验证 P3 就绪和真实依赖认证，不执行演示场景、更正或删除业务数据。模型探测会使用少量真实 Azure OpenAI tokens。业务调用使用 `p3_application` 凭据，诊断和任务页面使用 `p3_operator`。P4 使用独立 `p4_demo` 服务端身份，演示页不需要粘贴 token。脚本复制凭据，不在终端显示 token。

## Azure 连接与持久化

本机 P3 通过专用 AKS relay 访问 Azure 私有资源。脚本启动隐藏的转发维护进程，使用本机端口 55432 / 56380 / 59530，并在断线后重连。原有数据库连接通道保持独立，不由本脚本停止。

这套系统仍需要网络、有效的 kubeconfig、Azure 资源可用和专用 relay。已经出现过真实 relay 断线并自动恢复；断线期间就绪状态和业务请求可能失败。Docker 容器健康与后端连续可用需要分别判断。

`Stop` 停止容器和专用转发，保留 Temporal/P3 volumes 和 Azure 数据。已实际执行本脚本 Stop → Start，确认包括 PostgreSQL 在内全部恢复，原回执和 68 条 Temporal 历史事件保持一致。不要执行删除 volume 的命令；容器重建和数据清空是不同动作。工作流任务已被接收后应保留原 job ID，通过 `/p3/operations/{job_id}` 和 `/result` 查询，不把重新提交当作恢复。

## 本机、Azure VM 与 AKS Pod 的区别

| 项目 | 本机 Docker | Azure VM 上 Docker | AKS Pod |
|---|---|---|---|
| 应用镜像 | 当前 Linux 镜像 | 可以使用同一架构、同一摘要的镜像 | 可以使用同一架构、同一摘要的镜像 |
| 应用代码与依赖 | 由镜像提供 | 由镜像提供 | 由镜像提供 |
| 容器宿主 | Windows 上 Docker Desktop 的 Linux 虚拟环境 | Azure Linux VM | AKS Linux 节点 |
| 私有资源网络 | 当前经过桌面 relay | 配置 VNet、DNS、路由后从 VM 实际认证连接 | 配置 Service、DNS、网络规则和身份后实际连接 |
| 数据保留 | 本机 named volume / Azure 数据 | 磁盘、volume 或远程存储 | PVC / Azure 数据；Pod 文件系统不能作为持久化方案 |
| 配置与凭据 | 当前本机私密配置 | 文件权限、部署配置及所选身份方案 | Secret / ConfigMap 及所选工作负载身份方案 |
| 监督和恢复 | Docker 重启策略；电脑关机、休眠会停服务 | Docker/systemd；仍需监测和运维 | Deployment、readiness、liveness；仍需业务恢复验证 |
| 多实例与高可用 | 未验收 | 单 VM 不等于高可用 | Pod 可调度或扩容不等于应用已经支持多实例/高可用 |

可以复用镜像，但要重新验证部署环境。当前本机使用本地 PostgreSQL 为 Temporal 持久化，Azure 正式 Temporal 仍受 `BTREE_GIN` 参数权限阻塞。完成本机验证不会替代这项配置。

Pod 是 Kubernetes 的部署单位，可以运行兼容的容器镜像；AKS 节点通常由 containerd 等容器运行时启动镜像，无需在 Pod 内安装 Docker。应用代码可以相同，但 Compose 的依赖顺序、volume、端口和重启配置需要转换为目标 Kubernetes 资源并验证。

## P4 演示与等待时间

打开五场景演示页，选择故事并点击“开始演示”。页面展示真实保存、任务等待、召回内容、来源与检查结果。每轮使用独立数据范围；故事设定是固定演示输入，返回结果取自当前真实 P3。注册与登录账号服务仍未启用，不影响服务端身份执行五场景演示。

按用户“先跑通、时限长一点”的要求，P4 每步观察任务最多 30 分钟；网页观察原运行最多 2 小时；单次网页请求最多 60 秒，代理最多 65 秒。P3 每项依赖预检最多 60 秒，健康证据保留 60 秒后需要刷新。超时不会取消已受理任务或自动重发写入；可用“重新查询”核对同一 run ID。

P4 等待时间只控制观察。P3 的业务 job 自身仍有执行 deadline，实际业务失败、权限失败、结果不满足检查仍会明确停止，不会因为延长等待而变成通过。当前仅允许本机网页 Origin；不能把该本地代理配置直接开放到公网。
