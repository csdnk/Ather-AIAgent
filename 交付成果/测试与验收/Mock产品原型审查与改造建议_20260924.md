# Mock 产品原型审查与改造建议

日期：2026-09-24。对象：当前 `交付成果/原型Mock/index.html` 及其平台脚本。用途：判断它能否支持业务理解和产品评审，提出可执行的改造要求。

## 1. 审查结论

**当前 Mock 不宜作为无需讲解即可使用的业务评审主入口。它已经形成了可操作的工程行为模拟器，但业务任务、调用者边界、操作反馈和评审判定没有组织好。问题需要调整信息结构与交互，不是增加几段说明或更换配色就能解决。**

本次确认 8 项问题：5 项 P1（应在下一次业务评审前处理），3 项 P2（随交互重构处理）。这是针对产品原型用途的审查判断，不是对真实 P3 后端的缺陷判定，也不是甲方正式验收结论。

已有模拟并非没有价值：保存与长期就绪分离、来源和版本、四类召回结果、租户与撤权、异常和恢复等规则值得保留。现有页面也明确标注模拟，部分技术对象已折叠。主要问题在于这些材料没有形成易理解、可验证的产品体验。

- 浏览器独立标签页实查工作台、S01 前两步及身份扰动后的首步、召回表单与三组查询；查看首页实际布局。

- 核对当前完整流程图 SHA-256 为 `fb1e66847adbce9ccd518d45fd98e76245643d9d977d8bb6f09714cae35ba020`，与已有一致性报告及覆盖清单的图版本相同。本次未重新穷举图中所有节点。

## 2. Mock 到底是做什么的

“Mock”在工程讨论中常被笼统使用，需要先说明交付物的用途。

| 名称 | 主要验证什么 | 对本项目的意义 |
|---|---|---|
| 线框图 Wireframe | 页面结构、信息顺序、任务路径 | 先判断用户从哪里开始、需要哪些信息、到哪里结束 |
| 视觉稿 Mockup | 产品外观、布局、字体、颜色 | 判断呈现方式，静态图本身不能证明操作流程成立 |
| 交互原型 Prototype | 用户采取行动后，产品如何响应；流程能否理解、完成 | 本项目用于产品评审的主要目标 |
| 工程 Mock / 模拟数据与行为 | 用可控替身表达接口或服务在某种条件下的行为 | 支撑无真实后端时的演示和规则检查 |

Figma 将 Mockup 描述为聚焦视觉形式的静态表现；GOV.UK 的原型指南则强调在正式建设前探索、分享和测试设计，可以从纸笔草图到可交互代码原型。采用 HTML/JS 做原型完全合理。我们需要的是以可控模拟支撑的服务交互原型，不能仅以“页面漂亮”或“模拟步骤很多”判断是否合格。[R1][R2]

NN/g 的任务测试指南要求先确定用户目标，设置真实情境，让参与者实际完成动作，观察其困难；如果测试者事先被告知所有点击步骤，就无法充分验证入口与文案是否易懂。[R3] 这不禁止演示向导，但需要把“讲解演示”和“独立完成任务的测试”分开。

## 3. P3 原型应遵循什么边界

PRD V1.3 第 3.1 节明确：接入团队直接接入 P3，应用或 Agent 发起请求，终端业务用户通过上层应用间接使用记忆；P3 不承担聊天界面、Agent 任务规划和业务审批。

第 6.1—6.2 节明确：对外是 Remember 与统一 Recall，内部调度由历史轨迹和当前状态驱动，无需接入方另发调度请求。第 8.1、8.4 节进一步说明，这些能力通过接口完成，不代表必须新增独立管理页面。

因此，原型应清楚展示：**示例应用/调用方发起什么请求 → P3 返回什么结果 → 调用方如何继续 → 必要时展开内部原因。** 上层应用外壳可以用于演示，并须标明示例；不能把外壳当作 P3 本期新增交付功能。

平台式布局是合理的呈现选项，之前也有平台风格参考。问题不在侧栏和卡片本身，而在界面没有持续交代当前是谁、在模拟哪一层、这次操作为何发生。

## 4. 问题清单

### M01 / P1：原型定位和调用者边界表达不足

**证据 MA24-01：**首页是“企业知识空间 / 记忆服务工作台”，身份是“公司 A · 项目 Agent”，操作却由人点击保存、查看后台任务及切换运行视角。页面没有先建立一个具体任务及应用—P3 的交接关系。边界说明存在，但需要用户主动打开或进入接入页面。

**影响：**评审者容易把演示台理解为 P3 正式管理产品，也不容易判断自己正在扮演业务用户、接入开发者还是模拟控制者。

**改法：**首页明确“P3 服务行为演示”，先选择一个业务任务；操作区标明“示例调用方”，返回区标明“P3 返回”，内部诊断单独展开。保留平台风格，重新组织身份和任务关系。

### M02 / P1：完整主线过载，场景执行替代了业务操作

**证据 MA24-02：**S01 共 20 步，混合保存、即时使用、后台加工、长期读取、共享、越权删除、更正、在途撤权、快照、停用、恢复和检测。首步通过 `m.remember()` 保存预置内容；用户点击“执行下一步”，并未在这一页提交可见的业务输入。首步返回主要是保存状态，没有同步展示本次保存的预算正文。

**影响：**用户很难把自己的动作、输入内容和系统变化连在一起。讲解者虽能顺序推进，观看者仍可能不知道刚才究竟做了什么。完整性应由所有场景共同保障，不宜把所有边界塞进入门主线。

**改法：**拆成“保存并使用”“跨会话复用”“更正后再次使用”三个短任务，再展开共享、删除及故障专题。每个任务都有情境、可见输入、实际操作、结果及结束条件。保留全部需求覆盖材料作为进阶评审入口。

### M03 / P1：自然语言输入的外观与模拟能力不匹配

**证据 MA24-03：**在共享工作区、公司 A 项目 Agent、自动来源、K=3、预算 600 的相同条件下：

| 输入 | 实际浏览器结果 |
|---|---|
| 明天天气怎么样？ | 正常为空 |
| 我们最多能花多少钱？ | 正常为空；提示没有合格的相关内容 |
| 项目预算 | 完整可用；返回 20 万元预算等三条内容 |

源码 `platform-model.js:81` 使用字符串及相邻双字匹配；第 85 行的模拟分数按候选遍历顺序生成。页面虽然提示“确定性模拟”，但不解释支持哪些问法，输入框又呈现为可自由提问的体验。

**影响：**有相关预算资料却因问法变化显示“正常为空”，会把模拟器表达能力的限制误传为产品的检索行为，妨碍评审者判断需求。

**改法：**先为受支持的业务任务提供可编辑样例和明确的问法范围；任务内支持必要的同义表达。无法解释的输入显示“该输入超出本演示支持范围”，并提供样例入口。只有确定无相关样例时才演示“正常为空”。无需为修复原型立即接入真实模型。

### M04 / P1：脚本前置条件被改变后，仍可继续既定主线

**证据 MA24-04：**重置 S01 → 将身份改成“已认证 · 未开通” → 执行第一步。实际返回 `TENANT_NOT_BOUND`、保存被拒绝；进度仍变为 1/20，“A1保存项目约束”显示勾号和“已执行”，下一步仍是“立即使用当前记忆”。

场景执行器 `platform-app.js:59` 在调用动作后直接递增游标；没有对这一具体步骤的预期结果进行判定。界面写的是“已执行”，并非明说“通过”，但它继续推进依赖保存成功的剧情，也没有提示场景已经偏离。

**影响：**既不适合作为可自由探索的任务，也不能单凭执行计数作为流程符合预期的证据。

**改法：**明确“引导演示”和“自由试用”的边界。引导演示每步校验身份、前置状态与预期结果，偏离时停止并给出恢复入口；自由试用允许变化，但按实际状态给出后续操作。判定需支持“预期拒绝”，不能把所有失败码一律当测试失败。

### M05 / P2：步骤标题与结果缺少明确的时间对应

**证据 MA24-05：**S01 执行第一步后，大标题变成“立即使用当前记忆”，下方“本步结果”仍是上一操作的“已保存”。执行第二步后，大标题变成“后台加工并核验长期资格”，下方结果却是刚刚召回得到的“完整可用”。

源码中标题读取 `steps[cursor]`，结果读取最后一次操作 `model.last`；大标题没有“下一步”前缀，结果卡也没有已执行操作名称。

**影响：**用户必须自行推断标题与结果不属于同一次操作，容易误解后台加工或保存的真实完成状态。

**改法：**固定显示“刚刚执行：操作名 / 输入 / 结果”，另设“接下来：操作名”。执行后先展示当前动作结果，由用户再进入下一步。

### M06 / P2：业务界面过早要求理解内部机制

**证据 MA24-06：**召回首屏同时展示来源、调用方式、K、字符预算、正文表示、任务范围，以及“在最终交付前暂停”的竞态测试开关。首页展示任务号、Ready、Context；记忆详情提供“加工与索引核验”。

**影响：**调用参数、业务概念、内部加工与测试控制同层出现，用户需要先学工程概念才能理解核心价值。手动推进加工没有充分体现这是演示控制，也容易让人误以为业务调用者必须管理后台顺序。

**改法：**业务任务默认只展示当前身份/范围、输入和结果；接入参数放入“调用参数”；加工过程用可观察状态表达；模拟推进、故障注入、暂停交付放入独立演示控制区。高级工程用途继续保留。

### M07 / P2：结果缺少任务内的持久回看与对照

**证据 MA24-07：**S01 的已执行步骤呈现为勾号和标题，没有逐步结果回看按钮；中心“本步结果”只渲染最后一次操作。检查细节需要进入记忆、召回、运行或追踪页面。历史结果和追踪能力存在，但没有直接绑定为主线中每一步的业务回顾。

**影响：**更正前后的 20 万元与 15 万元、撤权前后可读与不可读，很难在原任务内直接比较。用户需要记住前面的内容和对象编号。

**改法：**保留任务时间线：每次输入、操作、结果和原因均可回看；更正、删除、授权变化提供明确的前后对照。进阶 Trace 作为附加证据，不替代业务结果解释。

### M08 / P1：已有验收没有证明业务原型易懂、可用

**证据 MA24-08：**2026-09-22 报告的证据重点是模型测试、页面导航、23 个专题和 161 步执行、表单、身份、响应式及链接检查；报告也已说明是模拟冒烟检查。当前材料没有证明目标评审者在不被告知点击顺序时能够完成任务、解释结果及识别 P3 的范围。

**影响：**这些检查可以证明部分实现和规则，但不能据此得出“业务演示已经合格”。此前用页面数、专题数和测试数说明完成程度，未充分回答用户是否看懂。

**改法：**保留工程回归，新增业务任务与理解度验证。每次记录是否独立完成、何处停顿、需要什么提示、如何解释结果、是否误认产品范围。实际结果形成证据后，再更新原型验收结论。

## 5. 推荐制作与改造顺序

### 第一步：从需求推导任务，再决定页面

按“PRD 产品目标及约束 → 业务情境 → 调用者动作 → 可观察结果 → 状态/异常 → 页面与操作”建立对应关系。流程图用于检查后台交接及分支；原型负责让评审者看到这些规则对任务结果的影响。

先做低细节线框，确认以下三个任务可以独立完成，再投入视觉细化：

| 任务 | 可见情境和动作 | 必须看懂的结果 | 需求关联 |
|---|---|---|---|
| 保存并使用当前约束 | 应用提交“预算20万元”，随后查询预算 | 内容已保存、来源明确；适用当前记忆立即可用，长期状态另列 | FR01、FR02、FR07、FR08、FR10 |
| 在新会话复用历史 | 明确切换到新会话，再由应用查询已加工历史 | 返回历史正文与来源；用户知道为何可以跨会话取得 | FR07、FR08、FR10 |
| 更正后重新取用 | 指定原预算，改成15万元，再查询并回看旧结果 | 新结果采用有效版本；旧结果为何失效得到解释 | FR05、FR11、FR15 |

### 第二步：把同一任务串成连续交互

每个任务固定呈现“当前情境—本次输入—P3结果—调用方下一步”。示例应用若呈现最终答案，要标清为应用侧样例；P3 正式交付仍是记忆材料、来源和状态。

正常主线通过后，再加入无记忆、处理中、来源故障、预算不足、更正、删除、共享/撤权等分支。保持当前可信规则，不用简化界面为由删除异常需求。

### 第三步：修复模拟器与场景执行器

明确自由输入范围；修复 M03 的不支持输入与正常空混淆；给引导步骤增加输入、预期、实际和偏离说明；持久保留步骤回顾；把系统自动动作与演示推进控件分开表达。

已有 23 个专题及规则模型可保留为“完整需求评审”层。无需把全部工程材料挤进入门任务，也无需推倒全部模型重写。

### 第四步：完成两类验收

**工程行为检查：**既有规则回归继续有效，新增场景前置条件与预期核验；页面结果必须与当前模型一致。

**业务可用性检查：**让未参与实现的目标评审者仅根据任务描述操作，不预先告诉点击顺序；引导演示可以随后提供，但其完成情况单独记录。[R3]

以下为建议验收条目，尚未执行，也不是已约定的合同指标：

| 编号 | 给参与者的任务或问题 | 验证标准 |
|---|---|---|
| UX01 | “让助手记住预算20万元，并在下一次使用时取出。” | 能完成输入和取用，指出返回的正文及来源；记录提示次数 |
| UX02 | “预算改为15万元，确认之后不会继续使用旧值。” | 能找到更正对象，区分新旧版本并解释当前结果 |
| UX03 | “在另一次会话里使用以前保存的约束。” | 能区分会话、当前信息和长期历史；不能只靠页面文字宣称已经跨会话 |
| UX04 | “换一种说法询问同一个预算问题。” | 受支持同义问法一致；超出模拟范围时明确说明，不能误报业务空结果 |
| UX05 | “观察共享被撤销之后会发生什么。” | 能解释新请求、在途交付与旧结果的不同检查点；进阶任务单独开展 |
| UX06 | “保存被拒绝后，接下来该怎么办？” | 展示实际失败及可行下一步，不推进依赖保存成功的剧情 |
| UX07 | “哪些界面是示例调用方，P3交付什么？” | 能区分上层应用、P3服务、内部自动处理及演示控制 |
