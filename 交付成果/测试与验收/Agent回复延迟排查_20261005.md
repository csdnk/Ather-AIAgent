# Agent 回复延迟排查

2026-10-05；本次只读取证，没有修改业务代码、服务配置或 Azure 资源。

后续实施更新：本报告保留的是优化前的诊断记录。首字优化已实施并更新测试环境，当前结果见 [Agent 首字优化实施与验收](Agent首字优化实施与验收_20261005.md)，不要把下述旧链路当作最新运行行为。

## 结论

主要延迟来自 P3 启动调度缺少公平性，以及 Agent 将记忆保存纳入回复发布前置条件。已将持久化任务创建时间、启动意图哈希键和 Temporal 实际启动历史关联：待启动任务按哈希键排序，后提交、键值较小的后台评估任务反复先于聊天保存任务启动。每轮调度的 2 秒处理预算和后台循环的 5 秒等待进一步放大积压下的延迟。本机 localhost 认证连接延迟、逐次登录校验、串行来源读取和非流式输出也增加等待。

## 已确认的排队机制

PostgreSQL 的 pending_intent_rows 使用 ORDER BY key 读取待启动意图；key 是哈希编号，不代表提交先后。IntentBridge 在同一个锁内串行转交任务，每轮最多读取 100 条并按 2 秒时间预算停止继续处理，后台协调循环配置等待 5 秒。其 start/control 轮换不区分用户交互和后台评估，没有基于创建时间的公平性保证。

两个慢保存任务的意图键分别以 e53 和 f33 开头。L07/L08 证明，在它们等待期间，后提交的较小键值后台评估任务持续越过它们。这里的 82/127 是等待期间其他工作流的启动数量，不是提交瞬间的队列长度；38/48 才是其中确认后提交先启动的数量。

Temporal 历史显示，工作流创建后，工作流任务通常在约 0.04–0.3 秒内开始，两个保存工作流本身仅执行约 4.4 秒。主要长等待发生在 P3 向 Temporal 转交启动请求之前。已核对相关线上源码与工作树一致；目标启动意图未记录错误，没有证据支持将这两次长等待归因于 Temporal RPC 重试退避。每轮内部数据库与 RPC 的精确耗时占比尚未单独测量。

## 当前调用结构

登录身份校验 → P3 召回 → 结果复核 → 最多 3 个来源逐个读取 → 再复核 → LLM 非流式生成 → P3 复核 → P3 保存并等待 → 最终复核 → 发布整条回复。

每次 P3 调用/结果轮询通过 SessionTokens 获取实时令牌，并执行身份版本检查与远端 introspection。当前认证 HTTP 客户端每次新建 localhost 连接，重复付出约 2 秒开销。前端轮询也需要认证，可能与同一会话的后端令牌锁竞争。

## 建议处理顺序

1. 让 LLM 答案在必要来源有效性校验后发布，记忆保存使用持久化异步任务和独立状态；保存失败可恢复，不丢弃已生成答案，也不把未保存显示成已保存。
2. 修复受理到 Temporal 启动的长间隔：以创建时间和稳定次序实现先到先处理，并结合任务类别配额或等待时间提升优先级，防止后台任务和交互任务互相饿死；交互请求到达时及时唤醒调度器。保留有界处理及恢复语义，补受理、转交、启动和完成的阶段耗时。在相同后台负载下验证启动等待的 p95 与最大值，不只测空队列。
3. 优化内部认证连接：在保持 issuer、签名、受众及撤销检查的情况下使用正确本机连接地址/连接复用，避免反复付出 localhost 连接延迟。不能通过关闭鉴权提速。
4. 加流式输出和明确的检索/生成/保存阶段状态；将安全上允许独立执行的来源读取并行化。
5. 超时保留操作编号并查询原任务状态，避免用户反复重试生成重复流程。当前 P3 任务后来成功而聊天仍失败，是需要修复的状态衔接缺口。

仅把 240 秒超时调大不能解决这些问题。当前证据支持瓶颈位于 Agent 串行编排和 P3 启动调度交界处；尚无证据表明需要扩容 VM 或更换 LLM 才能解决主要等待。
