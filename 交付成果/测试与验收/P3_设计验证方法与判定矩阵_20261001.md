# P3 设计验证方法与判定矩阵

日期：2026-10-01。用途：公司评审、测试准备与证据汇报。本文依据 PRD V1.4、总体 ADR、已有工程验收和 AKS 部署记录，提出验证方法；本次没有新增执行质量、性能、长稳或故障实验，也没有代填公司批准与签收。

## 公司问“设计验证了吗”，应回答什么

需要分别回答三件事：设计机制是否按规则工作；方案是否在目标场景和负载下带来预期价值；候选系统是否达到双方约定的交付条件。自动化测试数量、服务启动和界面演示都只能支持其中一部分。

每个设计结论使用同一条证据链：

**设计主张 → 对应需求与风险 → 场景/对照 → 预先约定的通过条件 → 实际结果 → 证据 → 结论与适用范围。**

例如，“保存与向量化分开”需要证明正文先可靠保存、向量故障不丢待办、未就绪不误报可召回，还需测保存响应时间与索引就绪等待时间，判断这个权衡是否满足业务。证明代码走了异步分支，还不能证明用户体验已经合格。

总体 ADR 当前仍为 Proposed，待联合评审。设计验证证据可供评审采用，但不自动将设计状态变为批准。

总体 ADR 的框架选型表仍有 Temporal 暂缓接入的历史表述，与2026-09-30实际接入结果不同。当前执行后端以最新Temporal设计/验收及AKS记录为准；本次不以旧选型文字否定现有实现，也不替公司批准该设计。

## 四类验证

| 类别 | 要回答的问题 | 验证方式 | 能形成的结论 |
|---|---|---|---|
| 机制与正确性 | 规则是否成立？ | 单元、契约、端到端、边界和竞争场景 | 在明确环境和场景内满足规则 |
| 故障与可靠性 | 出错后是否仍守住规则、能否恢复？ | 精确故障点、回报丢失、重复/乱序、重启和恢复 | 对指定故障的恢复能力及恢复时间 |
| 质量与方案收益 | 为什么选择这一方案，收益多大、代价是什么？ | 同数据、同硬件、同模型、同负载的对照测量 | 达到目标质量或有可复现的收益 |
| 集成与业务验收 | 在公司的真实系统中是否可用、能否交付？ | 真 P2/LLM/身份、部署、负载、备份恢复、公司 UAT | 对候选版本和约定范围给出验收结论 |

不必对每一个成熟组件穷举行业竞品，但必须验证本项目依赖的关键假设、接口兼容性、失败行为和运行代价。框架知名度不构成项目验证。

## P3 关键设计主张与验证矩阵

“已有证据”是对所列日期报告的核对，不表示本次重跑。测试替身、本地真实模型和 Azure baseline 的结论保持各自环境边界。

| 编号 / 主张 | 怎么验证 | 怎么判断 | 已有证据与待补范围 |
|---|---|---|---|
| DV-01 先保存、异步加工，saved 与 ready 分开 | 延迟/中断向量或模型服务；保存后查正文、任务和当前版本就绪状态；保存提交后在后台开始前中断进程；恢复后处理原任务 | 已确认保存的正文可读；待办不丢；未完整投影不得 ready；恢复不重复事实；分别报告保存响应、就绪延迟和积压 | 本地 Working/Temporal 有对应证据；AKS baseline 保存与后台加工通过，但立即 Recall 两次耗尽重试，用户侧时序尚需修复和复验 |

| DV-05 租户、会话与任务范围贯穿所有读取和后台路径 | 两租户、不同用户/Agent与两会话构造同文；合法共享与非法访问；检索、正文、旧结果、缓存、日志和后台操作分别测试；执行中撤权/停用 | 获准路径正常；禁止路径无正文泄漏、无越权改变；撤权传播满足约定窗口；拒绝行为有可追溯结果 | 本地隔离/授权控制有证据；当前云端 local_admin 不是 Entra 联合验收，真实身份和 P2 范围必须另测 |
| DV-06 Operate 的访问准备安全且有收益 | 回放相同访问轨迹；启用策略与关闭自动策略对照；固定缓存容量、热冷比和初态；注入重复事件、容量不足、乱序/丢失回执、损坏缓存 | 规则正确、未知动作不盲重提、读回确认后才报生效；同时看P95/P99、命中率、存储/迁移代价、动作次数与抖动；收益须超过测量波动且满足约定目标 | 本地控制与实际文件缓存有工程证据；AKS发现采样间隔异常并修复复验；真实P2物理迁移和调度收益尚未测，不能称“明显提速” |
| DV-07 ContextPack 在长度约束下保留完整事实和冲突 | 数字、单位、否定和两个冲突来源设置必需项；逐档收紧目标模型token预算；缺失来源/正文；压缩与原文对照，独立评审保真 | 总token不超预算；不能因截断丢否定/冲突一侧；引用可核验；无法完整放入时解释排除；压缩倍数与保真共同达标 | 本地预算/资格/冲突机制有证据；真实LLM提取、摘要与压缩质量尚未验收，literal baseline无法证明这些质量主张 |
| DV-08 运行架构在约定规模下可持续服务并可运维 | 固定语料规模、并发、资源、输入长度与后台负载；冷/热启动、积压、24/72小时阶段性长稳；磁盘满/依赖中断；从备份恢复到独立环境并校验数据 | 吞吐、尾延迟、错误率、就绪延迟、积压和资源达约定标准；无泄漏/持续增长；RTO/RPO与人工步骤达约定；备份恢复真实成功 | AKS单副本基础链路运行通过；性能、长稳、备份恢复、生产高可用尚未验收。Pod Ready和PVC Bound不能替代这些实验 |

三流程划分的验证还包括职责走查：对保存、更正、召回、调度、删除和未知结果分别指出唯一权威、状态所有者、输入输出及失败处理；再用集成场景核对实际接线。通过职责走查和场景测试可说明结构满足当前需求；没有对照和负载证据，不宣称它是行业最优或一定优于所有替代方案。

## 怎样设通过条件

正确性与安全规则是硬门槛，例如指定场景中未授权正文泄漏、丢失已确认保存、重复业务效果、错误交付旧/删除内容均不允许。也必须验证获准请求正常完成，不能靠拒绝所有请求获得“零泄漏”。记录测试覆盖、重复次数和并发条件；样本中零次违规只证明该覆盖范围，不能推导所有运行条件绝对安全。

质量、性能、成本和恢复目标必须在看结果前确定。记录数据规模、并发、输入长度、硬件、模型、版本与测量起止点。分别测保存响应、加工/就绪等待和Recall端到端延迟，不把数据库单次查询耗时当整个API响应。恢复时间应测到原任务和新业务请求按预期成功，而不是只测到Pod Ready。

当前 `product-acceptance.yaml` 仍标注旧 PRD V1.2、`enforce_now=false`，保留了早期性能/质量参考。它不能直接充当当前 V1.4 已批准标准，尤其 Working 已改为向量召回，原延迟定义和预算需要重新确认。缺少共同批准的阈值时，只报告测量结果和趋势，不填“达标”。已有24/72小时阶段安排可用于准备长稳执行，仍需冻结负载、观测项和退出条件。

状态分别填写：**已验证（注明范围）／未通过／未执行／依赖阻塞／双方接受的限制**。失败修复后保留原失败、补回归并在原条件复验；没有结果不写通过。单项通过、整体交付与正式签收分开。

## 质量与收益对照怎么做

1. 由公司业务人员提供一批代表性会议、任务和文档，以及预期事实、来源、授权范围和问题。每个关键错误类型有样本；规模按希望估计的精度、业务覆盖和成本确定。
2. 开发调参与最终验收集分开。语料、问题与标注版本固定，验收样本不用于反复调参；矛盾标注由第二位评审者复核。
3. 只为对应主张选必要对照：语义召回对关键词；压缩对原文；调度对关闭自动策略；异步对同步等待。在隔离实验环境运行，不能为对照关闭现有服务的授权或安全守卫。
4. 若主张“P3提升Agent任务效果”，固定同一个P4/LLM和相同问题，比较不用P3与使用P3；检查任务正确率、关键事实、引用、输入token、费用和延迟。模型自身知识能答对的问题不能单独证明记忆收益。
5. 固定资源、配置和热冷状态，重复运行并报告分布、波动及失败项。LLM输出采用盲评或独立规则核验，不能只让生成该摘要的模型宣布自己的摘要正确。

不要把“最终成功样本的压缩比”当总体效果：失败、未产出、关键信息损失和费用都应保留。对照只改变要研究的机制，其他条件一致；无法保持一致时记录差异和结论限制。

| 字段 | 应填写的内容 |

| 设计/需求 | DV编号、FR/ADR编号、主张、失败风险 |
| 验证对象 | 提交/镜像Digest、配置、模型、真实/替身Provider、资源和环境 |

| 通过条件 | 预先确认的规则、指标、阈值、测量起止点与审批版本 |
| 实际结果 | 通过/失败/未执行，分布、异常、操作ID、workflow/run、正文版本/哈希及效果计数 |
| 证据 | 证据编号、测试报告、必要截图/演示；原始响应和日志按编号保存在项目外 |
| 结论 | 支持哪项主张、适用范围、未覆盖、缺陷和复验、业务见证与签收 |

截图适合展示，判断应落到可复查的数据。Temporal历史说明执行过程，P3任务与原正文/实际效果说明业务结果；日志与Trace辅助定位。HTTP 200、Temporal Completed、任务succeeded、业务目标完成必须按相应完成条件分别核对。

## P4 真实使用与项目完整性

公网IP解决访问路径，P4端到端测试解决上层能否真正使用P3，两者分别验证。当前AKS服务均为ClusterIP，可让同集群P4通过 `http://p3:8080` 调用，也可通过受控内网接入；公网IP不是联合测试前提。公司远程浏览器演示时，可为P4/Web配置统一HTTPS入口，P3和Temporal继续通过集群内网访问。

当前Web入口是P3监测控制台，展示健康、任务和日志。仓库旧P4 Simulator调用 `/api/v1/context`、`/api/v1/memory/events` 等旧接口，没有当前P3的Bearer接入；当前统一服务使用 `/p3/recall`、`/p3/remember` 等。不能只修改base_url就宣布新P4联调完成。

最小联合验证需要真实上层调用链：用户输入 → P4调用P3 Recall → P4使用返回的ContextPack及来源形成回答 → P4调用P3 Remember保存新的材料 → 查询加工状态 → 后续会话再次使用。先适配当前接口、身份、范围、幂等ID、异步状态及错误处理，再部署独立P4测试客户端；基础接口验证可以用真实ContextPack的正文与来源形成确定性参考回答，不能使用脱离P3结果的预设事实或Mock记忆。参考回答不能代替真实LLM质量验证。

至少执行跨会话记忆、明确更正和删除、合法/非法范围、未就绪与依赖失败、请求重试及重启这些场景，并把P4请求与P3操作ID、Temporal工作流、真实正文/来源证据对应。若声称提升Agent质量，另以固定LLM和相同问题比较不用P3与使用P3，检查正确答案是否确实来自P3材料。

具体接口映射、本机启动前提、AKS接入及用例步骤见[P4接入当前P3与业务闭环验证计划](../开发协作/P4接入当前P3与业务闭环验证_20261001.md)。该文件是待实施计划，不是新联调结果。

2026-10-01补充的[多场景跨会话云端实测](P3_多场景跨会话验证方案与实测_20261001.md)使用独立HTTP客户端，18项已执行中15通过、3未通过，另有真实身份阻塞和P4/故障未执行项。更正、指定长期删除与范围隔离在本轮样例通过，但无答案和同范围混合主题相关性未通过；当前generation搜索/组包缺少有效的相关性拒绝行为。该证据不包含P4 Web或真实LLM质量，不能据此宣布全部设计验收完成。

P4参考客户端可证明当前接口可消费；公司真实P4或业务等价客户端参与后，才形成相应上层集成证据。即使P4闭环通过，还须核对PRD必验需求覆盖、真实P2/模型依赖、故障、性能和正式UAT才能判断约定交付范围完整。基础客户端验证不要求先建设整套正式P4管理平台，也不修改已有人员职责分工。

## 当前可以向公司怎么汇报

> 我们已经进行了分层验证。本地有机制、权限版本和精确故障点的工程证据，Azure上也跑通了基础保存、后台加工、长期召回，以及已完成数据和执行历史的重启保留。验证同时发现了立即召回的时序问题和Temporal重启后的P3自动恢复问题，已登记；周期采样问题已经修复复验。真实P2/LLM的质量、目标负载性能、调度收益、灾备和业务UAT还需要按双方确认的标准验证，所以目前结论是基础工程机制和云端测试链路已验证，完整产品设计验收尚未完成。

开会展示一张设计验证矩阵、两三个代表性业务/故障例子、对应证据和未通过项，比只报测试数量更能说明验证深度。先解释设计解决的业务风险，再展示结果和边界。

## 接下来的执行顺序

1. 以当前PRD/ADR冻结必验主张、业务场景和通过条件，与公司确认质量、延迟、规模和恢复目标。保留原职责分工，不在本表另行分配人员。
2. 修复并复验已发现的立即召回与自动恢复问题；在独立AKS测试环境补更正、删除、撤权及在途故障场景。避免在当前演示数据上直接做破坏性故障实验。
3. 用真实模型、P2和身份接入跑同一组正确性/故障契约，再进行语义质量和调度收益对照。
4. 跑目标负载、长稳、备份恢复与候选版本升级/回退，最后由公司业务角色执行UAT并记录签收。现有UAT文档仍为not_run，不能用开发方冒烟代填。
