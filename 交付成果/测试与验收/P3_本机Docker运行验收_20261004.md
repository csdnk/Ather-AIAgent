## 4. 重要失败与限制

| 问题 | 已确认情况 / 当前边界 |
|---|---|
| Recall 与后台任务耗时 | 已成功的召回仍可能接近数分钟；保存成功不等于投影即时 READY。按用户要求性能暂缓，不作为本阶段核心功能联通阻断项 |
| 原 Recall deadline | 原失败 job 保留 `attention_required / DEADLINE_EXCEEDED`；修复后以新的明确查询操作验证成功，没有修改旧终态 |
| Operate deadline | 存在历史 `attention_required / DEADLINE_EXCEEDED`，也有成功和取消任务；不能声称所有后台流程均无失败 |
| relay 断线 | 实际出现连接丢失及短暂 HTTP 503，维护进程重连后恢复；本机环境仍依赖 Azure 网络 |
| 容器更新中断 | 更换容器期间 HTTP 查询断开；沿原更正 job 恢复并成功。首次完整脚本及后续删除脚本的失败记录保留 |
| 项目级测试环境 | 首次收集缺 jsonschema；第二次日期格式校验缺 rfc3339-validator，按已声明 dev 依赖补齐后单项通过。transfer/recovery 证据缺真实 P2 端点，仍未验收；原失败保留 |
| Recall 极短超时回归 | `test_source_timeout_preserves_working_and_records_reason` 使用 10 毫秒来源预算，在本轮异步线程调度下两个来源均超时；200 毫秒诊断可正确降级。原测试仍失败，保留并转后续性能/预算阶段；未修改生产超时 |
| 参考本地缓存冷热场景 | `test_operate_uses_prepared_files_and_cools_without_new_requests` 的首次 heat Recall 返回 400 `EXECUTION_INTERRUPTED`；使用参考 SQLite/lexical 与本地文件冷热存储，不能作为本文真实 Azure 缓存通过或失败证据。该扩展场景尚未完成；没有直接归因为性能，也没有修改测试使其通过 |
| Docker 初始启动 | 早期 Docker Desktop 故障，定点端点删除曾被自动审批拒绝；未执行该删除，后续 Docker 正常启动并完成本次构建 |
| 存储迁移 | warm/cold 真实迁移当前不支持；增加 Azure 权限不会自动补齐实现 |
| 生产验收 | 长稳、备份恢复、灾难恢复、多实例、完整网页业务与 Azure 正式发布仍待验收 |

这套业务运行时使用的 PostgreSQL、Redis、Milvus、Ceph、LLM 和 BGE 都是真实实现。仓库内测试替身、旧 Mock 原型和本次排除的 P4 代码仍存在；结论只适用于本文实际运行的 P3 链路。

## 5. 与 Azure 正式部署的关系

同架构镜像可复用于 Azure VM 或 AKS Pod，但网络、持久卷、配置/身份、监督和实例数量需要按目标环境配置并验收。电脑休眠或关机后本机服务不能持续对外运行；单 VM 或多个 Pod 的存在也不能代替高可用验收。

Azure 正式 Temporal 仍缺 `postgresp3.azure.extensions` 中允许 `BTREE_GIN`；VM 与附属网络资源仍需管理员代建或授予创建权限。清单见[Azure 权限与配置汇总](../部署运行/P3_Azure权限与配置汇总_20261004.md)。本机 Temporal 使用本机 PostgreSQL 完成工程验证，没有解除 Azure 数据库参数限制。
