## 本次修改

1. 通用 CI 原本直接执行全部 Python 测试，却没有提供 Temporal 测试要求的 CLI。现在复用仓库的固定版本安装脚本，通过已有 SHA256 校验下载，并在 pytest 前设置 `P3_TEMPORAL_CLI`。专用 Temporal 流水线继续保留。
2. 源码没有引用 `echarts` 和 `echarts-for-react`，移除这两项依赖。Vitest 从 3.2.7 更新到 4.1.11，更新其配套测试包，并将 `brace-expansion` 和 `js-yaml` 更新到已修复版本。没有使用强制跳过依赖兼容性的安装选项。
3. npm 10 在生成升级锁文件时出现内部依赖解析异常，因此仅在项目外使用 npm 11.21.0 生成锁文件。最终重新安装、测试和构建仍使用 Node 22／npm 10，与当前 CI 的主版本一致。没有修改本机全局 npm。
4. 前端使用项目外的 54 文件快照，复制时逐文件核对。验证完成后只回写 `package.json` 和 `package-lock.json`；其他 52 个文件保持一致。依赖目录、构建输出和原始日志均留在项目外。

5. PG 服务级回归改为在测试中显式注入既有 PG 组件，保留 HTTP 鉴权、跨租户隔离和 Trace 入库断言；正式服务继续拒绝直连 PG。观测测试改用独立 schema，取消逐项清理 public 表，避免测试之间污染正文提供方绑定。
6. 两个公开演示读取完整服务配置，模型替身移到测试目录。真实文档上传/解析替换预制解析结果，摘要样例按阈值构造并分页核对全文；缓存只按 scope/hash 删除。等待结果前落盘原 operation/job 身份，拒绝覆盖已有运行证据。等待 Temporal 就绪有明确期限，未就绪时不准入业务。
7. 同步三个验证脚本的调用接口和证据标签。通用 CI 新增 pinned PostgreSQL 17 服务、健康检查与必须提供 DSN 的设置；真实 CI 尚未运行。操作方式见[配置化演示与验证](../开发协作/P3_配置化演示与验证_20261002.md)。

可选 `compose.p4-demo.yaml` 仅用于专用 development/test 本机联调：P4 与 Web 共享网络命名空间，P4 监听 loopback 8090，Web 只发布宿主 loopback；凭据以服务端单文件只读挂载。Web 端口同步进入精确 Origin allowlist，外部域名、通配符、userinfo、路径、空查询/片段/端口均拒绝。Nginx 保留 Origin，清除外带 Authorization/Cookie，仅转交演示接口。默认 Web 和生产 Compose 返回演示未启用，不启用 P4 自动重启。

恢复顺序：核对原 transfer → 校验完整原运行、冻结定义和执行器版本 → 在 hold 内确认原定义 → 核对或提交原 activation → 读回原定义/初始状态并检查当前所有权 → 安装本地运行并派发一次。无原业务日志且无已发布 head，才可在新状态链建立空初始状态；旧 pending 预约及字节保留。丢响应只核对同一 transfer ID 的原回执；不能获得确定证据则停止，不自动换 run/operation/job ID。

同实例并发调用在同一锁内核对与派发；每次提交使用仅存在本地的执行令牌。submit 抛错时先使令牌失效，排队中的旧包装任务不会执行，合法重试才能取得新的本地令牌。这个令牌不改变任何业务身份，也没有修改 P2 并发行为。已有激活记录若在当前 owner 下继续推进，只返回当前状态；旧回执不能倒退运行或接管后续 owner。
