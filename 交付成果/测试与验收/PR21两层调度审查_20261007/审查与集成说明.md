## 为什么判断有真实执行能力

本轮审查核对了生产装配链，而非只采信 PR 描述：

1. `runtime/flows/application.py` 装配 `ContinuousOperate`。
2. `runtime/storage/azure.py` 将 `RememberPipeline.read_authority` 注入 `RedisExecutor`，启用 promote/demote 能力。
3. `read_authority` 在前后授权和版本复核之间读取 Ceph，不使用 Redis 或进程内正文缓存充当持久正文证明。
4. Redis 执行器实际创建/撤销热副本；降温前必须完成权威正文核验。
5. `MemoryRecordSync` 使用条件写入更新缓存位置；动作成功状态、位置登记及事件在同一 PostgreSQL 事务中发布。
6. 持久化到期队列由既有 Temporal 周期任务读取，再进入公共任务执行流程；未另建一个并行调度器。

与后台原有改动合并后，普通 `read_body` 的单次正文读取、阶段计时、权限/版本复核和相关任务定向查询仍保留；调度取证通过独立 `read_authority` 完成，二者职责没有混用。

## 集成时修复的阻塞问题

旧的 `pending()` 只按用户作用域和记忆 ID 查待处理任务，未检查记忆版本。若 v1 任务进入 attention_required，即使尚无任何 Redis 副作用，v2 已有合法事件，周期执行仍会不断推迟 60 秒，无法创建 v2 评估。

修复：`pending()` 比较完整 MemoryRef（包括作用域和版本），与已有 `enqueue()` 一致。同版本 pending/running/retry_wait/recovery_wait/attention_required 仍拦截重复评估；旧动作记录没有被删除或改写。

新增回归对五种状态分别测试：原代码五项均失败；修复后持久化 v2 记忆，发送 Recall.access，经消费、due、periodic 创建新版本任务，确认 v1 任务保留、没有额外副本 action、跨作用域不互相阻塞。同一 v2 转入 attention 后仍不重复创建评估。

同时纠正文档中“本次未修改 Remember/Runtime”的表述：完整 PR 确实包含二者的必要适配，未改的是 Remember 保存写入逻辑与 Recall 选择缓存地址的逻辑。

## 保留的限制与下一步验收

- Ceph＋Redis＋PostgreSQL＋Temporal 的真实云端业务闭环尚未在本轮运行。发布后需验证同一合成记忆“多次有效读取→升热→Redis 副本存在→MemoryRecord 地址写回→到期降温→副本消失→Ceph 原文仍可读”，并保留原动作编号和内容指纹。
- Redis 操作与 PostgreSQL 发布不是分布式原子事务，期间可能短暂不一致，依靠原动作核验与恢复收敛。
- 旧版本已经存在 unknown 副作用的场景仍须先按原动作确认和清理。本轮版本准入修复没有绕过这一保护，也未宣称该场景可以无条件自动恢复。
- Recall 尚未以 cache_location 字段选择读取地址；现有 TieredBodyCache 可以按作用域与正文摘要读 Redis 副本，因此真实副本调度仍有作用。新的地址字段不是授权凭证，读取方仍需校验和回退。
- Remember 后续重建记录可能清空 cache_location，需要后续事件/评估修复。Redis TTL/容量回收也可能造成漂移，不保证即时扫描发现。
- 没有跨 Worker 的搬迁字节速率限制，也没有同负载 CPU、吞吐及长期运行对照，不能断言资源问题已全部解决。
