## 1 判断

**正常业务主线基本闭合，完整的异常与跨模块协作闭环尚未闭合。三流程分工可以保留，需要优先补齐新增 Remember 与 Recall、Operate 之间的读取、分块、地址及恢复协议。**

现有图已经连通：原文保存 → Working → 适用加工与提取 → 正式 E/S 记忆 → 索引核验与 Ready → Recall 权威读取和组包 → 真实访问事件 → Operate 调整 → Remember 确认地址交接。只查 Working 也有独立入口。上述是一组可选择、异步协作的路径，不表示每次请求必须顺序执行全部步骤。

已经成立的设计边界包括：Remember 拥有事实与资格；Recall 负责上下文；Operate 保持内部自动运行；索引命中不代替授权；未知效果先查原动作；元数据交接失败不重新迁移；删除先阻断使用；日志不代替持久恢复事实。这些不需要推翻。

以下问题分为“图中缺项或歧义”和“具体协议待补”。它们不是本轮观察到的运行故障；风险示例说明按当前图直接实现时可能出现的分歧。

## 2 优先问题清单

| F02 | 高 | B.1、B.8 | 外部保存的恢复前提未落到具体步骤 | 调 P2 前保存操作身份，崩溃后能定位已保存原文 |

### F01 正文读取有上层入口，但 B 侧的缓存与回源流程缺失

**证据：**B.3 标题写“Working 内容写入与正文读取”，实际节点只有初始写入；长内容“登记引用，标记正文未缓存”。B.10 明确引用“B.3b 按范围读取并核验精确版本”，当前完整图却没有 B.3b。A.1b 已写“按 MemRecord 的存储引用读正文”，因此不能说系统完全没有读取设计；缺的是新存储/缓存方案下 B 侧的完整展开。

**风险例：**保存一段长内容后立即只查 Working。A 找到记忆引用，B 发现正文未缓存，接下来是直接读 P2、分段读、等待缓存还是返回失败，提供方与消费方可能作出不同实现。Redis 故障、缓存版本过旧也有同样问题。

**建议：**补 B.3b：授权和精确版本核验 → 查有效缓存覆盖 → 缺失部分按权威引用回源 → 校验内容及版本 → 返回正文/片段与逐项状态 → 按策略回填。区分“未缓存”“无记录”“读取失败”和“业务失效”。

B.7 又把缓存清理交给 C，而 B.3 直接写 Redis；B.8 已提出统一版本键、阻止旧回填和回源限流，但还需明确 B 写入/回填与 C 清理共用的代次检查和原子约束。无需让每次读取都进入 C 的迁移队列，也不能认为 C 的同 Memory 串行自动覆盖 B 的直接缓存写入。

### F02 P2 写入成功但 B 尚未提交时，恢复依据还不具体

**证据：**B.1 顺序是“绑定请求 ID → P2 独立保存完整原文 → 事务提交来源索引与 Working”。失败注释和 B.8 说“查原操作后补关联”，但图中没有展示在调用 P2 前如何持久保存这个可查询的原操作身份。

**风险例：**P2 已保存，进程在收到地址后、提交本地来源索引前停止。此时如果操作身份仅在内存，Worker 无法从未提交的 Working 反推出那个 P2 对象。仅有孤立文件延迟清理并不能完成原保存请求。

**建议：**把公共规则落到 B.1：调用前持久登记保存意图，绑定租户、业务幂等键、内容指纹和稳定 P2 操作 ID。P2 按该身份去重并支持结果定位，随后本地事务补交来源索引、Working 和待办。若 P2 不支持操作查询，也必须约定另一种可靠的对象定位与核验方法。登记操作意图不等于提前宣称保存成功。

### F03 大文本加工失败后“读原文”仍可能无法进入模型

**证据：**B.4 因超过长度或模型预算进入后台；质量不通过时转 B.5 读原文。B.5 也要求长内容缺失细节读取原文，但没有展开原文超过提取模型预算时的处理。

**风险例：**原文已经长到不能一次送入模型，压缩质量又不通过；直接回退原文只恢复了可信材料，并未解决输入长度问题。B.4 已有分段检查点，但它是否覆盖提取阶段以及如何合并候选尚不明确。

**建议：**保留原文作为证据，同时规定有界分段提取、必要上下文、跨段候选合并与去重、来源片段绑定和批次完成条件；预算耗尽则保存未完成状态。若 B.5 等待 B.4 产物，还应说明产物未完成时是等待还是按受控原文路径推进，避免两条支线重复提取。

### F04 索引已经按块写入，Recall 仍按整条记忆描述候选

**证据：**B.6 写入身份为 `memory_id / version / chunk_id` 并核验全部预期块；A.1a 输出仍是 `memory_id、version、score、来源`，A.1 主要按记忆版本去重、排序和整组预算。

**风险例：**一条长记忆的多个块占满 Top K，导致其他记忆没有进入候选；如果简单去重又不规定如何聚合分数，最终名次不确定。另一个问题是命中短片段却读取整篇正文，最后因预算不足整条排除。

**建议：**先确定返回整条 Memory 还是可引用片段。整条模式需约定块级召回后如何聚合、候选不足时是否补取，以及聚合后的排序口径；片段模式需携带 chunk、偏移、来源版本和完整性边界。两种模式均须保留 Memory 级授权、冲突关系和最终资格核验。不能只是添加 chunk_id 字段而不定义使用语义。

### F05 “新索引地址”和“正文存储引用”不能靠同一个模糊概念交接

**证据：**B.2 的 MemoryRecord 保存正文引用；A.1b 据此读取权威正文；C.3 接收的是“新索引地址”，随后调用 B 更新 MemRecord；B.10 对应表述为“更新 MemoryRecord 引用”。

**风险例：**若 C 给的是向量索引位置，B 却把它覆盖到正文引用字段，下一次 A 的权威读取就无法按原约定执行。若“索引地址”实际指正文位置，名称也会让接口实现产生分歧。

**建议：**在交接契约中分别定义正文对象引用、向量投影引用和缓存驻留位置，名称可沿用正式契约。明确此次动作改变哪一种位置、是否保留旧可读路径以及证据类型。B 只条件更新对应引用；如果 P2 返回的是逻辑解析入口，也要明确其可解析的对象类型和稳定性保证。

### F06 固定本轮目标需要配套的失效和终止规则

**证据：**C.1 固定目标、后续需求进入缓冲区1；C.2 资源不足等待更新；C.3 规定异常未处理完不释放串行权。图中已有独立删除清理和墓碑，配套规范也有有限查询与人工升级，但具体如何结束旧本轮仍未展开。

**风险例：**本轮一直等待资源，期间对象版本更新；或者 P2 动作长期 Unknown，后续需求不断积累。任务进入 Failed/人工状态之后，业务本轮是否仍持有串行权、如何接续、何时允许新动作，都不能仅靠 Task 状态推定。

**建议：**明确本轮对外部事实变化的反应：未提交外部动作时，失效目标可取消或重新进入准入；动作在途时，先核对或受控取消原动作，不能直接释放互斥制造第二个冲突动作。资源等待应有新鲜度检查、周期对账及升级条件，不能只依赖一次资源更新通知。删除阻断必须立即生效，后续物理清理与旧动作处置建立明确关联。

“固定目标”应防止普通热度变化不断改写本轮，不应让旧版本、删除或撤权后的操作继续获得执行资格。

### F07 原 action_id 的重试和新计划尝试要分开

**证据：**C.3 的“Failed：位置冲突 → ④”返回 C.2 重规划；C.2 又规定动作意图固定 action_id。协同规范要求同 ID 绑定同输入、同键异义冲突。图中没有说明重规划改变执行参数后沿用哪个 ID。

**风险例：**确认原动作失败后换了目的地址，却继续使用原 action_id，会触发幂等冲突或被 P2 当作旧请求；如果原动作仍 Unknown 就换 ID，则可能重复执行。

**建议：**保留业务本轮/计划关联；查询或重试同一个不可变动作时保留 action_id。只有原动作终态与副作用已核实、允许重新计划时，才建立关联的新动作尝试及新 action_id，并保留前后关系。动作结果、实际层和地址交接仍要分别核验。

### F08 Episodic 到 Semantic 的箭头没有交代生成机制

**证据：**B.5 中 LangMem 之后先输出结构化候选；连线进入 Episodic 候选，再从 Episodic 候选连接到 Semantic 候选，两类候选各自进入 Remember 校验并汇入正式提交。

**风险：**这可能被理解为 Episodic 候选自然转成 Semantic 候选，也可能被理解为同一次提取输出两类结果。前者没有明确事实提炼步骤，后者的并列输出却被画成了先后关系。

**建议：**如果同次模型调用输出两类候选，从结构化输出处分支；如果要从事件进一步提炼事实，增加明确的提炼步骤、输入资格和证据关系。两种方案均可成立，但应选择或显式区分，不能靠一根连线兼任两种语义。

## 3 另外两项需要收拢

**提取水位与并发提交。**B.5 只在零候选分支明确“提交水位”，非零候选路径还应明确候选提交与处理水位的原子关系。结合 B.1 的会话序号、B.5 的范围和来源版本，规定连续已处理边界、并发重试以及中途失败的处理。已有幂等和 CAS 原则可以复用，但需要落到具体提取批次，避免重复或跳过输入。

**文档基线不同步。**当前完整图为 P3 概览、Remember B.1—B.10、Recall 和 Operate；独立 Remember 图及 README 仍包含旧编号，独立 P3 图还保留上一版详细公共底座。B.10 的 B.3b 引用也尚无对应子图。应以完整图为源同步分图与目录，避免开发者依据不同版本分工。这是协作问题，不是运行机制缺失。

## 4 建议处理顺序

1. 先确定正文、来源、Artifact、分块、缓存和位置引用的含义，处理 F01、F04、F05；A/B/C 的交接才能对齐。
2. 再补保存、加工和迁移的异常状态及恢复前提，处理 F02、F03、F06、F07。
3. 明确 B.5 的候选生成及水位提交，处理 F08 和批次并发。
4. 将明确后的流程同步到完整图、分图和目录，再据此补逐操作接入卡与契约样例。

设计核对时至少逐一走通：长 Working 立即读取、Redis 失效回源、P2 保存后本地提交前崩溃、长文压缩不合格、多块命中、等待资源期间删除、位置冲突重规划、迁移成功但地址提交失败。每条都能回答“持久保存了什么、谁接手、下一步是什么、凭什么结束”，才算该项设计闭合；本次未执行这些运行场景。
