# P3 协同开发规范

版本：1.0；日期：2026-09-20。适用新 P3 流程及公共底座。文中“必须”为团队交付规则；自动检查只覆盖可验证的一部分，领域语义仍须代码评审。

## 依据与维护来源

产品范围以 PRD V1.3 和后续用户明确决策为准；ADR 解释技术取舍。历史批次限制不得缩减产品要求。V1.3租户增量及原V1.2追踪范围见[基线切换说明](<../01_需求基线/04_PRD_V1.3基线切换与增量.md>)。当前优先搭建系统，指标门禁暂缓。

Python `contracts/models.py` 和 `rules.py` 维护字段、枚举与状态候选边；`ports.py` 定义接口。JSON Schema 自动生成，禁止手工修补生成文件。HTTP 映射维护路径与权限，不代表新路由已经上线。日志字段由 `Telemetry.emit/summary` 实现维护。

## 所有权与评审

| Owner | 维护范围 | 变更需要共同确认的人 |
|---|---|---|
| B / Remember | 来源、记忆、版本、生命周期、加工及最终资格 | MemoryReadPort 改动：A、C；公共机制接入：RF |
| A / Recall | Recall、Embedding、向量适配、预算和 ContextPack | EmbeddingPort/VectorPort 改动：B；访问事件：C；装配：RF |
| C / Operate | 输入视图、策略、Action、执行证据及对账 | 事件与记忆资格：B、A；任务和执行适配：RF |
| RF / 集成负责人 | runtime、Host、依赖、配置、契约生成和流水线 | 任何公共契约变更：所有受影响消费者 |

开发者使用独立分支和工作目录，避免多人操作同一 checkout。建议分支 `p3/<owner>/<issue>-<purpose>`，按仓库实际基线分支创建，不假设 main/master。提交聚焦一项可验收行为；跨模块改动先提交兼容契约和样例，再接生产方、消费方。

公共接口变更由 RF 与受影响 Owner 共同评审；领域改动至少由另一名开发者评审。作者不得单独确认自己的跨流程兼容性。以上是评审制度，当前尚未绑定远端用户账号。

## 所有流程必须遵守的规则

1. **身份**：使用服务端 TrustedContext；每次读取/写入按对象范围授权。Trace ID、调用方自报 scope 和 Azure 目录身份不能替代业务授权。
2. **数据归属**：不直接写其他流程的领域状态；A/C 使用 B 的读取与 final_guard。现有历史内部耦合修改时逐项收敛，不借新增功能扩大绕过接口的路径。
3. **事务**：业务结果、Task 完成、需要原子交接的事件共用 UoW。事务内禁止网络调用、模型推理和跨 await 等待；不可嵌套开启另一事务。
4. **幂等**：稳定操作 ID 绑定输入内容。同键异义返回冲突；重试原操作保持 ID。业务唯一性不能依赖日志去重。
5. **任务**：注册公共 TaskHandler，使用统一领取、租约、截止与配额；禁止新增流程私有任务引擎。提交前检查当前 lease、授权、版本和删除屏障。
6. **事件**：事件生产方在事务内提交 Outbox；消费效果/待办与 Inbox 去重在事务内提交。消费者不能在持有事务时执行外部动作。
7. **失败**：无结果、依赖失败、降级、结果未知分别表达；不能用空数组吞掉错误，不能把技术调用返回当业务完成。
8. **恢复**：每种持久任务说明 run/recover 行为。只有证明可安全重做才重做；Unknown 查询原 ID。人工恢复保留对象、原因、权限、修订号和结果。
9. **阻塞与取消**：同步模型/SDK 不阻塞事件循环；超时后仍运行的线程保留物理并发槽位。取消等待不能宣称撤销了外部动作。
10. **日志与 Trace**：节点接 observed/attach_provider 或显式 span；任务/事件传播上下文。必须记录阶段、结果状态、错误码和关联 ID，默认不写正文、凭证、完整向量或异常消息原文。
11. **健康**：新依赖注册有超时的探针，写明探测深度。unknown 不显示为正常；依赖暂时失败不直接触发 liveness 重启。健康查询不能修改业务任务。
12. **配置**：密钥通过部署环境提供；模型、tokenizer、向量空间与持久绑定有版本。不可静默切模型或将有数据的库指向空后端。新增配置写入示例并拒绝不合法组合。

## 接口变更步骤

提供方先写具体输入、输出、失败与幂等样例，双方确认事务与恢复责任。保持兼容时新增可选字段并验证旧消费者；破坏性变更新版本/适配器，明确数据迁移和回退，不把字段默认值用于伪造身份、来源或版本。

修改模型后运行 Schema 生成，再执行统一校验。PR 必须列出受影响消费者和他们的验证证据。新增事件消费者对历史事件是否回放必须明确，不假设订阅后会自动补发历史。

## 完成定义

每项功能交付必须包括：代码、契约与样例、权限边界、正常和关键失败路径、日志/Trace、依赖探针或复用说明、恢复策略、运行配置、实际测试结果、未覆盖项。没有真实环境时提交可控故障测试，并标记真实联调待验证。

至少考虑相关场景：重复请求、同键异义、撤权、旧版本/删除竞态、处理中退出、迟到返回、依赖中断、外部执行后丢响应。按变更选用有意义的测试，不为纯文案变更强加业务测试，也不把替身结果登记为真实模型或服务器结果。

## 合并与发布规则

仓库 PR 模板要求填写 Owner、需求来源、消费者、故障语义和验证结果。统一命令 `python scripts/p3/validate_collaboration.py` 必须返回 0；这是本地可执行门禁，不需要 Milvus 服务或模型权重，但需要安装验证依赖。

GitHub 工作流 `p3-collaboration` 的 job `p3-gate` 与 Azure 流水线 job `P3Gate` 调用同一入口。首次远端成功运行后，由仓库维护者将对应检查设为目标分支必需检查；开启 PR 合并、至少一名非作者评审、修改后重新审核及禁止普通成员绕过检查。保留已有 CI 要求，不以本门禁替代整个仓库其他检查。

Azure Repos 的 PR 构建验证必须在目标分支的 Branch policies 中绑定本流水线，YAML 的 pr 触发不能替代该策略。GitHub/Azure 的真实团队账号、项目和目标分支尚未提供，因此本轮不生成虚假的 CODEOWNERS，不声称已启用远端保护。RF 应将上面的角色映射到实际账号后配置路径评审。

正式合并仍需确认提供方与消费方都通过，模型/Milvus/Provider 变更另附相应真实联调结果或明确阻塞；不得把本地门禁当作生产发布批准。

## 文档与材料管理

当前状态统一维护在本目录；旧验收报告按日期保留。代码仓库中的设计文档描述机制或产品目标，入口注明当前实现范围。发现旧状态要修改正文或明确历史范围，不能只叠加相互矛盾的通知。

用户阅读的成品放交付成果；业务代码、测试、PR 模板、流水线和必要配置留仓库。个人环境、下载权重、日志和原始测试报告放项目外工作区；不提交凭证、缓存和助手草稿。
