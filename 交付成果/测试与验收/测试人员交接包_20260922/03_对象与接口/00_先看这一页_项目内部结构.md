# 先看这一页：项目内部是什么结构

先读本页，再按顺序读[公共运行底座](01_公共运行底座_对象与接口.md)、[三个业务流程](02_三个业务流程_对象与接口.md)。每一段先描述流程与调用接口，随后展开这段涉及对象的完整字段表；同一对象后续再出现时只引用。需要快速查阅时，看[主要接口清单](03_主要接口清单.md)和[对象字段定位](04_主要业务对象设计.md)，无需重新通读流程。

## 四个模块怎么分工

| 模块 | 负责什么 |
|---|---|
| RF：公共运行底座 | 确认身份，保证数据提交、后台任务、事件投递可靠，提供日志、健康与故障处置 |
| B：Remember | 保存材料，形成和维护记忆；负责投影写入、核验和索引发布；提供正文并判断读取资格 |
| A：Recall | 根据问题检索和筛选记忆，组装上下文；向 B 提供 Embedding 编码能力 |
| C：Operate | 根据存储和访问情况决定内容放哪，执行迁移或清理，并检查实际结果 |

## 顺着一次使用看全局

用户保存“预算 30 万元” → **RF 验证身份，B 保存材料** → **B 登记加工任务，RF 调用 B 的处理器执行** → **B 调 A 的 Embedding 得到向量，再自行组织投影、写入核验并发布索引**。

用户再问“预算多少” → **A 取得块命中** → **A 调 B 审查资格** → **A 按记忆形成合格候选并占 Top K** → **A 调 B 读取完整正文** → **A 排序组包** → **B 最终复核，RF 事务提交上下文**。Working-only 路径直接向 B 受控读取，不走长期向量候选步骤。

这期间，**B/A 的存储与访问变化由 RF 投递给 C** → **C 判断是否需要调整存储，调用执行器，并核验结果**。RF 的权限、事务、日志与健康能力贯穿这些步骤。

最容易混淆的是后台任务：**RF 领取任务，只是取得这项工作的执行权；怎样提取记忆仍由 B 的业务处理器完成。** RF 也不会代替 A 决定哪些记忆更相关，或代替 C 判断迁移目标是否正确。

## 后两篇怎么读

每一步固定为两部分：先讲谁调用谁、用了什么接口、产生什么结果；再展开本段对象的全部字段、类型、必填项、默认值及约束。先读流程，再按需逐项核对表格。嵌套对象可点击跳转，后续重复使用不重复抄表。一个对象是一份结构化信息，不一定对应一张数据库表。

`Port.方法`是源码中的接口名称，常用于进程内调用，不等于一个 HTTP 地址。RF 的 `tasks.progress`、`dispositions`、`lifecycle` 则是已实现的运行服务入口，也会在对应步骤讲到。

状态标记：**【已有】**代表已有本地实现；**【基础】**代表基础路径能运行，完整能力未接通；**【待接】**代表对象和接口已设计，但业务接入未完成。**【文档设计】**代表尚未加入代码契约，例如本轮补充的独立候选资格审查接口及两个输入输出对象。均不能直接等同于生产验收通过。
