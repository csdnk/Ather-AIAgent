## 1. 请求进来，RF 确认身份【已有】

### 流程与接口

入口调用 `IdentityPort.authenticate` 验证凭据，得到 **Principal（调用者身份）**，其中 `principal_id` 表示是谁，`permissions` 表示能做什么，`auth_epoch` 表示当前授权代次。

Principal 中的 `home_scope` 是 **Scope（数据归属范围）**，包括租户、应用、用户、Agent，以及可选的会话等限制。用户不能靠请求中自报一个租户编号就扩大权限。

RF 随后建立 **TrustedContext（本次调用的可信上下文）**，把 Principal、`operation_id`、`trace_id`、`deadline_at` 传给后续模块。这里 `operation_id` 用来识别业务操作和重复请求，`trace_id` 用来串起排查记录，`deadline_at` 是这次工作的截止时间。

操作具体记录时，B/A/C 调用 `IdentityPort.authorize`，交入 **RecordRef（目标记录引用）**：`owner` 指所属模块，`object_id` 指哪份记录，再带上 Scope 和版本。RF 据此判断是否允许操作；`revalidate` 在执行或提交时复查授权，防止请求开始后已经撤权却仍然提交。

同租户共享也要有明确许可，许可由 **AuthorizationGrant** 记录“给谁、哪个资源、哪些权限、何时失效”。这不是同租户用户天然互通所有数据。

## 2. B 要保存材料，RF 保证相关记录一起提交【已有】

### 流程与接口

B 调用 `UnitOfWork.transaction`，得到 **Transaction（事务操作接口）**。它的 `get` 读取记录，`put_if_revision` 只在当前修订符合预期时写入，避免旧结果覆盖刚更新的数据。

B 会在这个事务中保存材料，同时登记后面要执行的任务和要发出的事件。正常结束一起提交，中途失败一起回滚。否则可能出现“材料没保存，任务却已经启动”的问题。模型推理和外部网络等待放在短事务外。

这里 UnitOfWork 和 Transaction 是协调读写的接口，不是新的业务数据对象。

### 本段对象的完整字段

本段没有新增业务数据对象；使用上面的既有对象和事务接口。

## 3. B 登记工作，RF 领取后交给 B 执行【已有】

### 流程与接口

B 先组成 **TaskSpec（任务说明）**，写清 `kind` 是什么工作、`input_ref` 指向什么输入、`idempotency_key` 怎样防重复、`deadline_at` 何时截止。然后调用 `TaskPort.enqueue`，RF 返回 **TaskRecord（持久任务记录）**：除了任务说明，还记录 `task_id`、`state`、`attempt`、`result_ref` 等进度。

RF 的 Worker 调用 `TaskPort.claim` 领取可执行任务。领取后 TaskRecord 带上 **Lease（租约）**：`owner_id` 是当前执行者，`token` 是这次领取凭证，`until` 是有效期。`TaskPort.renew` 用来续租，旧执行者不能拿失效租约提交结果。

**接下来真正调用的是 B 的 `TaskHandler.run`。** RF 把 TrustedContext 和 TaskRecord 交给它；B 的处理器负责读取输入、提取记忆、调用编码等业务。C 的后台工作也是注册自己的处理器，复用同一套领取机制。

B 运行后给出 **RunResult（本次运行结论）**，其中 `outcome` 表示运行结论，`effect_status` 表示是否产生实际效果，`result_ref` 指向结果。需要完成任务时，处理器通过 `TaskPort.complete`，把业务输出与任务完成放在同一事务提交。仅仅从处理器返回“成功”不能替代持久提交。

执行中如果需要保存阶段成果，处理器调用 `tasks.progress.checkpoint`，写 **CheckpointRecord**，记录 `stage`、输入指纹和 `output_refs`。如果在等依赖，调用 `tasks.progress.wait`，写 **TaskWaitRecord**，记录 `dependency_id`、`next_check_at` 和原操作编号。是否可以从某阶段继续，由 B/C 判断，RF 不猜业务进度。

RF 另用 **AttemptRecord** 保留每次尝试的证据，用 **WorkerHeartbeat** 记录执行者最近的活动和当前任务。看到心跳只能说明执行者有活动，不能据此宣布记忆加工成功。

## 5. 运行出问题，先定位，再决定怎么恢复【已有】

### 流程与接口

每个节点产生 **NodeLogRecord（节点日志）**，记录 `flow`、`node`、`phase`、`trace_id`、耗时及原因码。统一日志接口是 `MonitoringPort.emit`；查询任务和相关证据可用 `DiagnosticsPort.task / operation / related`。日志辅助排查，不能代替业务事实。

查健康时调用 `MonitoringPort.health`。探针先形成 **HealthObservation（单项健康证据）**，其中 `state` 表示状态，`fresh_until` 表示证据有效期；汇总成 **RuntimeHealthSnapshot（运行健康快照）**，分别说明 `liveness` 是否存活、`readiness` 是否就绪，并列出证据。证据过期或配置变了，不能沿用旧结论。

要自动处置，部署时先登记 **SignalDefinition**，说明测什么和采样周期；测量产生 **SignalObservation**，记录数值、时间和证据。再登记 **DispositionRule**，说明阈值、连续次数、冷却时间、要执行的维护类型及独立复验方式。维护类型由 **OperationDefinition** 约定输入输出、权限和恢复策略，并绑定实际处理器。

运行服务 `dispositions.observe / cycle` 处理样本、推进采样与对账。规则触发后创建 **IncidentRecord（异常记录）**，记录目标、状态、关联 `operation_id` 和复验证据；再通过原 TaskPort 安排维护。**OperationRecord** 记录该操作的状态、关联任务与结果，**MaintenanceRecord** 记录谁因什么原因做了维护。

维护执行完，再由 `dispositions.reconcile` 推进独立业务复验。复验通过才能关闭 IncidentRecord；维护任务成功不等于业务已经恢复。健康查询本身也不会触发维护。

若任务需要受控恢复，调用 `TaskPort.request_recovery` 提交 **RecoveryRequest**，带上 `task_id`、预期修订和原因。RF 调业务处理器的 `TaskHandler.recover`，得到 **RecoveryDecision**，说明继续做、查询原操作还是转人工，并带上证据。外部效果未知时不能直接新建操作重做。

## 6. 运维登记配置，备份后验证能否恢复【已有】

### 流程与接口

`lifecycle.activate` 登记 **ConfigurationSnapshot（配置快照）**，记录版本、`config_hash`、提供方和策略版本。它描述已部署配置，不等于自动热切换模型或数据库。

`lifecycle.backup` 创建 **BackupManifest（备份清单）**，记录 `backup_id`、一致性水位和恢复核验状态；其中 `location` 使用 **ResourceLocation（资源地址）**，由资源类型、提供方、对象键及内容指纹定位实际文件。这个地址对象也会用于业务正文、缓存等资源。

`lifecycle.restore` 写入独立新位置并核验结果，不覆盖在线库。当前备份范围是 RF SQLite，操作需要明确授权的运维主体，不代表已完成向量库、原件存储及整个生产系统的联合恢复。

### 本段对象的完整字段

本段首次展开：[ConfigurationSnapshot](#runtime-configurationsnapshot)、[BackupManifest](#runtime-backupmanifest)、[ResourceLocation](#runtime-resourcelocation)。嵌套请求/结果所需的子对象也一并列全。
