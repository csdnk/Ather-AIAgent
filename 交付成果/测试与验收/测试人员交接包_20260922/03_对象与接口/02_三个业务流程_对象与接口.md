## B · Remember：保存材料，形成记忆

<a id="b-1"></a>

### 第一步：用户把内容交给 B【已有】

#### 流程与接口

用户通过 `/p3/remember`，由入口调用 `RememberPort.save`。输入是 **RememberRequest（保存请求）**：`source` 描述来源，`selection` 限定范围，`content` 是输入内容。文本路径中，来源用 **SourceInput** 表示外部编号、版本与发生时间，正文用 **TextInput** 的 `text` 保存。

B 在 RF 事务里保存后返回 **RememberReceipt（保存回执）**，说明 `saved` 是否保存、形成哪些 `memories`、产生哪些 `task_ids`。回执中的 **MemoryRef** 用 Scope、`memory_id`、`version` 精确指向记忆；**SourceRef** 指向来源版本和内容指纹。

这一步成功代表已保存，不代表长期索引已经 Ready。材料的来源编号、记忆编号和后面的块编号各自有用途，不能混用。

<a id="b-2"></a>

### 第二步：B 保存记忆，RF 安排后台加工【基础】

#### 流程与接口

当前基础读取使用 **MemorySnapshot（记忆快照）**，直接包含 `content` 正文，以及 `status`、`projection_state`、来源等。`RememberPort.get` 读取它；`correct / lifecycle / delete` 处理更正、归档等状态变化和删除。

B 同时登记 TaskSpec。RF 领取后调用 B 的处理器；处理器通过 `ExtractionPort.extract` 提交 **ExtractionRequest**，带原文、来源、已有记忆及策略版本，返回 **ExtractionResult**，包含候选事实、模型及策略来源。默认基础路径保留原文形成事件记忆，真实提取模型与完整冲突处理仍有待接部分。

新增设计【待接】把记录分得更清楚：**SourceRecord** 登记原始来源及 `original_location`；**ProcessingRecord** 用 `task_id`、`stage`、产物和记忆引用记录加工进度；**MemoryRecord** 登记权威记忆，用 `body_location` 指向正文，并关联索引清单。它们复用 RF 任务，不另建一套队列；MemoryRecord 是目标业务结构，不能误以为当前已全面替代 MemorySnapshot。

<a id="b-3"></a>

### 第三步：B 建索引，但不执行一次完整 Recall【基础；多块发布待接】

#### 流程与接口

B 调共享能力 `EmbeddingPort.embed`，交 **EmbeddingRequest**，主要字段是 `texts`、`usage` 和 `model_space`；取回 **EmbeddingResult**，里面有向量、输入指纹和维度。这里 `usage=passage` 表示为待入库内容编码。

*B 取得编码结果后，组织 ProjectionTarget 和 ProjectionRequest，调用向量存储适配器完成写入与核验；当前调用名为 `ProjectionPort.project / inspect`。新增多块写入/核验契约为 `GenerationProjectionPort.project / inspect`，仍属于 B 的建库职责，业务接入尚待完成。两组投影接口及其对象现位于 `remember/contracts`；搜索接口独立为 A 的 VectorSearchPort / GenerationSearchPort。基础 SQLite/Milvus 写入实现也已迁入 B，新多块接口仍只完成契约。*

新设计由 **ProjectionManifest（索引发布清单）** 记录这版记忆的 `generation`、`body_hash`、`expected_chunk_count` 和全部块；其中每个 **ChunkDescriptor** 说明 `chunk_index`、字符范围、向量编号和输入指纹。全部预期块核验后，B 才调用 `MemoryFoundationPort.publish_projection`，用清单和预期修订更新 MemoryRecord。

因此“向量写请求被接受”和“记忆可被正式检索”是两个时点。A 的 Embedding 返回向量及编码信息；B 负责关联记忆、块、索引批次，写入、核验并发布索引。A 不替 B 组织投影业务，也不决定索引 Ready；A 自己的 Recall 仍负责查询和组包。

### 第四步：A 来要正文，B 提供内容并核验资格

#### 流程与接口

当前【已有】A 调 `MemoryReadPort.working / load`，分别按范围取 Working、按 MemoryRef 取记忆，得到 **MemoryReadBatch**，包含正文条目、资格和关系信息。最终提交前调用 `final_guard`，返回 **EligibilityBatch**，说明每条记忆当时是否仍可用及授权代次。

新增【待接】`MemoryFoundationPort.load_bodies` 返回 **FullBodyReadResult**，每条说明 `outcome`、完整 `content`、来源及读取路径。成功结果带 **GuardStamp（核验版本戳）**，记录对象修订、关系修订、授权代次与正文指纹，让 A 最后提交时能发现“刚读完就被改了”的情况。

#### 本段对象的完整字段

已在前文定义，本段直接复用：[MemoryRef](#remember-memoryref)。

本段首次展开：[MemoryReadBatch](#remember-memoryreadbatch)、[EligibilityBatch](#remember-eligibilitybatch)、[FullBodyReadResult](#remember-fullbodyreadresult)、[GuardStamp](#remember-guardstamp)、[ConflictGroup](#remember-conflictgroup)、[ArtifactRecord](#remember-artifactrecord)、[EligibilityResult](#remember-eligibilityresult)。嵌套请求/结果所需的子对象也一并列全。

### 第二步：根据当前事实决定是否迁移【已有基础】

#### 流程与接口

C 把当前层级、成功读取次数、内容大小、可用容量及输入水位组成 **SchedulingInput**，调用 `SchedulingPort.decide`，得到 **PlacementDecision**，其中 `outcome` 是保持或调整，`target_tier` 是目标层级，同时保存原因和策略版本。

需要执行时生成 **ActionIntent（明确动作）**，绑定 `action_id`、内容指纹、提供方实例和 `expected_epoch`。这个 action_id 是具体执行动作的编号，不是 RF 的 task_id。

新增视图设计【待接】由 **BufferEntry** 登记驻留地址、热度和保护引用，由 **SchedulingRound** 记录本轮输入水位、动作列表和次数上限，便于解释本轮为什么做这些动作。

### 第三步：执行器实际操作，C 核验结果【已有本地】

#### 流程与接口

C 调 `SchedulingPort.execute`，内部通过 `ExecutorPort.submit` 交 ActionIntent；执行器返回 **ExecutionFeedback**，说明原动作状态、观测和原因。`ExecutorPort.verify_read` 进一步产生 **ReadProof**，证明在目标位置实际读到了预期内容，关键是 `readable`、`content_hash` 和核验时间。

C 用 **ActionRecord** 持久保存动作、状态、反馈和清理进度。结果未知时，经 `SchedulingPort.reconcile`、`ExecutorPort.query` 查询原 action_id，不能换个编号盲目再做一次。

目前本地文件缓存复制与读取核验已有实现，这不等于生产介质迁移已经验收。

<a id="c-4"></a>

### 第四步：新地址交给 B，之后才处理旧副本【待接】

#### 流程与接口

新增 **MigrationPlan** 把源地址、目标地址、保护、地址交接与旧副本清理串起来。地址使用 RF 的 ResourceLocation；**ProtectionReference** 记录哪个任务或动作仍需要保留某份资源，避免它被过早删除。

C 把新地址与读取证明组成 **ReferenceHandoff**，带上 MemoryRef、预期对象修订、旧/新地址和证明引用，调用 B 的 `MemoryFoundationPort.accept_handoff`。B 返回 **ReferenceHandoffReceipt**，说明是否接受，以及新的修订。

满足交接和保护条件后，生命周期协调逻辑调用 C 的 `LifecycleCleanupPort.release_protection / cleanup`。清理请求 **CleanupRequest** 明确目标与保护编号；返回 **CleanupReceipt**，逐项记录清理状态和证据。不能仅凭“复制成功”就先删旧副本。

这条新增交接链仍需服务接入。职责边界是：C 证明新位置可读，B 决定权威地址能否变更，清理再按保护规则进行。
