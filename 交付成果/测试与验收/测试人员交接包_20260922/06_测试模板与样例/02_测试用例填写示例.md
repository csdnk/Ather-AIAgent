## TC-RF-HTTP-001 未认证访问健康接口

- 依据：PRD V1.3 租户与身份要求；RF HTTP 接入说明的业务请求认证规则。
- 模块/入口：RF，HTTP；P1；已实现，可在服务启动后执行。
- 前置：独立 HTTP 实例已启动；客户端不附带默认 Authorization 或会话凭据。
- 数据/故障：无业务数据、无故障注入。请求超时使用登记的环境配置。

| 步骤 | 操作 | 预期结果 | 证据 |
|---|---|---|---|
| 1 | 不带认证 GET /p3/live | HTTP 200，确认进程可响应 | 状态码、响应时间 |
| 2 | 不带认证 GET /p3/health | HTTP 401；不返回租户业务数据或健康快照 | 状态码、脱敏响应 |
| 3 | 使用合法已登记凭据 GET /p3/health | 在现有基础测试环境 HTTP 200；schema_version=p3/health/2；production_acceptance=false | 脱敏响应及对应 trace |

清理：无新增业务数据。注意 health 的 HTTP 200 不等于 ready=true；就绪门禁应单独测试 /p3/ready。
参考：[已有 HTTP 测试](https://github.com/csdnk/Ather-AIAgent/blob/2ee5b0e6c20246af63821ae19daaf44314aa3686/AgentJYS-main/tests/runtime/flows/test_http.py)。

## TC-B-HTTP-002 相同操作 ID 与同内容重复保存

- 依据：已有 TC-P3-02 保存幂等；完整框架讲解的保存入口和事务幂等规则。
- 模块/入口：B + RF，POST /p3/remember；P0；已实现。
- 前置：独立空库，已登记 t1 下 alice 的合法保存权限；本地 lexical 配置；本用例 operation_id 未使用。执行时使用固定的一份请求，不在重试时重新生成时间字段。
- 请求头：Authorization 使用测试凭据引用；X-Operation-ID=`tc_b_002_本次运行唯一编号`。
- 请求体：将 occurred_at 一次性替换为本次有效 UTC 时间，以下其余字段固定。

```json
{
  "selection": {},
  "source": {"kind": "text", "external_id": "tc_b_002_source", "external_version": "1", "occurred_at": "2026-09-22T01:00:00Z"},
  "content": {"kind": "text", "text": "项目预算为30万元"}
}
```

| 步骤 | 操作 | 预期结果 | 证据 |
|---|---|---|---|
| 1 | 发送固定请求，记录回执与原始 task_ids/memories | HTTP 200，有保存回执；不把保存成功当作索引 Ready | 脱敏请求、响应 |
| 2 | 同凭据、同 operation_id、同请求体再次发送 | HTTP 200，返回与首次相同的业务回执及标识 | 两次回执对比 |
| 3 | 用开发提供的只读记录检查入口按该操作/来源核对保存记录与初始任务 | 不额外创建重复的来源/记忆事实及初始任务；后台正常派生任务与重试重复创建要区分 | 按操作关联的只读快照 |

等待：无需等到全部后台处理完成才能比较保存回执。清理：关闭隔离实例，按登记流程复位本测试库。观察入口未提供时，第 3 步标记阻塞，不能仅凭相同响应推断持久层完全正确。
扩展用例单独编写：同 operation_id 改正文，应拒绝且原事实不变；具体 HTTP 错误映射查当前接口，不在本样例猜测状态码。

## TC-RF-SVC-003 维护完成但业务复验失败

- 依据：RF 实现说明“独立业务复验后才关闭异常”；流程为信号 → Incident → 原 Tasks → 业务复验。
- 层级：服务集成，调用 Foundation.dispositions 与 Foundation.tasks；P0；已实现，但需要测试夹具，不能只靠手工点击 HTTP 完成。
- 前置：隔离库、可控时钟、一个已授权目标；注册信号、操作、规则、维护处理器和独立验证回调。采用已有夹具 verification=False、samples=1；复验期限沿用该夹具配置。
- 故障注入：维护处理器成功返回，但独立业务验证回调返回未通过；不伪造“业务已恢复”。

| 步骤 | 操作 | 预期结果 | 证据 |
|---|---|---|---|
| 1 | observe 提交一个满足阈值的新鲜故障样本 | 创建一个异常及关联维护任务/操作，标识可追溯 | Incident、task_id、operation_id |
| 2 | tasks.run_once 执行维护任务 | 维护执行完成；不能据此将异常直接标 resolved | Task/Operation 状态、Incident |
| 3 | dispositions.reconcile 执行业务复验 | 现有夹具下 state=verifying，异常未关闭 | Incident 状态 |
| 4 | 按已有夹具推进 31 秒并再次 reconcile | state=attention_required，verification=unknown | 时钟配置及 Incident |
| 5 | 再推进 10 秒，提交同目标持续故障样本 | 不创建另一个未决操作；异常记录数量仍为 1 | 操作关联和异常列表 |

清理：销毁隔离实例、恢复回调和模拟时钟；不影响共享真实依赖。
参考：[RF 测试](https://github.com/csdnk/Ather-AIAgent/blob/2ee5b0e6c20246af63821ae19daaf44314aa3686/AgentJYS-main/tests/runtime/p3/test_runtime_services.py)中的 test_maintenance_success_does_not_close_failed_business_verification。
