## 原因与修改

1. Trace 聚合查询持有日志写入锁；异步主线程写入观测记录时等待同一锁，导致整个 HTTP 服务无法及时响应。查询改用独立只读 SQLite 快照，并增加覆盖聚合字段的索引。
2. 后台任务轮询反复读取、解析和校验已完成任务。改为在事务内通过状态索引读取活动任务，保留租约、并发限制、恢复与隔离校验。
3. 事件投递循环反复还原已经确认的历史事件。改为只读取待投递记录；事件批次之间主动让出执行机会，避免长批次持续占用异步主线程。
4. 对话脚本原先只显示 ReadTimeout。现在超时会标明中文步骤、HTTP 方法和路径，不自动重试写入，也不输出凭据。

没有清空数据库或重置历史任务。日志读取仍按数量和时间保留策略过滤；物理清理在启动和写入周期执行，页面读取不再触发清理。`last_pruned_at` 表示最近的物理清理时间。

## 补充：跨会话等待条件不匹配

用户失败运行 `dialogue_ddbb4e404de5468691f5175867b73811` 的长期提取与索引任务均为 succeeded。针对该业务范围的现场召回返回 HTTP 200、outcome=available，耗时 0.812 秒，正文包含“我的饮品偏好是可乐”。脚本的跨会话等待条件仍为“无糖咖啡”，因而一直等待，最终报告“跨会话长期召回超时”。这次失败与最初的 HTTP ReadTimeout 原因不同。
