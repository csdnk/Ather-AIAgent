# Agent 首字优化实施与验收

日期：2026-10-05。范围：现有 Agent 用户页面、本机 BFF、Azure 隔离测试 P3。

## 实施结果

已打通真实模型增量输出与页面增量展示，记忆保存不再阻塞回答显示。P3 召回任务获得独立调度机会，与其他启动任务轮流处理；同类任务按提交时间排序。新请求唤醒调度器，有处理进展时短暂让出后继续处理，不再每轮固定空等 5 秒。

入口：[Agent 用户平台](http://localhost:19010/)。本机 BFF 更新后需重新登录。管理后台入口与账号数据体系保持独立。

## 真实端到端测量

测量路径：登录 user_a → 页面使用的聊天 API → 当前 Azure P3 → 实际配置的 LLM → 增量读取回答 → 确认 P3 保存成功。未使用模拟模型或模拟 P3。

“首字”从提交消息前计时，到客户端首次读取到非空模型正文；不是转圈、状态提示或预置寒暄。API 测量客户端每 250 毫秒检查一次，因此包括检测延迟，不能等同于浏览器绘制时间。

| 编号 | 问题类型 | 首轮仅流式与 FIFO 改进后的首字 | 完成调度优化后的首字 | 完整回答 | P3 保存 |
|---|---|---:|---:|---:|---|
| F01 | 检索霁月项目负责人及交付日期，简短回答 | 58.645 秒 | **18.562 秒** | 18.905 秒 | 成功 |
| F02 | 结合记忆生成六点交付检查清单 | 60.145 秒 | **26.903 秒** | 29.682 秒 | 成功 |

F01 第一份增量包含 1 个字符、状态为 pending；F02 的正文长度依次为 2、303、604、615 个字符，前三份状态为 pending，最后一份为 complete。两条对话都实际得到 P3 召回结果并最终保存成功。

这是同一组问题的顺序实测，不是控制全部后台负载、缓存与数据变化的基准实验。不能据此承诺所有请求均达到该时间，亦未形成 p95 或并发容量结论。

## 代码行为

1. 模型请求使用流式响应，解析正文增量与正常结束标记。首段立即校验并持久化，随后按短时间窗口发布；截断或异常流不标为完整回答。
2. 前端在 pending 状态下显示已收到正文，生成阶段按 250 毫秒间隔增量读取；检索阶段显示检索状态。保存状态使用独立、较慢的刷新节奏。
3. 答案完成和待保存记录一起持久化。保存使用原始消息、稳定操作编号，不保存模型编造内容。保存状态不决定答案是否可读。
4. 保存请求若状态不确定，查询原操作，不以“未查到”作为再次提交的依据。已持久化的待保存记录可在重新打开会话、身份仍有效时继续处理。当前恢复由会话读取触发，并非无人访问也持续运行的独立保存守护进程。
5. 本机认证连接复用 HTTP 客户端，默认以 127.0.0.1 访问已配置的本机身份服务；JWT 的公共 issuer、签名、受众、实时账号版本及令牌有效性检查保留。
6. P3 待启动任务按召回/其他任务交错取出，各类内部按创建时间排序。跨调度轮次也轮换处理机会，避免每轮只处理一个任务时后台任务被持续挤占。控制任务原有轮换、幂等、确认和重试恢复机制保留。
7. P3 仍保留每轮约 2 秒的转交预算；有处理进展时约 50 毫秒后继续下一轮，无进展时恢复原轮询间隔。新受理请求触发唤醒。

## 权限和失败处理

- 每份发布的正文快照之前仍检查身份及 P3 来源有效性，用户/租户归属仍由后端确定。
- 账号停用后不再追加正文；其他用户、其他租户及管理员不能读取个人会话。
- 发现召回结果失效时停止流式输出，清除当前保存的正文和来源快照，重试使用新的召回代次。
- 模型连接异常时仅保留已经通过发布校验的正文，明确标记回答未完成；重试清空旧片段，旧执行不能覆盖新执行。
- 已经合法显示过的内容无法从用户记忆中撤回，流式发布仍以每次校验时的权限与来源状态为准。
