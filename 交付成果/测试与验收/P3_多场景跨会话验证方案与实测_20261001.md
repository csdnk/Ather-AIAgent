# P3 多场景跨会话验证方案与实测

日期：2026-10-01。目标：在新会话不携带旧聊天正文的条件下，检验长期记忆可用性、版本与来源一致性，以及不该共享的内容是否被隔离。

**本轮已执行18项，15项通过、3项未通过；另1项依赖阻塞、2项未执行。** 跨会话记忆、范围隔离、明确更正与删除在本轮指定条件下通过；无答案与混合主题相关性未通过。本轮使用独立 HTTP 参考客户端调用 Azure P3，没有接入 P4 Web，也没有调用聊天大模型。15项通过中含CS-17材料准备和CS-21原文哈希检查，不能说成15项全部是跨会话产品功能通过；CS-18只判定正确材料存在，无关项仍完整报告。

测试脚本与原始响应在项目外保存，正式结果在本文按证据编号汇总。没有修改产品代码或云端配置，没有修复或隐去本轮失败。

跨会话不是换一个窗口就算通过。P3 本身没有聊天会话管理对象，`client_session` 是上层客户端标记；必须同时证明新 HTTP 请求没有旧正文、长期范围相同、返回内容确实来自前序会话保存的 P3 记忆。

## 范围规则：应记得与不应串入

- 同一用户在同一项目中开 A/B/C 会话：保存带各自 `session_id`，长期 Recall 使用共同 `task_id`，不限制旧或新 `session_id`。
- 同一用户切换不同项目：长期 Recall 使用不同 `task_id`，不得混入另一个任务范围的正文。此处的项目范围是测试映射，生产需由 P4 的可信业务上下文管理，不能把浏览器随意填写的项目 ID 当作权限。
- Working：明确限制对应 `session_id`；当前会话允许读取，新会话不继承旧会话 Working。这条规则与同用户长期记忆跨会话共享同时成立。
- 跨用户/租户：需真实的两个凭据与授权配置。请求体伪造 user_id 被拒绝是边界证据，不能代替完整多租户联合验收。

示例调用的共同项目范围：

```json
{
  "query": "青禾项目预算和汇报安排是什么？",
  "selection": {"task_id": "mc_unique_meeting"},
  "sources": "long_term",
  "token_budget": 2000
}
```

新会话只发送上述问题及可信范围。预算20万、汇报时间、旧聊天摘要、expected答案均不加入检索请求；期望值只保留在测试判定端。所有业务请求使用当前 P3 Bearer，原命令使用稳定 `X-Operation-ID`。

## 失败诊断与下一步

CS-11、19、20共同暴露了相关性筛选不足：同范围材料可以找到并排序，但低相关或无答案内容仍可能入包。当前[SQLiteGenerationSearch](../../AgentJYS-main/src/aether_agent_memory/recall/basic/generation_search.py)计算作用域内命中分数后均进入排名；[候选资格检查](../../AgentJYS-main/src/aether_agent_memory/recall/basic/candidates.py)核对版本、正文和权限；[ContextAssembly](../../AgentJYS-main/src/aether_agent_memory/recall/basic/assembly.py)将合格材料按数量/token预算组包，可选reranker主要调整顺序。没有得到能支撑这组无答案/相关性要求的拒绝行为。存储与鉴权正确不等于材料能回答当前问题。

需要先固定代表性正/负问题、无答案与混合主题标注，确定相关性覆盖、无关项比例和无答案行为目标，再为真实Embedding/Reranker或其他判定机制设计拒绝/降级策略，保留当前版本/来源/权限守卫并复跑失败样例。本报告不直接给出未经标定的相似度阈值，也不通过减少测试主题、客户端隐藏返回项或增加超时宣布修复。

执行顺序：保留本轮3项失败 → 完成P4当前契约与页面接入 → P4复跑CS场景并记录页面与后端证据 → 独立环境接真实身份、模型/P2并执行EXT样例及故障场景 → 固定负载与公司UAT。P4可以继续接入展示当前能力，但公司演示必须说明相关性限制；要求无答案/精确筛选的业务验收应以修复复验为前提。

本轮结束后再次查询，四个现有Pod仍Ready，重启计数均0，P3 readyz为ready。没有以此替代业务判定，也没有执行长稳、备份恢复或生产高可用验收。原始响应、固定探针与逐请求日志保存在项目外，按CS编号追溯；已核对记录中无Bearer凭据。
