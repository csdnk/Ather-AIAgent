## 1. 当前结论

继续采用 Budibase 开源自托管版作为管理界面的候选。固定版本 v3.47.0 已在本机与真实 Keycloak 26.8.0 完成基本 OIDC 登录；实例实际许可为 free，没有借助试用功能。独立的 BFF Authorization Code + PKCE 登录与 Budibase 登录可以通过签名身份进行同账号核对，跨账号核对被拒绝。

这证明基础登录和身份关联可行；尚未证明完整管理 API、短期 REST 委托、业务租户隔离和撤销同步。平台管理员、租户管理员、普通用户的业务权限仍需由新平台目录和 API 实现，不能用本轮 Budibase 用户权限测试替代。

P3 的隐式身份选择已形成候选修改：多个有效身份返回 FORBIDDEN，不再按租户名排序选择第一个。真实 Azure PostgreSQL 的失败复现与修改后回归均已执行。该候选只在隔离源码和测试中使用，未部署到现有常驻 P3。

## 4. 重要问题与处理

1. **跨实验复用数据卷**：独立审查发现固定 Compose 项目名会让新目录生成的新密码复用旧账号数据库。先复现失败，再改为每个实验独立项目名；配置专项通过。固定端口一次只运行一套实验。
2. **localhost Secure Cookie**：Keycloak 正常签发 Secure Cookie，Python CookieJar 与浏览器对 localhost 的行为不同，初始真实协议测试报登录 Cookie 不存在。测试客户端仅对两个精确实验 origin 模拟浏览器行为，未关闭服务端安全 Cookie。
3. **缺少 token audience**：初始 Budibase access token 没有 aud，身份关联原语按要求拒绝。给实验 client 加入专用 audience 后，在新实验实例上完成真实关联验证；未放宽验签、issuer 或 audience 检查。
4. **旧多组织监测页兼容性**：旧页面先调用不带租户的 `/p3/auth/me`，获得身份后才显示组织选择器。新隐式拒绝规则会阻止旧多组织账号完成首次登录。因此该 P3 候选不能单独发布到仍承载旧页面的环境；必须随新 BFF 唯一租户登录与入口替换一并验证、切换。现有源码主目录与部署未接收此修改。
5. **运行环境发生变化**：中途重新检查时 Docker 镜像与容器清单为空，与此前下载状态不同；本任务没有执行 Docker reset/prune。已按当前状态重新拉取并建立专属实验环境，未将此前状态当作当前证据。

独立审查检查了身份逻辑与实验配置，并对新增签名关联原语另行审查。数据卷问题已修复；新增原语未发现 Critical/Important 问题。旧页面兼容性保留为明确发布门槛，不能声称已经回归通过。

## 5. 下一步实施顺序与退出条件

1. 完成生产用途的 Admin BFF 网络与会话适配：固定可信 Budibase/JWKS 地址，验证同 issuer 的登录会话，建立服务端关联，处理重新登录、过期、注销和账号切换。禁止直接接收浏览器提交的身份文档作为证明。
2. 在真实 Budibase 发布应用中验证短期 REST 委托：请求只访问固定管理 API，身份不混用，凭据不进入共享配置、导出和日志。该项是低代码接入仍待完成的关键门槛。
3. 建立 PostgreSQL 业务目录、唯一有效租户归属、平台/租户管理员权限、管理 API、审计与身份同步状态；测试跨租户与提权反例。
4. 接入新 Agent 会话、LLM、P3 Recall/Remember 与原请求恢复，再实施管理页面。
5. 用户与管理员正反例验收通过后切换旧入口，再删除被替换代码和配置；P3 数据与共享契约保留。

当前没有新的普通用户 Agent 页面可交付使用，没有完成租户/用户 CRUD，没有清理旧 P4，也没有完成 Azure 新平台部署。本报告是阶段进展与验证边界，不是产品替换完成报告。
