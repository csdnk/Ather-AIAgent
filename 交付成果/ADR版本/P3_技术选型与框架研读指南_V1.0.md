## 2. 用一条请求理解它们的位置

```text
可信身份 → P3 业务租户与资源授权
    │
    ├─ Remember：保存来源和事实 → 提交后台待办
    │      └─ LangMem 候选提取 → 自有校验/版本提交
    │             → 共享 Embedding → 向量投影 → 核验长期就绪
    │
    ├─ Recall：选择来源 → Query Embedding → 候选检索
    │      → 当前资格核验/精确正文 → 融合/可选重排
    │      → 冲突组织/token 预算 → 最终核验 → ContextPack
    │
    └─ 两侧持久事件 → Operate：重新读取当前状态
           → 计算期望 → 持久动作 → 执行 → 查询观察 → 收敛

共同使用：事务、任务、Outbox/Inbox、授权、Trace、日志、健康与恢复
正式存储集成：通过 Provider 对接 P2；本地适配器用于阶段验证
```

LangMem 不是大模型本身；BGE 是模型；FastEmbed 是调用封装；ONNX Runtime 负责执行模型；Milvus 保存并搜索向量。LlamaIndex 提供可参考的流程组织，不能让这些部件自动变成满足 PRD 的完整 Recall。

直接从本项目[ThreeFlows 装配入口](../../AgentJYS-main/src/aether_agent_memory/runtime/flows/host.py)阅读：看它如何把 `Foundation`、Remember、Recall、Operate 和可替换适配器组合起来。先分清“默认注入了谁”和“代码支持谁”。

## 3. Remember：LangMem 应该怎么看

### 3.1 为什么选，具体借什么

我们需要把对话或文本转为结构化候选。LangMem 提供模型调用、Schema 约束和已有记忆参与提取的组织方式，可以减少这部分适配工作。它不负责我们要求的业务租户、来源可信性、正式版本、删除屏障，以及事实和待办的一次事务提交。

直接采用的边界是：`ExtractionRequest → LangMem Core → ExtractionResult`。候选还需 Remember 审核才能成为正式事实。选择这条边界，可以保留自有持久化和 P2 对接，避免把权威数据交给框架默认 Store。

### 3.3 我们用在哪里，有什么限制

读本项目[extraction.py](../../AgentJYS-main/src/aether_agent_memory/remember/basic/extraction.py)中的 `LiteralExtraction`、`LangMemExtraction.from_model`、`extract`，再读[Remember Service](../../AgentJYS-main/src/aether_agent_memory/remember/basic/service.py)。

当前适配显式关闭自动更新和删除，输出要求带原文证据；校验还要求事实文本出现在证据引文中。这是保守的逐字依据约束，**不等于已经实现语义提纯、改写、压缩和冲突裁决**。真实模型未注入时走逐字保存，不能向甲方说 LangMem 已完成真实理解链路。

学习实验：分别输入“我喜欢咖啡”“我不喝咖啡”“同事说他喜欢咖啡”“假如我喜欢咖啡”，记录候选和证据；在模型返回、正式提交前退出，再恢复。检查是否仅出现一组正式效果，而非要求模型调用只发生一次。

### 3.4 具体例子：LangMem 与大模型分别做什么

输入来源 `source_01` 的正文：“本项目最终批准预算为十五万元。”

```text
Remember 提取任务
  → LangMem：组织提取指令、输出 Schema 和输入消息
  → 已配置的大模型：根据输入生成结构化结果
  → LangMem：组织为候选结果返回
  → 我们的适配器：检查事实文本和原文证据
  → Remember：确定正式 ID、版本、来源及提交资格
  → 在事务中保存事实与后续待办
```

候选示意为 `text="最终批准预算为十五万元"`，`evidence_quote="本项目最终批准预算为十五万元。"`。LangMem 是组织模型调用的库；生成文本的能力来自配置的大模型；正式 ID、权限和版本由 Remember 决定。三者分别承担不同责任。

如果模型返回“预算为五十万元”，原文依据校验应拒绝，不能因为 JSON 格式正确就提交。如果返回忠实改写但不满足当前逐字证据约束，也可能被现有适配器拒绝；这说明当前规则偏保守，需要另行设计语义提纯质量，不能简单放开检查。

如果模型已经返回、事务尚未提交时进程退出，恢复后可能再次调用模型。最终是否重复形成正式记忆，由业务幂等和事务决定。给 LangMem 配一个 Store 并不能自动获得这个保证。

读懂标准：能指出“模型输出结束的位置”和“正式事实提交的位置”，解释为什么更正和删除不能直接听从模型生成的 ID。

### 4.3 怎样转成我们的实现

读[retrievers.py](../../AgentJYS-main/src/aether_agent_memory/recall/basic/retrievers.py)的来源检索与覆盖状态，再读[components.py](../../AgentJYS-main/src/aether_agent_memory/recall/basic/components.py)及[Recall Service](../../AgentJYS-main/src/aether_agent_memory/recall/basic/service.py)。接口以[Recall ports](../../AgentJYS-main/src/aether_agent_memory/recall/contracts/ports.py)为准。

融合需要有自己的确定语义。例如 RRF 可写为 `score(d) = Σ 1 / (k + rank_i(d))`，但必须固定 k、名次起点、并列顺序和归并键。本地 LlamaIndex 快照的 RRF 按节点 hash 归并、名次从零开始；项目契约按 `memory_id + version` 归并、名次从一开始。名称相同不代表输出相同。默认多查询生成也可能额外调用大模型，不能无意识引入延迟和成本。

学习实验：准备 Working 与长期记忆两路结果，让同一版本同时命中，让旧版本仍留在向量索引，再中断长期来源。打印原始候选、剔除理由、融合名次及最终包。有效 Working 是否足以降级，由来源要求和策略判定；必须来源失败不能伪装成正常无结果。

读懂标准：能解释向量 TopK 为什么不能直接返回用户，能追踪每条候选为何保留、被拒绝或因预算未进入 ContextPack。

### 4.4 具体例子：统一接口怎样支持替换与组合

| 接口或类型 | 输入 | 输出 | 可替换的位置 |
|---|---|---|---|
| `QueryBundle` | 文本及可选查询信息 | 统一查询对象 | 包装查询，不承担业务身份认证 |
| `BaseRetriever.retrieve/aretrieve` | 查询 | `List[NodeWithScore]` | 换检索来源或向量适配，保持外层调用方式 |
| `BaseNodePostprocessor.postprocess_nodes` | 查询及候选列表 | 新候选列表 | 加入过滤、重排等步骤 |
| `BaseSynthesizer.synthesize` | 查询及材料 | 回答结果 | 更换回答组织方式或模型 |

`NodeWithScore` 表示节点与分数。节点包含正文、标识、metadata 等信息，但字段存在不代表已经通过 P3 当前版本或授权核验。

组合方式有两种：把多个检索器装进一个融合检索器，对外仍然提供检索接口；或者把后处理器排成列表，前一步输出交给下一步。下面是查询引擎的简化示意：

```python
nodes = retriever.retrieve(query)
for processor in processors:
    nodes = processor.postprocess_nodes(nodes, query_bundle=query)
response = synthesizer.synthesize(query=query, nodes=nodes)
```

源码中的 `RetrieverQueryEngine` 也提供只检索的 `retrieve/aretrieve`，所以它并非必须生成回答。它可以承载定制逻辑，关键是默认组件尚未实现 P3 的业务保证。

本项目的组合例子是“Working 来源检索器 + 长期记忆检索器 → 候选汇总”。两个来源必须同时返回执行状态：Working 找到一条材料、长期来源超时，与两个来源都成功但只找到一条材料，是不同结果。因此我们的来源契约除候选外还需保留覆盖状态与失败原因，不能只用一个列表表达一切。

例如检索命中预算旧版 20 万和新版 15 万：后处理器可以扩展成调用 Remember 核验，但“哪个版本已失效”的依据必须来自 Remember。若用户在检索后撤权，还需交付前再次核验。仅调整 Query Engine 的提示词无法实现这些保证。

## 5. Embedding、重排、预算与向量库

### 5.1 BGE + FastEmbed + ONNX Runtime

已补充**第三方源码中文注释版**（FastEmbed 0.8.0、ONNX Runtime 1.30.0）：先读 [TextEmbedding](../架构设计/第三方源码中文注释/fastembed/text/text_embedding.py) → [Query/Passage 基类](../架构设计/第三方源码中文注释/fastembed/text/text_embedding_base.py) → [ONNX 具体实现](../架构设计/第三方源码中文注释/fastembed/text/onnx_embedding.py) → [分词与批次执行](../架构设计/第三方源码中文注释/fastembed/text/onnx_text_model.py)；会话装配看 [OnnxModel](../架构设计/第三方源码中文注释/fastembed/common/onnx_model.py)，真实推理边界看 [Session.run](../架构设计/第三方源码中文注释/onnxruntime/capi/onnxruntime_inference_collection.py)。各方法前和内部均标出输入输出、处理阶段及 P3 适配责任。

**目的：把文本变成可比较的向量。** BGE 决定编码能力，FastEmbed 负责模型加载及调用封装，ONNX Runtime 执行计算。采用本地路径便于明确模型空间和部署依赖，但中文领域效果、截断、算力和版本兼容仍要验证。

阅读顺序：

1. [BGE / FlagEmbedding](https://github.com/FlagOpen/FlagEmbedding)：先读目标模型卡、Query 指令、最大长度与相似度用法，不先读训练代码。
2. [FastEmbed](https://github.com/qdrant/fastembed)：看文本输入、批量编码、支持模型及模型缓存。
3. [ONNX Runtime Python API](https://onnxruntime.ai/docs/api/python/api_summary.html)：看 InferenceSession、输入输出和 Execution Provider；先不研究算子优化。
4. 本项目[p3.py](../../AgentJYS-main/src/aether_agent_memory/recall/embedding/p3.py) → [native.py](../../AgentJYS-main/src/aether_agent_memory/recall/embedding/native.py) → [backends.py](../../AgentJYS-main/src/aether_agent_memory/recall/embedding/backends.py)，看业务接口如何落到模型后端。

Remember 的 Passage 和 Recall 的 Query 共用模型空间约定：模型/修订、分词预处理、指令、截断、归一化、维度必须兼容。“都是 512 维”不能证明空间相同。更换模型通常需要新投影及明确切换，不能悄悄混用旧向量。

双编码检索指 Query 和 Passage 分别编码后比较。本项目长期记忆采用稠密向量检索；多来源召回指 Working 与长期记忆等业务来源的候选汇总、去重和排序。

#### 三个名称分别是什么

| 名称 | 类型 | 实际工作 | 不负责什么 |
|---|---|---|---|
| BGE（BAAI General Embedding） | 智源推出的模型系列 | 通过训练好的参数把文本编码成向量 | 不保存记忆，不决定事实当前是否有效 |
| FastEmbed | Python 模型调用库 | 加载支持的模型、分词、组织批次、调用推理并整理向量 | 不管理 P3 的版本、任务或权限 |
| ONNX | 模型交换格式 | 描述模型的计算结构与参数，常见文件为 `.onnx` | 文件格式本身不会执行计算 |
| ONNX Runtime | 推理执行引擎 | 加载兼容模型，在 CPU 或配置的其他硬件上执行计算 | 不理解 P3 的业务成功条件 |

BGE 决定模型如何编码；FastEmbed 帮程序调用模型；ONNX Runtime 实际执行计算。它们是同一条向量生成路径中的不同层次，不是三个依次理解文本的大模型。

#### 从一句正文到向量，再到查询

```text
正文：“项目预算上限为十五万元”
  → P3 EmbeddingPort：绑定用途 Passage、模型空间和输入身份
  → FastEmbed：使用相应 tokenizer，将文本转换为模型输入
  → ONNX Runtime：执行选定 BGE 模型的计算
  → FastEmbed：按模型配置整理输出，得到向量
  → P3 适配器：检查结果数量、维度、数值和输入绑定
  → 投影任务：保存向量及记忆版本引用

问题：“这个项目最多能花多少钱？”
  → 同一模型空间的 Query 编码
  → 查询向量与存量正文向量比较
  → 找到语义相关的记忆候选
```

下面仅展示 FastEmbed 的基本调用方式；示例模型名称不构成新增选型，实际使用以项目模型绑定为准。完整项目必须保留 Query/Passage 预处理约定和上述校验。

```python
from fastembed import TextEmbedding

model = TextEmbedding(model_name="BAAI/bge-small-zh-v1.5")
vectors = list(model.embed(["项目预算上限为十五万元"]))
```

首次使用通常需要取得模型文件，后续可利用本地缓存。无可用模型文件时加载会失败，不能伪造一个零向量作为成功。部署要明确模型文件的位置与版本，不依赖每次启动都能联网下载。

ONNX Runtime 常由 FastEmbed 间接调用。它可通过 Execution Provider 选择执行后端；安装了运行时不等于自动具备 GPU 环境，图优化也不保证所有模型一定更快。当前先读 CPU 主链及模型加载、输入输出、线程资源与兼容性，不必先研究底层算子。

本项目 `NativeP3Embedding` 将模型描述绑定为业务模型空间，并在数据库中核对原有绑定。这样可以拒绝把新模型向量混入旧投影；当前实现入口是本节前面链接的 `p3.py`。语义相关的错误事实仍可能获得高分，后续 Recall 必须核验版本与来源。

学习实验：同一模型编码一组中文问句与正文，检查对应关系；故意改变空间标识，确认系统拒绝混用，而不是勉强返回结果。

### 5.2 Sentence Transformers / CrossEncoder

第三方源码中文注释版：[cross_encoder/model.py](../架构设计/第三方源码中文注释/sentence_transformers/cross_encoder/model.py)，依据已安装的 Sentence Transformers 5.7.0。按 `__init__ → predict → rank` 阅读，内部标明组批、联合输入、前向计算、分数变换和恢复输入顺序；此版本路径与旧教程的 `CrossEncoder.py` 不同。

**目的：在少量候选内提高相关性排序。** 双编码先快速找候选，CrossEncoder 再联合输入“问题 + 某条候选”输出分数。它增加推理时间，所以不对全部记忆逐条执行，也不能找回第一阶段从未召回的材料。

读[CrossEncoder 使用说明](https://www.sbert.net/docs/cross_encoder/usage/usage.html)，重点看成对输入、`predict`、长度截断、批处理和分数含义；再读本项目[reranking.py](../../AgentJYS-main/src/aether_agent_memory/recall/basic/reranking.py)与[config.py](../../AgentJYS-main/src/aether_agent_memory/recall/basic/config.py)。

本项目默认 `disabled`，配置为 `required` 或 `fallback` 时才启用。研究重点是：重排超时如何反映到结果、降级是否可见、分数是否仅用于排序。不同模型的分数不能直接解释为统一可信概率。

#### Sentence Transformers 与 CrossEncoder 分别负责什么

**Sentence Transformers 是 Python 模型工具库；CrossEncoder 是联合读取两个文本并评分的模型方式，也是该库提供的一个调用类。** 实际能力来自加载的模型权重，它们不是两个先后执行的重排模型。

Sentence Transformers 也可以运行生成向量的模型，但我们当前的向量生成路线采用 FastEmbed；这里采用它是为了加载和调用重排序模型。

| 对比项 | 前面的双编码检索 | CrossEncoder 重排 |
|---|---|---|
| 输入组织 | 问题与正文分别编码 | 每次联合输入问题与某条正文 |
| 输出用途 | 用向量比较，从大量内容中找候选 | 对已经找到的候选逐对打分 |
| 可提前计算 | 正文向量可提前计算和保存 | 最终分数依赖这次问题，需重新计算 |
| 使用范围 | 大范围候选发现 | 少量已获准候选重排序 |

#### 具体例子：最终批准预算

用户问“项目最终批准的预算是多少？”，初步检索得到：

| 候选 | 内容 | 为什么可能需要重排 |
|---|---|---|
| A | 项目最初申请预算 20 万元 | 主题相关，但“申请”与“批准”不同 |
| B | 项目最终批准预算 15 万元 | 与问题关注点直接对应 |
| C | 项目已支出 8 万元 | 也与预算相关，但回答的是支出 |

CrossEncoder 分别读取 `[问题, A]`、`[问题, B]`、`[问题, C]`。假设输出分数为 `[0.45, 0.91, 0.20]`，排序便为 B、A、C。**这些分数仅为示意，不是实测值，也不表示 B 有 91% 的事实正确概率。** 模型可能排序错误；必须用领域样本验证。

```python
# 调用方式示意：model_path 是已选定并固定版本的重排模型路径
from sentence_transformers import CrossEncoder

model = CrossEncoder(model_path, device="cpu", trust_remote_code=False)
scores = model.predict([
    ("项目最终批准的预算是多少？", "项目最初申请预算20万元"),
    ("项目最终批准的预算是多少？", "项目最终批准预算15万元"),
])
```

项目中 Recall 只依赖 `Reranker.rerank(ctx, query, documents)`，具体适配器 `CrossEncoderReranker` 再调用该库。当前实现会延迟加载模型、检查成对输入是否超长、按批次推理，并校验分数数量与有限数值；超长时拒绝，而非静默截断后当作完整正文完成评分。

执行使用受限线程与计算槽位。调用方超时不意味着 CPU 推理线程已经停止，因此旧计算未结束前不会立即释放槽位让新任务无限堆积。这是项目适配器补充的资源控制，不是调用一次 `predict` 就自动获得的业务保证。

流程位置为“已获准候选与正文 → 融合 → 可选重排 → 预算与最终复核”。即使 B 的分数最高，如果 B 已被删除，也必须排除；如果初步检索根本没有找到 B，重排器无法把它凭空补回来。

学习实验：固定候选对比启用前后顺序，再让重排器超时，分别验证 required 和 fallback。无论哪种策略，都不能绕开授权和版本核验。

### 5.3 tiktoken

第三方源码中文注释版（tiktoken 0.14.0）：[registry.py](../架构设计/第三方源码中文注释/tiktoken/registry.py) 的 `get_encoding` → [core.py](../架构设计/第三方源码中文注释/tiktoken/core.py) 的 `Encoding.encode/decode`。注释解释编码表缓存、特殊 token 策略、Rust 调用边界，以及为什么截断后必须重新检查正文。

**目的：让最终上下文符合真实长度预算。** 字符数、汉字数与 token 数不等价，同一文本在不同 tokenizer 中也可能不同。

读[tiktoken](https://github.com/openai/tiktoken)的 `get_encoding`、`encoding_for_model`、`encode/decode`，再读本项目[tokenization.py](../../AgentJYS-main/src/aether_agent_memory/recall/basic/tokenization.py)。当前默认 `o200k_base`，这是配置选择，不代表已确定下游一定采用某款模型。

ContextPack 的文本预算不等于整个模型窗口；下游还需为系统提示、消息包装、工具定义和输出预留空间。读懂目标是能解释计数涵盖哪些文本、引用/标题是否占预算、冲突组超预算如何整体处理。当前完整冲突组仍是 ADR 记录的待完善项。

#### 具体例子：按 token 计数怎样落地

```python
import tiktoken

encoder = tiktoken.get_encoding("o200k_base")
text = "[来源：会议纪要，版本2] 项目预算十五万元。"
token_count = len(encoder.encode(text))
```

这里计数的对象是准备交付的字符串，包含引用与正文。不能只计算正文，再添加大量标题、引用而不计入预算。示例不硬写 token 数，实际数值由指定 tokenizer 算出。

假设一次完整组装实际计算为 90 token，允许预算为 80，系统需要按规则舍弃较低优先级材料并重新计数。如果两条材料共同表达一个必须保留的冲突组，不能为了凑数只保留其中一方。tiktoken 只负责分词计数，哪些材料可以舍弃仍是 Recall 的规则。

学习实验：中文、英文、数字和引用混排，展示同一包的字符数与 token 数；预算不足时如实裁剪或舍弃合规单元，不能截出改变否定和条件含义的片段。

### 5.4 Milvus / pymilvus，以及 P2 Provider

**目的：保存与检索向量候选。** 读[Milvus 文档](https://milvus.io/docs)中的 Collection/Schema、标量过滤、Search、Upsert/Delete 和一致性；Python 调用参考[pymilvus](https://github.com/milvus-io/pymilvus)。本项目入口：[milvus.py](../../AgentJYS-main/src/aether_agent_memory/recall/basic/milvus.py)。

重点不是先调索引性能，而是回答：向量与哪条记忆的哪个版本绑定？查询时如何强制 scope？写入成功是否等于可检索？删除延迟时怎样阻止旧内容交付？最后一项仍依赖 Remember 权威资格与最终核验。

P3 正式使用 P2 的对象、向量和约定控制能力；Milvus 是已准备的适配路线，不是未经联合评审就新增的第二套生产权威。看[协作接口目录](../../AgentJYS-main/docs/p3/contracts/01_协作接口与事件目录.md)，区分接口约定、适配器和真实端到端证据。

学习实验：先通过故障替身验证超时、旧版本和错误；有真实服务后再验证写入可见性、scope 过滤与恢复。本阶段没有真实 Milvus，不能把协议测试写成真实联调通过。

#### 具体例子：数据库与客户端的区别

Milvus 是运行中的向量数据库服务；pymilvus 是 Python 程序调用它的客户端。类似“数据库与驱动”的关系，安装 pymilvus 不会自动得到一个可用 Milvus 服务。

一次向量记录可概念性表示为 `记忆ID=m1、版本=2、模型空间=s1、业务范围=甲公司/用户A、向量=…`。服务端按可信范围查询，返回候选 `m1@2` 及分数；Recall 再向 Remember 核验和取得精确正文。

如果索引里仍存在 `m1@1`，删除旧向量是后台清理责任；立即阻止旧正文进入新 Context 则依赖 Remember 的当前资格。向量库成功返回一条记录，只说明完成了检索步骤。

## 6. 公共可靠底座：事务、任务和事件

### 6.1 为什么目前使用 SQLite 与自有最小机制

当前单机阶段需要把业务记录、待办和事件放进同一事务，并尽快验证三个流程。SQLite 可以降低部署复杂度，UoW 统一事务入口；代价是我们要维护任务状态机、有限重试、去重与恢复，且不能直接推导出多主机高可用能力。

| 机制 | 需要读懂的语义 | 本项目源码 |
|---|---|---|
| UoW / 原子提交 | 同一连接事务中一起提交或回滚；不跨越模型、Milvus、P2 的网络调用 | [storage.py](../../AgentJYS-main/src/aether_agent_memory/runtime/foundation/storage.py) |
| CAS / revision | 更新时带预期版本，旧读者不能覆盖新状态 | 同上，以及[公共 ports](../../AgentJYS-main/src/aether_agent_memory/runtime/contracts/ports.py) |
| Outbox | 保存业务事实时同时保存“待发事件”；发不出去仍有待办 | [events.py](../../AgentJYS-main/src/aether_agent_memory/runtime/foundation/events.py) |
| Inbox / 消费去重 | 按消费者和稳定事件身份去重，业务结果与消费记录可靠衔接 | 同上 |
| 任务与租约 | 领取、续约、过期、尝试、截止时间、有限重试 | [tasks.py](../../AgentJYS-main/src/aether_agent_memory/runtime/foundation/tasks.py) |
| 提交屏障 | `guard` 核对租约身份与有效期，提交前再次检查；防旧执行者迟到覆盖 | 同上 |
| 恢复判定 | 公共层发现异常，流程 Handler 决定重做、查询、终止或人工处理 | 同上与各流程 Service |

先读[公共基础通俗说明](../架构设计/公共基础通俗说明.md)，然后读[SQLite 原子提交](https://www.sqlite.org/atomiccommit.html)、[Transactional Outbox](https://microservices.io/patterns/data/transactional-outbox.html)。Outbox 是模式，不是协议标准，也不是要安装的第三方产品。

外部调用不能长时间占着本地事务。通常先提交意图，再调用外部，再事务提交结果；中间失败由持久状态解释。租约屏障只能阻止不合格的本地提交，**不会自动撤销已经发生的远端副作用**，远端仍需稳定操作 ID、查询和幂等协议。

### 6.2 用五个故障理解恢复

| 注入位置 | 正确解释与处理 | 必须查看的事实 |
|---|---|---|
| 业务提交后、投递前退出 | Outbox 仍在，恢复投递 | 业务记录、待发事件 |
| 消费提交后、确认前退出 | 再投递可发生，不能重复计热或重复产生业务效果 | 消费去重与领域结果 |
| Worker 领取后退出 | 租约过期，触发领域恢复 | Task、Attempt、Lease、恢复记录 |
| 旧 Worker 在接管后返回 | 本地提交被旧租约屏障拒绝 | 新旧租约身份、版本冲突 |
| 外部执行成功但回执丢失 | 保留 Unknown，查询原操作 | Action、原 action_id、执行端观察 |

理解完成的标志是：即使技术日志被清理，仍能从事实和待办确定下一步；但保留日志时能够解释这个决定的完整执行过程。

### 6.3 连续例子：保存预算后如何可靠地通知 Operate

1. Remember 在一个本地 UoW 事务内保存 `m1@2`、后续投影任务，以及稳定事件 `event_01`。任一必需写入失败，整笔事务回滚。
2. 事务提交后进程退出。再次启动时，事件仍在 Outbox，投递器可以继续发送；用户已保存的事实不会依赖内存队列存活。
3. Operate 消费事件，在事务中一起更新调度输入并记录自身已处理 `event_01`。不同消费者分别维护自己的消费身份。
4. 若外部投递确认丢失，同一事件再次到达，Operate 根据消费记录避免重复业务效果。

这里 SQLite 是存储软件，UoW 是我们组织事务的方式，Outbox/Inbox 是表与处理规则组成的机制。无需为每个词分别安装一个框架。

再看旧 Worker：A 领取任务获得租约标识 L1；A 卡住后租约过期，B 接管获得 L2。A 迟到提交时，系统发现 L1 已不匹配而拒绝提交。记忆本身还要检查版本和删除状态——租约有效与业务对象有效是两道不同的检查。

## 7. Operate：Controller 模式应该怎么看

**目的：让动作状态依据当前观察持续收敛。** 不直接根据一条事件宣布“应该搬迁且已经成功”，而是重新读取有效事实、策略、资源与当前放置，再计算差异。

读[reconcile.go](../架构设计/第三方源码中文注释/controller-runtime/pkg/reconcile/reconcile.go)的 `Request`、`Result`、`Reconciler` 和 level-based 注释；接着读[controller.go](../架构设计/第三方源码中文注释/controller-runtime/pkg/internal/controller/controller.go)，理解出队、错误与重新排队。官方入口：[controller-runtime](https://github.com/kubernetes-sigs/controller-runtime)。

本项目对照[Operate Service](../../AgentJYS-main/src/aether_agent_memory/operate/basic/service.py)与[executor.py](../../AgentJYS-main/src/aether_agent_memory/operate/basic/executor.py)：

```text
事件或周期触发 → 重新读当前对象与状态 → 计算期望
    → 已满足：记录观察，不重复执行
    → 有未决动作：查询同一 action_id
    → 允许新动作：持久保存意图 → 执行 → 回读确认
```

借鉴的是循环、状态和异常语义；热度算法、容量预算、相邻层级、删除资格、动作协议与数据安全仍由我们实现。队列去重只能合并唤醒，不能替代动作幂等。Kubernetes 的 finalizer 可帮助理解外部清理过程，但本项目不因此必须使用 CRD。

学习实验：执行端完成动作但故意丢响应，观察 Unknown → 原 ID 查询 → 收敛；再让执行端失去历史，验证继续保留未知。本地目录缓存执行只能证明本地副作用，不能证明已实现 P2/P1 的正式物理分层。

### 7.1 具体例子：事件只负责唤醒，观察决定动作结果

假设 `m1@2` 的访问情况使策略希望增加一个可用缓存副本，当前观察到副本不存在。Operate 保存动作 `action_01` 后发起执行。执行端创建成功，但响应在网络中丢失。

此时客户端只知道“结果不明”，应持久保存 Unknown。下一次 Reconcile 先查询 `action_01`，再核对目标版本与实际副本，证据符合才确认完成。若重复事件又唤醒一次，同一当前状态已经满足期望，就不再创建新动作。

如果记忆在这期间被删除，下一轮必须按最新资格判断阻断或清理，不能照旧事件继续增加副本。controller-runtime 借给我们的是这种重新观察并推进的方式，缓存策略与删除处理仍需我们定义。

## 8. Trace、日志、健康与恢复的分工

### 8.1 先明确四类记录

| 记录 | 回答的问题 | 能否单独用来恢复业务 |
|---|---|---|
| Trace / Span | 一次请求及关联任务经过哪些节点、谁调用谁、耗时和错误在哪里 | 不能，可能缺失、采样或清理 |
| 结构化技术日志 | 节点输入输出摘要、错误类别、阶段与定位信息是什么 | 不能替代正式提交事实 |
| 健康检查 | 当前进程、依赖、Worker 和任务状态是否适合继续工作 | 只能触发处理，不能宣布业务完成 |
| Task / Outbox / Action / 操作记录 | 什么已提交、谁有执行资格、什么待办或结果仍不明确 | 恢复判断的持久依据 |

### 8.2 参考什么，当前实际用了什么

读[OpenTelemetry Signals](https://opentelemetry.io/docs/concepts/signals/)了解 Trace、Metrics、Logs；读[W3C Trace Context](https://www.w3.org/TR/trace-context/)了解 `traceparent`、trace-id、parent-id、flags。W3C Trace Context 是传播格式标准，OpenTelemetry 是遥测规范与实现生态。仅生成类似格式的 ID 不等于完成跨服务标准接入。

当前读本项目[telemetry.py](../../AgentJYS-main/src/aether_agent_memory/runtime/foundation/telemetry.py)：

- `Node`、`span` 建立节点与父子关系，记录开始、返回、失败或取消。
- `emit` 保存 schema_version、时间、服务/实例、trace_id、span_id、parent_span_id、request_id、operation_id、节点、阶段等；执行结束带耗时，错误带类别和栈位置。
- `summary` 控制输入输出摘要、脱敏与大小；日志不是默认复制全部对话、凭证和正文的地方。详细内容应通过授权来源读取。
- `Telemetry` 使用本地 SQLite 日志存储，按天数和记录数清理；Host 默认配置为 14 天、20 万条，属于当前工程默认值，不是合同保留期。
- `producer_context` 与持久任务上下文支持关联延续；`observed` / `attach_provider` 为已装配的组件和适配器接入节点记录。

一个 `trace_id` 用于查关联链；单次节点用 `span_id`，业务对象另有 memory/recall/action ID。长时间自动 Operate 可能汇聚多个请求，不能强迫全系统终身共用一个 Trace；需要通过事件、任务和对象 ID 跨链关联。未来接 OTel 时可用 Links 表达多来源因果关系。

读[diagnostics.py](../../AgentJYS-main/src/aether_agent_memory/runtime/foundation/diagnostics.py)看授权查询及关联；读[health.py](../../AgentJYS-main/src/aether_agent_memory/runtime/flows/health.py)看依赖探测、超时、Worker 状态和任务异常。依赖失败应报告影响范围；liveness 不宜因为 Milvus 短暂中断而触发不断重启。readiness 与后台领取资格也需要分别处理。

当前尚未接通 OTel SDK/OTLP 导出与真实跨 HTTP 传播。依赖文件里出现 OTel 不足以改变这个结论。后续接 Application Insights 或 Collector 时，要验证上下文传递、脱敏、采样、重试、缓冲及导出失败，不只是加一个包。

学习实验：用一个 trace_id 查询保存与后台加工节点；注入模型超时和日志写入失败，检查业务结果、错误日志、健康报告分别表达什么。日志失败不得把已经发生的外部效果误转成盲目重试。

### 8.3 具体例子：如何凭 trace_id 查到出错节点

以下用短名称代替实际 Trace/Span 标识，只展示关系：

```text
Trace T：保存与其关联加工
  Span S1：Remember 接收并保存
    Span S2：提交本地事务 → returned
    后台加工任务（保存生产方关联）
      Span S3：模型提取 → returned
      Span S4：Embedding → returned
      Span S5：向量投影 → failed，依赖超时
```

按 T 查询可定位到 S5，再通过 task_id 查任务状态与尝试记录。Remember 的“已保存”事实仍然成立，而长期投影尚未完成；不能把整条链粗略显示成“全部成功”或“内容没保存”。`returned` 只表示某函数正常返回，还需看业务状态和事务是否实际提交。

日志应包含节点、父子关系、时间、耗时、错误类别与受控输入输出摘要。敏感正文通过授权的来源接口查阅；凭证不应进入日志。健康检查若显示向量服务不可用，说明当前依赖问题；何时重试、旧任务还能否加工，则由任务和 Remember 当前版本规则共同决定。

未来 OpenTelemetry SDK 负责生成和传播标准遥测，OTLP 负责导出，Collector 可接收和转发，Application Insights 提供 Azure 侧存储与查询。当前本地 Trace 实现尚未连通这整条导出链，示例不代表已部署这些组件。

Prometheus、Azure Monitor 的指标建设按当前安排暂缓。可以阅读[Azure Kubernetes 监测概览](https://learn.microsoft.com/en-us/azure/azure-monitor/containers/kubernetes-monitoring-overview)，理解未来采集去向；无需现在搭建完整监控平台。

## 9. Temporal：学习可靠执行，但暂不替换当前底座

读[本地 SDK README](../../P3_框架研读与工程验证_V1.0/sources/temporal-python/README.md)、[Python SDK](https://github.com/temporalio/sdk-python)及[Activity Execution](https://docs.temporal.io/activity-execution)。本地仅保存 README 等选读材料，不是完整可运行仓库。

阅读顺序：Workflow/Activity 分工 → Event History/Replay → Workflow ID → 各种 Timeout/Retry → Heartbeat/Cancellation。Workflow 依据历史重放编排；Activity 执行真实外部调用。重放不意味着将所有外部请求再发一次，但 Activity 超时或失败重试仍可能重复执行外部副作用。

它适合持久编排，不能自动提供跨 P2 与本地数据库事务，也不能替我们决定旧记忆是否有效。当前任务规模先由统一 SQLite 机制验证，避免同时维护两套权威执行状态。若以后采用 Temporal，ADR 必须定义哪些 Task/重试/恢复被替换、在途任务如何迁移、业务 Outbox 是否保留。

学习实验独立运行：停止 Worker、恢复 Worker、观察历史，再制造 Activity 已生效但未确认。能解释“重放编排”和“业务幂等”差别即可，暂不阅读全部服务端源码。

具体理解可以用三步 Workflow：“提取 → 投影 → 确认”。Worker 在提取结果已写入 Temporal 历史后退出，新 Worker 重放时可使用历史结果推进到后续步骤；如果提取调用已经发生但 Activity 结果尚未可靠确认，Activity 仍可能重试。Temporal 保存的是编排历史，不能代替 Remember 的正式事实与幂等提交，也不会自动把外部调用变成只发生一次。

## 10. 身份、租户与授权：Entra、OpenFGA 和自有规则

**目的：确认调用者是谁，并限制其实际可访问资源。** 一个有效云端令牌不自动赋予任意记忆访问权。

| 名称 | 边界 |
|---|---|
| 业务 tenant | 客户或组织的数据与许可边界 |
| user / agent / session | 业务租户内主体及会话范围 |
| Entra tenant | 身份目录，不直接等于业务 tenant_id |
| Kubernetes Namespace | 集群资源与策略范围，不自动实现数据授权 |

读[Azure 多租户架构指南](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/overview)、[Entra 访问令牌](https://learn.microsoft.com/en-us/entra/identity-platform/access-tokens)、[OWASP 授权指南](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。重点看签名、issuer、audience、有效期、调用权限，以及身份到业务租户的受控映射。业务请求不能自行指定一个 tenant_id 就获得访问权。

本项目读[identity.py](../../AgentJYS-main/src/aether_agent_memory/runtime/foundation/identity.py)：可信上下文、Scope/Grant、重新核验和授权版本。当前 ADR 明确保留缺口：独立租户停用、外部身份映射、Entra 接入及共享资源候选发现尚未完整完成，不能因为单对象 Grant 已有就宣布完整租户能力交付。

OpenFGA 读[建模指南](https://openfga.dev/docs/modeling/getting-started)，理解对象、关系、tuple 与 Check 的关系；用于学习“谁能通过什么关系访问哪个对象”。当前复杂关系规模尚不要求新增授权服务，采用它也不会自动解决 Recall 候选发现、版本有效性或授权缓存失效。

学习实验：同租户不同用户默认不可互读；明确授权后可用；撤权后新 Recall、旧 Context 再获取和后台结果提交均复核。允许列表查询与单对象读取要分别验证。

具体例子：张三持有合法 Entra 令牌，P3 先验证它确实签发给本服务，再查受控映射，得知张三属于甲公司的业务租户。访问李四的记忆仍需对象授权；“同公司”不自动代表所有数据互通。若未来使用 OpenFGA，可以通过对象关系检查表达共享许可，但 Recall 依旧要获取获准候选范围并复核当前记忆资格。当前代码尚未实现完整 Entra 接入，这条路径属于设计目标。

## 11. Azure、容器、AKS 与 PostgreSQL 演进

采用顺序为单实例可运行、故障可解释，再验证多副本与集群运行。AKS 托管控制平面，不托管我们的业务正确性。

| 主题 | 官方入口 | 本项目要学到的程度 |
|---|---|---|
| 容器基本运行 | [Docker 概览](https://docs.docker.com/get-started/docker-overview/) | 镜像与配置分离、持久卷、非 root、退出信号和可复现版本 |
| AKS 架构 | [AKS Baseline](https://learn.microsoft.com/en-us/azure/architecture/reference-architectures/containers/aks/baseline-aks) | Deployment、Service、资源限制、RBAC、NetworkPolicy、滚动发布和回退 |
| 探针 | [Kubernetes 探针](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/) | startup/liveness/readiness 分工；别把依赖故障都变成重启 |
| 服务身份 | [Managed Identity](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/overview)、[AKS Workload Identity](https://learn.microsoft.com/en-us/azure/aks/workload-identity-overview) | VM 与 Pod 如何获得访问 Azure 服务的身份；不取代业务用户授权 |
| 密钥 | [Key Vault](https://learn.microsoft.com/en-us/azure/key-vault/general/overview) | 凭证权限、读取和轮换；正文与业务审计仍由各自存储负责 |
| 数据库演进 | [PostgreSQL 并发控制](https://www.postgresql.org/docs/current/mvcc.html) | 事务隔离、竞争领取、唯一约束、CAS、连接管理和迁移 |
| 单机备份 | [SQLite Backup API](https://www.sqlite.org/backup.html) | 取得一致快照、恢复演练、备份点与之后可能丢失的数据 |

多副本前，不能简单把 SQLite 放到共享卷。迁移 PostgreSQL 要重新验证任务领取、去重、删除竞态和租约屏障；对象及向量备份也要单独处理。恢复旧数据库时，还须对账外部动作并核查旧授权/删除状态，不能直接开放流量导致数据复活。

学习实验：优雅退出时停止领取新任务；强制退出由持久恢复处理。未来做滚动发布时验证在途任务和契约兼容；备份恢复需说明恢复时间点和可能的数据损失，不用“有备份”概括全部承诺。

具体例子：P3 Worker 的 Pod 被终止，AKS 启动替代 Pod，这是进程恢复；新 Worker 从持久任务中发现过期租约，再由 Handler 判断是否继续，这是业务恢复。若外部缓存动作已执行但尚未确认，还要查询原 action_id。三个步骤分别由容器平台、公共任务机制、Operate 领域逻辑负责。

Pod 通过 Workload Identity 访问 Key Vault，证明的是“这个服务可以读取获准密钥”；用户通过 Entra 访问 P3，证明的是调用者身份。服务拿到向量库凭证以后，仍必须按原业务用户的范围检索，不能因为数据库连接有较大权限就把它传递给用户。

项目负责人可以按以下问题检查是否真的理解：

1. LangMem 返回了候选，为什么还不能算正式保存？
2. 向量命中旧版本，哪一步阻止它进入 ContextPack？
3. Query 和 Passage 维度相同，为什么仍可能不兼容？
