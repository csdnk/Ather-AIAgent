# P2 E4/E5/E6 三态引擎调研报告（v1.0）

> 合同依据：横向合同 第一条（1）（5）「时序/文件/块引擎的调研工作，作为后续实现的支撑」  
> 里程碑：M0 提交调研结论 | GA 阶段再评估实现 | 版本：v1.0

---

## 1. 调研目的与范围

### 1.1 目的

在 M0 阶段对 AetherEngine 完整六态愿景中的 **E4 文件引擎、E5 块引擎、E6 时序引擎** 进行技术调研，明确数据模型、与 P1/P2 共享底座的关系、业界对标、实现复杂度与建议里程碑，**不在 M0~M-MVP 实现**。

### 1.2 范围

| 引擎 | 数据模型 | M0 动作 | 实现阶段（建议） |
|---|---|---|---|
| E4 文件 | POSIX 语义文件/目录 | 调研 | GA 或后续版本 |
| E5 块 | 块设备 / LUN | 调研 | GA 或后续版本 |
| E6 时序 | TimeSeries / Metrics | 调研 | GA 或后续版本 |

同步调研合同 GA 项：**Checkpoint 高吞吐通道、跨引擎事务（实验特性）**。

---

## 2. E4 文件引擎调研

### 2.1 业务需求（来自项目分解）

- AI 训练 checkpoint、日志、模型 artifact 的大文件顺序写；
- 与 E2 对象引擎差异：POSIX 语义（rename 原子性、目录遍历、append）、低延迟元数据、与 CSI/FUSE 挂载对接。

### 2.2 业界对标

| 产品 | 特点 | 可借鉴 |
|---|---|---|
| CephFS / Lustre | 分布式 POSIX | 元数据/数据分离 |
| JuiceFS | 对象后端 + POSIX 网关 | 与 E2 协同 |
| Alluxio | 缓存层 | 热数据加速 |

### 2.3 与 P2 共享底座关系

- **Segment**：按目录子树或 inode 范围分段，生命周期与 E1/E2 一致；
- **WAL**：文件 create/write/truncate/rename 操作入 WAL；
- **Tier**：冷文件整段迁移至温/冷层；
- **P1 Block**：大文件 extent 映射到 Storage Block。

### 2.4 初步方案建议

| 项 | 建议 |
|---|---|
| MVP 路径 | GA 前不单独建设；训练场景优先走 E2 Multipart + Range |
| 完整 E4 | FUSE/CSI 网关 + inode 元数据引擎 + extent→P1 Block |
| 风险 | POSIX 语义与 S3 对象语义并存，需 P4 清晰路由 |
| 工作量粗估 | 6~9 人月（含 P4 CSI） |

### 2.5 M0 结论

**M0 不实现**；M-MVP/M1 训练数据走 E2；E4 详细设计推迟至 **2027 Q2 GA 调研结项**。

---

## 3. E5 块引擎调研

### 3.1 业务需求

- 为数据库、VM 卷、RDMA 训练提供原生块访问；
- 与 P1 HCI 块服务关系紧密，P2 是否再包一层需避免重复。

### 3.2 业界对标

| 产品 | 特点 |
|---|---|
| Ceph RBD | 块→对象→物理 |
| SPDK bdev | 用户态块、低延迟 |
| P1 规划 | 已含 Block 原语，E5 可能是语义封装 |

### 3.3 架构选项对比

| 选项 | 描述 | 优缺点 |
|---|---|---|
| A. P2 不建 E5，P1 直出块 API | P4 块网关直调 P1 | 简单；六态不完整 |
| B. P2 E5 作为 P1 Block 的命名空间/配额层 | 统一 Segment/Tier | 与合同六态一致；需定义 LUN 模型 |
| C. E5 仅调研，生产用 P1 | 最小工作量 | 合同 GA 要求「调研 E5」 |

### 3.4 M0 结论

推荐 **选项 B 为 GA 目标架构**，M0~M1 **不实现**；块 IO 热路径由 P1 承担，P2 仅预留 `EngineKind::Block` 与 proto 扩展位。

## 4. E6 时序引擎调研

### 4.1 业务需求

- Agent 监控指标、引擎访问热度、OTel metrics 长期存储；
- 与 P3 调度信号、P1 资源监控衔接。

### 4.2 业界对标

| 产品 | 特点 |
|---|---|
| Prometheus + Thanos | pull 模型 + 长期存储 |
| InfluxDB / VictoriaMetrics | 高压缩时序 |
| Apache IoTDB | 边缘时序 |

### 4.3 数据模型草案

```text
SeriesId = tenant + metric + labels
Sample   = (timestamp, value)
Segment  = 时间窗口 [t0, t1) + 列式压缩块
```

### 4.4 与 P3/P1 关系

- P3-B3 消费 **访问行为/热度** 时序聚合；
- P1 Tier 决策可读取 E6 降采样结果；
- OTel metrics 经 P1 总线写入 E6（IF-07 延伸）。

### 4.5 M0 结论

M0~M-MVP 用 **OTel + 外部 Prometheus** 代替；E6 引擎 **GA 调研结项**，不在三态 MVP 范围。

## 5. Checkpoint 高吞吐通道调研（GA 实验特性）

### 5.1 场景

大模型训练 checkpoint（数十 GB~TB）需绕过通用对象 PUT 开销，直写 P1 Block 并注册到 E1/E2 元数据。

### 5.2 技术要点

- 零拷贝 / RDMA（依赖 P1）；
- 独立 WAL `OperationKind::CheckpointCommit`；
- 与 E2 Multipart 关系：Checkpoint 走 fast path，常规模型走 E2。

### 5.3 M0 结论

**实验特性**，GA 前输出 feasibility report；M-MVP 用 E2 Multipart 满足基本 checkpoint 存储。

---

## 6. 跨引擎事务调研（GA 实验特性）

### 6.1 场景

单次 Agent 写入同时更新向量（E1）、对象（E2）、图（E3），需原子提交或最终一致。

### 6.2 方案对比

| 方案 | 说明 | 复杂度 |
|---|---|---|
| Saga + Outbox | 各引擎 WAL + 补偿 | 中；可 M1 做 E2 tombstone Outbox 铺垫 |
| 2PC 协调器 | 中央事务管理 | 高 |
| 最终一致（推荐 MVP） | 无跨引擎原子 | 低；当前架构 |

### 6.3 M0 结论

M0~M1 **不实现跨引擎事务**；E2 Outbox/Reconcile 可作为 Saga 铺垫（M1 可选）。

---

## 7. 六态 proto 扩展预留（v0.2+）

M0 v0.1 仅冻结 E1/E2/E3 + Fusion + SegmentControl。建议 v0.2 预留（不实现）：

| Service | 说明 |
|---|---|
| FileService | Open/Read/Write/Stat/Rename |
| BlockService | Attach/Read/Write/Flush |
| TimeSeriesService | WriteSamples/QueryRange |

字段号分配需在 v0.2 冻结前与 P4/P1 联合评审。

## 10. 总结

本报告完成合同要求的 **E4/E5/E6 及 GA 实验特性调研**，结论为：当前阶段聚焦 **E1/E2/E3 三态** 是正确的合同边界；文件/块/时序引擎在共享 Segment/WAL/Tier 底座上具备扩展路径，实现推迟至 GA 调研结项，避免影响 M0/M-MVP 交付节奏。
