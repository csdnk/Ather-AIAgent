## 二、B1 工作流摘要

`B1 Embedding 下推` 的核心工作流可以归纳为：

1. 上游 `P4 / Agent / RAG / B2` 提交文档片段、对话片段、RAG 证据、工具结果或记忆内容。
2. `B1 Sidecar` 在写入链路旁路接入，完成字段校验、来源识别和是否需要向量化的判断。
3. 对长文本执行基础切分，生成 `chunk_id`，并绑定 `source_id / object_id / trace_id / metadata`。
4. 调用 `EmbeddingWorker` 生成向量，输出 `embedding / embedding_ref / embedding_model / embedding_dim`。
5. 将向量写入 `P2-E1`，必要时更新 `P2-E2` 原文/摘要/metadata，并可选写入 `P2-E3` 关系。
6. 把 `chunk_id / source_id / embedding_ref / metadata / status` 返回给 `B2` 或调用方。

对应的主要动作是：

- 识别语义资源
- 文本切分
- embedding 计算
- 原文与向量映射绑定
- 写入或模拟写入 `P2`
- 返回状态、错误码、trace

---

## 三、B3 工作流摘要

`B3 语义智能分层调度器` 的核心工作流可以归纳为：

1. 从 `B2` 接收 `memory signal`，包括重要性、使用频次、时效性、是否进入上下文、是否被纠错等信息。
2. 从 `P2` 接收对象状态、向量状态、`Segment` 状态、访问统计、图关系、索引状态。
3. 从 `P1/P2` 接收 `Tier` 容量、负载、访问时延、迁移成本和执行反馈。
4. 聚合语义价值、访问热度、任务上下文和资源状态，计算调度优先级。
5. 输出 `Promote / Demote / Pin / Prefetch / Evict / Keep` 等动作或建议。
6. 接收执行反馈，记录 `action_status / execute_latency / error_code / trace_id`，形成闭环。

对应的主要动作是：

- 聚合 B2 记忆价值信号
- 读取对象/Segment/Tier 状态
- 输出调度动作
- 接收执行反馈
- 记录原因、状态与 trace

## 四、MVP 验收场景（三模块联动部分）

### 场景 1 · 文档入库与 RAG 知识召回

- `P4` 上传文档或知识片段，`P2-E2` 先保存原文对象，`B1 Sidecar` 完成文本切分、embedding 生成和 `object_id -> chunk_id -> embedding_ref` 绑定
- 用户发起问答时，`B2` 通过 `P2-E1` 检索相关 chunk，并结合原文与 metadata 组装 `Context Pack`
- **问答结束后自动写入一条 Episodic Memory；热点 chunk 或高频证据由 `B3` 输出 `Promote / Pin` 建议，低频对象保持 `Keep`**

覆盖动作：

- `B1`：识别输入、切分文本、计算 embedding、写入 `P2-E1`、返回 `embedding_ref`
- `B2`：检索证据、构建上下文、写入 Episodic Memory
- `B3`：根据命中热度和对象状态输出 `Promote / Pin / Keep`

### 场景 2 · 多轮 Agent 会话与跨会话续办

- Agent 框架把当前轮对话、任务状态、工具结果写入 `Working Memory`，保证当前会话即时可用
- 会话结束、任务阶段完成或上下文超预算时，`B2` 将高价值过程归档为 `Episodic Memory`，并将稳定规则、偏好、经验沉淀为 `Semantic Memory`
- **归档和沉淀过程中需要向量化的内容由 `B1` 处理；跨会话召回频繁命中的记忆由 `B3` 给出 `Promote / Demote / Pin` 建议**

覆盖动作：

- `B1`：对归档记忆和长期记忆执行向量化
- `B2`：写入 Working、归档 Episodic、沉淀 Semantic、召回历史记忆、构建 `Context Pack`
- `B3`：消费 `memory signal`，对记忆对象做 `Promote / Demote / Pin`

### 场景 3 · 热点任务高峰下的分层调度闭环

- 多个 Agent 在短时间内重复访问同一批规范条款、故障案例、用户画像或任务经验，`B2` 持续输出访问热度、上下文命中和纠错反馈
- `B3` 结合 `B2` 的记忆价值信号、`P2` 的 `Segment/Object` 状态和 `P1/P2` 的 `Tier` 资源状态，生成分层调度动作
- **执行层返回 `action_status / execute_latency / error_code / trace_id` 后，`B3` 记录闭环结果；若热点内容被提前加载，则后续 `B2` 召回性能提升**

覆盖动作：

- `B1`：提供可追溯的 `chunk / embedding / source` 基础对象
- `B2`：输出 `ACCESS / ARCHIVAL / PROMOTION_HINT / DEMOTION_HINT` 等记忆信号
- `B3`：输出 `Prefetch / Promote / Demote / Evict / Keep`，并消费执行反馈

## 六、结论

如果目标是用 3 个场景覆盖三个模块的大多数动作，这 3 个场景的组合已经比较完整：

1. `场景 1` 覆盖 `B1` 最核心的写入旁路和 `B2` 的证据召回入口。
2. `场景 2` 覆盖 `B2` 当前项目的主线能力，也是 `B1` 为记忆服务的主要落点。
3. `场景 3` 覆盖 `B3` 的调度决策、动作输出和反馈闭环。

因此，后续无论是写需求、补接口，还是做 MVP 演示，这 3 个场景都可以直接作为三模块联调主场景使用。
