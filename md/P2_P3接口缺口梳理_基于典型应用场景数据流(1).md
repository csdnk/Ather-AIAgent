# P2 当前缺失接口梳理：基于 P3 典型应用场景数据流的接口对账

**版本**：v0.1  
**用途**：用于 P2/P3 接口评审、P2 接口修订、P3-B1/B2/B3 联调准备  
**对账基准**：以 P3 已确定的四条典型应用场景数据流为基准：文档上传、用户查询、记忆维护、对象更新。  
**核心结论**：P3 需求文档中的数据流与接口需求已经明确，当前主要问题是 P2 接口仍以 E1/E2/E3 存储引擎功能为中心，尚未充分对齐 P3 所需的“语义资源闭环”和“调度对象视图”。后续不是重做 P3 流程，而是 P2 需要按 P3 的数据流补齐统一元数据、对象映射、状态内省、迁移执行反馈等接口。

---

## 1. 当前接口问题总述

P2 当前接口能够表达基础存储能力，例如：

- E1 向量写入、删除、检索、基础 Segment 内省；
- E2 对象 PUT/GET/HEAD/DELETE/LIST/Range/Multipart；
- E3 节点、边、属性、向量投影和融合查询；
- SegmentControl 的 Freeze、Unfreeze、OnMigrateComplete、OnMigrateFailed。

但 P3 的 B1/B2/B3 不是只需要“能存、能查、能冻结”，而是需要在 Agent/RAG 业务流中形成以下闭环：

```text
source_id / object_id
    -> chunk_id
    -> vector_id / embedding_ref
    -> memory_id / evidence_id / task_id
    -> segment_id
    -> tier / block_id / route_epoch
    -> action_id / feedback
```

当前 P2 缺少的核心不是单个字段，而是缺少一层 **P2 Catalog / Metadata Registry / Scheduling View**，用于维护并暴露对象、chunk、向量、记忆引用、Segment、Tier、Block、迁移反馈之间的稳定映射。

## 2. 主责边界

### 2.1 P2 应主责的部分

P2 应主责维护和暴露以下存储侧映射与状态：

| 映射或状态 | 主责模块 | 说明 |
|---|---|---|
| `object_id / raw_ref / content_ref` | P2-E2 | 原始对象、文档、文件、工具结果、RAG 证据等统一落点 |
| `object_id -> chunk_id` | P2-E2 / B1 协同，P2 保存 | chunk 可由 P4/P2 预切分，也可由 B1 切分，但最终映射应由 P2 保存并可查 |
| `chunk_id -> vector_id` | B1 生成，P2-E1 保存 | B1 负责 embedding，P2 负责 vector 与 chunk 的稳定绑定 |
| `vector_id -> segment_id` | P2-E1 | 向量引擎内部映射，必须由 P2 提供 |
| `segment_id -> block_id / tier / node / route_epoch` | P2/P1 | Segment 路由、层级、块位置和迁移一致性状态 |
| `ObjectStats / SegmentStats / IndexStatus / AccessStats` | P2 | 给 B3 提供调度对象视图 |
| `Freeze / Unfreeze / route update` | P2/P1 Executor | 物理执行过程中的生命周期控制与路由切换 |

### 2.2 P3 应主责的部分

P3 不应把语义判断责任推给 P2。以下字段由 P3 负责：

| 语义信号 | 主责模块 | 说明 |
|---|---|---|
| `memory_id / memory_type` | B2 | 记忆对象标识与类型 |
| `importance` | B2 | 记忆重要性 |
| `context_used_flag` | B2 | 是否进入过 Context Pack |
| `user_defined_flag` | B2/P4 | 是否用户显式设定 |
| `correction_flag` | B2 | 是否被用户纠错或降权 |
| `ttl / status` | B2 为主，P2 存储侧同步 | 记忆生命周期与召回过滤 |
| `semantic_hot_score` | B3 | B3 聚合 B2 语义信号与 P2 状态后计算 |
| `policy_version / reason` | B3 | 调度策略版本与解释 |

### 2.3 P4/P1 应提供的部分

| 内容 | 主责模块 | 说明 |
|---|---|---|
| `tenant_id / user_id / agent_id / session_id / task_id` | P4 | 业务入口上下文和身份隔离字段 |
| `source_id / source_type` | P4 为入口，P2/B1/B2 保存 | 原始业务来源、文档来源、工具结果来源 |
| `tier capacity / storage node / physical migration` | P1/P2 | 资源层状态、真实迁移执行和失败回滚 |
| `monitor trace / latency / error_code` | 监控平台 + 各模块 | 全链路可观测 |

## 3. P2 当前缺口总览

| 缺口编号 | 缺失接口/能力 | 当前 P2 状态 | 对 P3 的影响 | 优先级 |
|---|---|---|---|---|
| GAP-01 | P2 Catalog / Metadata Registry | 未形成统一接口 | object、chunk、vector、memory、segment 无法稳定追溯 | P0 |
| GAP-02 | ObjectMetaForP3 | E2 主要是 bucket/key/data/ObjectMeta | P3 缺少 source_id、object_id、content_ref、status 等业务追溯字段 | P0 |
| GAP-03 | ChunkMeta | 当前 E2 未定义 chunk 元数据接口 | B1 向量化结果无法稳定追溯到原文片段 | P0 |
| GAP-04 | VectorMeta | E1 records 主要是 id/values/graph_node_id/metadata_json | B2/B3 无法稳定反查 vector 对应 chunk/object/memory/segment | P0 |
| GAP-05 | MemoryStorageRef | P2 无 memory 存储映射模型 | B2 记忆落地到 E1/E2/E3 后缺少统一引用 | P0 |
| GAP-06 | 最小关系图 Schema | E3 是通用图接口 | B2 的 session-task-rag-evidence-memory-object-chunk-vector 关系无法稳定写入 | P0/P1 |
| GAP-07 | BatchGet 元数据接口 | 当前是 E1/E2/E3 分散查询 | B2 构建 Context Pack 需要多次散查，性能和字段稳定性不足 | P0 |
| GAP-08 | SegmentStatV2 | 当前 SegmentStat 字段过粗 | B3 无法判断 tier、近期热度、可迁移性和路由一致性 | P0 |
| GAP-09 | SegmentMembership | 当前没有 segment 反查成员接口 | B3 无法从 Segment 追溯到 object/chunk/vector/memory | P0 |
| GAP-10 | ObjectStats / AccessStats | 当前 E2/E1 未形成调度视图 | B3 无法做对象级冷热、过期、删除、业务优先级判断 | P0 |
| GAP-11 | TierState | 当前未明确 P2/P1 给 B3 的资源层状态接口 | B3 不知道当前层级容量、负载、时延和迁移成本 | P0 |
| GAP-12 | TierAction 执行接口 | P2 只有 Freeze/回调，不等于 B3 动作接口 | B3 Promote/Demote/Pin/Prefetch 没有标准接收方 | P0 |
| GAP-13 | TierActionFeedback | P2 回调 Ack 不等于 B3 策略反馈 | B3 无法形成动作闭环和策略评估 | P0 |
| GAP-14 | 状态同步与删除隔离 | E1/E2/E3 状态未统一 | 删除、过期、禁用对象可能继续被召回或调度 | P0 |
| GAP-15 | 统一 Trace Schema | 有 trace_id，但缺 memory_id/action_id/object_id 等统一贯通 | 联调和验收问题难追溯 | P0 |
| GAP-16 | 访问计数口径拆分 | 当前 access_count 是段级累加 | 无法区分 probe、hit、Top-K 命中、时间窗口热度 | P0 |
| GAP-17 | IndexStatus | 仅 index_type，不含 index_state | B3 不知道索引是否构建中、重建中、可迁移 | P1 |
| GAP-18 | RelationStats | E3 图关系没有调度摘要接口 | B3 难以利用图关系做预取和关联调度 | P1 |

## 4. 按 P3 典型应用场景数据流梳理缺口

## 4.1 场景一：文档上传 / 原始对象写入链路

### 4.1.1 P3 基准数据流

```text
P4 上传文档/对象
    -> P2-E2 保存原文对象，返回 object_id/raw_ref/content_ref
    -> B1 获取文本或 chunk，完成 embedding
    -> B1 写入 P2-E1，返回 vector_id/embedding_ref
    -> B1/B2 记录 source/object/chunk/vector 映射
```

### 4.1.2 P2 当前不足

P2 E2 当前 ObjectService 更接近 S3 对象接口，字段以 `bucket/key/data/ObjectMeta` 为主；这能支撑对象读写，但不足以作为 P3 的语义资源入口。P3 需要的是稳定可追溯的 `object_id/source_id/source_type/raw_ref/content_ref/chunk_ref/status/metadata_ref`。

### 4.1.3 P2 需补接口

#### A. `ObjectMetaForP3`

**用途**：作为 P3 引用 E2 原始对象的统一元数据。

建议字段：

```rust
pub struct ObjectMetaForP3 {
    pub object_id: String,
    pub bucket: String,
    pub key: String,
    pub raw_ref: String,
    pub content_ref: Option<String>,
    pub source_id: Option<String>,
    pub source_type: Option<String>,
    pub tenant_id: String,
    pub namespace: String,
    pub object_type: String,
    pub size_bytes: u64,
    pub checksum: Option<String>,
    pub status: String,        // active/deleted/disabled/expired/superseded
    pub version_id: Option<String>,
    pub created_at: i64,
    pub updated_at: i64,
    pub trace_id: String,
}
```

建议接口：

```text
PutObjectWithMeta
GetObjectMetaForP3
BatchGetObjectMetaForP3
UpdateObjectStatus
ListObjectsBySource
```

**MVP 要求**：必须支持 `object_id/source_id/source_type/tenant_id/status/trace_id`。

---

#### B. `ChunkMeta`

**用途**：承接 B1 chunk 切分结果或 P4/P2 预切分结果，保证 chunk 可追溯。

建议字段：

```rust
pub struct ChunkMeta {
    pub chunk_id: String,
    pub object_id: String,
    pub source_id: String,
    pub source_type: String,
    pub tenant_id: String,

    pub embedding_ref: Option<String>,
    pub vector_id: Option<String>,
    pub process_status: String,
    pub error_code: Option<String>,
    pub trace_id: String,
}
```

建议接口：

```text
UpsertChunkMeta
BatchUpsertChunkMeta
GetChunkMeta
BatchGetChunkMeta
GetChunksByObject
UpdateChunkEmbeddingStatus
```

**MVP 要求**：必须支持 `object_id -> chunk_id`、`chunk_id -> object_id/source_id`、`chunk_id -> vector_id/embedding_ref`。

## 4.2 场景一子流程：B1 Embedding 写入 P2-E1 链路

### 4.2.1 P3 基准数据流

```text
B1 接收 P4/P2/B2 的文本或 chunk
    -> 生成 embedding
    -> 写入 P2-E1
    -> 保留 embedding_model、embedding_dim、chunk_id、source_id、object_id、metadata、trace_id
```

### 4.2.2 P2 当前不足

P2 E1 当前写入接口为 `collection、records[id, values, graph_node_id, metadata_json]`。这可以写向量，但 P3 需要的 `chunk_id/source_id/object_id/memory_id/embedding_model/status/segment_id` 不能只藏在 `metadata_json` 里，否则后续 B2/B3 无法稳定查询和联调。

### 4.2.3 P2 需补接口

#### C. `VectorRecordForP3`

**用途**：规范 B1 写入 E1 的向量记录结构。

建议字段：

```rust
pub struct VectorRecordForP3 {
    pub vector_id: String,
    pub collection: String,
    pub namespace: String,
    pub tenant_id: String,
    pub values: Vec<f32>,
    pub embedding_model: String,
    pub embedding_dim: usize,
    pub object_id: Option<String>,
    pub chunk_id: Option<String>,
    pub source_id: Option<String>,
    pub source_type: Option<String>,
    pub memory_id: Option<String>,
    pub graph_node_id: Option<String>,
    pub metadata_json: String,
    pub status: String,
    pub trace_id: String,
}
```

建议接口：

```text
InsertVectorsForP3
BatchInsertVectorsForP3
GetVectorMeta
BatchGetVectorMeta
GetVectorsByChunkIds
GetVectorsByObjectIds
GetVectorsByMemoryIds
```

**MVP 要求**：必须支持 `vector_id -> chunk_id/object_id/source_id/segment_id` 反查。

---

#### D. `VectorMeta`

**用途**：B2 检索和 B3 调度时反查向量元信息。

建议字段：

```rust
pub struct VectorMeta {
    pub vector_id: String,
    pub collection: String,
    pub namespace: String,
    pub tenant_id: String,
    pub segment_id: Option<String>,
    pub object_id: Option<String>,
    pub chunk_id: Option<String>,
    pub source_id: Option<String>,
    pub source_type: Option<String>,
    pub memory_id: Option<String>,
    pub embedding_model: String,
    pub embedding_dim: usize,
    pub status: String,
    pub created_at: i64,
    pub updated_at: i64,

```

建议接口：

```text
BatchGetVectorMeta(vector_ids[])
GetVectorMetaByChunkId(chunk_id)
GetVectorMetaByMemoryId(memory_id)
ListVectorMetaBySegment(segment_id)
```

**MVP 要求**：E1 检索命中后，B2 必须能从 `hit.id/vector_id` 批量反查到 `object_id/chunk_id/source_id/memory_id/status`。

## 4.3 场景二：用户查询 / B2 Context Pack 构建链路

### 4.3.1 P3 基准数据流

```text
P4/Agent 发起用户查询
    -> B2 构建 Context Pack
    -> B2 调 P2-E1 检索向量
    -> 根据 vector_id 反查 chunk/object/memory/evidence
    -> 调 P2-E2 获取原文/摘要/metadata
    -> 调 P2-E3 获取关系/证据链
    -> B2 返回 Context Pack 给 P4/Agent
```

### 4.3.2 P2 当前不足

P2 当前 E1/E2/E3 都能分别查，但缺少 B2 构建 Context Pack 所需的批量元数据组合查询。若只返回 `hits[id, score, graph_node_id]`，B2 还需要大量散查，且无法保证字段一致。

### 4.3.3 P2 需补接口

#### E. `BatchResolveSearchHits`

**用途**：将 E1 检索命中一次性解析为 B2 可用的上下文候选。

建议字段：

```rust
pub struct ResolvedSearchHit {
    pub vector_id: String,
    pub score: f32,
    pub object_id: Option<String>,
    pub chunk_id: Option<String>,
    pub memory_id: Option<String>,
    pub evidence_id: Option<String>,
    pub source_id: Option<String>,
    pub source_type: Option<String>,
    pub text_ref: Option<String>,
    pub summary_ref: Option<String>,
    pub relation_refs: Vec<String>,
    pub status: String,
    pub tenant_id: String,
    pub namespace: String,
    pub trace_id: String,
}
```

建议接口：

```text
BatchResolveSearchHits(vector_ids[])
BatchGetObjectBytes(object_ids[] / chunk_ids[])
BatchGetRelationsByEntityIds(ids[])
```

**MVP 要求**：B2 至少能从检索结果稳定拿到 `chunk_id/object_id/source_id/status/text_ref`。

---

#### F. 检索过滤字段增强

P2 E1 检索接口应支持以下过滤字段：

```text
tenant_id
namespace
user_id
agent_id
source_type
status
created_at / updated_at
time_range
memory_type 或 object_type
```

**原因**：B2 构建 Context Pack 时必须过滤 deleted、disabled、expired、跨租户、跨用户、跨 Agent 的数据。

**MVP 要求**：至少支持 `tenant_id/namespace/status/source_type` 过滤。

## 4.4 场景三：记忆维护链路

### 4.4.1 P3 基准数据流

```text
B2 接收对话、RAG、工具、用户显式设定
    -> 写入 Working Memory
    -> 归档 Episodic/Semantic Memory
    -> 记忆原文/摘要写入 P2-E2
    -> 记忆向量写入 P2-E1
    -> 记忆关系写入 P2-E3
    -> 删除/纠错/过期状态同步到 E1/E2/E3
```

### 4.4.2 P2 当前不足

P2 当前没有针对 B2 记忆体系的落地引用模型。P2 不需要理解记忆语义，但必须保存 B2 记忆与 E1/E2/E3 存储对象之间的映射。

### 4.4.3 P2 需补接口

#### G. `MemoryStorageRef`

**用途**：记录 B2 memory 落到 P2 的对象、向量和关系引用。

建议字段：

```rust
pub struct MemoryStorageRef {

    pub relation_ids: Vec<String>,
    pub status: String,
    pub ttl: Option<i64>,
    pub created_at: i64,
    pub updated_at: i64,

}
```

建议接口：

```text
UpsertMemoryStorageRef
GetMemoryStorageRef
BatchGetMemoryStorageRef
UpdateMemoryStorageStatus
DeleteMemoryStorageRef
```

**MVP 要求**：B2 写入一条 memory 后，必须能反查其对应的 `object_id/vector_id/chunk_id`。

#### I. 删除、禁用、过期状态同步接口

**用途**：保证 B2 删除/纠错/禁用记忆后，E1/E2/E3 不再召回或调度相关数据。

建议接口：

```text
UpdateObjectStatus
UpdateChunkStatus
UpdateVectorStatus
UpdateRelationStatus
PropagateDeleteByMemoryId
PropagateDeleteByObjectId
```

建议状态枚举：

```text
active
deleted
disabled
expired
superseded
pending_embedding
embedding_failed
```

**MVP 要求**：`deleted/disabled/expired` 数据不得进入 E1 检索结果、B2 Context Pack 或 B3 Promote/Prefetch 候选。

## 4.5 场景四：对象更新 / 删除 / 版本变更链路

### 4.5.1 P3 基准数据流

```text
P4 对对象进行更新或删除
    -> P2-E2 更新 object/version/status
    -> P2-E1 同步更新相关 vector 状态或重算引用
    -> P2-E3 同步更新关系状态
    -> B2/B3 消费状态变化，避免使用旧数据
```

### 4.5.2 P2 当前不足

当前 P2 E2 有 DELETE，但缺少和 E1/E3/B2/B3 统一的版本、tombstone、outbox、reconcile 机制接口描述。对象更新会影响 chunk、vector、memory、relation、segment 统计，如果没有同步机制，B2 可能召回旧内容，B3 可能调度过期 Segment。

### 4.5.3 P2 需补接口

#### J. `ObjectChangeEvent / Outbox`

建议字段：

```rust
pub struct ObjectChangeEvent {
    pub event_id: String,
    pub event_type: String, // create/update/delete/expire/disable/restore
    pub object_id: String,
    pub version_id: Option<String>,
    pub affected_chunk_ids: Vec<String>,
    pub affected_vector_ids: Vec<String>,
    pub affected_relation_ids: Vec<String>,
    pub tenant_id: String,
    pub namespace: String,
    pub status_before: Option<String>,
    pub status_after: String,
    pub trace_id: String,
    pub created_at: i64,
}
```

建议接口：

```text
ListObjectChangeEvents
AckObjectChangeEvent
ReconcileObjectVectorRelationStatus
```

**MVP 要求**：至少能在对象删除/更新后，将相关 vector/chunk/relation 标记为不可召回或待重算。

## 4.6 场景六：B3 语义调度与 P2 状态内省链路

### 4.6.1 P3 基准数据流

```text
B3 获取 B2 memory signal
    -> B3 获取 P2 ObjectStats / SegmentStats / AccessStats / RelationStats
    -> B3 获取 P1/P2 TierState
    -> B3 计算 Promote/Demote/Pin/Prefetch/Evict/Keep
    -> P1/P2 Executor 执行动作
    -> P1/P2 返回 ActionFeedback
```

### 4.6.2 P2 当前不足

P2 当前 SegmentStat 只有：

```text
segment_id, state, row_count, size_bytes, index_type, access_count
```

## 4.7 场景七：B3 调度动作与执行反馈链路

### 4.7.1 P3 基准数据流

```text

    -> P1/P2 Executor 接收动作
    -> Executor 调 P2 Freeze
    -> P1/P2 执行迁移或状态更新
    -> Executor 调 P2 OnMigrateComplete/Failed
    -> P1/P2 向 B3 返回 ActionFeedback
```

### 4.7.2 P2 当前不足

## 9. 最终结论

P2 当前接口并非完全不能用，基础 E1/E2/E3 能力已经覆盖了向量、对象、图和 Segment 生命周期控制的基本功能；但这些接口仍是“存储引擎内部能力接口”，尚未充分服务于 P3 已定义的典型应用场景数据流。P3 需要的不是单独的 VectorService、ObjectService、GraphService 和 SegmentStat，而是围绕 Agent/RAG 语义资源形成的可追溯、可召回、可调度、可反馈的接口闭环。

因此，P2 后续修订重点应放在三件事上：

1. **补统一元数据映射**：打通 `object_id -> chunk_id -> vector_id -> segment_id`，并支持与 `memory_id/source_id` 关联；
2. **补调度对象视图**：提供 `SegmentStatV2 / SegmentMembership / ObjectStats / AccessStats / TierState`，支撑 B3 判断对象在哪里、热不热、能不能迁移、值不值得迁移；
3. **补执行反馈闭环**：将 B3 的 `Promote/Demote/Pin/Prefetch/Evict/Keep` 与 P1/P2 的 `Freeze/迁移/路由切换/失败回滚/ActionFeedback` 打通。

在这些接口补齐前，B3 只能基于当前 SegmentStat 做粗粒度 Segment 级 Heuristic 演示，不能将其表述为完整的语义智能分层调度能力。
