# 召回流程详细设计 V0.1（开发实施版）

更新：2026-09-07。维护方：Recall 负责人（A）。第二章设计 Embedding 与向量投影写入，第三章设计 Recall Runtime；第五、六章整理我们提供的功能及外部依赖。规范化字段统一维护在[《召回数据定义》](召回数据定义_V0.1.md)，未确认的外部协议、保证和责任集中维护在[《跨模块待确认事项》](跨模块待确认事项_V0.1.md)。本文规定 A 侧可直接实现的行为；外部真实路径按该清单的启用条件接入。

## 1. 要实现什么、边界在哪里

我们需要建设 **Recall Runtime（召回流程）、Semantic Embedding（共享向量化模块）和 Vector Projection（向量投影写入机制）**，负责人均为 A。第二章说明向量怎样生成、交给 P2 存储并确认；第三章说明 Recall 怎样使用 Query 向量检索。第五、六章分别说明对外功能和外部依赖。

Recall 接收 Query、授权范围、筛选约束和预算，自行确定检索模式，产出 ContextPack、执行结果及可追踪证据。主线是：确定来源 → 找候选 → 核验资格 → 取正文 → 排序与预算 → 最终复核 → 可靠提交后返回。上游不传检索模式，P4 只承担网关接入与转交。

| 归属 | 谁定义什么 |
|---|---|
| Recall Runtime（A） | 本次请求、来源选择策略、执行、候选快照、上下文、访问观察、排序/预算及本地核验规则 |
| Semantic Embedding（A） | Passage/Query 向量化契约与实现、模型版本、向量输出、输入绑定和幂等复用；供 B 和 Recall Runtime 调用 |
| Vector Projection（A） | VectorProjectionPort / VEC-001 的写入、查询、删除、未知结果恢复及 ProviderResult；P2 执行物理存储与索引 |
| Remember（B） | Memory、Working、生命周期/TTL、Projection 领域状态、正式内容映射、衰减与冲突策略 |
| Operate（C） | 调层/预热动作、放置与释放生命周期、热度和调度阈值 |
| P2 | Provider 的请求响应和物理实现 |
| Runtime Foundation（RF） | 共享事件 Schema、摄取、身份与基础持久化机制 |
| P4 | 网关接入、请求/响应转交；不判断检索模式，网关接收不证明模型使用 |
| 实际调用方 / Agent Runtime（承接方待确认） | 实际注入模板、接收和模型使用证据；Recall 只提出消费需求，不指定其内部实现 |

三个模块由同一负责人建设，各自维护所属契约与状态。B 负责 Projection Build 编排和 ProjectionState；A 负责向量及投影机制结果。Recall Runtime 不直读 B/C 内部 key，不在在线搜索中补写索引，也不接管 C 的控制动作。

## 2. Embedding 与向量投影写入怎么实现

本章设计 A 负责的 SemanticEmbeddingCapability 和 VectorProjectionPort（VEC-001）机制。Embedding 生成真实向量；投影机制把 B 指定的向量及关联信息交给 P2，确认写入、更新、删除及未知结果。B 负责决定构建对象、切分片段、编排任务和最终 ProjectionState；P2 负责物理向量存储与索引。

贯穿例子：B 将《项目接口约定》V3 的片段 chunk-1 交给 A，以 Passage 用途生成向量；B 随后发起该片段的投影写入，A 调用 P2 并交回机制结果，B 执行 Ready Guard。用户后续查询时，Recall 以 Query 用途调用同一 Embedding 能力，所得 Query 向量只用于搜索。

~~~text
B 准备正文片段 → A Embedding（Passage）→ 向量结果交给 B
B 发起投影写入 → A VectorProjectionPort → P2 存储/索引
                                       → A ProviderResult → B Ready Guard → B ProjectionState
Recall 问题 → A Embedding（Query）→ Query 向量 → VEC-002 搜索
~~~

两次能力调用通过输入摘要、片段身份和模型版本关联。生成向量不自动触发存储；Query 不写入长期索引。以下八节说明这条完整协作链，不能把它作为在线 Recall 的九至十六阶段。

### 2.1 校验输入并区分 Query、Passage 和投影操作

**本节解决“接收什么任务、允许产生什么结果”** 调用方必须明确用途；投影写入、删除是另一次有授权的机制调用。

**第 1 步：接收输入与调用依据**

Embedding 接收文本或受控片段、usage、模型契约、source_hash、身份与 deadline。Query 来自 Recall；Passage 来自 B 已准备好的片段。投影机制接收 B 指定的目标、动作和版本依据，upsert 还必须关联已验证的 Passage 向量。

**第 2 步：核对授权、输入摘要和限额**

核验当前调用权限、输入是否属于本租户、实际字节与 source_hash 是否一致，检查非空文本、模型输入 token 上限与剩余时间。超长输入明确拒绝，由 B 按其切分规则准备新片段；模块不静默截断、改写文本或跨租户复用向量。

**第 3 步：确定执行分支并固定约束**

Query / Passage 向量化继续第 2.2 节；已持有可信 Passage 结果的投影请求从第 2.4 节进入。delete 不重新 Embedding，进入第 2.4 节核验准确目标，再按第 2.7 节删除规则执行。非法、越权或资源不足在推理和 P2 调用前拒绝。

**开发对照：字段、错误处理与接口**

本节产物为 [SemanticEmbeddingRequest](召回数据定义_V0.1.md#19-semanticembeddingrequest共享向量化请求) 或 [VectorProjectionRequest](召回数据定义_V0.1.md#21-vectorprojectionrequest向量写入或删除请求)。它们不继承 RecallExecution，不要求虚构 recall_id、检索模式或上下文预算。模块错误与 Recall 的四终态分开；Recall 消费 Query 错误时仍按第 3.2 节和第 4 章映射。

### 2.2 绑定模型、检索空间和复用条件

**本节解决“这次向量应由哪个模型产生、能否使用已有结果”** 每个请求固定模型及预处理版本，不能随配置更新切换。

**第 1 步：解析获准模型契约**

确认 model_id、model_version、dimension、dtype、embedding_schema_version、预处理版本及输入限制。Query 与 Passage 可使用模型声明的不同前缀或编码方式，但必须位于获准的兼容检索空间；不能仅凭维度相同认定兼容。

**第 2 步：计算本地复用身份**

以租户、usage、source_hash、模型及预处理绑定、检索空间计算复用摘要。先校验当前调用授权，再判断是否命中。不同 usage、正文、chunk 输入绑定、模型或 Schema 不共享结果；同一正文是否属于同一 Memory 仍由 B 判定。

**第 3 步：验证已有结果或排队执行**

命中时校验受控结果及向量摘要、版本和用途；不能解析或证明的旧引用作未命中并重新推理。未命中进入对应 usage 的有界队列。V0.1 只复用已完成结果，不合并不同请求的在途计算；每个请求遵守自己的截止时间和推理次数。

**开发对照：字段、错误处理与接口**

向量复用只复用计算结果，不复用写入授权、P2 操作状态或 B 的 Ready 结论。模型和空间不兼容返回 EMBEDDING_BINDING_MISMATCH，正文摘要不符返回 EMBEDDING_INPUT_INVALID。契约和空间消费映射由 AL-B05、AL-B08 确认。

### 2.3 执行真实推理并验证向量

**本节解决“取得与本次输入准确绑定的合法向量”** 例子中的结果必须能证明来自 chunk-1 的 V3 输入。

**第 1 步：按用途分配资源**

Query 与 Passage 使用独立队列、并发额度和推理执行资源。V0.1 不把两种用途合成一个 batch；不让 Passage 批量任务占满 Query 的保留额度。共享设备无法证明隔离时分开部署或降低 Passage 准入，实际吞吐须测量。

**第 2 步：执行推理并保留输入对应关系**

只将兼容模型、用途和预处理的请求放入同一批次。按稳定输入 ID 回填结果；单条失败不得错配后续条目，也不能用零向量补齐成功数组。推理前由 SemanticEmbeddingExecution 可靠占用本次尝试额度；**共享模块的执行协调者是推理唯一 Retry Owner**，只使用 EM-04 和原 deadline，崩溃不归零。模型 SDK 不另行重试；调用方的传输重试只重新附着原执行或补取结果，不能创建新的推理请求来取得新额度。失败终态的同调用重放仍返回原失败，超时不切换不兼容模型。

**第 3 步：验证并保存结果**

核对实际模型、用途、Schema、维度、有限数值和输入摘要。向量按已批准 dtype 的规范字节计算摘要并受控保存。Query 的调用在此形成共享结果，由第 2.8 节交付 Recall；Passage 的结果交付 B，B 决定是否继续提交投影。

**开发对照：字段、错误处理与接口**

本节产物为 [SemanticEmbeddingResult](召回数据定义_V0.1.md#20-semanticembeddingresult共享向量结果)。Recall 在第 3.2 节再次核对检索兼容性后形成自己的 QueryEmbeddingResult；共享模块不创建 Recall 的执行记录。推理失败用 EMBEDDING_COMPUTE_FAILED，超过期限用 EMBEDDING_DEADLINE_EXCEEDED；没有可信向量时不创建成功结果。构建投影只接受 usage=Passage。

### 2.4 构造投影请求并固定目标和幂等绑定

**本节解决“准备把哪一个片段的哪一版向量写到哪里”** B 已取得向量并决定写入，A 负责形成可恢复的机制请求。

**第 1 步：核对 B 的目标与向量结果**

沿用原工作包的五元组：memory_id、chunk_id、memory_version、model_version、projection_schema_version。核对 B 的正式内容引用、版本、获准范围、表示及检索元数据，与 Passage 输入摘要、模型、维度及目标空间一致；B 的片段身份不是 A 重新生成的 Memory。

**第 2 步：固定逻辑目标与操作身份**

逻辑目标绑定租户、Provider、检索空间和完整五元组；不只用 memory_id 做物理覆盖键。upsert 和 delete 的操作幂等身份分开，均在发出前固定。同目标、同动作、同载荷复用原 operation_id；同身份换向量、元数据或内容映射直接报 PROJECTION_IDEMPOTENCY_CONFLICT。metadata_hash 只摘要 scope、memory_type、occurred_at 的规范化语义值，不含 owner_metadata_evidence_ref；更换证据引用仍须重新核验授权和语义，不能借此修改原载荷。准确字段、摘要输入及版本兼容规则见数据定义 21.4。

**第 3 步：可靠保存请求和操作记录**

将不可变请求、载荷引用、目标绑定与操作索引一致保存，再允许发出 P2 调用。目标已收到获准删除指令时先保存退役标记，阻止旧 upsert 重新执行；不能仅靠删除向量字节防止迟到写入复活。

**开发对照：字段、错误处理与接口**

本节产物为 VectorProjectionRequest、ProjectionTargetBinding 和 VectorProjectionOperation。target_digest / operation_key / request_fingerprint 的计算见数据定义第 21～23 章；source_hash 不等于向量摘要。B 的写入授权、五元组和 Ready Guard 输入按 AL-B08 对齐；P2 物理 ID、元数据编码及幂等保证按 AL-P205、AL-P206 对齐。未可靠保存不宣称受理，不调用 P2。

### 2.5 调用 P2 执行向量写入

**本节解决“让 P2 实际接收并执行存储操作”** A 是 VEC-001 的契约 Owner 和消费方，物理存储与索引由 P2 实现。

**第 1 步：领取操作并保存调用意图**

校验当前租约、目标未退役和当前写入授权。以 CAS 保存本次调用类型、序号、稳定幂等键及消耗次数，再发出远程调用。进程在保存后、发送前崩溃，也按可能已发送处理，恢复先查证，不重新获得次数。

**第 2 步：向既有 upsert 能力提交载荷**

通过已确认适配把真实向量、稳定目标、模型/维度/Schema、B 的身份与内容映射、检索过滤元数据及授权范围交给 P2。向量库中保存的是向量和获准元数据；正式原文仍按 B 的内容契约保存，不能把本步骤误写成 A 向 OBJ-001 写正文。

**第 3 步：记录原始响应并核对对应关系**

保留操作引用、实际目标和版本等原始证据，再按契约转换为 A 的 ProviderResult。HTTP 成功或队列接收只能证明其约定阶段；ACCEPTED、PENDING 不能写成 READY。响应丢失或效果无法确认进入 UNKNOWN。

**开发对照：字段、错误处理与接口**

对接为 RP2-06、RP2-07；实际 P2 报文由适配契约映射，不要求 P2 返回我们的本地字段名。V0.1 每个机制操作只包含一个向量，批量由 B 拆成独立操作；后续 P2 批量优化必须保留逐项身份和结果，不能用整批成功掩盖部分失败。底层 SDK 关闭叠加写重试，由 A 的操作协调层统一控制。

### 2.6 确认实际存储、元数据与索引状态

**本节解决“写入请求被接收之后，实际完成到了哪一步”** 例子中要查证 chunk-1 / V3 的向量及关联信息，而不是仅看写入接口是否返回成功。

**第 1 步：查询同一操作与准确目标**

优先使用 provider_operation_ref 查询；首次响应丢失、尚无该引用时，必须能按原幂等键查询操作，或取得契约认可的等效权威证据。查询准确目标的对象存在、绑定摘要、模型/维度/Schema、元数据和索引可查询性。不能用一次 ANN 搜索没命中证明未写入或已删除。

**第 2 步：按证据形成机制结果**

| ProviderResult | A 需要持有的事实 | 后续动作 |
|---|---|---|
| ACCEPTED | P2 已受理同一操作，但尚无完成证据 | 查询进度 |
| PENDING | P2 明确操作仍在执行或索引尚未达到约定完成条件 | 在恢复预算内继续查询 |
| READY | upsert 的准确目标、载荷绑定及已签收可查询性条件全部满足；delete 则为第 2.7 节的删除完成条件满足 | 保存机制完成证据并交给 B |
| FAILED | 已知拒绝或明确失败，且不是“可能仍在执行” | 返回实际原因；不把未知当失败 |
| UNKNOWN | 写入效果、操作对应关系或必要完成证据无法确认 | 保持待核验，禁止盲目再次写入 |

**第 3 步：核验后交付 B**

只有证据与原请求目标一致才采用；版本、向量绑定或元数据不符时不得 READY，记录 PROJECTION_BINDING_MISMATCH 并保留实际观察。P2 明确完成但缺必要可查询性证据时继续 PENDING 或 UNKNOWN，具体取决于已有事实。

**开发对照：字段、错误处理与接口**

本节产物为不可变 ProviderResult 观察版本，定义见数据字典第 24 章。P2 的持久化、read-after-write、index_ready、是否需要 search probe 及删除可见性由 AL-P207 确认；未确认前真实 READY 路径关闭。A 的 READY 不写 B 的 ProjectionState；B 仍复核当前 Memory、正文和模型等 Ready Guard。

### 2.7 处理未知结果、更新和删除

**本节解决“中断后怎样继续，以及旧向量怎样安全退出”** 操作恢复使用原目标和原载荷，不重新生成向量替换正在确认的请求。

**第 1 步：未知结果先查询**

从可靠操作记录恢复租约、已消耗次数和最近结果。PENDING / UNKNOWN 只按原操作查询；达到调用方等待期限就交回最新已保存的机制状态和 operation_id，后台在独立恢复窗口内继续。恢复窗口或查询额度耗尽后标记 attention_required，保留 UNKNOWN/PENDING 及证据供 B 决策；不能改写为成功或永久失败。

只有 P2 已证明前次未产生效果、不会迟到生效，且契约允许同幂等键安全再提交，A 才可在原写次数额度内重发。普通 not_found、超时或本地失租均不足以证明这一点。FAILED 的同键重放仍返回原结果；READY 重放只说明原操作完成，不证明当前对象仍存在。B 发现对象缺失时不能据历史 READY 恢复领域可读。

**同目标重建的当前实现边界。** VectorProjectionRequest 明确区分普通首次/重复写与 rebuild 意图；本版同五元组 rebuild 在 P2 调用前返回 PROJECTION_REBUILD_UNSUPPORTED。B 的新 task/attempt/caller_request_ref 不改变 operation_key，也不能重开 settled 操作。只有 Memory/model/schema 的真实版本变化且获得 B 授权，才可按新五元组写入；不得为绕过幂等而伪造版本。同版本重建的代际身份、旧写失权和删除屏障统一列入[待确认事项第 7 章](跨模块待确认事项_V0.1.md#7-同版本投影重建必须一起确认的决策)，确认后另升契约版本启用。

**第 2 步：更新写新目标，不偷换旧目标**

Memory 版本、模型版本或投影 Schema 变化时，由 B 准备新的五元组和向量，形成独立目标。A 将新目标的机制结果交给 B，B 决定切换领域可读状态及何时清理旧目标；旧操作的迟到 READY 只属于原版本，不能覆盖新目标或替 B 宣告当前可读。

**第 3 步：删除准确目标并阻止复活**

消费 B 的获准删除指令，先持久化目标退役标记，停止新旧 upsert 重发，再提交精确 delete。P2 必须提供条件写/代际屏障，或能证明既有在途写已结束后再执行删除；只收到 delete Ack 还不够。完成须证明准确目标已不可查询、原在途 upsert 不会重新创建它，保留删除证据。同五元组退役后 V0.1 禁止 upsert；B 指定“新 attempt”也不能解除退役，重建按上面的关闭规则处理。

**开发对照：字段、错误处理与接口**

A 的退役标记只限制本机制的写操作，不是 B 的 Memory/Projection 生命周期。删除接口、精确对象查验、在途写屏障与历史键保留按 AL-P206、AL-P207、AL-B08 确认；不支持时报告能力缺口，不能默认已安全删除。多个 chunk 各自回报结果，B 汇总领域任务状态；A 不把一条成功扩大为整份 Memory 成功。

### 2.8 可靠保存结果并交给调用方

**本节解决“如何交付真实结果，并让调用方在丢失响应后继续查询”** Embedding 输出和投影机制结果分别提交，不把两次调用伪装成跨服务事务。

**第 1 步：保存本次可信结果**

Embedding 成功结果与受控向量可靠绑定后交付；无法保存或校验则不返回成功对象。投影原始观察、ProviderResult 和 Operation 的最新结果引用在同一可靠边界更新；CAS 失败的旧 Worker 不能改写新结果。A 保存失败而 P2 可能已执行时，返回机制暂不可用，恢复后查询 P2，不能重新盲写。

**第 2 步：按能力边界返回**

Query 向量交 Recall；Passage 向量交 B。投影 submit/query 向 B 返回 operation_id 和已保存的最新 ProviderResult；B 可重复查询补取，V0.1 不依赖新增回调或共享事件。正在执行时返回实际 ACCEPTED/PENDING/UNKNOWN，不能借用 Recall 的 COMPLETE_AVAILABLE。结果重读仍核验当前调用权限。

**第 3 步：保留历史、交由 B 完成领域处理**

例子中，A 保存 V3/chunk-1 的 READY 证据，B 再检查当前 Memory 仍为 V3、正文有效、模型及 Schema 匹配后转 ProjectionState=Ready。如果此时 Memory 已变 V4，B 不采用旧 READY；A 保留 V3 的机制事实，按 B 后续指令清理。

**开发对照：字段、错误处理与接口**

新数据对象见《召回数据定义》第 19～25 章；写路径不生成 SearchHit、ContextSelected 或 ContextEmitted。模块错误分类为：EMBEDDING_INPUT_INVALID、EMBEDDING_BINDING_MISMATCH、EMBEDDING_BUSY、EMBEDDING_COMPUTE_FAILED、EMBEDDING_DEADLINE_EXCEEDED；PROJECTION_REQUEST_INVALID、PROJECTION_SCOPE_DENIED、PROJECTION_IDEMPOTENCY_CONFLICT、PROJECTION_TARGET_RETIRED、PROJECTION_BUSY、PROJECTION_BINDING_MISMATCH、PROJECTION_PROVIDER_FAILED、PROJECTION_EFFECT_UNKNOWN、PROJECTION_RECOVERY_EXHAUSTED、PROJECTION_NOT_DURABLE、PROJECTION_REBUILD_UNSUPPORTED。最后一项表示当前契约不支持请求中的同目标重建，受理前拒绝且不调用 P2。保留脱敏外部原因和证据；受理前拒绝不是伪造的 P2 失败事实，写超时不等于 FAILED。

**模块参数：实验基线，独立于 Recall 的 P 参数。** 受理时固定下面的 policy_version 与配置快照，重启不重获预算；真实上线限额须结合模型、设备和 P2 能力确认。

| ID | 参数与实验默认值 | 执行规则 |
|---|---|---|
| EM-01 | Embedding 单批最多 32 条；单条 token 上限取固定模型契约 | Query/Passage 分批；不自动切分或截断输入 |
| EM-02 | Query 最多等待 2000 ms；Passage 最多等待 10000 ms | 与调用方剩余 deadline 取更小值，排队也计时 |

## 3. 主链路怎么实现（A-01）

本章按一次请求的执行顺序分为八节，每节对应一个环节。贯穿例子都是用户问“这个项目之前定过哪些约定？”，请求带有当前会话和项目信息，没有指定记忆类型；后续候选和内容仅用于说明流程。

### 3.1 校验请求并选路

**本节解决“请求能不能受理、去哪里查”** Recall 自己完成这个决定；上游提供问题和必要信息，P4 网关只负责转交。

使用上面的例子：Recall 先确认请求是否合法、调用方有权查什么，再决定读取工作记忆、长期记忆，还是两类都查。

**第 1 步：收到问题和必要信息**

Recall 收到问题、调用身份、当前会话/任务、项目范围，以及可选的类型/时间筛选、明确的上下文预算和幂等键等信息。上游不用告诉 Recall“只查工作记忆”或“两种都查”。

**第 2 步：检查并整理参数，识别是否为重试**

先检查编号格式、筛选条件和预算是否合法。例如，时间范围写反了，或者指定了不支持的记忆类型，就拒绝请求。

新请求没有指定记忆类型时，按当前策略支持的类型处理，不预先排除工作记忆或长期记忆。同键重试则先取回原执行绑定，用原规则解释和比较请求；同一个键换了问题或其他请求语义，不能覆盖原执行。

**第 3 步：确认调用方有权查什么**

Recall 根据可信的授权证据确认，而不是只相信传进来的编号：

- 当前会话/任务是否合法，调用方是否有权读取其中的工作记忆。
- 调用方是否有权读取指定范围内的长期记忆。

没传当前会话/任务，就没有定位工作记忆的条件，但仍可能查长期记忆。传了越权的编号则拒绝，不能删掉编号后继续查；权限无法确认时也拒绝。重试同样要重新验证权限。

**第 4 步：结合权限和类型筛选，确定检索模式**

“符合条件”表示：范围明确、已获读取授权，而且没有被类型筛选排除。它不表示已经知道这个来源里有相关内容。

| 检查结果 | 本次查哪些记忆 | Recall 内部模式 |
|---|---|---|
| 工作记忆、长期记忆都符合条件 | 两类都查 | combined |
| 只有工作记忆符合条件 | 只查工作记忆 | working_only |
| 只有长期记忆符合条件 | 只查长期记忆 | long_term_only |
| 两类都不符合条件 | 拒绝，并说明原因；不是“查完没有结果” | 不生成模式 |

在例子中，假设会话合法，两类读取都已获授权，也没有类型限制，Recall 就选择 combined。问题中的“之前”用于后续相关性检索，不作为删掉工作来源的理由。同键重试沿用原选择，新增权限也不扩大原来的检索模式。

**第 5 步：确认能够受理，固定本次执行的约束**

新请求还要通过并发、队列和事件记录容量检查。受理时可靠保存“查哪些来源、为什么这样选、用了哪版规则”，同时固定截止时间、预算、策略、注入模板和 token 计数版本，建立请求、幂等索引与执行记录的绑定；受理前拒绝的请求不虚构执行记录。

到这里，例子中的请求被受理，两类来源都需要查，随后进入第 3.2 节。以后某个来源超时，只能记录该来源没有查完整，不能把原模式改成单路。重试复用原执行及其绑定，不另建一条重复执行路径。

这套规则优先减少漏召回，尚未证明质量或延迟最优。为什么先这样做、以后怎样评测优化，见[调研与取舍](#自动选路调研项目取舍与后续评测)。

**开发对照：字段、错误处理与接口（第一次阅读可以跳过）**

**本节产物。** [RecallRequest](召回数据定义_V0.1.md#recall-request)内嵌[SourceSelection](召回数据定义_V0.1.md#source-selection)，并与[RecallRequestIndex](召回数据定义_V0.1.md#request-index)、[RecallExecution](召回数据定义_V0.1.md#recall-execution)可靠绑定。字段只在《召回数据定义》维护。

**策略与入口边界。** 策略标识仍为 scope_union_v1。W/L 只是“工作/长期来源是否符合条件”的简称，不是上游参数。上游不传 retrieval_mode、source_selection 或 allowed_sources；这些值由 Recall 产生。新入口收到客户端模式/来源字段即 REQUEST_INVALID。

**参数与分支映射。** 原始筛选仅接受 memory_types、occurred_after、occurred_before。类型沿用 B（Remember）的 Working、Episodic、Semantic；未传时按本策略批准类型展开，显式空列表、未知类型或非法时间范围拒绝。先整理类型/时间，再选模式。各分支只映射适用的类型和已授权范围：Working 不发到长期分支，完整筛选仍保留在标准请求中，不修改 B/P2 的 filter Schema。

**授权与拒绝原因。** 所有显式 session/task 都须验证身份、归属、请求范围及相互一致性。只有两个 ID 都未提供才记 no_current_scope；非法或越权 ID 不能丢弃后重选。单有 tenant_id 不证明长期权限，合法 session/task 也不自动授权长期读取。权限证明未知/服务不可用用 AUTHORITY_UNAVAILABLE，明确越权用 SCOPE_DENIED；未知权限不能当作明确不授权。某一来源明确未授权时，可以使用另一已授权且适用的来源。

**每来源的记录顺序。** 依次判断“无当前范围（仅 Working）→ 未获该来源读取权限 → 类型排除 → eligible”。没有任何已授权且可定位的来源用 SCOPE_DENIED；原本有可读来源，但类型筛选排除了全部来源，用 REQUEST_INVALID。两种情况都在受理前拒绝，不产生正常空结果。并发、队列或 Outbox 容量不足用 ADMISSION_BUSY，同样不创建虚构的 RecallExecution。

**不靠内容猜测选路。** Query 只用于后续相关性检索。“刚才”“以前”、问题长短、Working 命中数和未经校准的相似度都不能用来跳过另一适用来源。业务硬限制须由已确认的结构化授权/筛选契约表达；本版不承诺从自然语言中识别这类限制。

**不把故障当策略。** Redis/向量服务健康、缓存命中、Projection 是否建好、剩余预算和检索空间绑定缺失，都不能用来缩小已确定的来源集合。故障按原规则处理；未签收的能力不接真实流量，也不能因此把该来源标为“未请求”。

**幂等与重试绑定。** 同幂等键、不同 fingerprint：IDEMPOTENCY_CONFLICT；同键执行中：复用同一执行，不另起有副作用的路径。重试先加载原 SourceSelection、模式、类型展开规则及 policy_version，重验权限后比较原绑定下的请求语义；新增权限不扩大原模式，撤权不能继续返回旧内容。重试按原执行绑定的策略/模板校验，不能用新默认配置制造伪冲突。新策略只影响新执行；旧请求版本不自动转换，旧执行仅走受控旧版重放，无法安全解释时要求新键重试。已终态重放与重启恢复见第 3.8 节。

**同键并发等待。** 请求索引唯一约束决定首次受理者；竞争失败者读取同一执行并附着等待，不分配第二份执行/Outbox/读取额度。只有持租协调者推进阶段。每个附着调用在自己的接入 deadline 与原执行剩余期限较早处停止等待，返回同一关联的暂不可用；单个等待者断开不取消其他等待者或重置原执行。原执行超期按 3.8.1 收尾，已有结果按重放规则交付，不能由每个等待者独立发起后台恢复。

**预算约束。** 沿用 P-04/P-05 有界发现、P-06 总量、正文限额及最终 token 裁剪；业务 deadline 用尽不启动新的推理、检索、正文读取或事实复核，未完成来源保留缺失。提交查证和不含正文的失败收尾使用 3.8.1 的独立恢复额度，不能借此继续业务执行。

**后续使用哪些读取能力。** Working 通过 B 认可的能力读取；长期候选通过 VectorSearchPort（VEC-002）发现；正式正文按 B 的映射经 CanonicalLoadCapability / ContentStorePort 加载。Prewarm 只是可选的正文热副本，不是第三个检索来源，也不与 Working 共用业务语义。

P-16=0 不允许后续重放正文；当前在线首次交付仍须先确认可靠提交，其受控快照在本次交付结束后立即清除。执行元数据、幂等索引和提交证明至少保留至 P-22 恢复窗口及有效载荷保留窗口两者的较晚结束点；未解决提交不能因窗口耗尽而自动删除。数据定义附录 B.3 是分层清除规则。后台事件重试不占在线请求预算；实验上限不能当作生产吞吐/SLO 承诺。

### 3.2 生成 Query 向量

**本节解决“怎样把问题变成长期检索可用的输入”** Recall 调用共享的向量生成能力，把问题转换为供 P2 搜索使用的问题向量，并检查它是否与目标检索空间兼容。

接着上面的例子：本次选择了 combined，需要查长期记忆，因此要为“这个项目之前定过哪些约定？”生成问题向量。

**第 1 步：根据已固定的模式，判断是否需要生成向量**

只查工作记忆时，跳过本节的向量调用，直接进入第 3.3 节读取当前会话/任务中的 Working。只查长期记忆或两类都查时，才执行后面的向量生成与校验。

这来自本版的两条读取路径：Working 按当前授权范围读取，长期记忆按问题相关性做向量检索；两类来源仍分别受后续资格检查约束。

**第 2 步：确认本次要使用的模型和检索空间**

读取本次执行已经绑定的检索空间与兼容规则，确认需要哪一版模型、向量维度和输出格式。已有长期向量与问题向量必须能在同一获准空间里比较，不能临时换一个不兼容模型凑结果。

**第 3 步：以 Query 用途调用共享能力**

Recall 将本次问题交给共享的向量生成能力，明确用途是 Query。例子中产生的是“这个项目之前定过哪些约定？”的检索输入，不在这里为历史正文重新生成向量，也不负责重建长期索引。

**第 4 步：检查实际返回的向量**

不能只看“调用成功”。Recall 还要检查实际模型及版本、向量长度、数值、数据类型、输出 Schema，以及与目标检索空间的对应关系，确认结果确实绑定本次问题。

检查通过后才保存可信的问题向量结果；空向量、伪向量和不兼容结果都不能交给 P2。

**第 5 步：保存结果，或记录长期分支不能继续的原因**

例子中，向量生成并校验成功，随后进入第 3.3 节。暂时性故障只在允许次数和剩余时间内重试。

如果最终没有可信向量，就停止本次长期检索。combined 在剩余时间允许时仍继续 Working，并保留长期来源缺失；long_term_only 没有其他来源可用，只能进入失败收尾。不能把向量失败解释为“长期记忆没有相关内容”。

**开发对照：字段、错误处理与接口（第一次阅读可以跳过）**

**本节产物。** [QueryEmbeddingResult](召回数据定义_V0.1.md#query-embedding)只表示成功且可信的向量结果，usage=Query。working_only 跳过调用，也不创建该对象；失败不能生成空向量成功对象。

**调用与校验。** 使用我们建设的共享 SemanticEmbeddingCapability（IF-06），沿用原契约，依赖 AL-B05、AL-RF04。核验实际 model_id/model_version、dimension、dtype、embedding_schema_version、usage、输入绑定证据及 retrieval_space_ref；source_hash 绑定本次 query，若共享能力有额外预处理，保留原契约映射证据。本节描述 Query 调用，Embedding 模块的建设责任与 Passage 用途见[5.4](#54-构建并提供-embedding-共享模块)；Projection 写入及恢复见第 2.4～2.8 节。

**失败与重试。** 首次调用前，将 Query 的共享调用关联可靠绑定到 RecallExecution：caller_ref 使用 A 的固定调用身份，caller_request_ref 使用本执行的 recall_id，usage 固定 Query；重启、超时和结果补取均使用同一绑定。共享模块独立负责 EM-04 推理；Recall 只按 P-08/P-09 和原剩余 deadline 重新附着/补取，不换 ID、不重开失败执行、不再自行重试模型。每次附着调用记录到 RecallReadLedger；同进程直接等待仍复用一个共享执行。生成失败记 QUERY_EMBEDDING_FAILED；模型、维度、usage、Schema 或空间不兼容记 EMBEDDING_CONTRACT_MISMATCH，禁止调用 VEC-002。失败由 SourceReadResult、Execution 和 Trace 记录长期来源不可用，不改变已固定模式；跳过发现时由收尾阶段补齐来源记录，见 3.8.1。

**阶段顺序。** V0.1 先结束 Query Embedding 阶段，再进入候选发现；不把 Working 与 Embedding 跨阶段并行。combined 只有在仍有安全继续条件时才转入 Working 发现；deadline 用尽则按第 4 章收尾。

### 3.3 发现候选

**本节解决“哪些记录可能与这次问题有关”** Recall 按已选来源取得一小批候选线索，保存它们的原始引用和读取完成证据，供后面核验。

接着上面的例子：本次两类来源都要查，问题向量也已经准备好，现在分别读取当前任务相关的 Working 和长期向量候选。

**第 1 步：按原模式分发读取任务**

working_only 只读 Working，long_term_only 只做长期向量检索，combined 在两条分支都能执行时同时发起。这一阶段中，Working 与 Vector 可以并行；某一边先返回，不会取消另一边原本应完成的读取。

如果上一节已确认长期向量生成失败，本节继续记录该来源不可用，并在条件允许时处理 Working，不重新改选模式。

**第 2 步：在当前授权范围内读取 Working**

通过 Remember（B）认可的能力，读取当前会话/任务内有限数量的工作记忆。Working 是当前工作状态的一部分，不等于把全部聊天记录都取回来。

假设例子中得到一条当前任务记录的候选。B 可能返回内联内容，也可能只返回引用；这里先保留受控结果，是否能使用还要经过第 3.4、3.5 节。

**第 3 步：用问题向量向 P2 查找长期候选**

把已经验证的问题向量、获准范围、适用筛选和数量上限交给 P2 的向量搜索能力，取回相近候选的稳定引用及来源顺序。

假设例子中找到两份历史项目约定，其中一份还有一条重复命中的引用。此时只是找到了线索；向量命中并不能证明正文仍有效、仍有权限读取，也不能直接拿来回答用户。

**第 4 步：保存每个候选来自哪里**

Recall 保留每个候选的稳定原始引用、所属来源、来源内顺序及读取证据，让后续能查到对应的记忆事实和正式正文。所谓“恢复原文”，是后面按这些引用读取已保存的内容，不是把向量反向解码成文字。

**第 5 步：分别判断两个来源有没有查完整**

读取返回零条，可能是确实没有候选，也可能是超时或只完成了一部分；必须结合完成证据判断。完整只指本次范围、筛选和数量边界内完成，不代表扫描了全部记忆。

在例子中，假设两路都有完成证据，候选与来源结果保存后进入第 3.4 节。若某路未完成，就保留该路缺失，最终再结合安全内容决定降级返回还是失败。

**开发对照：字段、错误处理与接口（第一次阅读可以跳过）**

**本节产物。** 每来源形成[SourceReadResult](召回数据定义_V0.1.md#source-result)；取得可信的向量搜索响应时保存[VectorCandidateSet](召回数据定义_V0.1.md#vector-set)。发现引用不能提前指向尚未验证的 RecallCandidate，后续沿 candidate_id 建立关联。

**Working 读取。** 必须有界且属于当前会话/任务，受 P-04 与 P-06 约束；B 决定当前性和 TTL，Recall 的数量上限不改变它们。B 提供的内联正文也要在第 3.5 节验证，只有引用时按正式映射加载。能力与完成证明待 AL-B01 确认，失败/部分读取分别记 WORKING_UNAVAILABLE、WORKING_PARTIAL。

**长期读取。** 使用 VectorSearchPort（VEC-002），受 P-05/P-06、模型空间和已授权 filter 约束，契约待 AL-P202 确认。向量命中只提供候选线索，不证明 Memory 有效。完成 TopK 搜索只表示本次 filter、模型空间与数量边界内完成，不表示扫描全库。搜索故障、部分结果或引用无效分别按 VECTOR_UNAVAILABLE、VECTOR_PARTIAL、CANDIDATE_REFERENCE_INVALID 留证。

**来源完整性。** source_coverage 分别记录两路状态，不能只看 returned_count。

| source_coverage | 含义 |
|---|---|
| complete | 在本次 filter、limit 和快照边界内完成，有完成证据；允许零条 |
| partial | 仍有未确认部分；即使返回零条也不是已确认空 |
| unavailable | 该必需来源没有可信结果 |
| not_requested | 本模式不要求该来源，不影响完整性 |

**完成与结果的区别。** B 已确认删除、过期、越权、旧版本或长期 Projection 非 Ready，是已知排除；B 查询失败、正文丢失、损坏或版本不明，是结果缺失。正常 TopK 限制、明确策略过滤及正常 token 裁剪不自动降级。最终结论统一按[第 4 章](#4-结果故障与恢复a-02)判定，不能用发现阶段的 complete 代替后续安全校验。

**重试与阶段名称。** 可重复读仍受单一 Retry Owner、P-08/P-09 和原 deadline 限制；不拼接不同尝试冒充一次完整搜索。总流程中的 RUNNING_VECTOR_SEARCH 沿用历史名称，working_only 也经过候选发现阶段，但不调用 VEC-002。

### 3.4 核验资格

**本节解决“找到的候选现在有没有资格被使用”** Recall 通过 Remember（B）核对权限、版本和记忆状态，只有资格得到确认的候选才进入正文加载。

接着上面的例子：已经找到一条 Working 候选和两份历史约定的候选引用，现在要检查它们是否属于本次获准范围、是否仍然有效。

**第 1 步：用稳定引用向 B 核对候选事实**

把发现阶段保存的原始引用交给 B 认可的能力，确认它对应哪条记忆、哪个版本、什么类型。Recall 不自行从向量索引编号猜出 Memory 身份，也不把搜索结果当成权威事实。

**第 2 步：逐项核对范围、权限和当前版本**

即使入口已经校验请求范围，候选仍要核对是否确实处于该范围、调用方当前是否可读，以及发现版本是否仍是 B 确认的当前版本。

例如，历史约定的旧版本仍可能被向量搜索命中。B 已确认它过时，就排除该候选；不能在原候选上悄悄换成另一版正文。

**第 3 步：按来源检查各自的有效条件**

Working 要由 B 确认属于当前会话/任务、类型是 Working、状态为 Active，并且 TTL 尚未到期、仍具当前性。

长期候选除通用的生命周期、类型与权限检查外，还要确认对应 Projection 已 Ready，且模型和 Schema 与本次检索空间兼容。Working 不要求先具备长期 Projection。

**第 4 步：区分已知不能用和暂时无法确认**

已确认删除、过期、越权或版本过时的候选，是有证据的排除。B 查询失败或必要事实缺失的候选，则先隔离，并记录“无法确认”，不能当成正常排除来掩盖缺失。

两种情况都不能继续加载未获批准的正文；正文看起来再相关，也不能代替授权证据。

**第 5 步：保存资格结论，交给正文加载环节**

在例子中，假设一条 Working 和两份历史约定的当前版本均通过检查，就保存各自的资格结论和证据，进入第 3.5 节取得获批正文映射并读取内容。重复引用会继续保留来源证据，稍后统一去重。

本节通过只表示这个检查时点有资格使用；正文是否完整、返回前是否仍有效，还分别由第 3.5 和第 3.7 节检查。

**开发对照：字段、错误处理与接口（第一次阅读可以跳过）**

**本节产物。** [CandidateValidationResult](召回数据定义_V0.1.md#candidate-validation)关联原 SourceReadResult、candidate_id、B 契约及证据，结论为 accepted、excluded 或 unverifiable。accepted 只证明此时资格通过，不证明正文已加载；无事实证据不能伪造 accepted 或 excluded。

**通用与分支校验（RULE-01）。** 核对 Scope、当前版本、生命周期/类型及候选授权。Working 要求 Active、Working 类型及 TTL/当前性；长期额外核对 Ready Projection、模型/Schema 和检索空间。相关度不能覆盖权限，不能用检索 filter 代替授权。

**失败规则。** 已知不合格用 MEMORY_INELIGIBLE 等权威排除原因；长期 Projection 非 Ready 用 PROJECTION_NOT_READY，不得用于拒绝有效 Working。B 事实读取失败用 MEMORY_READ_UNAVAILABLE；必要授权或版本事实未知时隔离并记缺失，请求级授权/安全证明失败按第 4 章阻断整个结果。未授权正文不得加载。

**职责与历史事实。** B 提供当前记忆事实和长期可读性证据，相关边界见 AL-B01、AL-B03、AL-B05、AL-P201；Recall 只保存本地校验结论。内容映射或正文后续失败不回写这次历史 accepted 观察，而由加载结果或缺口记录表达。

### 3.5 加载正文

**本节解决“怎样把已获准的候选变成可信正文”** Recall 根据 B 批准的内容映射读取对应片段，并检查身份、版本、范围和完整性，通过后才形成可排序的候选。

接着上面的例子：Working 与两份历史约定都已通过资格检查。假设其中一份约定事先已有有效热副本，另一份需要从正式存储读取。

**第 1 步：取得正式内容映射和获准范围**

B 告诉 Recall 哪个内容引用、哪个版本、哪种表示和哪段范围允许读取，以及怎样验证它们。只有资格结论，没有可验证的内容映射，仍不能随意去存储里拼路径取正文。

**第 2 步：按获批路径读取内容**

Working 已由 B 在获准读取中提供内联正文时，使用这份受控结果继续校验；只有引用时，再按正式映射加载。

读取长期约定时，若已获准启用 Prewarm，优先尝试热副本；命中且通过校验后使用该副本，未命中、不可用或校验失败时，再按正式正文路径读取。未启用 Prewarm 时，直接读取正式正文。热副本中的内容仍是原来的长期记忆；它只是提前准备好的读取副本，不会变成 Working，也不是第三个候选来源。

**第 3 步：检查拿到的内容是否确实是那一份**

Recall 核对租户与范围、记忆及内容版本、表示、字节范围和完整性证明。缓存返回了内容，也必须与权威映射给出的期望一致；不能只相信缓存自己报告“校验通过”。

例子中，预热的那份约定通过这些检查后，才可用于本次召回。加载长期原文依靠已保存的引用，不需要从向量中还原文字。

**第 4 步：热副本失败时，在剩余时间内回退正式内容**

如果热副本不存在、过期、被释放、损坏或读取超时，就隔离该副本，按正式内容映射回退。正式内容读取成功且验证完整，不因缓存失败而降低本次结果状态。

Recall 不在这次在线请求中等待 Operate 重新完成预取，也不负责创建或删除热副本。正文读取受既定大小、总字节数、并发和截止时间限制；最终不能验证的内容不能进入排序。

**第 5 步：保存可信正文及其来源证据**

在例子中，假设 Working 内联内容、热副本中的约定以及正式存储中的另一份约定都通过验证，就保存正文与资格、内容映射、实际读取路径之间的关联，形成第 3.6 节可处理的候选。

失败的读取也保留诊断和缺口，但不把残缺或不可信字节装成成功候选。预取是否真正被用到，要依据这里留下的实际读取证据判断。

**开发对照：字段、错误处理与接口（第一次阅读可以跳过）**

**本节产物。** 合法映射确认后形成[ContentLoadResult](召回数据定义_V0.1.md#content-load)；资格已批准且正文 validated=true 时，才形成[RecallCandidate](召回数据定义_V0.1.md#recall-candidate)。映射未知直接记 CONTENT_MAPPING_INVALID，不伪造 expected_identity 或成功正文引用。

**正式读取与完整性（RULE-02）。** 按 B 的映射经 CanonicalLoadCapability / ContentStorePort 加载；依赖 AL-B02、AL-P203。外部原始类型、范围编码、hash 算法和契约版本由原 Owner 定义并保留映射证据。不能安全转换或独立校验的片段不得使用，整对象 hash 不能证明任意子串。正式内容缺失/不完整用 CONTENT_UNAVAILABLE，完整性校验失败用 CONTENT_INTEGRITY_FAILED。

**Prewarm 读取。** 在 B 确认资格和内容映射后才读取，必须匹配租户/Scope、Memory 版本、表示、content_ref/content_version、字节范围和权威期望 hash。缓存自身的 hash 不能作为唯一证明；失效、释放、损坏或超时就隔离并在剩余 deadline 内回退正式内容。回退成功且信息完整，不因缓存故障降级。Recall 不等待 C 重新预热，也不写/删热副本；本版不扩展到候选集或整包 Context 缓存。相关边界仍待 AL-C01、AL-C04、AL-P204 确认。

**回退与观察。** Prewarm 初版只探测一次，受 P-07 限制并预留正式回退时间；已由 Provider 完成的回退不重复触发。用 PREWARM_FALLBACK 保留缓存诊断，最终是否降级由正式回退结果决定。实际 Provider、层级、generation 或动作归因证据不足，不凭配置补写；安全校验与预取归因分别判断，访问事实见第 5 章。

**加载限制（RULE-11）。** 受 P-19/P-20/P-21 限制。按来源优先级、来源内 rank、稳定引用确定加载准入顺序，不由并发完成快慢抢字节预算。超单片段限制只能改用 B 已批准且有独立范围证明的小片段，否则 CONTENT_LIMIT_EXCEEDED；总字节用尽留下的未加载候选也是缺失。成功、失败、丢弃、重试和回退实际收到的字节都计入 P-20。每候选最多一个内容片段或一个冲突组引用，额外切片另设输出限制。

#### 3.5.1 调用前记账、并发准入与崩溃恢复

本规则适用于已受理执行的身份/范围复核、Query 共享调用、Working/Vector 发现、MemoryRead、正文/Prewarm 和最终复核；状态和字段统一见数据定义 3.3 的 RecallReadLedger / RecallReadAttempt。受理前接入检查使用独立有界请求上下文，不虚构 Execution。推理次数仍只由 SemanticEmbeddingExecution 记账，最终提交恢复走 3.8.1。

1. **固定调用身份。** call_key 绑定本执行、阶段、能力、准确逻辑目标、获准输入和批次成员；重试和重启不变。批量调用按稳定身份排序并按已确认服务上限拆分，一批一个键；不能改批次或换适配器绕过已消耗次数。初次资格查询与最终复核属于不同阶段，各有自己的调用键。
2. **先原子预占再调用。** 当前持租者在同一 CAS 中追加调用意图、占用一次 P-08，并预留这次可能接收的正文上限。元数据/向量/推理结果不计正文额度；正文、失败残留、Working 内联正文都计入。预占失败或保存结果未知时不得发出调用，先查账。关闭下层 SDK 的隐式重试。
3. **保证总量和单次上限。** 任意时点必须满足 `已扣额度 + 在途预留 ≤ P-20`。单片段预留覆盖完整获批字节且不超过 P-19；多个内联 Working 正文须逐片段受限并预留整次响应上限。只有可证明响应有界或可在接收层硬限制的路径才能启用，不能先无限下载再截断。字节口径是 A 接收并交给内容适配层的原始正文 byte，JSON/base64 的包装、协议头、向量和元数据不计；内层压缩须能限制解压后的正文 byte。
4. **按顺序授予额度。** 准入协调者按稳定候选顺序和 `prewarm → canonical → canonical 重试` 处理每条加载链；不能让后续候选越过正在等额度的前序候选。已准入且各自有预留的调用可按 P-21 并发。额度暂被在途调用占用时先等待结算；全部结算后仍不足才记 CONTENT_LIMIT_EXCEEDED。Prewarm 只有在本次预留后仍能为该片段的首次正式回退留出额度时才探测，否则直接正式读取，跳过可选缓存不单独降级。
5. **结算或保守扣费。** 正常返回/取消时，先可靠保存实际接收量和受控结果，再原子将预留转为实际扣费并释放余量；完整性失败的字节也扣费。崩溃导致实际字节未知时，恢复将该次预留全额转为保守扣费，次数不退还；不填写一个猜测的实际字节数。后续重试另占次数和字节。迟到回调只能留下审计证据，不能返还已结算的保守额度或改写结果。
6. **恢复与输出关联。** 重启先读原账本、清算旧租约在途项，再判断是否有重试额度。ContentLoadResult 引用本链调用记录；Working 内联正文只在发现调用中扣一次，后续本地校验不重复扣。实际已知字节与未知的保守扣费分开记录，预算判断使用两者之和；不能用事后统计字段代替预占账本。

例如只剩 65536 byte 时，8 个并发调用不能各自认领同一余额：仅第一个成功 CAS 预占的调用可接收一个 65536 byte 片段。若其进程在结算前崩溃，该额度按未知全额扣除，重启后不会重新得到这 65536 byte。

### 3.6 排序

**本节解决“可信候选怎样去重、排顺序、保留冲突”** Recall 先合并同一内容的重复命中，再融合来源顺序，应用 B 已确认的语义策略，并识别必须一起呈现的冲突成员。

接着上面的例子：一条 Working 和两份历史约定已安全加载，其中一份约定有重复命中引用，现在要把它们整理成可解释的稳定顺序。

**第 1 步：只接收已通过资格与正文校验的候选**

本节使用前两节形成的可信候选。引用未解析、权限未知、正文损坏或版本不能确认的项，不能因为相似度高就重新进入排序。

**第 2 步：按内容身份合并重复命中**

同一记忆版本、同一获准内容和范围被重复发现，只保留一份内容，同时保留所有真实来源证据。不同版本先按 B 的当前版本事实排除旧项，不把新旧内容混在一起。

例子中，那份历史约定的重复引用在这里合并；两份不同的约定仍各自保留，文字相似本身不构成同一内容的证明。

**第 3 步：融合各来源原有的顺序**

Working 使用 B 提供的当前性/优先级顺序，长期候选使用 Provider 的顺序。Recall 根据这些来源内排名和本次固定策略得到基础顺序，不直接把两种来源的原始分数放在一起比较。

同一来源对同一内容重复命中，也只取最佳排名，不能靠重复次数提高权重。

**第 4 步：应用 B 已确认的语义策略，核对冲突**

根据 B 已确认的衰减、证据和冲突策略调整基础顺序，并保存依据。策略需要的事实缺失时，只能使用 B 明确批准的回退；没有获准回退，就隔离受影响候选并记缺失。

如果两份约定存在必须保留的冲突，Recall 要确认完整成员和提示依据，后面一起保留或一起裁剪。不能静默删掉其中一方，也不能自行宣布“没有冲突”。

**第 5 步：保存稳定排序，交给上下文组装**

在例子中，假设 B 的语义证据齐全且确认没有必须成组的冲突，去重后的 Working 与两份约定就按最终顺序进入第 3.7 节。

排在前面不表示一定能够返回；下一节仍要检查预算和临近返回时的权限、版本与有效期。

**开发对照：字段、错误处理与接口（第一次阅读可以跳过）**

**本节产物。** [RankedRecallCandidates](召回数据定义_V0.1.md#ranked)保存去重后的稳定 entries、final_rank、固定 policy_version 及可追踪排序依据，不增加未经验证的候选。

**先校验、再去重（RULE-01、RULE-02、RULE-03）。** 遵守第 3.4、3.5 节；相关度不能覆盖权限，Working 不要求长期 Projection。按 identity_key 合并同一内容，保留全部来源证据；先按 B 当前版本排除旧项，不混合版本。

**代表候选的唯一选择。** 同一 identity_key 的已验证成员按 `Working 优先 → 本来源有效 rank 升序 → candidate_id 的 Unicode 标量序` 选第一条代表；排序键相同则使用 content_result_ref 标量序。代表的 candidate_id、content_result_ref、正文和实际加载路径作为一组保留，不能拼接不同加载结果的“正文+热命中证据”。其他成员仅并入来源/排名证据；相同内容的向量分数不重复放大，物理归因必须追到实际采用的加载结果。

**融合来源顺序（RULE-04）。** 不直接比较不同来源 raw_score。Working 用 B 的当前性/优先级顺序，长期用 Provider 顺序；校验剔除后各来源从 1 稳定重排。同一来源、同一内容只取最佳 rank。

~~~text
base_score(x) = Σ [source_weight(s) / (rrf_k + rank_s(x))]
~~~

同分依次按 Working 优先、memory_id、memory_version、content_ref、范围排序。权重、rrf_k 与算法版本绑定固定 policy；参数见 P-13/P-14/P-15，本版不设未经校准的相似度阈值。

**应用 B 语义策略（RULE-05）。** 记录既有策略版本与输入/输出证据，规范化为 final_rank；不增加未验证/重复候选，不拆散必需冲突成员；并列或 B 明确无需调整时沿用基础稳定顺序。不规定 B 的语义策略必须以乘法系数表达。语义输入缺失时，仅 AL-B04 批准的回退可用并记 SEMANTIC_POLICY_FALLBACK；否则隔离受影响候选，记 SEMANTIC_POLICY_UNAVAILABLE，不能编造 confidence、衰减或“默认无冲突”。

**识别冲突原子组（RULE-06）。** 冲突完整成员及提示一起保留、一起裁剪。只有 B 能确认完整成员且全部安全加载才可呈现，并记 CONFLICT_PRESENTED；成员缺失/范围未知则整组隔离，记 CONFLICT_UNSAFE。实际预算组在第 3.7 节形成并经最终复核重算；保留冲突呈现和批准的语义回退按第 4 章记录结果降级。

### 3.7 组装上下文

**本节解决“哪些内容能在返回时安全、完整地放进预算”** Recall 把排序结果按实际注入模板试装，在返回前通过 B 批量复核，再只用已加载且可信的内容重算最终上下文。

接着上面的例子：去重后的 Working 和两份项目约定已有稳定顺序，现在要把它们组织为实际供调用方使用的文本。

**第 1 步：把内容组成不可拆分的预算组**

普通候选可以单独成组；必须共同呈现的冲突成员，连同提示和必要证据组成一组。一个冲突组要么完整放入，要么整组不放，不能只留下更短或排名更高的一方。

例子中，B 已确认没有必须成组的冲突，因此可以分别尝试装入这些内容。

**第 2 步：按实际模板试装，并计算整包 token**

按组的顺序依次尝试加入，用本次已固定的模板和 token 计数方式计算实际注入文本。正文、引用、冲突提示和分隔符都占预算，不能只把每条正文的独立 token 数相加。

某组装不下时，跳过整组，继续尝试后面较小的组；不能随意截断正文，也不预先给 Working 和长期来源硬分固定比例。

**第 3 步：通过 B 批量复核当前权限与有效性**

临近返回时，对**全部已经安全加载、经排序后可能用于本次组装的候选**做最终复核，包含试装未进入预算的替补候选。核对当前授权、版本、状态；Working 还核对 TTL 和当前性。范围以稳定 candidate_id 集合冻结，按 B 已确认批量上限拆分，每条记录独立证据；只使用试装前已有内容，不新增候选或下载新版本。第一次资格检查通过不代表最终复核通过。

确认发生变化的项要剔除；必要事实无法确认的项也要隔离并记缺失。如果请求级授权或安全证明失败，则不能发布内容。

**第 4 步：剔除变化项，重新检查冲突组和预算**

只在本轮最终复核通过且证据仍在有效窗口内的集合中重组；没有最终证据的替补不得加入。移除一个冲突成员后，按 B 的完整冲突规则重新判断整组是否可呈现，必要时整组移除。先计算最终合格组数 eligible_count，再从空包按固定顺序渲染并计算整包 token，得到 packed_count；试装计数不作为最终 E/P。V0.1 只做一轮全候选复核，各批允许原 P-08 内的瞬时重试；返回未知或到组装/提交时证据已过期的项隔离并记缺口，不通过无限复核循环耗尽请求。

例如，一条 Working 在最后复核时已过期，就移除它，再用仍可信的历史约定重算；不能为了补足上下文临时读取新版本或重新搜索。需要新内容时，应另建执行。

**第 5 步：形成待提交的上下文包及预算结论**

在例子中，假设三份内容都通过最终复核且能够装入预算，就形成包含当前任务记录、历史约定及其引用的上下文包，进入第 3.8 节提交。

正常裁剪后仍有安全内容，不自动表示降级；但有合格内容却没有任何完整组能装下，是预算失败。只有来源与事实足以确认没有合格内容，才能判为正常空，不能仅凭包里零条内容下结论。

**开发对照：字段、错误处理与接口（第一次阅读可以跳过）**

**本节产物。** [RecallBudgetGroup](召回数据定义_V0.1.md#budget-group)绑定不可拆分成员、渲染文本与排序依据；[ContextPack / ContextItem](召回数据定义_V0.1.md#context-pack)绑定最终条目、原子组、实际注入文本和复核证据。本节形成待提交结果，可靠提交确认在第 3.8 节完成。

**按实际模板装配（RULE-07、RULE-08）。** 形成 RecallBudgetGroup，按 order_key 尝试加入；同一 tokenizer 每次重算整体 token，正文、引用、冲突提示、分隔符全部计入，诊断元数据不计入。超预算跳过整组，继续尝试后面较小组；不做无范围证明的逐字硬截断，不给来源硬分 token 比例。P-03 限制最终 token，P-19/P-20/P-21 限制正文读取，二者不能互相替代；模板与计数对接仍待 AL-P403 确认。

**最后复核并重算（RULE-09、RULE-10）。** 复核范围包括全部已加载可组装候选和替补；逐条证据、通过/排除/未知及有效截止统一保存到 FinalValidationBatch。每个最终 ContextItem 引用其中的通过证据。先形成最终可信集合、重算完整冲突组及 E，再做最终预算装配得 P。确认版本变化用 MEMORY_VERSION_CHANGED，事实未知按缺失处理；请求级安全失败按第 4 章阻断。至少一组安全进入时，正常裁剪不自动降级，单独记 BUDGET_TRUNCATED。合格组全部装不下则 FAILED_UNAVAILABLE / BUDGET_UNSATISFIABLE；不能写成 COMPLETE_EMPTY，也不隐式重跑搜索。需要新内容时另建执行；来源缺失且无可信内容等情况统一按第 4 章判定。

**复核时点与边界。** 发出前复核的是“最后复核时点的授权与 Memory 快照”，不是跨服务线性一致事务。变化项剔除后只重组已验证内容，不偷换新正文。若要求删除瞬间停止在途字节，需另行确认 AL-B03 及实际接收端的撤销保证。复核与收尾始终受原 deadline 和 P-10 约束，时间不足不能跳过安全检查。

**包内容约束。** used_tokens 是 rendered_context 的最终精确计数，必须不超 token_budget；不能用条目计数之和替代。失败和正常空都不注入占位正文：items=[]、groups=[]、rendered_context=""、used_tokens=0，原 token_budget 仍保留；两者由终态及原因区分。

### 3.8 提交并返回

**本节解决“怎样确认结果已经可靠保存，再交给调用方”** Recall 将最终结果、执行终态、最小 Trace 和已产生事件的待投递记录一致提交，确认成功后才返回。

接着上面的例子：上下文包已组装并复核完成，两类来源都有完成证据，当前没有未解决缺失；接下来还要可靠保存，才能返回“完整可用”的结果。

**第 1 步：根据全部证据确定拟议结果**

综合来源完整性、安全校验、仍未解决的缺失以及实际装入的内容，确定拟议终态：完整可用、正常空、降级可用或失败不可用。详细判断顺序统一见第 4 章。

例子中，两路完整、内容可信且预算允许，拟议结果为完整可用。即使某次缓存读取失败，只要正式回退成功且信息完整，也不会单凭这次缓存故障降级。

**第 2 步：整理最小执行证据和已经发生的事件**

保存能解释本次选路、候选处理、正文加载、复核与预算结论的最小 Trace；把实际已经发生的本地事件整理为待投递记录。普通日志不复制完整问题、向量、正文或上下文。

此时尚未发生的交付、接收或模型使用，不能提前记成事实。

**第 3 步：可靠一致提交结果、终态、Trace 与 Outbox**

通过已确认的基础持久化能力，把这些相互关联的记录放在同一可靠提交边界中。Outbox 用来保证本地已保存的事件可以继续补发；远端事件消费者尚未确认收到，不等于本地提交失败。

结果不能只写出一半就对外宣布完成。只有确认该提交成功，最终结果和终态才允许发布。

**第 4 步：提交结果未知时先查询确认，再恢复**

例如，保存请求超时，可能是没有写入，也可能是已经写入但回复丢失。Recall 先查提交或结果记录，确认已有事实，再安全恢复收尾，不能把超时直接当作回滚并盲目重复执行。

只要还不能确认可靠提交，就保持未终态，对外只报暂不可用，不发布 Context 或业务终态。业务 deadline 不延期；提交查证与安全收尾走 3.8.1 的独立恢复控制，不改写已冻结的结果。

**第 5 步：返回已确认结果，按真实交付情况继续记账**

例子中，可靠提交确认后，Recall 才把包含当前任务记录和历史约定的上下文包及最终结果返回给调用方。后续实际交给传输层、调用方收到、模型调用使用，分别按对应证据记录。

实际交给传输层前还要检查本地时间未超过本次交付期限和所用证据有效截止；此处不再远程复核。若提交已成功但等待回包导致交付时已过期，保留原不可变终态，本次不发正文并返回 REPLAY_REVALIDATION_REQUIRED；后续新接入按重放规则处理，不把保存成功直接记成 ContextEmitted。

同键重试时仍先检查当前权限和结果有效性；允许重放就返回原不可变结果。版本或有效期已变化，则要求新键重试，不修改旧结果伪装成本次重新检索。

**开发对照：字段、错误处理与接口（第一次阅读可以跳过）**

**本节产物。** [RecallTrace](召回数据定义_V0.1.md#recall-trace)、最终 ContextPack、RecallExecution 终态，以及已经产生的本地事件与 Outbox；它们的可靠提交边界由 AL-RF02 确认。Recall 不指定底层数据库产品，也不替 RF 定义共享事件 Schema。

**阶段保存与最终提交。** 各阶段输出先可靠保存为[RecallCheckpoint](召回数据定义_V0.1.md#checkpoint)，再用 CAS（版本比较更新）推进；失租 Worker 的迟到回调不得覆盖新状态。底层事务、租约与存储机制由 RF 确认 AL-RF02。最终提交必须包含结果、终态、最小 Trace 与已产生事件的 Outbox，确认成功后才返回。写超时先查 commit/result，不等于已回滚。

**提交未知与终态发布。** 未确认可靠提交时记 FINALIZATION_NOT_DURABLE，保持 RUNNING_TRACE_FINALIZATION 或已有未终态检查点；传输层只报暂不可用，不发布 Context 或终态。先计算拟议终态，再提交；durable_finalization 是确认提交后的事实，不是在事务前预知成功。

**事件投递。** 本地可靠 Outbox 已提交、远端尚未 Ack 时可记 ACCESS_OUTBOX_PENDING，不单独降低 Context 状态。后台按同 event_id 可靠补发；ContextEmitted 只能在真实交给传输层后记录，不能预先包含在尚未发生的交付事实中。网关 Ack 不证明实际调用方收到或模型使用；具体观察和消费边界见第 7 章及 AL-RF03、AL-P402。

**已终态重放。** 新到达的同键调用有独立的接入 deadline 和只读复核额度，受 P-02/P-08 和实例准入约束；它不重置原 RecallExecution 的业务 deadline、调用账本或推理额度。先复核当前调用者授权及 B 的版本/有效性，通过才返回原不可变快照并保留原 validated_at；本次重放证据附在交付观察中。权限撤销则拒绝；版本/TTL 变化或内容已清除则 REPLAY_REVALIDATION_REQUIRED，要求新键重试，不改旧终态。复核预算不足不发正文。P-16=0 不提供后续正文重放。

**重启与内容保护。** 重启先恢复调用账本、最终提交身份及租约，再推进仍有效的检查点；不倒退状态、不延长原业务 deadline。调用方断开不延长在线工作，超期仅允许下面的查证与失败收尾。失效候选剔除，重新发现新版本必须新建执行。Query、向量、原文和完整 Context 只用受控加密存储/引用，不进普通日志；删除后可清除内容并保留合法脱敏审计。

#### 3.8.1 提前失败与截止后的可靠收尾

**来源记录闭合。** 每个进入最终归并的执行必须有 working、long_term 两份 SourceReadResult。正常发现阶段产生的记录直接引用；如果在请求复核或 Query 阶段失败而未进入发现，由最终收尾协调者生成缺少的记录，并标记 producer_stage=RUNNING_TRACE_FINALIZATION。未请求来源记 not_requested；必需但未调用来源记 unavailable、read_attempted=false，保留拟读取边界和阻断原因（如 QUERY_EMBEDDING_FAILED、DEADLINE_EXCEEDED），没有完成证据。可能已发出但未获得可靠结果的来源记 read_attempted=true。不得伪造发现检查点、搜索空结果或外部 observed_at；未执行阶段在 StageTrace 中记 skipped。已有 complete/partial 发现事实不因后续正文或提交故障改写，后续缺口另记。

**提交身份与防旧写。** 首次受理时固定 RecallFinalization 的 commit_id、P-22 截止和 P-23 总额度。准备稿、拟议终态及已发生事件的引用可靠保存后，提交必须同时比较执行未终态、当前 lease_token/state_version、finalization.generation 和准备稿摘要；同一 recall_id 只能有一份最终结果。存储侧提交可用/正常空结果时，还必须验证业务 deadline 及所需最终证据有效截止未过；不能只在客户端发请求前检查。提交成功以唯一结果和提交证明为准，超时仍未知。当前可用的 RF 能力须按 AL-RF02 证明能实现这些原子条件，能力缺失时不启用真实交付。

| 恢复时观察到的事实 | A 的确定动作 | 允许的输出 |
|---|---|---|
| 已有同一 commit_id / recall_id 的可靠最终结果 | 采用原结果及证明，不重跑阶段、不重复产生 RecallCompleted；过期后不主动补发正文 | 后续同键调用按重放规则检查；P-16=0/已清除则拒绝正文重放 |
| 未终态，业务 deadline 和最终证据仍有效 | 核验准备稿及原状态版本；在剩余额度内按同一提交身份尝试原子提交 | 只有确认成功才返回；不换提交键掩盖未知 |
| 原准备稿的最终证据已过期，业务 deadline 尚未到 | 不补跑已结束的复核阶段；原子返回既有最终结果，或隔离原准备稿后提交无正文失败结果 | 无既有结果时为 FAILED_UNAVAILABLE / NO_TRUSTWORTHY_CONTEXT；隔离未知则不发布 |
| 业务 deadline 已过，尚未证明有最终结果 | 调用存储侧“隔离旧提交并失败收尾”：原子检查唯一最终结果；若已有则返回原结果，否则递增 generation、使旧提交失权，并一致保存不含正文的失败包、最小 Trace、两来源记录和已发生事件的 Outbox | 确认成功后 FAILED_UNAVAILABLE；未能完成隔离仍不发布终态 |
| 查询超时、普通查无记录或无法原子隔离旧提交 | 保留 commit_unknown，按 P-23/P-24 查证；普通 not_found 不能证明迟到提交不会生效 | 暂不可用，无 Context、无业务终态 |
| P-22 或 P-23 耗尽 | 置协调标记 attention_required，保留最后证据和最小幂等标记，停止自动调用；告警交 RF/值守处理 | 仍未终态，不伪造失败或成功，不删除未知提交记录 |

首次最终提交及每次后续调用前，都在 RecallFinalization 中可靠占用 P-23 次数和调用意图；原期限/证据有效时允许同稿重交，截止后仅查证或隔离失败收尾。不发起新的推理、搜索、正文读或 B 复核，不计入在线读账本。退避、单次时限见 P-24，实例调度不能占用在线保留容量。未知最终提交期间禁止启动第二条业务执行；人工恢复也只能查证原身份或安全隔离，不能修改原成功结果。

超期失败收尾只使用已保存的脱敏事实，清除成功准备稿的正文候选，不把旧最终复核当作现在仍有效。fatal_reason 优先保留已确认的安全/不变量失败，否则为 DEADLINE_EXCEEDED；未获得可交付最终复核时 E=P=0、G=true，来源发现覆盖仍保持真实值。这使其不能被归为 COMPLETE_EMPTY。完整失败原因优先序见 4.1。

原子隔离确认尚无最终结果后，丢弃旧准备稿中未提交的 ContextSelected 草稿；它们不能引用失败空包中不存在的 item。已提交的发现/校验/加载事实保留，新的 RecallCompleted 只随最终失败包提交。若隔离操作发现旧成功结果已经提交，则沿用其 Pack 和事件，不删除已成立的事实。

## 4. 结果、故障与恢复（A-02）

### 4.1 只返回四种业务终态

| execution_state | result_class | recall_availability | 条件 |
|---|---|---|---|
| COMPLETE_AVAILABLE | complete | available | 有安全内容，必需来源完整，无未解决缺失 |
| COMPLETE_EMPTY | complete | empty | 来源全部确认，且权威事实/正常规则确认无合格内容 |
| DEGRADED_AVAILABLE | degraded | available | 有安全内容，但来源、内容、语义或必要解释仍有缺失 |
| FAILED_UNAVAILABLE | failed | unavailable | 安全失败，或无法组成可信上下文 |

判定只使用以下输入，不能根据“有没有返回条目”猜终态：

| 符号 | 字段 | 含义 |
|---|---|---|
| U | safety_blocked | 请求级授权或结果安全证明失败 |
| G | unresolved_gap | 必需来源/内容/语义/必要解释仍有未解决缺失；成功回退可消除 |
| D | required_sources_confirmed | 本模式所有必需来源有界完成；不含可选缓存 |
| E | eligible_count | 最终复核后、预算前的合格内容组数 |
| P | packed_count | 实际进入 Pack 的安全组数，必须 P≤E |
| B | budget_blocked | E>0，但全部合格组都装不下 |
| T | durable_finalization | 结果、终态、最小 Trace 和已产生事件的 Outbox 已可靠一致提交 |

按顺序判断：

1. T=false：不发布 Context 或终态；保持 RUNNING_TRACE_FINALIZATION 或已有未终态检查点，传输层只报暂不可用，恢复时继续确认提交。
2. 计数非整数/负数、P>E，或 B=true 但 E=0/P>0：清空待返回内容，INVARIANT_VIOLATION，失败并告警。
3. U=true：清空内容，FAILED_UNAVAILABLE。
4. P>0：G=true 或 D=false 时 DEGRADED_AVAILABLE，否则 COMPLETE_AVAILABLE。
5. P=0、E=0、D=true、G=false：COMPLETE_EMPTY。
6. 其余均 FAILED_UNAVAILABLE：全部组装不下为 BUDGET_UNSATISFIABLE；缺失导致无可信内容为 NO_TRUSTWORTHY_CONTEXT；其他装配失败为 ASSEMBLY_FAILED。

实现时先计算拟议终态，再提交；T 是确认提交后的事实，不是在事务前预知成功。

**多故障的确定优先序。** 先应用上述 U/G/D/E/P/B/T 决策；同一失败执行有多个原因时，fatal_reason 依次选择 INVARIANT_VIOLATION、SCOPE_DENIED、TRACE_SAFETY_UNPROVEN、请求级 AUTHORITY_UNAVAILABLE、REQUEST_INVALID、DEADLINE_EXCEEDED、BUDGET_UNSATISFIABLE、NO_TRUSTWORTHY_CONTEXT、ASSEMBLY_FAILED 中第一个适用项，其余事实保留在 reason_codes。FINALIZATION_NOT_DURABLE 表示尚未提交，不参加已提交业务失败原因的覆盖。候选级授权未知只产生缺口，不提升成请求级授权失败。

缺口按 `(reason, affected_ref)` 去重，按原因码目录顺序及 affected_ref 的 Unicode 标量序稳定输出；历史诊断单独保留。只有同一目标、版本、范围的可信成功回退/完整重读能消除对应缺口，不能因别的候选成功或事后权威排除而清除未解决故障；PREWARM_FALLBACK 留作诊断不强制 G=true。最终 E/P/来源覆盖/缺口和摘要一并从采用的证据重算，未提交准备稿的旧摘要不能沿用。

正常规则排除不等于故障；故障零条不等于正常空。批准的语义回退、保留冲突呈现、非安全关键解释缺失仍令 G=true。token 裁剪单独记 truncated，TopK 上限不叫 token 裁剪，也不能替代来源完成证据。

| ASSEMBLY_FAILED | 不可用 | 有合格内容但组装不能产生合法结果 |
| INVARIANT_VIOLATION | 安全失败 | 状态/计数/结果互斥条件被破坏，拒绝发布 |

受理前协议错误与执行终态分开：400/403/429/503 只是待 AL-P401 确认的 HTTP 映射示例，HTTP 200 不证明 COMPLETE_AVAILABLE。

### 4.3 重试与中断

逐阶段处理见[主链路各节](#3-主链路怎么实现a-01)，各调用边的重试责任如下。

| 调用边 | Retry Owner / 可重试条件 | 禁止事项 |
|---|---|---|
| Query Embedding 推理 | 共享 Embedding 执行协调者；EM-04 与原共享 deadline | Recall 再加一层模型重试、SDK 暗重试、失败后换调用 ID |
| Query 共享调用附着 / VectorSearch | A 当前阶段；同稳定 call_key，P-08/P-09 及原在线预算允许 | 附着当成新推理、换批次/键重获次数、不兼容模型替代 |
| Working / MemoryRead / CanonicalLoad | A 的能力调用协调层；可重复读、同授权边界，每次结果重新验证 | A 与 Adapter 各自满额重试，叠加放大 |
| Prewarm | 内容加载协调层；初版只探测一次，失败转正式内容 | 缓存重试耗尽回退预算 |
| AccessTrace Outbox | 按 RF 契约的 A 侧 dispatcher；后台以同 event_id 重投 | 重投换 ID、无可靠摄取证据就 Ack |

在线排队、推理等待、远程读取、复核与可用结果提交共用原业务 deadline，始终预留 P-10；预算耗尽不跳过安全复核，也不再发起搜索。唯一例外是 3.8.1 的提交查证及不含正文的失败收尾，使用独立恢复额度；终态重放的新接入只读复核也不重置原执行。断开/重启不能回退终态；“执行成功”不能推断 ContextEmitted。Projection 写/删与 TierAction 的重试、取消、对账均不由 Recall Runtime 接管。

## 5. 我们需要提供的功能

本章按 Recall 负责人（A）的建设任务整理功能。5.1～5.3 由 Recall Runtime 提供：召回结果、真实访问记录和预热使用核验；5.4 是 Embedding 共享模块，向 Remember 提供正文向量化，也供 Recall 自用；5.5 是向量投影写入、查询与删除机制。各节说明“做什么、给谁、输入、输出”；实际契约沿用原工作包，跨模块待确认事项统一记录在[第 8 章](#8-哪些事项必须与外部确认)。

### 5.1 根据查询返回可信上下文

| 项目 | 说明 |
|---|---|
| 功能是什么 | 接收查询，在授权范围内发现、校验和读取记忆，完成去重、排序与预算控制，返回可供上游使用的上下文 |
| 提供给谁 | 上游调用方 / Agent Runtime；请求和响应可经 P4 网关转交 |
| 需要的输入 | Query、调用身份与可验证的授权范围、当前 session/task（如有）、筛选约束、预算/deadline 和幂等键，并对齐 tokenizer/模板约定；请求不传检索模式 |
| 得到的输出 | ContextPack（按终态携带可信条目或空内容）、四类业务终态及允许对外展示的原因/裁剪说明；受理前拒绝返回请求错误，不虚构执行记录 |

例如，上游问“这个项目之前定过哪些约定？”，Recall 自行判断应查 Working、长期记忆或两者，返回已验证的约定内容，并明确结果是完整可用、正常空、降级可用还是失败不可用。

同键重试沿用原执行绑定；重放前仍检查当前权限和内容有效性。结果、终态及必要证据可靠提交后才返回，提交未知时先查结果。P4 负责转交；实际调用方负责后续注入与模型调用。

实现见[第 3 章](#3-主链路怎么实现a-01)，结果与恢复见[第 4 章](#4-结果故障与恢复a-02)。对接沿用 IF-01、AL-P401、AL-P403、AL-RF01；本地 RecallRequest、RecallTrace 等对象不直接变成新的公开接口，解释信息按获准范围提供。

### 5.2 提供真实访问记录

| 项目 | 说明 |
|---|---|
| 功能是什么 | 把一次 Recall 中实际发生的候选命中、资格校验、正文加载、上下文选择、发出和请求完成记录下来，可靠交付访问事实 |
| 提供给谁 | 按已有共享链路交给 RF 摄取，由 Operate（C）消费；Remember（B）的新增消费路径仍待 AL-B07 确认 |
| 需要的输入 | Recall 各阶段的真实观察，以及能够关联请求、Memory/表示版本、上下文条目和交付行为的证据 |
| 得到的输出 | 按 RF 已确认 AccessTrace 契约映射的访问事实，保留稳定身份和可追溯引用；投递失败可通过本地 Outbox 补发 |

例如，同一条约定可能先被检索命中、再被加载，最终因预算没有进入发出的上下文。Recall 要交付这些不同阶段的事实，不能把“已加载”写成“已使用”。实际调用方接收和模型请求使用，只有取得对应回执才能进一步确认。

本地记录与投递机制见[第 7 章](#7-访问记录怎么产生怎么投递a-03)，对接见[Operate 对接需求 RC-05](召回与调度优化接口对接需求_V0.1.md#1-双向接口与信息交接)及[Remember 对接需求 RB-07](召回与记忆形成接口对接需求_V0.1.md#1-双向接口与信息交接)。关联 IF-10、AL-RF02、AL-RF03、AL-C03；RF 接收确认不等于 C 已消费，热度和策略统计由 C 决定。

### 5.3 向 Operate 提供预热使用证据（A-04）

| 项目 | 说明 |
|---|---|
| 功能是什么 | 将成功预热动作与之后的真实访问关联，核验目标副本是否被加载、是否进入已发出的上下文，并说明证据缺口 |
| 提供给谁 | Operate（C），用于后续策略效果评估 |
| 需要的输入 | C/Provider 的动作与副本证据、Recall 的访问记录、RF/C 的观察期与记录完整性证据；模型使用结论另需实际调用方证据 |
| 得到的输出 | 可追溯的 PlacementVerificationRecord 及事实说明，包括命中结论、无法核验原因、关联证据和评估版本；具体交付方式按 RC-06 确认 |

本节规定 Recall 怎样把“某次预热动作”和“之后的真实访问”关联起来，向 Operate 提供可追溯的核验结论。交付内容包括：目标热副本是否被读取、是否进入已发出的上下文，以及哪些事实仍无法确认。Operate 使用这些结果评估预热策略、调整后续调度。

处理顺序：**明确分工 → 取得两侧证据 → 关联同一次预热与实际访问 → 保存核验结论并交付。**

#### 5.3.1 明确 Recall 与 Operate 的分工

这项工作的依据是[9 月 5 日补充文档](../../2026.9.5文档更新/AetherStore_P3_典型落地问题抽象与节点分工_V0.2(1).md)中的 A-04：Recall 负责定义 Promote / Prefetch 后真实 Recall 的验证事实，包括动作、后续召回、目标表示命中和上下文使用之间的关联。

| 工作 | 责任归属 | 本节写到什么程度 |
|---|---|---|
| 决定预热什么、何时预热、何时释放 | Operate | 消费已经发生的动作及其有效性证据 |
| 记录实际读取的副本、内容版本和上下文交付情况 | Recall | 复用第 7 章产生的真实访问记录 |
| 核验这次读取是否对应某次预热产生的副本 | Recall，按 A-04 | 提供有证据的命中结论或无法确认的原因 |
| 汇总策略命中率、评估成本与延迟收益、调整调度策略 | Operate | 明确交付口径和消费边界，策略效果评估由 Operate 负责 |

第 3.5 节负责加载正文，第 7 章负责记录访问事实，本节使用这些事实完成关联核验。核验作为旁路进行，在线 Recall 无须等待它完成才返回结果；核验记录不会修改 C 的 TierAction、Plan 或预热生命周期。

**贯穿例子。** 假设 Operate 在 10:00 成功预热《项目接口约定》的 V3 版本，产生热副本 hot-copy-17，动作标识为 prefetch-17。C/Provider 的证据说明该副本在 10:00 至 10:30 有效。10:05，Recall 请求 recall-42 查询项目约定。本节要把这次请求的真实使用情况与 prefetch-17 对应起来。

#### 5.3.2 取得预热动作证据和真实访问记录

开始核验前，需要取得动作侧和访问侧的证据；判断“没有使用过”时，还要知道观察期是否结束、相关记录是否齐全。

| 输入 | 提供方 | Recall 需要确认的事实 |
|---|---|---|
| 预热动作与实际副本证据 | C / Provider | 动作是否成功，目标 Memory、版本、表示和实际副本是什么，生效及更新、到期、释放时间是什么 |
| 正文加载与上下文交付记录 | Recall 第 7 章 | 实际读取了哪个副本、是否通过正文校验，内容是否进入已发出的 Context；关联的请求、内容条目和交付证据是什么 |
| 观察期与记录完整性证据 | RF / C | 相关访问记录是否完整，有无采集空洞，迟到记录的截止条件是否满足，时间是否可信 |
| 实际模型请求使用证据 | 实际调用方 / Agent Runtime | 同一 pack/item 是否确实用于模型请求；仅在取得相应证据时使用 |

Memory 身份、版本和内容资格仍以 B 的事实为准，通过既有资格、加载和来源证据关联。以上是对外部事实的消费需求，不在本包新增 C 的证据对象、API 或字段表。证据读取方式及范围见 AL-C02、AL-P204；完整性证据和交付方式见 AL-C03、AL-RF03。

**例子走到这里。** Recall 需要拿到“prefetch-17 成功准备了 V3 的 hot-copy-17”的证据，以及 recall-42 实际读取和交付内容的记录。仅有“计划把 V3 放到热层”，或者知道两件事发生时间接近，都不足以证明这次请求使用了该副本。

缺少必要证据时，保留缺口并给出无法核验的结论；正文已经独立通过安全校验的在线召回仍可继续。模型使用回执缺失时，模型使用事实保留未知，不影响已证实的读取或上下文交付事实。

#### 5.3.3 把真实访问关联到同一次预热

**第 1 步：确认动作属于本次核验范围**

本版核验已成功的 Prefetch / Promote 动作所准备的正文或 B 已认可 Artifact 副本。明确未成功或不属于该范围的动作，标记为不适用；动作是否成功仍未知时，标记为无法核验。Vector 搜索命中不作为正文热副本的命中证据，向量表示的核验范围另见 AL-C02、AL-P204。

**第 2 步：确认读取的确实是该动作对应的副本**

核对租户、Memory 及版本、内容表示、内容引用/版本、实际 Provider，以及能够唯一关联动作与副本的证据。名称相同或 Memory ID 相同，还不能证明是同一份预热内容；多个预热动作也不能重复认领同一次物理读取。

例子中，recall-42 读到的必须能对应 prefetch-17 产生的 V3 副本 hot-copy-17。若只知道读到了 V3，却无法证明实际来自哪个副本，就不能确认预热命中。

**第 3 步：确认访问发生在副本有效期间**

有效期间由 C/Provider 的生效与失效证据限定。更新、释放或新一代副本出现时，按权威事实截断原副本的有效期间。Recall 使用这些证据确定核验窗口，不自行制定 C 的 TTL 或 Prefetch Window。

例子中的 10:05 处于已证明的 10:00 至 10:30 范围内；如果副本在 10:03 已被释放，就需要按释放证据重新核对，不能继续沿用原先预计的结束时间。

**第 4 步：区分实际读取、上下文交付和模型使用**

实际读中目标热副本，才能确认加载命中；还要沿内容条目的来源证据追到 ContextEmitted，才能确认它进入了已发出的上下文。SearchHit、ContextSelected 或成功的 ContextPack 都不能单独证明已经发出。

例子中，若 recall-42 从 hot-copy-17 读取成功，并将对应内容放进已经发出的上下文，就有了肯定的上下文命中证据。若热副本未命中、改读正式正文，即使召回成功，也不能将这次读取记为预热命中。实际模型使用还需要调用方提供同一 pack/item 的使用证据。

**第 5 步：正向证据充分即可确认，否定结论等记录齐全后再下**

已经证实“读中该副本并用于发出的上下文”时，可以先确认命中。若目前只看到读取，或还没有找到使用记录，则不能立刻判定整个有效期内“仅被读取”或“没有命中”。

必须等有效观察期结束，并取得相关访问记录完整、迟到截止条件已满足的证据，才能下这些否定结论。例如，10:05 的请求因预算裁掉了内容，后面仍可能有其他请求使用它；在 10:30 前不能据此判断该次预热最终只被加载。

**开发对照：关联与时点规则。** producing_action_id 或原契约认可的等效精确证据必须能指向实际副本。若执行前 generation=g、成功后为 g'，使用成功后的 g' 关联，不要求仍等于旧 g。核验窗口采用 [window_start, window_end)；窗口非法、缺失、效力未知，或时间偏差超过 P-18 时，结论为不可验证，不修改原始时间凑窗口。记录完整性、水位和迟到截止由 RF/C 提供，不能只凭本地时钟认定记录已到齐。

#### 5.3.4 保存核验结论并交付 Operate

**先形成有明确含义的结论。** 每条结论针对已识别的动作、验证范围和证据版本；本地标记沿用现有五种结果。

| 交付给 Operate 的结论 | 成立条件 | 本地 outcome |
|---|---|---|
| 已进入发出的上下文 | 动作、副本和版本能精确关联，加载事实能追到 ContextEmitted | verified_context_hit |
| 仅被加载，未进入发出的上下文 | 有精确加载证据；有效观察期已结束、记录齐全，确认没有对应的上下文发出 | verified_load_only |
| 有效期内未命中 | 完整闭窗、记录齐全且迟到截止已过，确认没有目标副本的加载或上下文命中 | expired_without_verified_hit |
| 无法核验 | 动作、副本、版本、时间或记录完整性证据不足；也包括尚未闭窗且没有充分正向上下文命中证据 | unverifiable |
| 不属于本版核验范围 | 已确认动作尚未成功，或对象不属于本版正文/Artifact 范围 | not_eligible |

有加载证据但窗口未结束时，可以保留 load_hit=true，尚不能确认的 context_hit 保留 null，整体结论为 unverifiable / window_open。未知不写成 false。只有完整闭窗并确认记录齐全，才允许给出“仅加载”或“未命中”的最终结论；这些核验结论不改变 C 的动作状态。

**例子的最终交付。** 对 prefetch-17，Recall 保存“V3 的 hot-copy-17 被 recall-42 读取，并进入已发出的上下文”，连同动作证据、读取事件和内容条目引用，形成 verified_context_hit。若没有实际调用方的模型请求证据，model_use_hit 保留未知；不能把上下文已经发出进一步推断成模型已经使用。

本地结果字段只查[PlacementVerificationRecord](召回数据定义_V0.1.md#placement-record)，保存动作、关联请求/条目、核验窗口、命中事实、无法核验原因和证据版本。hit_after_prefetch 仅对合格 Prefetch 使用 context_hit 口径；Promote 或不适用时为 null。

保存位置与键见[数据定义](召回数据定义_V0.1.md#storage)。同证据摘要、规则版本和窗口复用结果；新/迟到证据生成新的 evaluation_version，保留旧结论。外部证据只存受控引用，本地实验记录按 P-16 保留；证据失效后不能宣称完整可复现，更长窗口所需保留由 AL-RF02、AL-B06 确认。

**再按已确认的通道交付。** 原始访问事实沿第 7 章的 AccessTrace 路径可靠记录，由 RF 摄取、C 消费；核验记录及必要的事实说明按[与 Operate 的对接需求](召回与调度优化接口对接需求_V0.1.md)中 RC-06 交付。读取、订阅或报告的具体方式仍待 AL-C03、AL-RF03 确认，不将本地记录直接当作新的共享事件 Schema，也不写入 C 的 TierAction 或 Plan。

**交付后由 Operate 做策略效果评估。** Recall 交付可追溯的使用事实和证据缺口；Operate 汇总这些结果，评价预热策略的命中率、成本和延迟收益，并决定后续策略。批量报表的交付机制仍需对齐，不能据本节默认新增 Recall 统计服务。

例如，交付记录涉及 10 次本版范围内成功的 Prefetch，其中 8 次已经完整闭窗；这 8 次里，5 次至少命中过目标热副本，3 次至少一次进入已发出的上下文。Operate 可据此计算：

| Operate 的统计示例 | 分子（动作数） | 分母（动作数） | 示例结果 |
|---|---|---|---|
| 上下文命中率 | 3 | 8 | 37.5% |
| 加载命中率 | 5 | 8 | 62.5% |
| 可核验覆盖率 | 8 | 10 | 80% |

其余 2 次保留未知，不当作未命中，也不从覆盖情况中隐去。同一动作在动作口径中只计一次；分母为零时使用 N/A。充分正向命中可以提前展示，正式批次比率仍只使用完整闭窗且证据齐全的样本。若按请求统计上下文或模型使用，则另按对应请求、交付和回执证据去重，不与动作分母混用。

要声明“预热降低了延迟”或“命中率提升 10%”，由 Operate 在同数据、策略和负载的基线与实验分组下评估，报告成本、尾延迟、未命中、迁移量和置信度；相对提升或百分点口径由 AL-PM01 确认。Recall 的命中核验提供事实依据，不单凭关联作性能改善结论。

本节验收应覆盖：动作与副本唯一关联、版本/generation 不符、观察期未结束或记录不全、迟到证据修订、缓存失败后回退正式正文，以及没有实际调用方使用回执。这些场景验证 Recall 的事实核验行为；Operate 的策略效果评估按其工作包验收。

#### 5.3.5 旁路核验的调用与恢复边界

V0.1 核验器按一次显式触发处理调用方已取得并固化的有界证据快照，执行“核验输入 → 计算结论 → 幂等保存 → 返回记录引用”。输入使用第 18 章的目标、窗口、source_evidence_digest 及规则版本；不在在线 Recall 内等待事件到齐，也不隐式启动持续轮询器。无新证据时重复触发复用原记录；闭窗或迟到证据形成新快照，再生成新的 evaluation_version。

受控运行通道负责可靠重投同一快照，A 在保存记录前失败不确认交付；重启按相同输入摘要查询，已保存则返回原版本，未保存则重新执行无副作用核验。新版本用前序版本比较及唯一约束提交，竞争失败者读取已提交版本，不能覆盖历史。缺证据/窗口未闭可保存 unverifiable；输入非法、快照已清除或无法持久化则明确返回核验不可用，不虚构结果。实际触发、快照大小上限和报告通道属于独立清单 AL-C03/RF03，未确认前只启用显式本地核验，不宣称已有自动调度服务。

### 5.4 构建并提供 Embedding 共享模块

**这是一项独立的模块建设任务，负责人同样是 A。** 我们需要实现 SemanticEmbeddingCapability；Remember 和 Recall Runtime 都通过它取得向量。Query/Passage 是同一共享能力的两种用途。

| 项目 | 说明 |
|---|---|
| 功能是什么 | 按模型契约把输入文本或片段转为真实语义向量，提供 Passage/Query 两种用途、模型版本追踪、输入绑定、校验和幂等复用 |
| 提供给谁 | Remember（B）以 Passage 用途生成待构建投影的正文向量；Recall Runtime（A）以 Query 用途生成检索问题向量 |
| 需要的输入 | 调用方提供待向量化文本/片段、usage、model_contract、source_hash 和 timeout；具体结构与编码由 A 的共享契约维护，B 确认其消费映射 |
| 得到的输出 | 与本次输入和用途绑定的合法真实向量、实际 model_version、dimension 及原契约要求的追踪信息；失败、超时或不兼容按契约明确返回 |

**我们需要建设的内容。**

| 建设项 | A 需要完成什么 |
|---|---|
| 共享契约与两种用途 | 定义并实现 SemanticEmbeddingCapability，区分 Passage 建投影与 Query 检索；B 无须感知 ONNX、SIMD 或具体推理后端 |
| 模型推理与向量校验 | 接入真实模型和推理实现，校验向量数值、维度、模型版本和输出格式；模拟向量不能作为真实能力验收结果 |
| 模型版本与空间兼容 | 维护模型契约和版本追踪，使同一检索空间中的 Passage/Query 向量可比较；模型发布与切换遵循受控验证和回退要求 |
| 输入绑定与幂等复用 | 追踪 source_hash；版本、文本、chunk 或 usage 变化时重新计算，符合原契约复用条件时才复用，不混用不同输入的向量 |
| 资源与故障控制 | 实现有界超时、队列和并发控制，区分 Query/Passage 资源使用，防止正文批量处理挤占在线查询；具体限额按既有验收配置确认 |
| 性能与验收证据 | 提供真实吞吐、P95/P99、错误率及隔离/混合负载结果，记录模型、维度、硬件、batch、并发和 warm-up 条件 |

例如，B 决定将《项目接口约定》V3 建成可检索记忆，准备好待向量化片段后，调用我们提供的 Embedding 模块，使用 usage=Passage。之后用户问“这个项目之前定过哪些约定？”，Recall 调用同一模块，使用 usage=Query，在兼容模型空间中取得问题向量，再交给 P2 检索。

Embedding 的交付止于向量及其契约事实；Memory 选择、内容切分的业务规则、Projection Build 编排和 ProjectionState 仍由 B 管理。向量写入机制按第 2.4～2.8 节实现，不能把“已生成向量”当成“投影已 Ready”。Recall 的 working_only 跳过 Query 向量化，不影响 B 在写路径按需使用 Passage 向量化。

依据见[冻结 Work Map](../../总设计/AetherStore_P3_Work_Map_V0.4.1.md)、[A 工作包](../../总设计/PROGRAM_A_RECALL_WORK_PACKAGE.md)和[Engineering WBS](../../总设计/AetherStore_P3_Engineering_WBS_V1.0.md)的 A-EPIC-01-T1～T4。原工作包的性能目标为 Effective Embedding Throughput ≥2000 item/s；口径与验收环境按[生产就绪补充](../../../../PPR/PROGRAM_A_Production_Readiness_Addendum_V1.0.md)和[未决事项](../../../../PPR/PRR_Open_Decisions_V1.0.md)确认，本节不宣称已经完成实现或性能验收。

向 Remember 的交接见[RB-08](召回与记忆形成接口对接需求_V0.1.md#1-双向接口与信息交接)，Query 调用见[3.2](#32-生成-query-向量)。模型空间对齐沿用 AL-B05，资源与调用约束沿用 AL-RF04；共享契约由我们建设，B 的消费确认不改变模块归属。

## 7. 访问记录怎么产生、怎么投递（A-03）

AccessTrace 记录业务访问；OTel Trace 记录调用耗时/重试；Runtime Structured Log 记录执行变化；Audit Log 记录身份与拒绝/重放依据。它们不能互相冒充，也不能靠日志行数计算使用次数。共享 AccessTrace 仍由 A/B 生产、RF 摄取、C 消费；B 的新增消费需求另见 AL-B07。

### 7.1 观察时点：命中、加载、选中、发出分开记录

| observation_type | 产生时点 | 此时能证明什么 |
|---|---|---|
| SearchHit | 来源返回有稳定引用的候选 | retrieved；尚未证明 Memory 有效 |
| CandidateAccepted | B 首次事实/权限/版本校验通过 | validated 在该 observed_at 时点成立，不表示正文已加载 |
| CanonicalLoaded | 正式内容或其可信 Prewarm 副本加载成功 | loaded；未证明入选 Context |
| WorkingLoaded | B 内联提供的 Working 正文完成校验 | loaded；不要求长期 Projection |
| ContextSelected | 最终复核和预算后确定进入待提交 Pack | selected；未证明发出 |
| ContextEmitted | 冻结结果实际成功交给传输层之后 | used_in_context；不保证 P4 已收到 |
| RecallCompleted | 终态可靠提交时 | 请求终态与来源汇总；零候选不虚构 memory_id |

这七类是 Recall 本地 observation_type，不是给 RF 新增共享枚举。共享报文只按 RF 已确认契约映射；B 后续删除不会抹掉历史 CandidateAccepted，最终排除记录说明未输出即可。

实际调用方接收/模型调用证据到达后才形成新的 ContextUseAssessment；agent_received、used_in_model_request 未知为 null，不是 false。模型调用使用了上下文，也不证明回答语义采纳。后到证据不覆盖原事件。

### 7.3 可靠落地与投递

[OutboxEntry 字段](召回数据定义_V0.1.md#outbox)单独维护本地事件摘要和外部编码报文摘要。

- 阶段已确认事实随检查点入 Outbox；最终 ContextSelected、RecallCompleted 随 Pack/终态一致提交。远端 Ack 不阻塞已经可靠提交的在线结果。
- ContextEmitted 只能在实际交付观察后追加。若交付后、记事件前崩溃，保留发送证据缺口，等待受控传输记录/实际调用方回执补证；不能根据成功终态反推发出。补证复用原 delivery_id；真正再次交付才用新 delivery_id。
- 同 event_id 不同 payload 必须拒绝并审计，不覆盖；同次投递重试保持事实 ID。

共享摄取的使用需求：不定义 RF 合同。RF 决定映射、去重、可靠 Ack、乱序/迟到、覆盖证明与错误语义；未取得其认可的可靠摄取证明，Outbox 不能 Ack。Ack 不等于 C 已消费，更不等于跨网络 exactly-once。

每请求准入预留最多 6×max_candidates_total+8 条事件额度；每执行/候选/业务阶段只记一次事实，重试细节进 OTel。再次真实交付另取发送事件额度。容量不足拒绝新准入，已受理请求用预留额收尾；已受理请求若无法可靠写 Outbox，则 FINALIZATION_NOT_DURABLE，不以“以后补日志”发布结果。

重启恢复未确认 Outbox，后台有限退避重投。未确认事件不因普通终态保留期而删除；敏感删除及本地保留窗口须消费 AL-B06、AL-RF02/03、AL-C03 的已确认规则，不替 RF/C 规定保存期。

### 7.4 计数与测试（查阅用）

先选 observation_type，再按业务唯一键去重；同一条目在多个阶段携带的 true 不能累加。只定义 Recall 的核验指标，不定义 C 的热度或权重。

**8 项 Recall 本地计数口径**

单事件 bytes/latency_ms 的唯一取值表见数据定义 15.4。业务加载字节只统计成功采用片段；重试实际流量和崩溃保守扣费分别来自调用账本，后者不能进入真实流量统计。单调时钟区间因崩溃无法还原时留 null，不从跨主机 wall clock 相减补数。

| 指标 | 去重单位/定义 | 不代表什么 |
|---|---|---|
| search_hit_count | 一次发现中每个 source+representation+候选观察一次 | 不等于有效记忆数量 |
| accepted_memory_count | recall+memory/version 去重的 CandidateAccepted | 不等于最终 Context 条目数 |
| content_load_count / bytes | 最终确认的内容加载事件；按物理表示区分来源 | 不把重试 span 的流量与业务加载量混算 |
| context_selected_count | pack+item 的 ContextSelected | 不证明上游接收 |
| context_emitted_count | pack+item+delivery 的 ContextEmitted | 不证明模型使用 |
| model_context_use_count | 实际调用方回执中 invocation+pack+item 去重 | 不证明回答的语义采纳 |
| trace_delivery_lag | durable 本地记录到 durable IngestAck 的差值 | 不等于 C 消费延迟 |
| source_failure_rate | 必需来源失败数/要求该来源的请求数 | 不把未请求来源或 cache miss 算失败 |

Vector hit 和正文加载可能属于不同表示，不能当成同一 representation 的两次最终使用。

原 EVT 场景保留阶段事实、重复投递、缺失证据、真实重放和 Working 无 Projection 等验收要求。原校验程序在当前工作区缺失；相关记录是历史说明，不作为本次新模块的验证结果。

| [Haystack ConditionalRouter](https://docs.haystack.deepset.ai/docs/conditionalrouter) | 用应用配置的条件表达式路由，也可设置明确兜底，不必调用 LLM | 借鉴确定性规则；本项目只用受控策略，不开放用户自定义可执行表达式 |

结论：没有公开依据证明“三种模式必须由网关选择”，也没有统一规定必须用大模型分类。我们的来源只有两类，本轮尚未取得项目评测证据证明“只查一边不会漏关键记忆”，且在线链路有 deadline/复核要求；因此选范围优先的并集基线。它多一次适用长期分支的成本是真实取舍，不能宣称已达到生产质量或延迟目标。

暂不采用“先查 Working，条数/相似度够了就停止”、关键词硬分类或 LLM 单选：Working 有命中不能证明长期没有重要偏好、事实或冲突；这些方案可能造成无法在结果状态中察觉的漏召回。默认 combined 也不表示两边正文全部注入，仍须经资格/正文校验、去重、排序和预算。

后续若要降低成本，先在离线/影子环境比较本基线与候选路由，不改变线上模式。样本应覆盖纯当前、纯长期、混合、无会话、权限收窄、歧义、注入诱导、故障和重试；按来源及业务类型报告应查来源覆盖率、标注相关记忆召回率、答案质量、误路由率、P95/P99 延迟、Embedding/向量调用量及 token。人工标注与抽样核验用于识别基线自身漏检，不能把基线结果当完整真值。无漏召回预算和真实评测证据前，不引入置信阈值或自适应提前停止；生产放行仍走 AL-PM01，权限边界不能用质量指标交换。
