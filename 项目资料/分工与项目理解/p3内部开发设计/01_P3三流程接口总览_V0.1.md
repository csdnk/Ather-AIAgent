# P3 三流程接口总览 V0.1

日期：2026-09-16。本文是接口开发视图，业务阶段沿用原流程，外部确认以原 AL 台账为准。

## 1. 三条主链与所有权

```text
Remember：事件 → 主事实 → 分类/生命周期
                    ├→ Working 当前可读 ──────────────────┐
                    └→ 正文/Artifact → 批准 Passage        │
                         → A 的 Embedding/向量投影机制     │
                         → B 的 Ready Guard ───────────────┤
                                                          ↓
Recall：Query → 校验/授权/选路/受理 → 执行复核 → 候选 → 资格核验
         → 正文校验 → 排序/预算 → 最终复核 → Context/可靠收尾
                                                          │
Remember 的 MemorySignal + Recall 经 RF 的 AccessTrace ────┤
                                                          ↓
Operate：事实消费 → 按表示计算热度 → 放置计划
         → 对比最新实际层级 → 动作 → Provider 反馈 → 对账
```

上图表达业务关系；受理阶段已完成自动选路，随后才进入执行复核。Working-only 不需要长期投影或 Query 推理。

| 事实/状态 | 唯一业务 Owner | 其他流程如何使用 |
|---|---|---|
| Memory 身份、版本、Type、生命周期、TTL、来源证据 | Remember/B | Recall 通过 B 能力读取、初查和最终复核；不回写 |
| ProjectionState 与领域 Ready 判定 | Remember/B | 消费 A/P2 提供的执行和可查询性证据，B 决定 Ready |
| Recall 执行、候选处理、排序、Context 与最终结果 | Recall/A | 上游获取结果；Operate 消费获准的运行事实 |
| Embedding 执行/结果、向量投影机制操作 | A | B 批准 Passage 和投影目标；A 计算、执行机制并返回证据 |
| 放置计划、调度动作、调度对账 | Operate/C | 消费 B/A 的事实；不更改 Memory 真值和 Recall 排序 |
| 真实字节、索引状态、实际层级和物理执行 | 对应 P2/内容/存储 Provider | A/B/C 依据明确证据判断，不从“已提交”推断完成 |
| 原子持久化、租约/CAS、公共授权与可靠摄取基础设施 | RF/既定基础设施 Owner | 各流程定义业务规则，通过 Port 使用，不各建一套数据库 |

## 2. 必需的双向接口

“方向”表示能力提供方向；通常包含请求与响应，不代表新增回调。

| 对接能力 | 提供方 → 调用/消费方 | 核心交接 | 原编号 | 优先级 |
|---|---|---|---|---|
| 可信身份及 Scope 授权 | RF/授权 Owner → A；B 提供归属事实 | 主体、逐来源权限、session/task 归属、一致性、有效窗口 | AL-RF01 | 受理前必须明确 |
| 当前 Working 读取 | B → A | 有界候选、版本/TTL、正文或合法引用、完整/部分证据 | RB-01；AL-B01/B03 | Working 链路首要接口 |
| 资格查询、最终/重放复核 | B → A | 每个准确候选的权限、版本、状态、有效期和证据 | RB-02；AL-B03/B06 | 输出 Context 前必须明确 |
| 正式内容映射 | B → A | 允许加载的表示、正文版本、范围、编码、期望摘要 | RB-03；AL-B02 | 正文读取前必须明确 |
| 正文实际读取 | Provider → A，经 B 认可的映射/读取边界 | 准确版本的有界字节及元数据 | RP2-02；AL-P203 | 长期链路必需；Working 内联正文可减少调用 |
| 质量、衰减、冲突与长期可读事实 | B → A | 既有策略版本、冲突成员、领域 Ready 与模型兼容依据 | RB-04/05；AL-B04/B05 | 排序/长期核验必需 |
| Passage 向量化 | A → B | 固定输入、用途、模型空间；共享执行与可核验结果 | RB-08；AL-B08/RF05 | 长期写路径首要接口 |
| 向量投影提交与查询 | A → B | 准确目标 upsert/delete、幂等操作、ProviderResult 五态 | RB-09；AL-B08/P205～208 | B 的 Make Recallable 必需 |
| 向量候选搜索 | P2 → A | Query 向量、授权筛选、TopK、稳定引用和完成证据 | RP2-01；AL-P202 | 长期召回必需 |
| Memory 变化通知 | B → C | 来源、Memory/表示/版本、事件身份、消费语义 | B-EPIC-07；C-EPIC-01 | C 并行确定契约 |
| 访问事实可靠摄取与消费 | A → RF → C | 多阶段真实观察、去重/补发、摄取确认和消费确认 | RC-04/05；AL-RF03/C03 | 可靠收尾及 C 输入 |
| 状态、检查点与终结存储 | RF → A | 唯一受理、预算预留、租约/CAS、唯一最终提交、查询未知 | AL-RF02/RF04/RF05 | 全链路基础 |

MemorySignal 与 AccessTrace 不是同一种事件。Recall 不替 B 产生 MemorySignal；B 读取 AccessTrace 的新通道仍关联 AL-B07，不能因 Remember 流程中提到访问证据便直接新增 B 订阅。

## 3. 可后置的配合

- **预热读取及动作归因**：RC-01～03/06，AL-C01～04、AL-P204。先确认合法正文映射和权威读取，再接可选热副本。不把缓存 miss 当成正文不存在。
- **Operate 优化策略**：C 可先用版本化启发式与模拟输入建立动作/对账闭环，不阻塞 A/B 的基础写读开发。其热度权重、防抖和预测策略由 C 决定。
- **Memoryize/复杂巩固**：B 可先交付明确的 Working 与长期事实路径，再按自身计划补压缩、Candidate 证据策略等；A 不自行给不确定内容判 Semantic。

Operate 在线消费和调度完成不作为 Recall 返回 Context 的同步前置条件；Recall 本地可靠记账和终结要求仍需满足。RF 摄取 Ack 也不等于 C 已消费。

## 4. 三流程内部先固定什么

| 流程 | 应由本组固定的阶段交接 | 必须保留的事实边界 |
|---|---|---|
| Recall | 已受理请求 → 复核输出 → Query/跳过输出 → 来源候选 → 合格候选 → 已验证正文 → 排序 → 最终候选集 → 最终提交 | 每次推进有检查点，执行状态版本与租约独立于 Memory 版本 |
| Remember | 受理 → 主事实 → Type/生命周期 → Working 可用或长期正文/Task → Passage 批准 → 投影机制结果 → Ready Guard | 主事实、Task、Artifact、ProjectionState、Signal 不共用一个“成功”状态 |
| Operate | 输入校验 → 热度 → Plan → 最新 Observation 比较 → Action → Feedback → Reconciliation | desired_tier 不冒充 observed_tier；Plan、Action、对账任务是不同对象 |

本目录只细化 Recall 的阶段契约。B/C 可按同样字段模板补齐自身内部接口，不要求把所有内部函数暴露为跨流程 Port。

## 5. 代码依赖与装配

新业务入口为 `recall/`、`remember/`、`operate/`；共享 Embedding 位于 `recall/embedding/`，向量投影机制位于 `recall/vector_projection/`。

- 通过构造函数注入契约。B 调 A 的共享能力；A 调 B 的读取能力是合理的双向业务关系，但不得互相导入对方的服务实现造成模块循环。
- 公共值对象和双方认可的协议放在既定契约层；具体实现由 bootstrap/装配层连接。先复用已有契约位置，不额外复制同名 DTO。
- Recall 不读取 B 的内部 Redis key，不修改 B 的领域表，也不从 Operate 的私有动作日志猜测内容有效性。
- 旧 B1/B2/B3 暂留兼容；新路径不能回调旧实现。不能把旧链路的功能完成度等同于新链路完成度。
- HTTP/RPC、路由、批量协议、超时数值和部署资源在相应 Owner 签收后确定；逻辑 Port 的完成不自动证明网络协议兼容。
