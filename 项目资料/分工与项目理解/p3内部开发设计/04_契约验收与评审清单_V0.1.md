# 契约验收与评审清单 V0.1

日期：2026-09-16。以下为接口验收要求；除第 4 节明确列出的既有证据外，不表示测试已经实现或通过。`CT-*` 是本目录测试索引，不代替原 AL 确认编号。

## 1. 每个关键接口需要的评审材料

提供方和调用方共同确认：

| 项目 | 应提供内容 |
|---|---|
| 身份 | 能力名、Owner、调用方、既有方法名、契约版本；本地 Port 与实际协议的映射 |
| 输入 | 字段/类型、必填/可空、大小限制、Scope/授权、准确版本/范围、deadline |
| 输出 | 成功/空/部分/拒绝/未知样例；逐项结果与来源完整性依据；证据引用的查询方式 |
| 状态与副作用 | 改变哪些对象；原子边界；“受理”“完成”“可使用”分别意味着什么 |
| 重试 | 幂等键及有效期、同键冲突、超时查证、允许重发的证据；谁拥有重试额度 |
| 资源 | 并发、队列、批量、字节和 token 上限；取消是否实际停止执行 |
| 生命周期 | 版本变更、撤权、删除、证据过期、保留/清理和重放行为 |
| 验收 | 双方可执行的测试样例、真实/模拟环境、结果证据和不支持项 |

现有字段约束不足时，先记录差异，不以测试替身宽松接受所有输入替代契约确认。最终签收记录维护在原[AL 台账](../Recall流程/运行时详细设计_V0.1/跨模块待确认事项_V0.1.md)，不在这里复制签字表。

## 2. 输入与响应的评审样例

### 2.1 无 session/task 的长期请求

以下是当前 `RecallInput` 结构的示意样例，不是生产身份或可直接发送的 HTTP body。执行测试时使用固定测试时钟或生成相对于测试时钟的 deadline。

```json
{
  "request_id": "recall-example-1",
  "trace_id": "trace-example-1",
  "query": "这个项目之前确定了哪些接口约定？",
  "scope": {
    "tenant_id": "test-tenant",
    "project_id": "test-project",
    "agent_id": "test-agent",
    "session_id": null,
    "task_id": null
  },
  "principal_ref": "configured-test-principal",
  "authorization_ref": "configured-test-evidence",
  "idempotency_key": "recall-key-1",
  "deadline_at": "2030-01-01T00:00:02Z",
  "token_budget": 512,
  "retrieval_constraints": {
    "memory_types": ["Episodic", "Semantic"],
    "occurred_after": null,
    "occurred_before": null
  }
}
```

测试前提：授权替身配置明确允许该主体的长期读取，返回与请求一致的 Scope；服务端有匹配策略与模型空间。期望 long_term_only，不要求为了合法受理而伪造 session/task。样例中没有检索模式字段，tokenizer/template 由配置解析。

### 2.2 Working 候选接口的语义样例

下表是语义样例，不规定 B 的 wire JSON 字段名。

| B 返回的事实 | A 应如何解释 |
|---|---|
| 0 条，批准范围已完整读取，有完整性证据 | Working 来源确认空；是否 COMPLETE_EMPTY 还要看其他必需来源和最终提交 |
| 2 条，批次只完成部分范围 | 保留可核验候选，同时保留来源缺口 |
| 0 条，超时/范围完成情况未知 | 来源未确认，不能认定为空 |
| 候选有正文，但版本或 TTL 无法核实 | 不采用不可信正文；保留无法核验事实 |
| 当前 session 明确不属于请求主体 | 拒绝相应授权请求，不能移除 session 后重选 long_term_only |

### 2.3 投影机制结果的语义样例

| ProviderResult | B 消费方式 |
|---|---|
| ACCEPTED / PENDING | 保留构建/等待状态，不能因为 A 已返回 operation_id 就置 Ready |
| READY，准确目标证据通过，B 当前版本一致 | 由 B 执行完整 Ready Guard 后决定领域状态 |
| READY，但 Memory 已更新到另一版本 | 历史机制结果，不把当前版本置 Ready |
| UNKNOWN | 查询原 operation，不换 caller_request_ref 或目标键盲写 |
| FAILED | 保留失败事实；同版本重建遵循已确认代际协议，当前不支持的 rebuild 不自动换键 |

## 5. 三层验证安排

1. **单模块规则测试**：确定性授权、存储、候选与推理替身；失败可以精确复现，检查无外部副作用、状态/预算正确。
2. **契约/模拟联调**：A/B/C 使用共同认可的字段和共享模拟状态；验证写入后的记忆确实可由读取侧看到、未知操作可查询。不同服务各自硬编码“成功”不算闭环。
3. **真实 Provider/RF 联调**：真实授权、数据库/进程恢复、P2 向量/正文/层级事实和模型部署；最后才做生产 SLO 与容量测试。

原生 ONNX 的真实推理验证可以提前做，但它只覆盖推理这一段，不自动将整个系统提升为第三层验证完成。
