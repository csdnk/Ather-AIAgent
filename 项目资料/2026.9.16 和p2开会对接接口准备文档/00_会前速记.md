讲解日期：2026-09-16。材料整理及静态核对：2026-09-15。按约 25 分钟设计；对象定义和实际业务接通分开说明。

## 开场可以直接这样说

“这份表定义的是 A 组调用 P2 时，需要发送什么数据、取得什么结果，以及怎样判断结果能使用。它围绕两条链路：在线 Recall 取得可信正文并形成上下文；投影维护把 B 批准的 Passage 向量可靠写入、查询和删除。B 决定记忆事实和领域 Ready，A 负责召回正确性与向量机制，P2 提供物理存储和索引事实。”

## 记住这两条线

```text
在线：Query 向量 → P2 搜索 → B 资格和准确正文映射 → P2 读取 → A 校验 / 排序 → B 最终复核 → Context
维护：B 批准 Passage → A 向量化 → B 批准投影 → P2 写 → 查原操作 + 查准确目标 → A 机制结果 → B 领域 Ready
```

Working 是 B 提供的候选来源；working_only 跳过 Query 向量和长期搜索。Prewarm 是正文加载加速路径。

## 六句话回答关键问题

1. **为什么字段多？** 它们回答身份、载荷、权限、操作关联和完成依据，分别防止串租户、读错版本、重复写及错误报成功。
2. **正文读取是否重复？** BP2-02 / RP2-02 共用一个公共能力，Remember 和 Recall 是两个消费者；保留需求编号及两侧适配视图。
3. **查询操作和查询对象是否重复？** 一个问“这次操作进展怎样”，一个问“这个对象实际怎样”。
4. **收到成功回包是否 Ready？** 要继续核对实际载荷、持久化、可查询性；A 的机制 Ready 之后，B 还要做领域 Ready Guard。
5. **所有类型是否有代码？** 本表 248 条记录对应 186 个不同对象字段，均已找到定义且类型相符。代码里的对象定义不等于所有业务调用已接通。
6. **当前到底实现到哪？** 已有契约、受理骨架、共享 Embedding 及 ONNX 本地验证；完整候选、正文、Context 链和真实 P2 对接不能据此宣称完成。
