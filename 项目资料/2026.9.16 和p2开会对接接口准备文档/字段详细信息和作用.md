# Search

## searchInput

| 字段                  | 谁提供、表示什么                                           | 为什么这样设计                                               |
| --------------------- | ---------------------------------------------------------- | ------------------------------------------------------------ |
| `query_vector`        | A 的 Embedding 模块生成的问题向量，例如 `[0.12, -0.38, …]` | P2 用它与已存储向量计算相关性。传真实向量，不能只传 A 本地的 `vector_ref`，因为 P2 未必能解析那个引用 |
| `usage`               | A 固定填写 `Query`                                         | 明确这是用于查询的向量。Query 和 Passage 可能采用不同前缀或编码方式，不能混用；Search 本身也不应把输入向量保存为长期投影 |
| `model_binding`       | 生成该向量时使用的模型及相关配置                           | 让接收方有依据检查模型、版本、维度、数据类型和预处理是否兼容。不能仅看“都是 1024 维”就直接比较 |
| `retrieval_space_ref` | 本次执行绑定的、已批准的检索空间引用                       | 指定查询哪一个逻辑向量空间，适配层再映射到实际索引。模型升级时可以同时存在旧空间和新空间，避免混检 |
| `scope`               | 经过认证和授权后批准的数据范围                             | 限定本次可以访问哪些租户、项目、Agent 等范围，避免检索到无权读取的数据 |
| `memory_types`        | Recall 筛选条件中的长期记忆类型                            | 可以是 `["Episodic"]`、`["Semantic"]` 或两者。列表必须非空且不重复。这里不传 `Working`，因为 Working 走 B 的独立读取接口 |
| `occurred_after`      | 可选的业务发生时间下界                                     | 限定“从什么时候发生的记忆开始查”，**包含这个时间点**。不筛选时显式传 `null` |
| `occurred_before`     | 可选的业务发生时间上界                                     | 限定“查到什么时候之前的记忆”，**不包含这个时间点**。不筛选时显式传 `null` |
| `top_k`               | Recall 根据固定策略确定的候选数量上限                      | 控制 P2 返回量、后续核验开销和延迟。必须大于 0；P2 若无法支持，不应悄悄改成更小的值而仍声称完整完成 |

**`model_binding` 是复合对象，里面的 8 个字段也各有用途。**

| 字段                       | 含义与用途                                                   |
| -------------------------- | ------------------------------------------------------------ |
| `model_id`                 | 模型标识，说明使用的是哪个模型                               |
| `model_version`            | 模型的具体版本，避免模型名称相同但权重已经变化               |
| `dimension`                | 向量长度，用于检查实际数组长度和索引维度是否匹配             |
| `dtype`                    | 向量的数值类型，例如 `float32`，约束表示精度和字节解释方式   |
| `embedding_schema_version` | Embedding 输出结构及解释规则的版本；它与模型权重版本分开演进 |
| `preprocessing_version`    | 预处理规则版本，例如 Query 前缀、文本处理方式；同一模型经过不同预处理也可能产生不兼容结果 |
| `retrieval_space_ref`      | 声明该向量所绑定的检索空间                                   |
| `model_contract_ref`       | 指向已确认的模型契约，用于查明上述配置、兼容条件和使用规则   |

**`scope` 里面的 5 个字段用于表达授权范围。**

| 字段         | 用途                     |
| ------------ | ------------------------ |
| `tenant_id`  | 所属租户，是基础隔离边界 |
| `project_id` | 限定项目范围             |
| `agent_id`   | 限定 Agent 范围          |
| `session_id` | 限定会话范围             |
| `task_id`    | 限定任务范围             |

## P2SearchResult

| 字段                     | 含义                                         | 为什么需要                                                   |
| ------------------------ | -------------------------------------------- | ------------------------------------------------------------ |
| `retrieval_space_ref`    | 实际使用的检索空间                           | A 可以核对是否查了正确的空间，发现路由或配置错误             |
| `requested_k`            | 本次约定的 K，应与请求 `top_k` 一致          | 避免请求 64 条却被服务端静默改成 10 条，导致 A 误判搜索已按要求完成 |
| `completion`             | `complete`、`partial` 或 `failed`            | 区分搜索完整完成、只完成一部分、执行失败                     |
| `hits`                   | 同一次搜索尝试返回的有序候选列表             | 保存原始结果及顺序，数量不能超过 `requested_k`               |
| `partial_reason`         | 部分完成的原因                               | `partial` 时必须说明原因；`complete` 时为 `null`。失败原因放公共 `error` |
| `ranking_contract_ref`   | 解释排序和分数的契约引用                     | 告诉 A 分数是什么、越大还是越小越好，以及返回顺序有什么保证  |
| `query_binding_evidence` | 本次查询确实应用了相应空间、范围和筛选的依据 | 防止只是“请求里写了过滤条件”，实际搜索却没有执行             |
| `completion_evidence`    | 本次搜索完成或部分完成的依据                 | 防止仅根据返回条数猜测是否查完                               |

`completion` 特别重要：

| 返回情况                                | 正确理解                                     |
| --------------------------------------- | -------------------------------------------- |
| 请求 10 条，返回 3 条，且有完整完成依据 | 可以是 `complete`，因为可能只有 3 条符合条件 |
| 返回 0 条，且有完整完成依据             | 可以确认本次有界搜索为空                     |
| 返回 0 条，但搜索超时或只完成一部分     | 不能说“没有相关记忆”                         |
| 返回 10 条                              | 也不能仅凭数量就认定搜索完成                 |

这里的 `complete` 表示**按约定完成了本次有界检索**。如果底层是近似向量搜索，它不额外保证找到了全库数学意义上的精确 TopK。

**`hits` 中每条候选是 `P2SearchHit`，有 7 个字段。**

| 字段                        | 含义与设计目的                                               |
| --------------------------- | ------------------------------------------------------------ |
| `projection_ref`            | 稳定的投影引用，A 将它交给 B 解析对应记忆和版本。P2 原有的 `SearchHit.id` 必须有明确映射，不能猜它就是 `memory_id` |
| `provider_rank`             | P2 给出的原排名，从 1 开始。保留原顺序，供后续融合排序使用   |
| `raw_score`                 | P2 原始分数，未提供时为 `null`。不同模型空间、不同距离指标的分数不能直接相互比较，也不能直接与 Working 分数比较 |
| `model_version`             | 该候选投影使用的模型版本，用于检查与 Query 空间是否兼容      |
| `projection_schema_version` | 该候选投影的数据结构版本，用于正确解释投影元信息；它不是 Memory 内容版本 |
| `identity`                  | 如果有可信依据，可以携带完整投影身份；否则为 `null`，由 B 根据稳定引用解析 |
| `source_evidence`           | 该候选引用、版本和排名的来源依据，便于追溯到原条目和空间契约 |

`identity` 是五元组：

| 字段                        | 定位什么                 |
| --------------------------- | ------------------------ |
| `memory_id`                 | 哪条记忆                 |
| `chunk_id`                  | 哪个片段                 |
| `memory_version`            | 哪个记忆版本             |
| `model_version`             | 使用哪个模型版本生成投影 |
| `projection_schema_version` | 使用哪个投影结构版本     |

之所以不能只用 `chunk_id`，是因为**同一个片段可能在内容更新、模型升级后存在多个投影版本**。完整身份用于区分它们。

如果 P2 没有返回完整身份，A 不能把“当前最新版本”补进去。否则可能把旧向量命中错误地关联到新正文。

------

**几个 `evidence` 字段使用同一种结构：`P2Evidence`。**

它们不是要求 P2 额外建设一整套审计系统，而是要求结果有可解释、可关联的来源依据。依据可以来自原响应及已确认契约，不一定需要独立的证据接口。

| 字段                    | 用途                                                         |
| ----------------------- | ------------------------------------------------------------ |
| `kind`                  | 说明证明的事实类别，例如查询范围绑定、候选版本绑定、搜索完成 |
| `contract_ref`          | 指向解释该证据含义、适用范围和有效条件的契约                 |
| `provider_evidence_ref` | P2 如果有独立可查询的证据对象，提供其引用；没有时允许 `null` |
| `observed_at`           | P2 提供的观察时间；未知为 `null`，不能拿 A 收到响应的时间冒充 |

三个位置分别关心：

```
query_binding_evidence → 是否按正确的范围和条件查询
completion_evidence    → 这一次搜索是否完成
hit.source_evidence    → 这一条候选的身份、版本和排名来自哪里
```

只有一个字符串或一个 `true`，但无法关联到对应请求和事实，不能自动视为充分证据。

**最后，Search 还带公共调用上下文。它们可以映射到 gRPC metadata 或 SDK 上下文，不一定全部放在请求 body 里。**

请求公共信息 `P2CallContext`：

| 字段           | 用途                                                     |
| -------------- | -------------------------------------------------------- |
| `request_ref`  | 标识并关联本次调用，便于匹配响应；与稳定的写入幂等键不同 |
| `trace_id`     | 串联 Recall、Embedding、P2 等调用日志，不用于鉴权        |
| `tenant_id`    | 已认证租户，必须与 `scope.tenant_id` 一致                |
| `provider_ref` | 本次调用的固定 P2 Provider 标识                          |
| `contract_ref` | 本次使用的 P2 协议及适配契约版本                         |
| `deadline_at`  | 本次调用截止时间，防止检索无限等待或耗尽后续处理预算     |

响应公共信息 `P2ResponseContext`：

| 字段                   | 用途                                                   |
| ---------------------- | ------------------------------------------------------ |
| `request_ref`          | 关联本次请求，避免响应串配                             |
| `provider_ref`         | 标明实际响应的 Provider                                |
| `contract_ref`         | 标明解释该响应所依据的契约版本                         |
| `provider_request_ref` | P2 自己的诊断请求编号，便于双方查日志；没有则为 `null` |
| `observed_at`          | P2 提供的观察时间，没有则为 `null`                     |
| `error`                | 结构化错误；正常无错误时为 `null`                      |

`error` 中各字段为：

| 字段             | 用途                                                         |
| ---------------- | ------------------------------------------------------------ |
| `raw_code`       | 保留 P2 原错误码或 gRPC 状态                                 |
| `category`       | 将原错误归入 A 能处理的类别，例如参数错误、绑定不匹配、服务错误 |
| `message`        | 脱敏后的诊断说明                                             |
| `retryable`      | P2 是否建议重试，未知为 `null`；A 仍要检查次数和剩余时间     |
| `retry_after_ms` | P2 建议等待多久再试，没有建议则为 `null`                     |
| `effect`         | 描述变更副作用；Search 是只读操作，因此使用 `not_applicable` |
| `evidence`       | 支撑错误及效果判断的来源依据                                 |

# 向量写入

## EmbeddingUpsertInput

**一、发送给 P2 的 5 个字段**

| 字段                       | 通俗理解                     | 为什么需要                                                   |
| -------------------------- | ---------------------------- | ------------------------------------------------------------ |
| `target`                   | **写入哪个投影目标**         | 准确确定租户、存储服务、检索空间及投影身份，避免覆盖错对象   |
| `provider_idempotency_key` | **这一次写入操作的固定编号** | 请求超时后重试，仍使用同一个编号，让 P2 识别这是原操作的重复提交 |
| `request_fingerprint`      | **这次写入内容和语义的指纹** | 防止使用同一个幂等键，却偷偷换了向量、目标或属性             |
| `payload`                  | **实际要保存的内容**         | 包含向量、模型信息、正文关联、检索属性及摘要                 |
| `precondition_ref`         | **执行写入前必须满足的条件** | 如果 P2 支持条件写或代际屏障，用它避免过期请求覆盖新状态；没有该条件方案时为 `null` |

`provider_idempotency_key` 和 `request_fingerprint` 的区别，可以用一个例子说明：

```
第一次：操作编号 K1，指纹 H1 → 提交写入
重试：  操作编号 K1，指纹 H1 → 仍是原操作
冲突：  操作编号 K1，指纹 H2 → 同一个操作编号换了内容，应拒绝
```

**幂等键负责识别“哪次操作”，指纹负责检查“是不是原来的请求”。**

`precondition_ref` 则解决另一个问题：这次请求即使内容没变，也可能已经过时。例如目标已经进入禁止旧写的代际，旧请求不能因为迟到就重新生效。这里必须使用 P2 认可的条件，不能直接拿 A 本地的租约编号代替。

**二、`target`：投影目标内部的字段**

| 字段                  | 含义和用途                                                   |
| --------------------- | ------------------------------------------------------------ |
| `tenant_id`           | 投影所属租户，参与目标隔离                                   |
| `provider_ref`        | 固定写入哪个 P2 Provider，避免重试时写到另一套服务           |
| `retrieval_space_ref` | 写入哪个检索空间，通常再映射到实际 collection                |
| `identity`            | 完整的投影身份，下面展开                                     |
| `physical_target_ref` | P2 中该向量对象的实际 ID。首次尚未分配时可为 `null`，但必须能通过稳定映射查回 |

`identity` 包含五个字段：

| 字段                        | 回答的问题               |
| --------------------------- | ------------------------ |
| `memory_id`                 | 属于哪条记忆？           |
| `chunk_id`                  | 属于哪个片段？           |
| `memory_version`            | 对应记忆的哪一版？       |
| `model_version`             | 使用哪个模型版本生成？   |
| `projection_schema_version` | 按哪个投影结构版本保存？ |

**三、`payload`：实际写进去的 12 个字段**

这是向量写入最核心的一组。Excel 在“公共字段”页第 75～89 行定义了载荷及检索属性。A组_P2接口逻辑字段表.xlsx (公共字段!F75:I89)

| 字段                   | 表示什么                                 | 设计用途                                                     |
| ---------------------- | ---------------------------------------- | ------------------------------------------------------------ |
| `usage`                | 固定为 `Passage`                         | 表明保存的是待检索内容的向量；本接口不写入 Query 向量        |
| `vector`               | 实际向量数组                             | 这是 P2 建立索引和计算相似度的数据，不能只传 A 本地的 `vector_ref` |
| `model_binding`        | 模型及输出规则                           | 让后续查询能够检查 Query 向量与已存向量是否兼容              |
| `source_hash`          | 原 Embedding 输入文本的摘要              | 绑定“这个向量是根据什么输入生成的”                           |
| `input_binding_digest` | 输入所属片段、来源版本及上下文的绑定摘要 | 防止文本相同却被错误关联到另一条记忆或另一个版本             |
| `vector_hash`          | 向量按固定编码形成的字节摘要             | 检查实际向量是否被替换、损坏或发生未经确认的精度变化         |
| `representation_id`    | B 批准的内容表示身份                     | 明确投影关联的是哪份获准表示                                 |
| `content_ref`          | 正式正文引用                             | Search 命中后，能够沿着关联找到正文                          |
| `content_version`      | 正文版本                                 | 防止旧向量命中后被配上新正文                                 |
| `approved_range`       | 对应的原正文片段字节范围                 | 明确向量关联原正文的哪一段                                   |
| `metadata`             | 用于检索筛选的属性                       | 保存 scope、记忆类型和业务发生时间                           |
| `metadata_hash`        | 上述检索属性的摘要                       | 检查范围、类型或时间有没有被改变                             |

**`model_binding` 的 8 个子字段**

| 字段                       | 用途                                                     |
| -------------------------- | -------------------------------------------------------- |
| `model_id`                 | 标识具体模型                                             |
| `model_version`            | 固定实际模型版本                                         |
| `dimension`                | 向量维度，必须等于实际数组长度                           |
| `dtype`                    | 数值类型，例如 `float32`；不能改变精度后仍沿用原向量摘要 |
| `embedding_schema_version` | Embedding 输出格式版本                                   |
| `preprocessing_version`    | 文本预处理及 Query／Passage 编码规则版本                 |
| `retrieval_space_ref`      | 声明该向量所属的兼容检索空间                             |
| `model_contract_ref`       | 定位完整模型规则，例如输入上限、归一化、字节序和数值编码 |

**`metadata` 的 3 个子字段**

| 字段          | 含义                                          | 与 Search 的关系                   |
| ------------- | --------------------------------------------- | ---------------------------------- |
| `scope`       | B 批准的租户、项目、Agent、会话和任务范围快照 | 后续 Search 根据获准范围筛选       |
| `memory_type` | `Episodic` 或 `Semantic`                      | 对应 Search 的 `memory_types` 条件 |
| `occurred_at` | B 定义的业务发生时间，未知为 `null`           | 对应 Search 的时间范围条件         |

## P2MutationResult

| 字段                       | 含义与用途                                                   |
| -------------------------- | ------------------------------------------------------------ |
| `operation_kind`           | 本接口应为 `upsert`，确保返回结果对应正确的操作类型          |
| `target`                   | 本次操作对应的准确目标，供 A 核对是否写错对象                |
| `provider_idempotency_key` | 关联原请求的幂等键，但仅回显这个键不能证明操作已执行         |
| `request_fingerprint`      | P2 已关联到的请求指纹；尚不能确认时为 `null`，不能用 A 的输入直接补成“已验证” |
| `provider_operation_ref`   | P2 为该操作提供的编号，后续可用于查询进度；尚未取得时可为空  |
| `operation_status`         | 统一解释后的操作状态                                         |
| `raw_status`               | 保留 P2 原始状态标签，方便排查和核对状态映射                 |
| `target_state`             | 已观察到的实际对象、载荷、持久化和索引状态                   |
| `resubmit_assessment`      | 在能判断时，说明是否具备安全重发原请求的条件                 |
| `evidence`                 | 支撑本次操作关联和执行进度的来源依据                         |

`operation_status` 的几个取值：

| 值          | 含义                                               |
| ----------- | -------------------------------------------------- |
| `accepted`  | 已受理                                             |
| `running`   | 执行中                                             |
| `completed` | 操作层面报告完成，仍需核对准确目标及完成依据       |
| `rejected`  | 明确拒绝                                           |
| `failed`    | 明确失败                                           |
| `not_found` | 查询没有找到对应操作记录，不能直接推断原写入没发生 |
| `unknown`   | 当前无法确认状态                                   |

**`target_state` 内部的字段**

| 字段                           | 用途                                                         |
| ------------------------------ | ------------------------------------------------------------ |
| `target`                       | 标识实际查验的是哪个准确目标                                 |
| `object_present`               | 对象是否存在；确认不存在才填 `false`，无法判断填 `null`      |
| `stored_request_fingerprint`   | 实际存储内容所对应的请求指纹；单纯保存或回显摘要不等于验证了载荷 |
| `stored_payload`               | 实际回读的载荷，可用于检查保存的向量和属性是否正确；未取得时可为空 |
| `durable`                      | 是否达到已约定的持久化条件                                   |
| `index_queryable`              | 是否达到该检索空间约定的查询可见条件                         |
| `delete_confirmed`             | 是否确认删除完成；普通写入观察不适用时为 `null`              |
| `late_write_barrier_confirmed` | 是否确认旧在途写已被排空或受到屏障约束；主要服务于删除及相关恢复流程 |
| `binding_evidence`             | 支撑“实际存储内容与原请求正确对应”的依据                     |
| `completion_evidence`          | 支撑持久化、索引可见或删除完成等结论的依据                   |
| `observed_at`                  | P2 提供的本次状态观察时间                                    |

**`resubmit_assessment` **

写请求超时可能只是响应丢失，P2 实际已经写入。直接换一个操作编号再写，可能造成重复或状态冲突。

它内部的字段是：

| 字段                        | 用途                                                         |
| --------------------------- | ------------------------------------------------------------ |
| `no_effect_confirmed`       | 是否已经证明原请求没有产生效果                               |
| `no_late_effect_confirmed`  | 是否已经证明原请求以后也不会迟到生效                         |
| `same_key_resubmit_allowed` | 协议是否允许沿用原幂等键重发相同内容                         |
| `idempotency_valid_until`   | 已确认的幂等键有效截止时间；没有时间型截止时由契约解释有效窗口 |
| `evidence`                  | 支撑这些判断及有效窗口的依据                                 |

# 投影查询

## Input

| 字段                       | 含义                             | 为什么需要                                                   |
| -------------------------- | -------------------------------- | ------------------------------------------------------------ |
| `target`                   | 原操作要写入或删除的准确投影目标 | 确认查询的是哪个租户、Provider、空间和投影版本，不能在查询时换成最新版本 |
| `operation_kind`           | 原操作类型：`upsert` 或 `delete` | 同一个目标可能先写后删，必须区分正在查哪一种操作             |
| `provider_operation_ref`   | P2 返回的操作编号                | 如果之前拿到了编号，就用它定位原操作；首次响应丢失时允许为 `null` |
| `provider_idempotency_key` | A 首次提交时使用的幂等键         | 即使没有拿到 P2 操作编号，也要能通过原键查询或进行等效查证   |
| `request_fingerprint`      | 原请求的固定语义摘要             | 确认查到的是原来的内容和操作，避免关联到同键但内容不同的请求 |

## 返回仍然使用 `P2MutationResult`

# 投影目标核验

## Input

| 字段                           | 表示什么                   | 为什么需要                                                   |
| ------------------------------ | -------------------------- | ------------------------------------------------------------ |
| `target`                       | 要核验的准确投影目标       | 避免查错租户、空间、片段或版本                               |
| `expected_request_fingerprint` | 期望对应的原写入请求指纹   | 用于核对当前存储内容是否对应当初那次写入；没有时可为 `null`  |
| `related_operation_ref`        | 关联的 P2 操作编号         | 将本次对象核验与之前的写入或删除操作关联；没有编号也可以为 `null` |
| `include_payload`              | 是否要求返回实际保存的载荷 | 需要检查具体向量和属性时为 `true`；已有充分绑定证明时可为 `false`，减少传输 |

`target` 的结构沿用写入接口：

```
tenant_id                 所属租户
provider_ref              哪个 P2 Provider
retrieval_space_ref       哪个检索空间
identity                  记忆、片段、记忆版本、模型版本、投影结构版本
physical_target_ref       P2 实际对象 ID，未知时可空
```

**`include_payload` 决定是否查看“具体存了什么”。**

| 设置    | 期望得到什么                                   |
| ------- | ---------------------------------------------- |
| `false` | 对象状态及必要证明，不要求把向量再次传回来     |
| `true`  | 请求回读实际向量、模型信息、正文关联和筛选属性 |

## P2TargetState

| 字段                           | 含义与用途                                                   |
| ------------------------------ | ------------------------------------------------------------ |
| `target`                       | 实际查验的目标。A 要核对它与请求目标一致；已确定物理 ID 时，应带回对应关系 |
| `object_present`               | 这个准确对象是否存在。确认不存在才为 `false`，无法判断为 `null` |
| `stored_request_fingerprint`   | 实际存储载荷对应的请求指纹，用来与期望指纹核对               |
| `stored_payload`               | 实际回读的投影载荷；未请求、对象不存在或无法取得时可为 `null` |
| `durable`                      | 是否满足已约定的持久化条件                                   |
| `index_queryable`              | 是否满足目标空间的查询可见性要求                             |
| `delete_confirmed`             | 是否已确认准确目标删除完成；普通写入核验不适用时为 `null`    |
| `late_write_barrier_confirmed` | 旧在途写是否已被排空或被有效屏障阻止，避免删除后重新出现     |
| `binding_evidence`             | 支撑“实际存储的是正确向量及关联信息”的依据                   |
| `completion_evidence`          | 支撑持久化、索引可查询，或删除及屏障完成的依据               |
| `observed_at`                  | P2 提供的本次状态观察时间；未知为 `null`，不能用 A 收到响应的时间冒充 |

**其中，最重要的三个状态是分别判断的。**

```
object_present = true
    对象存在

durable = true
    达到约定的持久化条件

index_queryable = true
    达到约定的索引查询可见条件
```

例如：

| 存在 | 已持久化 | 可查询 | 含义                                           |
| ---- | -------- | ------ | ---------------------------------------------- |
| 是   | 是       | 否     | 对象已经保存，但索引可能仍在构建               |
| 是   | 未知     | 未知   | 查到了对象，但还不能确认持久化和索引状态       |
| 是   | 是       | 是     | 这些基础条件已具备，还要核对实际载荷绑定和证据 |
| 否   | —        | —      | 权威查询确认目标不存在                         |

# 投影删除

## Input

| 字段                       | 含义                                           | 为什么需要                                                   |
| -------------------------- | ---------------------------------------------- | ------------------------------------------------------------ |
| `target`                   | B 批准删除的准确投影目标                       | 明确删哪个租户、空间、记忆片段及版本，避免误删其他投影       |
| `provider_idempotency_key` | 本次删除的固定幂等键                           | 同一次删除重试时沿用，让 P2 识别原操作；与写入幂等键区分     |
| `request_fingerprint`      | 删除请求语义的摘要                             | 防止沿用同一个删除编号，却换了目标或其他操作条件；不包含向量载荷 |
| `precondition_ref`         | P2 认可的条件删除或代际屏障条件                | 限制删除及旧写的生效条件，避免并发操作造成错误               |
| `related_upsert_keys`      | A 已知的、与该目标有关的历史在途写入幂等键列表 | 帮助 P2 核对是否还有旧写可能在删除后生效                     |

## P2MutationResult

| 字段                       | 在删除接口中的用途                                 |
| -------------------------- | -------------------------------------------------- |
| `operation_kind`           | 应为 `delete`，确认返回的是删除操作                |
| `target`                   | 返回本次操作对应的准确目标，供 A 核对              |
| `provider_idempotency_key` | 关联原删除请求                                     |
| `request_fingerprint`      | P2 已确认关联的删除请求摘要；无法确认时为 `null`   |
| `provider_operation_ref`   | P2 的删除操作编号，用于后续查询                    |
| `operation_status`         | 删除是已受理、执行中、完成、拒绝、失败还是未知     |
| `raw_status`               | 保留 P2 原始状态标签                               |
| `target_state`             | 当前取得的对象存在性、索引状态、删除及防迟到写事实 |
| `resubmit_assessment`      | 在有充分依据时，说明是否具备安全重发条件           |
| `evidence`                 | 支撑操作关联、进度和结果的依据                     |

# 正文元数据补充

## Input

| 字段                    | 含义                                         | 为什么需要                                                   |
| ----------------------- | -------------------------------------------- | ------------------------------------------------------------ |
| `content`               | 要查询元数据的准确正文目标                   | 指定正文引用、版本、表示及存储位置，避免查到其他对象的信息   |
| `approved_range`        | 本次准备读取、需要验证的字节范围             | 明确需要哪一段内容的校验依据，避免把整对象摘要误用于局部片段 |
| `version_condition_ref` | 与后续正文读取一致的版本条件或不可变定位依据 | 让元数据查询和正文读取针对同一版本，防止前后查到不同内容     |

`content` 内部的字段是：

| 子字段                | 用途                     |
| --------------------- | ------------------------ |
| `content_ref`         | B 提供的正式正文引用     |
| `content_version`     | B 批准读取的正文版本     |
| `representation_id`   | 具体内容表示的身份       |
| `representation_type` | B 定义的表示类别         |
| `bucket`              | 对象所在的存储空间       |
| `key`                 | 对应准确版本的对象定位键 |

## Output

| 字段       | 含义                               | A 怎样使用                                |
| ---------- | ---------------------------------- | ----------------------------------------- |
| `status`   | 本次元数据查询结果                 | 判断是否取得可用信息                      |
| `meta`     | 实际取得的正文元数据               | `status=ok` 时必须有；其他情况可为 `null` |
| `evidence` | 本次对象、版本和摘要范围的来源依据 | 检查这些信息是否确实对应本次目标          |

`status` 的四个值：

| 值                 | 含义                                               |
| ------------------ | -------------------------------------------------- |
| `ok`               | 成功取得元数据                                     |
| `not_found`        | 本次查询未找到准确对象，不能据此宣称 Memory 已删除 |
| `version_mismatch` | 实际对象与要求的版本不匹配                         |
| `failed`           | 查询失败，例如服务或传输故障                       |

**核心是 `meta`，内部有 8 个字段。**

| 字段                | 表示什么                                 | 设计用途                                                     |
| ------------------- | ---------------------------------------- | ------------------------------------------------------------ |
| `content_ref`       | 实际对象对应的正文引用                   | 核对查到的是不是目标正文                                     |
| `content_version`   | 实际证实的正文版本                       | 核对是不是 B 批准的那一版，不能直接拿 `memory_version` 替代  |
| `representation_id` | 实际对象对应的内容表示                   | 防止查到同一记忆的另一份表示                                 |
| `object_size_bytes` | **同一版本完整对象**的字节长度           | 判断批准范围是否越界、评估读取方式；它不是本次片段的长度     |
| `content_encoding`  | 字节表示或文本编码的契约标识，例如 UTF-8 | 说明后续怎样解释字节，并确保范围和摘要基于正确的字节表示     |
| `etag`              | Provider 返回的原始对象标识              | 可按已确认的协议语义用于对象比较或条件判断，不能默认当作内容哈希 |
| `checksum`          | Provider 实际提供的摘要信息              | 为完整性校验提供依据，必须明确算法、编码和覆盖范围；未提供时可为 `null` |
| `version_evidence`  | 上述元数据与准确版本关联的依据           | 防止只是把请求里的版本号原样回显，却没有证明实际对象就是该版本 |

**`checksum` 里面还有 4 个子字段。**

| 子字段          | 用途                                            |
| --------------- | ----------------------------------------------- |
| `algorithm`     | 摘要算法，例如契约认可的 SHA-256、BLAKE3 等     |
| `value`         | 摘要值                                          |
| `byte_encoding` | 计算摘要所使用的字节编码                        |
| `range`         | 摘要覆盖的范围；`null` 表示该摘要对象的完整字节 |
