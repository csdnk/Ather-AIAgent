# P3 当前代码实现层级核查

核查日期：2026-09-26。代码基线：`32487d0290f6560ebe274c086119316856149cf5`，分支 `codex/project-workspace`。本次以 `AgentJYS-main` 的 P3 实现、实际装配入口、本地回归和该提交的 GitHub Actions 为依据；没有修改业务源码。本报告不是产品验收签收。

## 1. 结论

**目前达到“核心业务模块已有实现、部分链路完成单机本地集成”的阶段，下一步重点是统一入口、接入真实依赖并修复集成门禁。尚不能认定为可正式交付的完整 P3 产品。**

相比 9 月 23 日，最重要的进展是 Remember 已实现新版 Recall 所需的资格检查、正文读取、关系读取和最终复核，并通过可选工厂接入。旧结论“B 侧这些接口尚未实现”已不适用于当前源码。但新能力没有自动进入所有既有启动入口。

判断层级使用以下口径：契约定义 → 模块实现 → 本地集成 → 真实服务集成 → 产品验收。测试替身、SQLite P2 替代器、文件夹冷热层演示，只证明其实际覆盖的层级。

## 3. 当前存在四条不同入口

| 入口 | 实际装配 | 影响 |
|---|---|---|
| `aether_agent_memory.app:create_app` | `build_runtime` → `MemoryRuntime` 与已有 `P3Runtime`/适配器 | 既有 API/部署路径；不能仅因仓库新增 Remember 文件就认定该路径获得全部新能力 |
| `python -m aether_agent_memory.runtime.flows` | 直接构造基础 `ThreeFlows` | 默认仍为基础 Remember/Recall，加 `operate/basic` |
| `aether_agent_memory.remember.local.create_runtime` | `RememberFactory` → `RememberPipeline` → `RememberBoundary` → `enable_generation_recall` | 新 Remember 与新 Recall 的明确本地集成入口，继续复用基础 Operate |
| `python -m aether_agent_memory.operate.standalone` | 独立控制器、内存状态、内存 P2 Mock | 单独演示；不自动替换前面三条入口的 Operate |

因此，部署前需要明确选择哪条业务宿主，并完成所需适配与启动配置。当前不能把四条路径各自的能力相加后宣称已经在一个服务中全部可用。

## 5. 距离可交付版本还差什么

按依赖顺序建议推进：

1. **恢复当前提交的工程门禁。** 修复独立 Operate 演示/测试类型检查，补全流程与协作门禁的 fakeredis/Lua 依赖，并让独立测试进入明确的验证入口。
2. **统一新能力的宿主与启动路径。** 决定正式 API 如何装配 RememberPipeline 与 GenerationRecall，确认部署不会继续运行旧流程。
3. **完成真实提供者集成。** 接入并验证真实 P2 的正文保存/范围读、新分块索引的 Milvus 检索、真实模型提取与摘要、Redis/Celery；已有适配代码和旧链路验证不能代替新路径联调。
4. **将独立 Operate 接入持久化与正式执行链。** 复用 RF 的任务、租约、事件和恢复机制，核实 P2 动作协议、重启恢复、跨进程互斥、真实读回及物理层迁移。
5. **开展产品验收。** 分别验证业务质量、租户/共享授权、故障恢复、吞吐与 P99、长时间运行及实际云部署。摘要质量、去重判断、冷热策略、压缩收益需要业务样本，不能由默认参数或 Mock 场景证明。
