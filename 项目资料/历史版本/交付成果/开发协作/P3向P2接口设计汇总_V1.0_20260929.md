# P3 需要 P2 提供的接口设计汇总

版本：V1.0　整理日期：2026-09-29　用途：P3/P2 接口评审、开发交接与联调准备。

**本文定义 P3 需要 P2 提供的接口：用于什么业务、什么时候调用、P3 发送什么、P2 返回什么、什么结果算完成，以及异常后怎样继续。按 Remember、Recall / Embedding、Operate 三条流程组织，保留已有设计的接口编号。**

英文方法名表示 P3 需要的逻辑能力。P2 可以采用自己的接口命名和传输方式，但必须完整表达对应的输入、输出和行为保证。同一底层能力可被多个流程复用，因此条目数量不等于必须新增的 RPC 数量。

## 1. 范围、职责和调用顺序

### 1.1 谁负责什么

| 参与方 | 负责的事实和决策 | 与 P2 的交接 |
|---|---|---|
| Remember / B | 记忆主事实、业务版本、有效性、正文映射、长期可用状态和删除授权 | 提供获准的正文及目标；取得存储、读取、删除的真实结果 |
| Recall / Embedding / A | 生成问题与片段向量、共享向量机制、召回组包 | 提供向量及其绑定；取得候选、正文和投影存储状态 |
| Operate / C | 调度原因、时机、对象、目标层级、优先级、恢复与对账 | 提供抽象动作；取得资源、执行状态和实际放置结果 |
| P2 / Provider | 物理对象、向量存储与搜索、实际放置、底层执行及其状态 | 提供可核对的版本、字节、状态和执行证据 |

正文公共契约 OBJ-001 归 B；A 根据 B 批准的映射消费正文读取能力。公共健康观察 HLT-001 / BackendHealthPort 归 C；B、A 消费适用观察，不另设一套相互矛盾的健康判断。

向量写入采用“B 批准目标并判断长期可用，A 承接共享向量机制，P2 提供物理事实”的接口职责边界。业务资格、语义质量及上下文交付由 P3 负责。

### 1.2 保存到召回

```text
B 固定本次输入、版本和写入身份
  → P2 保存正文 → 查询原操作 / 核验准确对象
  → B 确认主事实与正文映射
  → 如需要加工：B 生成并验质 → P2 保存加工结果
  → B 批准片段与投影目标 → A 生成向量 → P2 写入向量
  → A 查询原操作、核验目标 → B 判断完整集合是否长期可用
  → A 收到问题并生成问题向量 → P2 搜索候选
  → B 核验资格并批准正文版本 → P2 读取该版本正文
  → A 校验正文、排序 → B 最终复核 → A 交付带来源的上下文
```

短期 Working 的可靠内嵌正文可按既有方案走本地持久化路径；不是每条记忆都必须同步调用 P2。长期构建、真实外存及调度能力按本文件相应契约接入。

### 1.3 删除与调度

```text
删除：B 先建立业务失效屏障并批准清理范围
  → 正文经 B、向量经 A 请求 P2 删除
  → 查询原删除操作 + 核验目标及旧写屏障 → B 记录实际完成层次

调度：C 获取实际放置和资源状态 → 生成计划
  → P2 解析执行目标 → C 提交原动作 → P2 / Provider 执行
  → C 查询或接收反馈 → 再读实际放置 → 核对效果后结束动作
```

调度接口需要让 C 从“提交意图”走到“确认实际效果”：动作受理、物理执行和最终核验分别返回可追溯事实。

### 1.4 接口清单与共用关系

| 流程 | 原编号 | 已设计的能力 | 共用关系 |
|---|---|---|---|
| Remember | BP2-01 | 正文写入 | 加工产物 BP2-04 复用 |
| Remember | BP2-02 | 正文元数据核验、准确正文/范围读取 | 与 RP2-02、RP2-03 共用底层读取能力 |
| Remember | BP2-03 | 原正文写入/删除操作查询 | 返回原操作事实，不是再次写入 |
| Remember | BP2-04 | 加工产物持久化 | 复用 BP2-01，不新增“加工成功”接口 |
| Recall / Embedding | BP2-05 / RP2-06 | 向量写入 | 统一在第 4.3 节定义 |
| Recall / Embedding | BP2-06 / RP2-07、RP2-08 | 向量操作查询与准确目标核验 | 统一在第 4.4、4.5 节定义 |
| Remember | BP2-07 | 正文、加工产物删除核验 | 第 3.5 节；向量删除另列第 4.6 节 |
| 公共观察 | BP2-08 | 能力、健康、限额和恢复观察 | 与 C 公共观察协作，不能只拿“进程存活”代替 |
| Recall | RP2-01、RP2-02 | 向量搜索；复用公共正文读取 | 正文读取共用 BP2-02 |

| Recall 补充 | RP2-03—RP2-05 | 按需元数据、可选热副本读取、实际来源归因 | 非三个额外必调 RPC |
| Operate | CP2-01—CP2-06 | 放置、资源、目标解析、提交、查询、反馈 | 六项逻辑接口；反馈可由可恢复轮询满足 |
| Operate 支撑 | CP2-07、CP2-08 | 物理执行；冻结/解冻/取消 | 执行能力和控制边界，非两个固定 RPC |

## 2. 公共字段与处理规则

### 2.1 字段阅读约定

- B/A 表内列出逻辑适配视图的字段；字段名并非要求 P2 原报文逐字相同。适配器必须说明每个字段来自原响应、可信映射还是已确认的运行契约。
- `?` 表示逻辑字段存在但允许 `null`；未知不能用 `false`、`0`、空字符串或当前默认值代替。组合行中的字段分别存在，不表示使用带斜杠的字段名。
- `Id / Ref / String` 是非空标识或字符串；`UInt` 为非负整数；字节数按实际字节计算；时间使用约定时区的时间戳。涉及 C 的字段，现有设计只定义语义，具体类型、必填性和序列化仍需 C/P2 对齐。
- 字段清单表达 P3 的输入输出需求；第 6 章规定交付样例和行为通过标准。具体报文类型、必填性及逻辑字段映射由接口交接材料明确。

### 2.2 B/A 公共请求与响应

| 结构 | 字段 | 含义 |
|---|---|---|
| P2CallContext | `request_ref`、`trace_id` | 本次调用和链路关联；不能替代稳定幂等键 |
| P2CallContext | `tenant_id`、`provider_ref`、`contract_ref` | 已认证租户、固定 Provider、接口及适配契约版本 |
| P2CallContext | `deadline_at` | 本次调用截止；重试不能无限延长原执行期限 |
| P2ResponseContext | `request_ref`、`provider_ref`、`contract_ref` | 回应哪次调用、实际由谁提供、依据什么解释 |
| P2ResponseContext | `provider_request_ref?`、`observed_at?`、`error?` | Provider 诊断 ID、观察时间及错误；未知保留 null |
| P2Evidence | `kind`、`contract_ref`、`provider_evidence_ref?`、`observed_at?` | 证据类别、适用契约、外部引用、来源时间；实际证据须关联准确对象或原操作 |
| P2Error | `raw_code`、`category`、`message`、`retryable?`、`retry_after_ms?`、`effect`、`evidence[]` | 原始错误、分类、重试建议及副作用确定性 |

`effect` 为 `no_effect / may_have_effect / unknown / not_applicable`。只读操作用 `not_applicable`；写入超时不能默认 `no_effect`。鉴权使用正式身份通道，正文、向量和日志中不放凭据。

### 2.3 不能混用的身份、版本和摘要

| 数据 | 已有定义 | 适配要求 |
|---|---|---|
| B 正文 Scope | `tenant_id, project_id, user_id, agent_id, session_id, business_task_id, authorization_ref` | tenant 和批准依据必有；其他维度可空但不能扩大授权 |
| A 向量 Scope | `tenant_id, project_id?, agent_id?, session_id?, task_id?` | business_task_id 映射 task_id；必要的 user 约束必须由正式授权/空间契约承接，不能丢弃 |
| B 正文 Hash | `algorithm, value, coverage, byte_start?, byte_end?` | 区分全文、范围和规范请求摘要；范围摘要带准确起止 |
| A Hash | `algorithm, value, byte_encoding, range?` | 范围为半开字节区间；range=null 表示该摘要对象的完整字节 |
| 业务版本 | `memory_version, content_version` | 由 B 管理或批准的业务绑定 |
| 物理版本与路由 | `object_version, generation, target_generation, route_epoch` | 由实际权威方返回；不能用业务版本或本地租约令牌替代 |
| 操作身份 | B 的 client operation、A 的 provider idempotency key、C 的 action_id | 调用前持久化；回执丢失后仍能查原动作 |

两种 Hash 和 Scope 是不同的已有设计视图，不在本文件中合并为一套新 Schema。转换必须保留授权和字节覆盖语义。ETag 默认是不透明标识；不同算法的摘要不能直接比较。

### 2.4 完成、未知和重试

| 情况 | 正确处理 |
|---|---|
| 已受理 / 执行中 | 保存原操作关联并继续查询；不等于保存、索引或迁移已完成 |
| 操作报告 completed / succeeded | 再核验准确对象或实际放置，判断是否达到本次目标 |
| 回执丢失 / 超时 / 重启 | 按原操作、原目标、原幂等键查询；不能换键盲目重做 |
| 操作 not_found | 必须确认负查询的最终性与保留窗口；单次查不到不证明未执行 |
| 对象存在 | 还要匹配版本和实际载荷；存在不证明是本次操作正确写入 |
| ANN 搜索未命中 | 不能据此证明准确向量对象不存在或删除完成 |
| 同键不同载荷 | 返回冲突，不覆盖旧语义 |
| 部分返回 | 明确 partial 及原因；空列表可能是部分失败，不能一律解释为无结果 |

B/A 的 `P2ResubmitAssessment` 包含 `no_effect_confirmed?`、`no_late_effect_confirmed?`、`same_key_resubmit_allowed?`、`idempotency_valid_until?`、`evidence[]`。前三项均有据为 true，且原预算、窗口、授权和目标仍有效，才允许原键原载荷重发。C 如确需新计划，须先确认原动作结果并关联原动作，不以新 action_id 掩盖未知。

## 3. Remember：正文保存、读取和清理

本章定义正文接口。正文读取与 Recall 共用；向量写入、核验和删除统一列在第 4 章。

### 3.1 BP2-01：正文写入

**调用：** `put_content(context, BP2ContentWriteInput) → BP2ContentMutationResult`。B 已完成授权并持久化写入意图，需要 P2 保存准确正文时调用。

| 请求字段 | 定义与约束 |
|---|---|
| `client_operation_ref`、`idempotency_key` | 原写入的稳定身份；首次回执丢失仍可查询 |
| `request_fingerprint` | 规范写入语义摘要；同键换载荷必须冲突 |
| `resource_ref`、`scope` | 获准资源和授权范围 |
| `target_object_ref?` | 已预分配的稳定目标；P2 分配时可空，但必须可恢复查询 |
| `payload`、`expected_hash`、`expected_bytes` | 实际字节、可信全文摘要和真实长度 |
| `media_type`、`encoding`、`precondition_ref?` | 媒体类型、字节编码及防覆盖/版本条件 |

**共用变更响应 BP2ContentMutationResult：** `operation_kind=put/delete`、`client_operation_ref`、`idempotency_key`、`request_fingerprint?`、`provider_operation_ref?`、`operation_status`、`raw_status?`、`content_state?`、`resubmit_assessment?`、`delete_verification?`、`evidence[]`。

`operation_status` 为 `accepted / running / completed / rejected / failed / not_found / unknown`。`content_state` 使用下表；put 时 `delete_verification=null`。

| 正文对象结构 | 字段 |
|---|---|
| BP2ContentLocator | `provider_ref, resource_ref, object_ref, object_version?, generation?, address_contract_ref` |
| BP2ContentObservation | `locator, object_present?, actual_bytes?, actual_hash?, media_type?, encoding?, etag?, durable?, readable?, observed_at?, binding_evidence[], completion_evidence[]` |

**完成标准：** 原操作与准确对象相符，实际同版本字节/摘要/长度匹配，并满足约定的持久性和可读性。P2 回显 expected_hash 或返回 completed 均不足以单独确认完成。随后由 B 决定主事实提交，不由 P2 设置 Memory 状态。

**大对象分支：** 仅启用分片上传时使用创建上传、上传分片、列出分片、完成上传、终止上传能力。固定原写入身份与 upload_id，逐片核对，再验证最终全文。Complete 回执丢失不能新建上传；Abort 回执不单独证明全部残留已清除。

### 3.2 BP2-02：正文元数据与准确范围读取

**调用：** 按需 `head_content`，再按需要 `get_content / get_content_range`。已有充分元数据时可跳过 HEAD。

| 结构 | 逻辑字段 |
|---|---|
| BP2ContentMetadataInput | `locator, scope, approved_range, version_condition_ref?` |
| BP2ContentMetadataResult | `status, content_state?, evidence[]`；status 为 ok/not_found/version_mismatch/unknown/failed |
| BP2ContentReadInput | `content_binding_ref, locator, scope, read_purpose, approved_range, expected_hash, version_condition_ref?, max_response_bytes` |
| BP2ContentReadResult | `status, locator, data?, returned_range?, returned_bytes, coverage, content_state?, readable?, read_path, read_source_ref?, evidence[]` |

`approved_range` 为 `[start,end)`；`coverage` 为 complete/partial/unavailable；读取 status 可为 ok/partial/not_found/version_mismatch/unknown/failed；`read_path` 为 canonical/prewarm/unknown。expected_hash 可由调用方持有，不强制原 RPC 接收。

**完成标准：** 获准版本、实际返回范围、长度、编码、实际摘要均一致。HEAD 查 v3 而 GET 返回 v4 必须拒绝；整对象摘要不能伪装成任意片段摘要；partial 字节不得作为完整正文交付。物理 not_found 不自动改写 B 的记忆生命周期。

### 3.3 BP2-03：查询原正文操作

**调用：** `query_content_operation(context, BP2ContentOperationQueryInput) → BP2ContentMutationResult`。用于异步写入、删除等待、回执丢失、超时和重启恢复。

| 请求字段 | 要求 |
|---|---|
| `operation_kind` | 原动作 put/delete |
| `resource_ref`、`scope` | 原资源和本次获准查询范围 |
| `client_operation_ref`、`idempotency_key`、`request_fingerprint` | 原操作身份及原载荷语义，不按当前内容重算 |
| `provider_operation_ref?`、`known_locator?` | 已知则提供；首次回执丢失允许为空 |

返回第 3.1 节共用变更响应。应能区分已写但丢回执、仍执行、明确未执行、拒绝/失败及未知。若返回安全重发判断，须满足第 2.4 节，不能因一次 404 重新写入。

### 3.4 BP2-04：加工产物持久化

复用 BP2-01 请求/响应。B 固定加工输入、输出字节、摘要和新产物身份，P2 保存输出对象并证明持久、可读和完整。

**P2 不判断摘要、压缩或抽取是否语义正确。** B 同时检查质量结果和存储结果后才发布该表示。质量失败则按业务策略保留/回退原文；写入未知则查原操作，不能不断生成新产物掩盖旧写入未知。

### 3.5 BP2-07：正文与加工产物清理

**正文调用：** `delete_content(context, BP2ContentDeleteInput) → BP2ContentMutationResult`。B 先完成失效屏障、准确范围、共享引用和保留限制检查。向量删除走 RP2-09。

| 请求字段 | 定义 |
|---|---|
| `client_operation_ref, idempotency_key, request_fingerprint` | 稳定删除身份与原删除语义，和写入身份区分 |
| `locator, scope` | 获准删除的准确版本和范围 |
| `required_completion` | logical_invisible / current_version_removed / physical_erased |
| `precondition_ref?`、`related_write_refs[]` | 物理版本/代次条件及已知历史在途写关联 |
| `cleanup_authorization_ref` | B 已完成范围、共享引用和保留检查的依据；不替代正式凭据 |

**删除核验 BP2DeleteVerification：** `locator, required_completion, confirmed_level?, object_present?, late_write_barrier_confirmed?, residual_refs[], verification_coverage, retention_constraint_ref?, observed_at?, evidence[]`。

**完成标准：** 实际确认层次满足原要求，目标/范围覆盖完整，残留和旧写屏障有据。业务屏障、逻辑不可见、当前版本删除、物理擦除分别记录。一次未限定版本的删除不能解释为全版本擦除；软删除不能解释为物理擦除；迟到写不能让旧内容重新出现。

**残留清单能力：** `inspect_inventory(context, BP2InventoryInput) → BP2InventoryResult`，可由分页查询或准确清单核验等价满足，不强制另建 RPC。

| 结构 | 字段 |
|---|---|
| BP2InventoryInput | `resource_ref, scope, inventory_kind, target_set_ref, cursor?, page_limit, snapshot_ref?` |
| BP2InventoryResult | `resource_ref, inventory_kind, entries[], coverage, next_cursor?, snapshot_ref?, watermark?, observed_at?, evidence[]` |
| InventoryEntry | `object_ref, object_version?, generation?, provider_operation_ref?, metadata_evidence_ref?` |

本节 inventory_kind 使用 objects/versions/uploads；向量残留核验见第 4.8 节。coverage 为整个获准 target_set 的 complete/partial/unavailable。空的一页不等于整个范围无残留；当前对象列表不等于历史版本、分片残留均已覆盖。

### 3.6 BP2-08：能力、健康、限额和恢复观察

**逻辑调用：** `describe_capabilities / observe_health`；可由公共观察接口和已确认运行契约组合提供，公共 Port 归 C。

| 结构 | 字段 |
|---|---|
| BP2CapabilityInput | `profile_ref, resource_ref, scope, required_capabilities[], model_contract_ref?` |
| BP2CapabilitySnapshot | `provider_ref, resource_ref, capability_version?, capabilities[], backend_health, observed_at?, fresh_until?, limits_ref?, consistency_profile_ref?, resource_observation_ref?, model_binding_ref?, recovery_observation_ref?, evidence[]` |
| CapabilityEntry | `name, support, contract_ref?`；support 为 supported/partial/unsupported/unknown |

启动、环境切换、首次使用某能力、观察过期和恢复后使用。需要说明大小/并发/超时限额、可见性、幂等保留、负查询最终性和恢复水位。必需能力未知或不支持时，不能将依赖它的路径标为可用。正文路径可用不代表向量或调度路径可用。

## 4. Recall / Embedding：检索与向量投影

本章集中列出向量搜索、写入、操作查询、目标核验和删除；正文读取复用第 3.2 节。BP2-05/06 及 BP2-07 的向量部分统一归入本章，原编号用于对照。Remember 仍负责批准版本、投影发布与删除资格。

### 4.1 RP2-01：向量检索 search

**调用：** `search(context, P2SearchInput) → P2SearchResult`。A 生成并检查 Query 向量后，搜索获准范围内的长期候选。

| 结构 | 字段 |
|---|---|
| P2SearchInput | `query_vector, usage=Query, model_binding, retrieval_space_ref, scope, memory_types[], occurred_after?, occurred_before?, top_k` |
| P2SearchResult | `retrieval_space_ref, requested_k, completion, hits[], partial_reason?, ranking_contract_ref, query_binding_evidence[], completion_evidence[]` |
| P2SearchHit | `projection_ref, provider_rank, raw_score?, model_version, projection_schema_version, identity?, source_evidence[]` |

memory_types 为长期 Episodic/Semantic；时间筛选采用含下界、不含上界；top_k > 0。completion 为 complete/partial/failed；partial 必须说明原因，即使 hits 为空。

**完成标准：** 请求和实际空间、模型、范围、K 一致，候选引用稳定，返回完成性可解释。P2 命中只提供候选；B 仍负责当前资格，A 仍须读取可信正文。租户隔离不能用“先检索越权候选、再本地过滤”替代。

### 4.2 RP2-02：复用公共正文读取 BP2-02

与 BP2-02 共用底层能力；A 根据 B 批准的目标读取。B/A 请求视图不同，不是两套相互独立的正文真相。

| 结构 | 字段 |
|---|---|
| P2ContentTarget | `content_ref, content_version, representation_id, representation_type, bucket, key` |
| P2ContentReadInput | `content, approved_range, expected_hash, version_condition_ref?, max_response_bytes` |
| P2ContentReadResult | `status, content, data?, returned_range?, returned_bytes, meta?, read_path, placement?, cache_trace?, evidence[]` |
| P2ContentMetadata | `content_ref, content_version, representation_id, object_size_bytes, content_encoding, etag?, checksum?, version_evidence[]` |

A 侧读取 status 为 ok/not_found/version_mismatch/failed；read_path 为 canonical/prewarm/unknown。成功必须具有真实字节、范围、同版本元数据和证据。

**完成标准：** 实际范围等于获准范围，长度匹配，版本与可信期望摘要一致，接收额度及期限满足。P2 部分返回或结果未知时，必须保留原始状态、已接收范围和原因；A 不将这些字节作为 ok 正文交付。

### 4.3 RP2-06 / BP2-05：写入向量 upsert

**调用：** `upsert(context, P2UpsertInput) → P2MutationResult`。B 批准片段和目标，A 生成真实 Passage 向量并固定请求后调用。

| 结构 | 字段 |
|---|---|
| P2UpsertInput | `target, provider_idempotency_key, request_fingerprint, payload, precondition_ref?` |
| P2ProjectionTarget | `tenant_id, provider_ref, retrieval_space_ref, identity, physical_target_ref?` |
| ProjectionIdentity | `memory_id, chunk_id, memory_version, model_version, projection_schema_version` |
| P2ProjectionPayload | `usage=Passage, vector, model_binding, source_hash, input_binding_digest, vector_hash, representation_id, content_ref, content_version, approved_range, metadata, metadata_hash` |
| P2ProjectionMetadata | `scope, memory_type, occurred_at?` |
| EmbeddingModelBinding | `model_id, model_version, dimension, dtype, embedding_schema_version, preprocessing_version, retrieval_space_ref, model_contract_ref` |

vector 必须是实际数值数组，不能发送本地 vector_ref 字符串充当向量。维度、数值、dtype、编码及摘要必须匹配。模型版本相同、维度相同仍不自动说明检索空间兼容。

**共用变更响应 P2MutationResult：** `operation_kind=upsert/delete, target, provider_idempotency_key, request_fingerprint?, provider_operation_ref?, operation_status, raw_status?, target_state?, resubmit_assessment?, evidence[]`。operation_status 使用第 3.1 节七类状态。

**完成标准：** 匹配准确目标与实际载荷，取得持久性和索引可查询证据。accepted 只代表受理；inserted 总数不能替代逐项绑定和完成证据。A 向 B 交付机制结果，B 执行完整集合的长期可用检查。

metadata_hash 对 scope、memory_type、occurred_at 的规范语义计算，未知维度保留 null。仅回显输入摘要不是实际存储核验。同一五元组原地重建需要明确的代际与旧写屏障契约；不能用更换幂等键绕过旧操作。

### 4.4 RP2-07 / BP2-06：查询原向量操作 query_operation

**调用：** `query_operation(context, P2OperationQueryInput) → P2MutationResult`。

| 请求字段 | 定义 |
|---|---|
| `target`、`operation_kind` | 原准确目标和 upsert/delete 动作 |
| `provider_operation_ref?` | 已拿到则提供；无回执时可空 |
| `provider_idempotency_key`、`request_fingerprint` | 原键、原载荷，不能重新生成 |

用于受理后跟踪、超时、回执丢失、重启和删除等待。返回第 4.3 节共用变更响应；安全重发依据采用第 2.4 节。查询不到记录不证明对象未写入，也不授权换键重写。

### 4.5 RP2-08 / BP2-06：准确目标核验 get_projection

**调用：** `get_projection(context, P2TargetQueryInput) → P2TargetState`。

| 结构 | 字段 |
|---|---|
| P2TargetQueryInput | `target, expected_request_fingerprint?, related_operation_ref?, include_payload` |
| P2TargetState | `target, object_present?, stored_request_fingerprint?, stored_payload?, durable?, index_queryable?, delete_confirmed?, late_write_barrier_confirmed?, binding_evidence[], completion_evidence[], observed_at?` |

**用途：** 查“这个准确对象实际是什么状态”，而 RP2-07 查“那次动作执行到哪里”。include_payload=true 时按契约读取实际载荷；也可由已确认等价证据证明存储绑定。

**完成标准：** 对象、租户/空间、业务与模型版本、实际载荷、持久性和查询性相符。不能拼接不同目标或互不相容时点的证据；ANN 命中/未命中不能替代准确目标核验。

### 4.6 RP2-09 / BP2-07：删除准确向量 delete_projection

**调用：** `delete_projection(context, P2DeleteInput) → P2MutationResult`。B 已批准失效/删除目标后执行。

| 请求字段 | 定义 |
|---|---|
| `target` | 获准删除的准确目标和五元组 |
| `provider_idempotency_key`、`request_fingerprint` | 固定删除身份，与 upsert 区分 |
| `precondition_ref?` | Provider 认可的版本/代际条件 |
| `related_upsert_keys[]` | 已知相关旧写入，不因列表为空推定不存在迟到写 |

返回第 4.3 节共用变更响应，并通过 RP2-07/08 核验。**完成标准：** 准确目标已退出查询且删除事实、旧写不会复活的屏障有据。删除数量或一次搜索无命中不能单独证明完成。

### 4.7 RP2-03 / RP2-04 / RP2-05：补充能力

| 编号 | 输入与输出 | 使用规则 |
|---|---|---|
| RP2-03 元数据核验 | MetadataInput：`content, approved_range, version_condition_ref?`；MetadataResult：`status, meta?, evidence[]` | 按需 head/checksum；可信映射或读取响应已覆盖时可跳过 |
| RP2-04 热副本读取 | CachedReadInput：`content_read, cache_read_ref, fallback_owner`；返回 ContentReadResult 及 CacheTrace | 可选尝试已有热副本；失败后按唯一 fallback_owner 回正式正文路径；不是触发物理迁移 |
| RP2-05 实际来源 | P2ReadPlacement：`actual_provider?, observed_tier?, placement_generation?, observed_at?, producing_action_id?, evidence[]` | 随读取提供归因证据，不强制新增查询 RPC；未知不能按计划位置代填 |

P2CacheTrace 字段：`cache_read_ref?, cache_outcome, fallback_performed?, final_read_path, diagnostic_code?, evidence[]`；cache_outcome 为 hit/miss/invalid/unavailable/unknown。在线热副本读取与 C 的后台 Prefetch 分开计费、归因和记录，不隐式生成 TierAction。

### 4.8 向量残留清单核验

复用第 3.5 节 `inspect_inventory` 的输入输出结构，`inventory_kind=projections`，目标集合限定为获准的向量投影范围。

## 5. Operate：状态、调度与效果核验

本章基于 [S1] Operate 章和 [S3]。C 的接口字段为已有逻辑语义，尚不能把表格直接当作已冻结报文。以下按适用场景携带公共 `request_id / trace_id / schema_version`；各接口原设计列出的请求字段保持原义。

### 5.1 CP2-01：GetPlacement — 查询当前实际放置

| 项目 | 内容 |
|---|---|
| 何时调用 | 计划前、提交前观察过期、收到成功反馈后、Unknown 恢复、释放前以及重启对账 |
| C 发送 | `memory_id, memory_version`（适用时），`representation_id`，已知的 `provider_ref, target_id, mapping_generation`，`request_id, trace_id` |
| P2 返回 | `observation_id, memory_id, memory_version, representation_id, provider_ref, provider_name, current_tier, mapping_generation, generation, target_generation, route_epoch, readable, serving_ready, replica_count, supported_operations, observed_at, observation_source, state_version, error_code, evidence`；按场景保留适用性 |
| 完成标准 | 对应准确对象，真实层级、版本、路由、可读性和新鲜度可核对；不能只返回期望层级 |

current_tier 是按 P3 定义的热/温/冷逻辑层级；provider_name、物理对象和代次提供支撑证据。不能把 Redis、Ceph 或磁盘名称直接当业务层级，也不能由 C 自己填写当前事实。

### 5.2 CP2-02：GetResourceState — 查询资源和调度准入

| 项目 | 内容 |
|---|---|
| C 发送 | `resource_scope_id, provider_name`（适用时），`request_id, trace_id` |
| P2 返回：范围与健康 | `resource_scope_id, provider_name, state_version, observed_at, freshness, backend_health` |
| P2 返回：容量与预算 | `total_capacity_bytes, used_capacity_bytes, available_capacity_bytes, pressure_ratio, working_reserved_capacity_bytes, prewarm_budget_bytes, prewarm_used_bytes, pin_budget_bytes, pin_used_bytes` |
| P2 返回：并发与性能 | `active_migration_count, max_concurrent_migration, migration_bandwidth_bytes_per_sec, migration_bandwidth_budget_bytes_per_sec, read_latency_p99_ms, write_latency_p99_ms` |
| 完成标准 | 能解释资源范围、数据新鲜度、当前压力及在线保留预算；观察过期/未知或后端不可用时，不提交新的非保持动作 |

C 不从“已提交多少动作”反推真实资源占用。预算和新鲜度阈值属于运行契约，本文不另造数值。

### 5.3 CP2-03：ResolveActuationTarget — 解析不透明执行目标

| 项目 | 内容 |
|---|---|
| C 发送 | `memory_id, memory_version`（适用时），`representation_id, desired_tier, plan_id, trace_id`；已知 mapping_generation，有约束时 expected_route_epoch/valid_until |
| 复用旧目标时 | 携带此前 target_generation 或等价约束；首次解析不要求 C 预先提供 P2 才能生成的代次 |
| P2 返回 | `target_id, representation_id, provider_ref, provider_name, source_tier, supported_operations, mapping_generation, generation, target_generation, route_epoch, resolved_at, valid_until, error_code, evidence` |
| 完成标准 | 对象映射、版本和有效期一致，支持拟执行动作；失配或过期明确拒绝，不能静默换对象 |

C 只保存和转发 target_id，不解析 Provider 路径，不将 provider_ref 直接充当 target_id。解析成功不代表物理动作已完成。

### 5.4 CP2-04：SubmitTierAction — 提交抽象调度动作

| 项目 | 内容 |
|---|---|
| 调用前提 | 放置、资源、目标解析和冲突检查通过，原 action_id 与幂等键已固定 |
| C 发送：身份 | `memory_id, memory_version`（适用时），`action_id, idempotency_key, plan_id, representation_id, provider_ref, actuation_target` |
| C 发送：目标与约束 | `action_type, source_tier, desired_tier, target_generation, expected_generation, policy_version`；适用时 mapping_generation/expected_route_epoch/priority/deadline；request_id/trace_id |
| P2 返回 | `action_id, provider_task_id, provider_status, effect_status, side_effect, failure_stage, observed_at, error_code, retryable, evidence` |
| 完成标准 | 同一动作/幂等键重复提交只返回原事实；同键异载荷冲突；ACCEPTED/RUNNING 不解释为已达到目标层级 |

### 5.5 CP2-05：QueryActionStatus — 查询原动作

| 项目 | 内容 |
|---|---|
| 何时调用 | 反馈丢失、请求超时、P2/C 重启、Provider Unknown、正常进度跟踪 |
| C 发送 | `action_id, request_id, trace_id`；已知 provider_task_id，适用时 idempotency_key |
| P2 返回：关联 | `action_id, provider_task_id, memory_id, memory_version, representation_id, provider_ref` |
| P2 返回：状态与代次 | `provider_status, actual_tier, mapping_generation, target_generation, pre_generation, post_generation, expected_route_epoch, route_epoch, migration_stage` |
| P2 返回：效果与证据 | `effect_status, side_effect, failure_stage, readable, serving_ready, replica_count, completion_time, error_code, retryable, observed_at, evidence`；按实际阶段返回适用事实 |
| 完成标准 | 能区分仍执行、明确成功、明确失败、明确未执行和未知；“任务结束”不替代当前 Placement |

未知时先查原动作并对账。失败要说明已有副作用；不能把失败等同于“什么也没发生”。最终成功还须 CP2-01 核验。

### 5.6 CP2-06：WatchExecutionFeedback — 可恢复执行反馈

| 项目 | 内容 |
|---|---|
| C 提供 | `action_id, request_id, trace_id`；断点恢复时 feedback_cursor，适用时 consumer_id |
| P2 返回 | `feedback_id`，原动作/任务/对象关联，CP2-05 中适用的状态、层级、版本、路由、阶段、副作用、错误与证据；适用时 `next_feedback_cursor` |
| 实现方式 | 回调、事件流或轮询均可；MVP 可由 CP2-05 可恢复轮询提供等价能力 |
| 完成标准 | 重复反馈可去重；丢反馈、乱序及重启仍可查原动作；旧代次不能覆盖新状态；成功反馈后再次读取 Placement |

### 5.7 CP2-07：物理执行能力

该项是 P2 / Provider 的执行承接要求，不要求提供一个名为 CP2-07 的 RPC。

| 阶段 | 执行结果 | C 必须能核对什么 |
|---|---|---|
| Copy | 建立目标数据/副本 | 目标是否建立、版本是否一致 |
| Verify | 校验完整性和可读性 | 校验依据、readable、失败原因 |
| Cutover | 按条件切换服务路由 | 真实 route_epoch 和 serving_ready |
| Reclaim | 安全回收旧副本 | 副作用、剩余副本、权威副本可读性 |

不同动作不一定经过全部阶段。Prefetch 默认只建立同版本副本，不切路由、不删源副本；Demote/Release/Reclaim 必须先确认安全副本、版本和路由约束，且不存在有效 Pin 或冲突动作。Copy/Verify 不能冒充 Cutover；C 不自行递增 Provider 代次。

### 5.8 CP2-08：冻结、解冻、取消控制

| 能力 | 需要明确的输入/关联 | 需要明确的输出与保证 |
|---|---|---|
| Freeze | `action_id, provider_ref, generation` 及实际冻结目标 | freeze_state；冻结哪一层、从哪个阶段生效 |
| Unfreeze | 原 action_id 与冻结关联 | unfreeze_result、当前状态；成功/失败/取消/重启后的恢复规则 |
| Cancel | `action_id, provider_task_id` | cancel_result、side_effect；哪些物理阶段可取消，是否还可能迟到生效 |

这些是已有语义要求，实际签名和支持范围尚需映射。不能要求所有阶段都支持 Cancel；不支持必须明确返回。取消受理不能证明无副作用或旧写已排空。

## 6. 接口交付与通过标准

### 6.1 每项接口需要交付什么

| 交付内容 | 要求 |
|---|---|
| 可调用定义 | 逻辑编号对应的方法、契约版本、请求/响应字段类型、可空性及调用方式 |
| 请求与响应样例 | 正常、空结果、部分、拒绝、失败、未知和版本冲突；适用场景不得省略 |
| 身份与目标绑定 | 租户/授权范围、对象或向量目标、业务版本、物理版本及操作身份如何关联 |
| 完成保证 | 持久化、可读、可搜索、删除、路由切换、回收分别需要什么证据 |
| 异常与恢复 | 超时/取消/重启、原操作查询、幂等作用域和保留期、负查询最终性、允许重发的条件 |
| 运行约束 | 请求大小、并发、限流、deadline、可见性和状态保留窗口、健康观察有效期 |
| 支持边界 | 条件读写、分片、热副本、反馈形式、各阶段取消等能力的适用范围与不支持时的明确结果 |

接口样例使用脱敏数据。运行数值应按实际交付契约提供，不能让调用方自行猜测。操作记录保留窗口、查询可见性窗口和幂等有效期必须协调，保证回执丢失后仍有可靠恢复入口。

### 6.2 接口行为通过标准

以下是接口设计的验证要求，不是已执行的测试结果，也不代替完整测试用例。

| 行为 | 通过标准 | 关联需求 |
|---|---|---|
| 正文写入、读回 | 准确版本的字节、摘要、长度匹配；持久与可读事实可核对 | BP2-01/02/04、RP2-02 |
| 回执丢失 | 无远端回执 ID 时仍能按原调用方身份查到原动作，不重复写入 | BP2-03、RP2-07、CP2-05 |
| 重复与冲突请求 | 同键同载荷重放原事实；同键异载荷冲突 | BP2-01/03、RP2-06/07、CP2-04/05 |
| 暂时查不到 | 区分查询窗口内未知和有据未执行；无依据不重做 | BP2-03、RP2-07、CP2-05 |
| 范围读取与并发换版 | 返回批准范围的准确字节；换版、截断、摘要不符均不可作为成功正文 | BP2-02、RP2-02/03 |
| 多片段写入与索引延迟 | 返回逐项关联与状态，部分成功、索引未就绪不会伪装成全部完成 | BP2-05/06、RP2-06—08 |
| 搜索完成性 | 完整空结果、部分结果和失败可区分；模型、范围与排序来源明确 | RP2-01 |
| 删除与迟到旧写 | 删除层次、残留范围和旧写屏障可核验，旧内容不会重新出现 | BP2-07、RP2-07—09 |
| 调度反馈丢失/乱序/重启 | 原动作可恢复查询，重复反馈可去重，旧代次不覆盖新状态 | CP2-04—06 |
| 迁移与释放 | 实际层级、版本、路由和可读性满足目标；安全副本确认前不释放源副本 | CP2-01/05/07/08 |
| 资源无效或能力不支持 | 明确错误、适用范围和观察时间，不返回伪成功 | BP2-08、CP2-02/08 |
| 权限与版本冲突 | 拒绝越权和失配目标，不扩大范围、不换用其他版本继续执行 | 全部适用接口 |

### 6.3 核心、共用和条件能力

- **正文闭环需要：** 写入、准确读取/核验、原操作查询、删除核验，以及适用的能力/健康观察。
- **向量闭环需要：** 搜索、写入、原操作查询、准确目标核验和删除；正文读取复用公共能力。
- **调度闭环需要：** 实际放置、资源、目标解析、动作提交、原动作查询、反馈和真实执行效果；反馈可由可靠轮询满足。
- **条件启用：** 大对象分片上传、在线热副本读取、独立事件流。冻结/解冻/取消按动作阶段声明支持范围，不能省略不支持时的返回规则。
- **共用但必须有完整语义：** 加工产物复用正文写入；B/A 复用正文读取；反馈可合并到动作查询；残留核验可由分页枚举或准确清单等价满足。
