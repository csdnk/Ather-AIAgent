# REVIEW-006 真实 P2 通过能力明确的适配契约接入

- 状态：Proposed，待联合评审
- 日期：2026-09-18
- 需求：FR01、FR07、FR08、FR14、FR15
- 对应演示：S07
- 来源：S3 §4–5；S4 §3–8；S5 RD-08/09；S6
- 评审责任：见文末责任角色；具体姓名与评审结论尚未指定

本记录为本次评审包内的建议，不覆盖已有 ADR，也不将建议标记为已获批准。

## 背景与问题

P3 所需的精确版本、租户筛选和物理结果证据，不能仅凭 P2 RPC 名称判定已经满足。逻辑 DTO 和底层 proto 不是同一份协议。

## 建议决策

以能力端口隔离业务语义与 Provider 协议：对象保存/准确读取、向量写入/筛选检索、图关联查询、执行目标解析及状态核对。每项端口给出已有 RPC、缺口、降级或阻断条件。保留 memory version、mapping generation、target generation、route epoch 各自含义，禁止合成一个版本号。

## 方案比较

| 方案 | 取舍依据 |
| --- | --- |
| 直接把 P3 字段塞入现有 RPC 并宣称已支持 | 无法保证隔离、版本和原子性语义。 |
| P3 直接读取引擎内部库 | 形成隐式耦合并越过责任边界。 |
| 显式 Adapter 和能力验证 | 便于并行开发与真实替换；本次建议。 |

## 代价与影响

适配层与契约样例需要持续维护。Mock 聚合响应不是当前 gRPC wire schema；接口能力不满足时须阻断相关正式路径。P2 自身的三引擎验收不能由 P3 消费演示替代。

## 验证方式

同一版本的正文、向量引用、来源关系可以关联；模拟与真实 Provider 必须运行等价契约用例。精确读取、隔离或路由证据缺失时，不给正式通过结论。

## 待确认事项与责任

P2 与 A/B/C Owner 逐项确认能力表、真实样例、错误码及版本兼容策略。
