[主讲 PPT](P3_业务流程与落地方案_V4.3.pptx) · [逐页讲稿](逐页讲稿与会议记录.md)

本方案面向甲方说明最终业务目标与实施路径，不作为完成状态或验收记录。MVP 以 2026-12-01 为目标，细分节点为建议，真实 P2 以 10/10 可接入为前提。

## 项目目标：跨会话使用当前有效的记忆

服务应用、Agent 和 P4，连接分散在对话、任务和文档中的信息

| 项目 | 说明 |
| --- | --- |
| 持续可用 | 换一次会话，仍能找到相关记忆和原始来源 |
| 保持当前有效 | 更正后用新版本，删除或撤权按相应范围停止交付 |
| 结果可以追溯 | 交付内容有来源，未就绪或读取失败有明确状态 |

P3 的价值是让已经产生的信息可以在后续任务里持续使用。它不仅要存得下来，还要区分当前有效的版本、允许使用的范围，并说明材料来自哪里。应用或 Agent 用 P3 返回的材料完成回答和任务。项目目标包括内部维护与恢复，使服务在任务重试和进程重启后仍能继续工作。

## 业务场景：预算信息的一次完整生命周期

以“预算 20 万，后来更正为 15 万”为例

1. **保存信息**：记录预算 20 万，保留来源与权限。
2. **再次使用**：换一次会话，仍可找到相关材料。
3. **更正内容**：预算改为 15 万，后续使用新版本。
4. **删除或撤权**：删除后停止交付并清理，撤权仅限制被撤权方。

| 项目 | 说明 |
| --- | --- |
| 用户看到的结果 | 保存有状态，召回有来源，更正和删除会影响后续使用 |
| 系统持续完成的工作 | 后台加工、版本维护、检索准备、访问调度与失败恢复 |

用户第一次保存预算 20 万。适用的当前任务内容可以先使用，后台继续准备长期检索。跨会话请求时，系统取回相关且有效的材料。预算更正为 15 万后，旧版本不能继续作为当前预算交付。删除后，新查询和旧结果重取均不再交付相关正文，后台继续清理。撤权后，仅停止向被撤权方交付，其他有效授权仍可使用。外部身份撤销按双方约定的生效时间验证。物理清理可以在后台推进，但停止交付不能等待全部清理结束。

## 业务框架：存储与召回由内部维护支撑

按业务责任分工，共同组成一套记忆服务

应用决定何时保存信息、何时请求记忆。Remember 负责来源、版本和内容的维护，Recall 负责为一次请求组织可用材料。存储变化和实际使用记录交给内部 Operate，结合当前状态调整访问准备并核对执行结果。统一身份、任务和恢复机制支撑三条流程。P2 为各流程提供实际存取和约定的控制能力，不能替代 P3 判断一条事实是否当前有效。

## 记忆形成：先可靠保存，再准备长期使用

保存、当前任务可用、长期检索就绪分别表达

保存时检查身份、来源和重复请求，确认原始内容可靠保存。适用的当前任务记忆可以先用于当前工作。需要长期复用的内容，在后台获取固定版本、解析分块，并按需要抽取和压缩。模型生成候选后还要审核来源与内容，写入检索表示并核验，才能宣布长期检索就绪。不是每条记忆都必须经过全部加工步骤。任务可恢复，但旧版本或已删除内容不能因为迟到的后台结果重新生效。

## 记忆召回：交付能使用、可追溯的材料

找到相似内容之后，还要核对版本、权限与来源

1. **明确请求范围**：根据任务、身份，和指定来源选路。
2. **寻找相关记忆**：检索当前记忆，或长期记忆。
3. **核对有效性**：读取准确正文，检查版本与权限。
4. **组织并交付**：保留必要上下文，附来源和结果状态。

| 项目 | 说明 |
| --- | --- |
| 预算更正后 | 新请求使用 15 万，旧索引命中仍需重新核对 |
| 某个来源不可用 | 说明缺失或受限的范围，避免把读取失败当作没有内容 |

先判断要查哪些来源以及当前身份是否允许使用。检索获得候选之后，需要去掉不适用的版本、读取准确正文，再组织成有来源的材料。仍然有效但彼此冲突的内容要保留必要限定，不随意删去否定、数字和条件来压缩长度。交付前再核验一次，回应处理中发生的删除和撤权。返回的结果区分可用、正常空以及来源失败等情况，上层据此继续处理。

## 内部运行：根据使用情况持续调整访问准备

让常用内容更易访问，同时维护版本、权限和恢复能力

1. **观察业务变化**：保存、读取记录，及当前资源状态。
2. **形成调整方案**：按规则判断，保持或调整位置。
3. **执行并跟踪**：保留原动作身份，检查目标与进度。
4. **核对实际结果**：确认内容可读，再更新读取位置。

| 项目 | 说明 |
| --- | --- |
| 执行成功但回执丢失 | 查询原动作和实际结果，避免重复执行 |
| 调整访问层级 | 改变存取准备，不改变事实内容和使用权限 |

Operate 是内部持续运行机制。它依据存储与读取历史、当前有效性和资源情况决定访问准备。一次操作可能耗时或遇到超时，所以发起前保留动作身份，执行后核对目标内容和可读性，再交接读取地址。热、温、冷描述访问准备，与工作记忆、经历记忆和语义记忆的业务分类不同。MVP 覆盖基础规则与约定动作，具体存储介质和执行范围在联调基线中明确。

## P2 协作：业务处理与底层能力怎样衔接

每一项合作都明确谁负责、交付什么、怎样确认结果

| 业务需要 | P3 负责 | P2 提供及共同核对 |
| --- | --- | --- |
| 保存与读取 | 维护来源、版本和使用资格 | 实际保存和读取正文<br>内容与版本对应一致 |
| 长期记忆检索 | 组织记忆、审核候选并交付材料 | 写入、检索和清理<br>确认可检索及结果可读取 |
| 关系与冲突 | 解释事实之间的关系与限定 | 提供约定的关系查询能力<br>对象、关系和版本可以核对 |
| 访问调度 | 决定动作并跟踪、核验结果 | 提供约定的控制与执行反馈<br>实际效果、目标可读性可核对 |

甲方需要看到的是各项业务如何依赖 P2、责任如何分开。P3 不把底层成功回执直接视为业务完成，需要检查正文、检索可用性或实际动作结果。P2 团队负责其服务和环境，P3 开发负责适配，测试与对接人员负责样例和联调记录。关系远程映射、原操作查询及真实执行证据要逐项确认，不能假设所有需求已经由现有协议满足。段控制成功本身不证明物理数据迁移完成。

## P2 Mock 具体怎么模拟

当前用三类替身分别支撑本地服务、契约测试和独立调度演示。

| 模拟部分 | 当前实现 | 验证方法 |
| --- | --- | --- |
| 正文存取（本地服务） | SQLite 保存正文和校验值，按编号读取，支持分段读和删除 | 重新建立实例后读回原文，同编号禁止覆盖不同正文 |
| 向量状态（契约测试） | 保存向量、目标版本、幂等键和操作记录，脚本控制索引可见 | 核对已接收与可检索状态，删除后迟到写入不能恢复数据 |
| 分层调度（独立演示） | 内存保存正文、基础层级、热副本、容量和动作，脚本推进执行 | 核对副本内容和校验值，注入容量不足、版本变化、执行失败等情况 |

故障示例：向量模拟器先把向量与操作记录写入数据库，再主动抛出超时，模拟回执丢失。测试重新建立模拟器，使用原幂等键查回同一操作。重复提交返回同一操作编号。脚本明确开放索引可见后，再核对状态与保存的数据。

目前尚未合成覆盖全部 P2 接口的统一 Mock 服务。向量状态模拟器不计算实际相似度，Operate 独立演示不执行真实介质迁移。完整跨接口故障场景及真实 P2 集成仍按后续计划实施。

## 方案选择：按三条流程参考开源框架

### Remember：参考 LangMem 提取候选事实

重点借鉴后台提取能力，正式记忆仍由 P3 审核和提交。

| 项目 | 选择与理由 |
| --- | --- |
| 参考了什么 | 结构化候选提取、自定义输出字段、已有记忆输入。<br>把模型结果组织成候选，交给 P3 审核。 |
| 为什么参考 | LangMem Core 可以独立使用并配合现有存储，<br>便于保留 P2、版本管理和权限规则。 |
| 与其他方案比较 | Mem0 整套接入需重接其存储和更新流程；<br>全部自行实现提取，又会重复维护模型调用与输出约束。 |
| 本项目怎样采用 | 只接入候选提取，P3 核对原文证据后再保存。<br>正式更正、删除、版本和任务提交由 P3 管理。 |

官方入口：https://github.com/langchain-ai/langmem

### Recall：参考 LlamaIndex 拆分检索步骤

借鉴检索、融合和后处理分层，交付带来源的记忆材料。

| 项目 | 选择与理由 |
| --- | --- |
| 参考了什么 | 检索器拆分不同来源，融合器汇总候选，<br>后处理器组织过滤和排序，便于逐步组合。 |
| 为什么参考 | 这些模块与 P3 的召回步骤直接对应，<br>便于独立测试、替换检索来源和增加重排。 |
| 与其他方案比较 | Haystack 整体接管需重接 P3 的任务和失败处理；<br>当前已有召回分层，再增加一套流水线的收益有限。 |
| 本项目怎样采用 | 参考分层思路，由 P3 实现召回流程与候选融合。<br>来源状态、版本权限、冲突处理和上下文预算由 P3 核对。 |

官方入口：https://github.com/run-llama/llama_index

### Operate：参考 Controller 持续核对状态

借鉴 Kubernetes Controller 模式，由 P3 实现记忆调度控制器。

| 项目 | 选择与理由 |
| --- | --- |
| 参考了什么 | 事件触发后重新读取当前状态，比较实际与期望，<br>再执行必要动作，并重新观察结果。 |
| 为什么参考 | 冷热状态会变化，也会出现重复事件或回执丢失。<br>反复核对当前状态，便于恢复并避免重复执行。 |
| 与其他方案比较 | 定时任务或队列仍需补上状态判断和效果核对；<br>Temporal 适合复杂长流程，本期引入会增加服务与迁移。 |
| 本项目怎样采用 | 用 Python 实现控制循环，保留动作编号、查询与核验。<br>不直接引入 Go 控制器库，也不要求为记忆建设 K8s 集群。 |

官方入口：https://github.com/kubernetes-sigs/controller-runtime

以上比较针对 P3 的职责、存储和任务边界，不代表已完成统一性能排名。LangMem 接入提取适配，LlamaIndex 和 Controller 主要提供设计参考。

## 落地路径：每个阶段形成可检查的成果

需求、设计、实现、验证和交付衔接为同一条工作链

1. **明确业务**：场景与范围，完成条件。
2. **形成设计**：流程与责任，依赖与接口约定。
3. **实现和验证**：模块实现，持续业务回归。
4. **联调和交付**：真实依赖验证，验收、上线、交接。

| 项目 | 说明 |
| --- | --- |
| 开发怎样组织 | 按存储、召回、内部运行分工，统一身份、任务和恢复规则 |
| 测试何时参与 | 从业务规则阶段参与，随实现同步准备数据与检查方法 |

想法首先要变成可检验的业务规则，例如更正后应该返回哪个预算，删除后哪些路径必须停止交付。规则转成流程与责任边界，再拆成模块工作。测试从定义业务时开始，随着实现同步编写检查和准备环境。真实依赖联调逐步扩大范围，完整系统通过验收之后才发布。每次修复都回到相同的业务预期检查，避免局部修改破坏完整流程。

## 用例设计：把业务规则拆成可验证条件

每条用例关联需求和流程节点，只验证一个明确目标，逐步写出可观察的预期。

| 设计方法 | P3 中怎样选测试数据 | 必须检查的结果 |
| --- | --- | --- |
| 等价类 | 有效与无效输入<br>有权限与无权限用户 | 允许请求能完成<br>拒绝请求不改数据、不泄露正文 |
| 边界值 | 内容长度、预算、容量限制<br>分别取低于、等于和高于边界 | 边界内行为正确<br>超限按规则拒绝或降级 |
| 状态转换 | 已保存、就绪、更正、删除<br>分别在处理前和处理中切换 | 新版本可用<br>旧版本和迟到结果不能重新生效 |
| 决策表 | 组合权限、当前版本<br>正文可读性三项条件 | 仅符合全部条件的正文可交付<br>无法核实时明确报告原因 |
| 故障注入 | 超时、丢响应、重复事件<br>任务执行中重启 | 结果不假报成功、动作不重复<br>恢复后数据与状态一致 |

核心必测：保存、召回、更正、删除、隔离和恢复。数值边界从批准的配置取值。

测试设计采用常见的等价类、边界值、状态转换、决策表和故障注入方法。先从 PRD 和流程规则列测试点，再给每个测试点分配用例编号、负责人、优先级和适用环境。正常场景覆盖保存至跨会话召回的完整链路。边界用例按批准的配置选取边界前、边界上、边界后的值，不能临时编造产品限制。权限、版本、正文可读性采用决策表组合，覆盖允许、明确排除和无法核实。更正、删除、撤权与正在运行的任务分别拆成独立用例。高风险数据与安全用例优先，并在每轮候选回归执行。覆盖表必须能从需求追溯到用例及最新执行记录，阻塞和未执行项单独列出。本次不宣称通过某项标准认证。

用例设计与执行结果分开保存。一条用例对应一个可判断的目标，每个步骤分别填写操作、输入、预期响应、持久结果及证据来源。测试人员不能以当前代码输出代替批准的业务规则。

| 字段 | 填写要求 |
| --- | --- |
| 用例编号、标题、用例版本 | 编号唯一，标题包含触发条件和结果。修改预期时更新用例版本并重新评审 |
| 关联需求与流程 | 标明 PRD/设计版本、具体规则、Remember/Recall/Operate 节点，关联既有 TC 时保留原编号 |
| 层级、类型、优先级 | 单元、契约、服务集成、真实联调、系统或 UAT；正常、异常、边界或安全；区分核心必测和一般分支 |

## 没有 P2 时，测试怎样用 Mock 执行

测试人员准备固定数据和故障时序，脚本控制替身，再检查真实产生的数据与状态。

| 模拟对象 | 测试怎样操作 | 用什么结果判断 |
| --- | --- | --- |
| 正文存储 | 把原文写入独立 SQLite<br>重建实例后读回<br>切换为不可用后再次读取 | 正文、版本与指纹一致<br>重启后仍能读取<br>依赖不可用时明确失败 |
| 向量状态 | 写入向量与操作记录<br>先保持不可检索，再开放可见<br>注入“已写入但响应超时” | 受理和检索就绪分别核对<br>查回原操作，重试不重复<br>删除后迟到写入不能复活 |
| 调度动作 | 设置对象层级和剩余容量<br>显式推进动作，注入丢响应<br>查询原动作并核对对象 | 容量限制生效<br>动作不重复<br>实际效果与完成状态一致 |

**接入真实 P2 后：** 重跑同一业务用例，再测真实检索质量、权限、存储和故障恢复。

这三类替身分别使用。模拟状态通过，不等于真实 P2 联调或性能通过。

目前三类替身分别使用，不是一个统一的完整 P2 服务。正文使用 Remember 的 SQLite 实现保存独立数据，验证对象精确读取、持久化和不可用情况。向量模拟器持久记录目标、向量与原操作，测试脚本显式控制可检索状态，并可在提交后抛出超时模拟丢回执。测试需要检查记录和最终状态，不从返回码推断完成。Operate 独立演示替身在内存中管理对象、容量、动作，推进动作才改变效果，查询本身不推进状态。开发提供可重置的夹具、故障开关与观察入口，测试人员按用例组织数据并调用，不能直接把期待答案写入返回值后就判定系统通过。现有替身不能证明真实相似度检索、P2 持久性、权限集成或真实性能。真实 P2 到位后按相同用例编号与业务预期重跑，使用新的环境与执行编号。操作入口可以由各环境的适配驱动映射，不能为迁就真实结果改变预期。

## 执行与复测：每次失败都回到同一条用例

建议执行节奏：每次提交做自测与冒烟，每日构建做回归，候选版本做完整验证。

| 执行环节 | 工作 |
| --- | --- |
| 准备 | 固定版本、环境<br>装入隔离数据 |
| 执行 | 按编号步骤操作<br>按状态等待完成 |
| 判定 | 逐步对比预期<br>保存实际结果 |
| 修复 | 失败时登记缺陷<br>开发提交修复 |
| 复测 | 原用例再次执行<br>回归受影响流程 |
| 自动化怎样落地 | 每条脚本对应一个用例编号，使用固定夹具，断言响应及持久结果，运行后复位。 |
| 每次执行留下什么 | 执行编号、版本、环境、实际结果、证据编号、缺陷编号。失败记录保留。 |
| 缺陷怎样关闭 | 测试人员复测原场景及受影响链路，通过后关闭。阻塞、跳过和未执行单独统计。 |

同一用例可以执行多次，每次新增记录。开发标记“已修复”后仍要由测试复测。

建议在现有 pytest 基础上组织测试脚本和用例编号映射，不重新建立与业务无关的一套目录。开发负责模块级自测与必要的可观察入口，三位测试负责人维护业务自动化脚本、数据及人工执行记录，开发协助复杂故障夹具。测试实现包含准备环境、装入数据、执行操作、等待指定状态、核对响应与持久业务结果、清理数据。每次提交运行相关单元自测及核心冒烟，每日构建运行当时环境已具备的自动回归，候选版本运行范围内完整套件、真实联调及质量运行测试。环境不具备的用例明确记阻塞，不计通过。执行结论采用未执行、通过、失败、阻塞、不适用，不适用要写范围依据。缺陷记录包含关联需求和用例、版本与环境、复现步骤、预期与实际、影响、证据、负责人及修复版本。修复后由测试人员执行原用例，并回归受影响的上下游流程。版本变动后旧结果不自动继承。用例作者及测试负责人给出测试结论，陈凯组织阶段验收，业务签收另行记录。

## 系统测试：质量、性能与恢复怎样测

固定数据、模型、负载和机器条件，用可重复的测量支撑验收。

| 测试项与牵头 | 具体实施方法 | 输出证据 |
| --- | --- | --- |
| 记忆质量<br>赵旭东、肖宇 | 准备有标准答案的独立样本，保留数字、否定和来源<br>分别检查提取保真、召回相关性与版本正确性 | 逐条结果与错误样本<br>固定数据集的质量报告 |
| 性能与并发<br>肖宇牵头 | 固定规模、并发和输入长度，逐档增加负载<br>同时运行后台任务，分别测保存与完整召回 | 吞吐、延迟分位数<br>错误率与资源占用 |
| 长稳与故障<br>谭旭梁牵头 | 最终候选连续运行至少 24 小时<br>注入重启、依赖中断和重复事件，核对恢复后状态 | 运行曲线、恢复时间<br>一致性与重复动作检查 |
| 部署与恢复<br>谭旭梁牵头 | 按交付手册部署，演练备份恢复与回滚<br>恢复后重跑核心业务用例并核对数据 | 部署和演练记录<br>恢复后的业务回归结果 |

专项牵头为建议，三流程及运行人员配合。按批准指标验收，影响运行的修复后重跑长稳。

本页给出系统层测试方法和建议牵头，未改变现有人员的流程责任。记忆质量由赵旭东负责提取侧、肖宇负责召回侧，业务代表核对标准答案，评估集与调试样例分开并固定版本，记录每条错误而非只报一个均值。确定性规则严格比较权限、版本、数字和来源，模型语义质量按评审后的评分规则抽样复核。性能由肖宇牵头，三位开发及测试共同支持，固定规模、并发、输入长度、冷热比例、模型、硬件和后台负载，区分底层读写、保存入口与完整 Recall 的测量边界，记录吞吐、延迟分位数、错误率和资源。长稳和恢复建议谭旭梁牵头，每位测试核对所属流程。最终候选连续至少 24 小时，影响运行的修复需在新候选重新计时。部署与恢复由谭旭梁联合运行接手人验证，具体基础设施操作由被分派的开发或运行角色执行。性能门槛取合同和批准的需求，测量定义与数据集在 10 月 9 日准备节点前确认，10 月 23 日形成首批真实测量观察，11 月 6 日前补齐候选基线，不能临时编造数值或用 Mock 证明真实质量。

## 验收标准：用什么证据进入下一阶段

测试负责人出具结论，陈凯组织阶段验收，业务代表完成 UAT 签收。

| 关口 | 必须具备的结果 | 确认责任 |
| --- | --- | --- |
| 提测准入 | 范围与候选版本固定，开发自测通过<br>用例已评审，数据、环境和观察入口可用 | 对应开发提交<br>测试负责人检查 |
| 系统测试通过 | 核心业务与真实依赖必测项通过<br>质量、性能、长稳和恢复达标，阻断缺陷复测关闭 | 三位测试出报告<br>陈凯组织验收 |
| 业务验收通过 | 业务代表完成约定场景，逐项核对实际结果<br>一般遗留问题记录接受条件、负责人及关闭日期 | 业务代表签收<br>测试人员见证 |
| 上线交付 | 版本、配置、回滚与运行交接齐备<br>发布后核心冒烟与监控正常，失败则按预案回退 | 陈凯确认发布<br>运行接手人确认 |

交付证据：需求与用例对应表、执行记录、缺陷复测记录、专项报告及业务签收。

验收和任务分工分别说明。本页只解释各关口的条件和确认责任。提测先检查版本、范围、自测、用例评审、测试数据和观察入口，条件缺失时先补齐。系统测试通过要求约定核心业务和真实依赖用例通过，质量、性能、持续运行与恢复达到批准的口径，阻断和严重缺陷关闭且有复测记录。数据泄漏、丢失、旧或删除事实错误交付、核心功能不可用及故障假报成功均属于不能带入交付的阻断问题。业务 UAT 使用真实候选系统，由业务代表操作并签收，测试提供记录和见证。一般遗留问题必须明确接受人、限制、负责人和关闭日期，不能直接忽略。发布前确认部署、备份恢复、回滚和运行接手安排，发布后执行核心冒烟和监控核对，失败按演练预案暂停并回退。日期到达、Mock 通过或者测试报告出具都不能自动替代业务签收。

## 最终交付：能运行、能验证、能接手

完成约定环境中的 MVP，并交接持续使用所需的能力与材料

1. **固定交付版本**：服务、配置，模型与依赖。
2. **上线前演练**：备份恢复，部署、探测与回滚。
3. **验证关键业务**：保存、召回，更正、删除和隔离。
4. **运行接手**：监测、恢复，支持联系人与手册。

| 项目 | 说明 |
| --- | --- |
| 交付包 | 运行服务、接入说明、测试记录、部署恢复手册和签收记录 |
| 发布异常时 | 暂停切换，回退已验证版本，按演练方案恢复数据与任务 |

交付终点包括可运行服务和可接手的运行安排。发布前固定服务与配置版本，完成备份恢复和回滚演练，再验证关键业务。交付材料与服务版本一致，包含接入使用说明、测试和复验记录、部署恢复手册、业务签收以及运行接手人。发布过程中关键业务或探测失败时暂停切换，按演练方案回退。这样才能把最初的业务想法落实为甲方可以使用和持续运行的项目成果。
