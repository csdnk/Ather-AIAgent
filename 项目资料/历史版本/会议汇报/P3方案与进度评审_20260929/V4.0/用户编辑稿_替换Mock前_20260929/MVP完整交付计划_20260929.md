# P3 MVP 总体落地方案

版本：V4.0。更新日期：2026-09-29。

[主讲 PPT](P3_业务流程与落地方案_V4.0.pptx) · [逐页讲稿](逐页讲稿与会议记录.md)

本方案面向甲方说明最终业务目标与实施路径，不作为完成状态或验收记录。MVP 以 2026-12-01 为目标，细分节点为建议，真实 P2 以 10/10 可接入为前提。

## 项目目标：跨会话使用当前有效的记忆

服务应用、Agent 和 P4，连接分散在对话、任务和文档中的信息

| 项目 | 说明 |
| --- | --- |
| 持续可用 | 换一次会话，仍能找到相关记忆和原始来源 |
| 保持当前有效 | 更正后用新版本，删除或撤权按相应范围停止交付 |
| 结果可以追溯 | 交付内容有来源，未就绪或读取失败有明确状态 |

P3 的价值是让已经产生的信息可以在后续任务里持续使用。它不仅要存得下来，还要区分当前有效的版本、允许使用的范围，并说明材料来自哪里。应用或 Agent 用 P3 返回的材料完成回答和任务。项目目标包括内部维护与恢复，使服务在任务重试和进程重启后仍能继续工作。

## 业务场景：预算信息的一次完整生命周期

以“预算 20 万，后来更正为 15 万”为例

1. **保存信息**：记录预算 20 万，保留来源与权限。
2. **再次使用**：换一次会话，仍可找到相关材料。
3. **更正内容**：预算改为 15 万，后续使用新版本。
4. **删除或撤权**：删除后停止交付并清理，撤权仅限制被撤权方。

| 项目 | 说明 |
| --- | --- |
| 用户看到的结果 | 保存有状态，召回有来源，更正和删除会影响后续使用 |
| 系统持续完成的工作 | 后台加工、版本维护、检索准备、访问调度与失败恢复 |

用户第一次保存预算 20 万。适用的当前任务内容可以先使用，后台继续准备长期检索。跨会话请求时，系统取回相关且有效的材料。预算更正为 15 万后，旧版本不能继续作为当前预算交付。删除后，新查询和旧结果重取均不再交付相关正文，后台继续清理。撤权后，仅停止向被撤权方交付，其他有效授权仍可使用。外部身份撤销按双方约定的生效时间验证。物理清理可以在后台推进，但停止交付不能等待全部清理结束。

## 业务框架：存储与召回由内部维护支撑

按业务责任分工，共同组成一套记忆服务

应用决定何时保存信息、何时请求记忆。Remember 负责来源、版本和内容的维护，Recall 负责为一次请求组织可用材料。存储变化和实际使用记录交给内部 Operate，结合当前状态调整访问准备并核对执行结果。统一身份、任务和恢复机制支撑三条流程。P2 为各流程提供实际存取和约定的控制能力，不能替代 P3 判断一条事实是否当前有效。

## 记忆形成：先可靠保存，再准备长期使用

保存、当前任务可用、长期检索就绪分别表达

保存时检查身份、来源和重复请求，确认原始内容可靠保存。适用的当前任务记忆可以先用于当前工作。需要长期复用的内容，在后台获取固定版本、解析分块，并按需要抽取和压缩。模型生成候选后还要审核来源与内容，写入检索表示并核验，才能宣布长期检索就绪。不是每条记忆都必须经过全部加工步骤。任务可恢复，但旧版本或已删除内容不能因为迟到的后台结果重新生效。

## 记忆召回：交付能使用、可追溯的材料

找到相似内容之后，还要核对版本、权限与来源

1. **明确请求范围**：根据任务、身份，和指定来源选路。
2. **寻找相关记忆**：检索当前记忆，或长期记忆。
3. **核对有效性**：读取准确正文，检查版本与权限。
4. **组织并交付**：保留必要上下文，附来源和结果状态。

| 项目 | 说明 |
| --- | --- |
| 预算更正后 | 新请求使用 15 万，旧索引命中仍需重新核对 |
| 某个来源不可用 | 说明缺失或受限的范围，避免把读取失败当作没有内容 |

先判断要查哪些来源以及当前身份是否允许使用。检索获得候选之后，需要去掉不适用的版本、读取准确正文，再组织成有来源的材料。仍然有效但彼此冲突的内容要保留必要限定，不随意删去否定、数字和条件来压缩长度。交付前再核验一次，回应处理中发生的删除和撤权。返回的结果区分可用、正常空以及来源失败等情况，上层据此继续处理。

## 内部运行：根据使用情况持续调整访问准备

让常用内容更易访问，同时维护版本、权限和恢复能力

1. **观察业务变化**：保存、读取记录，及当前资源状态。
2. **形成调整方案**：按规则判断，保持或调整位置。
3. **执行并跟踪**：保留原动作身份，检查目标与进度。
4. **核对实际结果**：确认内容可读，再更新读取位置。

| 项目 | 说明 |
| --- | --- |
| 执行成功但回执丢失 | 查询原动作和实际结果，避免重复执行 |
| 调整访问层级 | 改变存取准备，不改变事实内容和使用权限 |

Operate 是内部持续运行机制。它依据存储与读取历史、当前有效性和资源情况决定访问准备。一次操作可能耗时或遇到超时，所以发起前保留动作身份，执行后核对目标内容和可读性，再交接读取地址。热、温、冷描述访问准备，与工作记忆、经历记忆和语义记忆的业务分类不同。MVP 覆盖基础规则与约定动作，具体存储介质和执行范围在联调基线中明确。

## P2 协作：业务处理与底层能力怎样衔接

每一项合作都明确谁负责、交付什么、怎样确认结果

| 业务需要 | P3 负责 | P2 提供及共同核对 |
| --- | --- | --- |
| 保存与读取 | 维护来源、版本和使用资格 | 实际保存和读取正文<br>内容与版本对应一致 |
| 长期记忆检索 | 组织记忆、审核候选并交付材料 | 写入、检索和清理<br>确认可检索及结果可读取 |
| 关系与冲突 | 解释事实之间的关系与限定 | 提供约定的关系查询能力<br>对象、关系和版本可以核对 |
| 访问调度 | 决定动作并跟踪、核验结果 | 提供约定的控制与执行反馈<br>实际效果、目标可读性可核对 |

甲方需要看到的是各项业务如何依赖 P2、责任如何分开。P3 不把底层成功回执直接视为业务完成，需要检查正文、检索可用性或实际动作结果。P2 团队负责其服务和环境，P3 开发负责适配，测试与对接人员负责样例和联调记录。关系远程映射、原操作查询及真实执行证据要逐项确认，不能假设所有需求已经由现有协议满足。段控制成功本身不证明物理数据迁移完成。

## 没有 P2 时：开发验证继续推进

业务规则保持一致，按阶段更换底层依赖

1. **本地验证**：用本地存储运行完整业务，检查保存、召回、更正、删除。
2. **模拟 P2 行为**：保存状态并主动制造故障，检查超时、重试和恢复。
3. **接入真实 P2**：复用同样场景与预期结果，重验实际存取、隔离和动作。

| 项目 | 说明 |
| --- | --- |
| Mock 怎样设计 | 保留对象、版本和动作状态，控制延迟、丢回执与迟到结果 |
| 切换以后验证什么 | 字段含义与业务结果一致，真实运行效果必须重新核对 |

没有 P2 环境时，两项工作可以先做。第一是让 P3 在本地持久存储上运行连续业务，验证自身规则和恢复。第二是让模拟器记住对象与操作状态，并故意制造延迟可见、写后丢回执等情况。它不能每次只返回成功。已有向量模拟器和相关测试可作为起点，完整跨接口的故障配置还要按业务场景补齐。真实环境就绪后复用业务数据和预期，重新验证实际存取、隔离、并发与执行效果。正式配置不静默退回模拟环境。

## 方案选择：围绕业务规则决定采用路线

复用成熟基础能力，由 P3 掌握事实、权限和交付判断

| 环节 | 采用路线 | 比较与取舍 |
| --- | --- | --- |
| 内容加工 | 按类型解析，模型辅助提取<br>P3 审核后保存正式记忆 | 整体交给通用记忆框架仍需补业务规则<br>保留来源、版本、更正和删除的控制权 |
| 相关记忆检索 | 本地语义模型寻找候选<br>P3 核验并组织材料 | 先采用可复现的本地编码基线<br>与远程服务比较质量、时延和资源开销 |
| 服务运行 | 单实例模块化服务<br>共享持久任务与恢复机制 | MVP 先控制部署和联调复杂度<br>多副本扩展时重新评估存储与调度 |

方案把通用能力和业务控制分开。文档解析使用专用组件，模型辅助抽取与压缩，但事实提交、版本、权限由 P3 处理。现有模型适配采用自有请求逻辑，不能因类名而称整个框架已接管。检索以 BGE 本地模型及 ONNX 运行方式形成可复现基线，并对材料做业务复核。服务采用统一入口、模块化职责与持久任务，便于 MVP 部署和恢复。与通用记忆/RAG 框架、远程语义服务、多微服务方案的比较来自需求适配分析，不是已完成的性能排名。正式模型与质量口径仍需通过代表性数据验证后固定。技术资料链接保存在备注中，仅供追溯。

## 落地路径：每个阶段形成可检查的成果

需求、设计、实现、验证和交付衔接为同一条工作链

1. **明确业务**：场景与范围，完成条件。
2. **形成设计**：流程与责任，依赖与接口约定。
3. **实现和验证**：模块实现，持续业务回归。
4. **联调和交付**：真实依赖验证，验收、上线、交接。

| 项目 | 说明 |
| --- | --- |
| 开发怎样组织 | 按存储、召回、内部运行分工，统一身份、任务和恢复规则 |
| 测试何时参与 | 从业务规则阶段参与，随实现同步准备数据与检查方法 |

想法首先要变成可检验的业务规则，例如更正后应该返回哪个预算，删除后哪些路径必须停止交付。规则转成流程与责任边界，再拆成模块工作。测试从定义业务时开始，随着实现同步编写检查和准备环境。真实依赖联调逐步扩大范围，完整系统通过验收之后才发布。每次修复都回到相同的业务预期检查，避免局部修改破坏完整流程。

## 测试设计：从业务预期生成检查场景

先明确怎样算正确，再覆盖正常、边界和故障情况

| 项目 | 说明 |
| --- | --- |
| 检查业务结果 | 核对内容、来源、当前版本和权限 |
| 覆盖状态变化 | 保存、更正、删除、撤权和处理中的变化 |
| 覆盖异常恢复 | 超时、重复请求、丢回执和处理中重启 |
| 分层记录结论 | 本地、模拟、真实环境各有结果和未执行项 |
| 保证可以复现 | 固定版本、样例和运行条件，保留失败与复测记录 |

当前先确定测试设计原则，不用一张看似完整的用例清单代替真实准备。按业务流程和状态转换拆场景，检查用户最终拿到什么结果。正常流程通过之后，还要覆盖边界和故障，包括操作已经完成但响应没有收到。开发侧做模块自测，测试侧按公开接口和连续业务验证，之后在真实依赖下重新执行。测试数据、执行条件和缺陷复测必须可追溯，测试数量不等于业务质量。

## 测试示例：更正和删除怎样验证

同一条预算业务，同时检查应该发生和不能发生的结果

| 执行场景 | 预期业务结果 | 重点补充的异常检查 |
| --- | --- | --- |
| 保存 20 万 | 有保存确认，保留原文与来源<br>长期未就绪时状态如实表达 | 重复提交、后台失败<br>处理中重启 |
| 更正为 15 万 | 后续使用新版本<br>旧结果重新获取仍需复核 | 旧索引命中、迟到加工<br>更正与召回同时发生 |
| 删除或撤权 | 删除后停止交付并后台清理<br>撤权后仅停止向被撤权方交付 | 旧结果重取、跨用户访问<br>删除后迟到写入 |
| 执行后丢回执 | 查询原动作，核对实际结果<br>确认后继续处理 | 操作是否重复<br>未完成是否被误报成功 |

先准备一组有明确正确答案的数据：两租户、两用户、两会话，预算原文和更正来源都保留。分别观察保存状态、当前任务可用与长期就绪。更正为 15 万后，验证新查询和旧结果重取。删除后，验证新查询、旧结果重取、旧索引和迟到任务都不再交付相关正文。撤权后，仅停止向被撤权方交付，并验证其他有效授权仍可使用。外部身份撤销按双方约定的生效时间验证。故障由测试主动控制，并同时核对实际数据和任务状态。相同预期适用于本地、模拟和真实 P2。

## 真实联调：先打通首条链路，再扩展范围

接口对齐、业务贯通与故障恢复共同进入验证

1. **接入准备**：环境、身份，样例与接口约定。
2. **首条真实链路**：保存正文，后台准备与召回。
3. **完整业务回归**：更正、删除、隔离，关系与调度。
4. **故障和运行验证**：异常恢复、质量，性能与持续运行。

| 项目 | 说明 |
| --- | --- |
| 每轮提交 | 实际业务结果、执行记录、问题归属和复测结果 |
| 发现接口差异 | P3 和 P2 分别修复自身实现，对接人员跟踪关闭 |

接入前先固定环境、身份、接口含义和可复现样例。先打通保存、后台准备、长期召回的最小真实链路，确认存入和取出的内容一致。再扩大到更正删除、跨租户与撤权、关系变化以及调度。随后验证丢回执、部分完成、依赖恢复与重启等故障，并测量质量与运行指标。对接人员提交复现材料，代码修改由相应 P3 或 P2 开发承担，不能因为能连接就称整个项目联调完成。

## 验收标准：按业务、质量和运行逐项通过

测试提供证据，技术负责人组织验收，业务方完成签收

| 验收范围 | 必须证明什么 | 谁确认 |
| --- | --- | --- |
| 业务与真实集成 | 保存、召回、更正、删除、隔离与恢复通过<br>约定的 P2、模型和身份链路有真实结果 | 测试出报告<br>技术负责人组织验收 |
| 质量与运行 | 达到约定质量和性能指标<br>最终候选连续运行至少 24 小时 | 测试测量<br>开发修复并复测 |
| 部署与恢复 | 部署、备份恢复、回滚和监测演练通过<br>关键业务在交付环境可复现 | 技术负责人<br>运行接手人 |
| 业务签收 | 业务必验场景通过<br>使用说明、限制和交接记录完整 | 业务验收代表签收<br>测试见证 |

验收分开看业务正确性、真实集成、质量性能、运行恢复和业务签收。PRD 中已有的核心读写、有效语义计算、压缩和调度目标需在固定测量条件下验证，不能用单元测试通过代替。MVP 长稳按最终候选连续至少 24 小时执行，影响运行的修复后重新计时。完整 Recall 的端到端时延与底层核心读写指标分开。阻断缺陷必须修复并复测，一般遗留项也要有接受条件和关闭计划。

## MVP 时间规划：开发、测试与联调并行

以 12/01 交付为目标，细分排期为建议，真实 P2 以 10/10 可接入为前提

9 月 30 日至 10 月 9 日固定最小业务范围、流程和接口约定、样例数据及环境责任。10 月 10 日至 11 月 6 日推进实现和真实联调，10 月 16 日检查首链阻塞，10 月 23 日交首轮真实闭环。测试设计从准备阶段开始，回归贯穿实现和修复。质量、性能与部署准备在十月同步开展。11 月 7 日至 13 日系统首验和 24 小时长稳，14 日至 20 日修复复测。21 日至 27 日业务验收与交接，28 日至 12 月 1 日发布检查和缓冲。这些是日历窗口，假期按实际出勤安排。若 P2 延迟，继续本地和模拟工作，重新排真实联调及交付预期，保留验收和修复窗口。

每个节点都提交可检查的成果，支撑下一阶段继续推进

## 最终交付：能运行、能验证、能接手

完成约定环境中的 MVP，并交接持续使用所需的能力与材料

1. **固定交付版本**：服务、配置，模型与依赖。
2. **上线前演练**：备份恢复，部署、探测与回滚。
3. **验证关键业务**：保存、召回，更正、删除和隔离。
4. **运行接手**：监测、恢复，支持联系人与手册。

| 项目 | 说明 |
| --- | --- |
| 交付包 | 运行服务、接入说明、测试记录、部署恢复手册和签收记录 |
| 发布异常时 | 暂停切换，回退已验证版本，按演练方案恢复数据与任务 |

交付终点包括可运行服务和可接手的运行安排。发布前固定服务与配置版本，完成备份恢复和回滚演练，再验证关键业务。交付材料与服务版本一致，包含接入使用说明、测试和复验记录、部署恢复手册、业务签收以及运行接手人。发布过程中关键业务或探测失败时暂停切换，按演练方案回退。这样才能把最初的业务想法落实为甲方可以使用和持续运行的项目成果。
