版本：V3.0。日期：2026-09-29。性质：面向最终交付的设计方案。目标沿用 PRD 的 2026-12-01 MVP，细分日期为本方案建议。

## 一、流程设计

目标是向应用、Agent 与 P4 交付可运行的记忆服务，覆盖保存、当前使用、长期化、召回、更正删除、内部基础调度、隔离和恢复。需求基线为 PRD V1.3 的 MVP P0 范围（FR01—15、FR17—18），FR16 预测预热属于后续 P1。MVP 长稳至少 24h，后续 Final 的 72h 与生产扩展独立验收。

### P3 整体流程框架

P3 对外提供 Remember 和 Recall。应用决定何时存、何时取，并用返回的记忆生成回答。Remember 维护来源、正文、当前版本与生命周期；Recall 只交付当前有效且获准的上下文。存储和实际读取形成事件，通过公共底座交给内部 Operate。Operate 据当前状态判断、执行并核对结果。公共底座负责身份、可靠任务、事务与事件，P2 负责契约内的底层存取和动作。后续都用预算 20 万更正为 15 万这一条场景解释。

### Remember：保存、加工与长期就绪

输入先做身份、来源和请求去重，再可靠保存。适用的当前任务内容可先进入 Working。长期链路通过持久任务获取固定版本、解析和分块，按需要压缩、提取和核验。模型输出只是候选；Remember 审查来源、冲突和版本，再形成正式记忆。所有预期块写入并核验后才能发布长期就绪。更正和删除先更新有效资格，阻断旧内容，再跟踪派生清理。后台失败不得让已确认事实消失，也不得提前宣称长期可检索。

### Recall：把有效记忆组织成上下文

Recall 接收问题、范围与预算，先决定使用当前记忆、长期记忆还是两者。长期路径完成编码、块检索和记忆级聚合，再由 B 审查资格并读完整正文。之后处理关系与排序、完整组预算和最终复核。只使用 Working 的路径可以跳过长期检索，但仍须核验和组包。结果区分完整、正常空、降级可用和不可用。来源失败不是没有命中；权限或当前版本无法确认时不得交付正文。

### Operate：持续判断、执行与核对

Operate 消费存储与读取事件、更新输入视图，再结合当前资格、容量、既有动作和规则产生决策。发起外部动作前持久化动作编号与目标。回执丢失时保留原编号，查询原动作并读取目标，而不是新建一次副作用。只有目标内容、版本和可读性得到核对，才能向 Remember 完成地址交接。交接前保留有效读取路径。MVP 保留 PRD 要求的基础规则和真实执行；具体介质与允许动作在最小契约基线中固定。

### P2 接口：按业务结果定义能力契约

P2 接口不能只按函数名或 HTTP/gRPC 成功码验收。正文路径要核对实际字节及当前内容绑定；向量路径要区分受理、持久写入与可检索，长期就绪由 B 发布。Recall 不因 P2 命中就绕开 B 的资格、关系和正文审查。关系能力与远程映射需要进入同一份契约，不能假定所有引擎入口都已可用。动作按原编号查询和独立读回。P2 负责其服务实现，对应 P3 开发负责适配；接口测试与对接人负责样例和差异记录。

| 链路与调用方 | P2 需要提供什么 | P3 如何确认完成 |
| --- | --- | --- |
| 正文存取 · Remember | 保存、精确版本读取、范围读取<br>返回正文、校验信息和存储位置 | 写入后准确读回；来源与内容版本绑定<br>读取失败、版本不符均不得当成功 |
| 向量写查 · Remember / Recall | 写入、检索、清理；查询原操作<br>模型空间、租户、批次与版本一致 | B 核对预期块后发布长期就绪<br>A 将命中交给 B 做资格与正文核验 |
| 关系读取 · 经 Remember | 按约定提供关系与版本证据<br>关系远程入口单列契约 | B 维护事实关系的业务含义<br>缺失、变化或不可验证时明确表达 |
| 动作执行 · Operate | 迁移 / 清理、原动作查询<br>目标状态与可读性检查 | 先核对真实效果，再由 B 交接地址<br>回执未知时保留原动作并恢复 |

### 没有 P2：保留业务流程，替换依赖实现

没有 P2 时不阻塞 P3 内部实现。第一层使用真实本地文件、SQLite 向量和本地缓存执行器，跑保存、后台加工、召回、更正、删除与重启恢复。第二层使用 StatefulVectorSimulator 和客户端桩，专门控制受理但不可检索、落盘后丢回执、删除后迟到写入等状态。现有源码提供这些可复用起点，但两者不等于完整 P2 服务。目标测试结构让本地、模拟和真实 Provider 共享业务预期、数据集与证据格式。切到真实 P2 后核对协议映射，并在真实读写、隔离、并发和物理动作上重跑。真实项缺环境就记录 not_run，不自动判通过；正式配置不能静默退回模拟器。

## 二、技术选型

每个模块按本方案固定采用路线、边界和替换点。比较基于 ADR 的框架研读与本次工程适配分析，不声称已经完成同条件性能排名。正式模型、版本和运行参数在基线阶段冻结；LLM 名称不由文档代填。

### Remember：加工内容，控制事实与版本

| 处理模块 | 采用路线 | 比较的技术 / 路线 | 选择理由与代价 |
| --- | --- | --- | --- |
| 输入与解析 | Pydantic 结构校验<br>pypdf / python-docx 解析 | Unstructured<br>通用文档处理框架 | 按文档类型轻量接入<br>复杂版式需补规则与失败处理 |
| 抽取与压缩 | P3 Python 处理步骤<br>HTTPX 调模型，校验 JSON | LangMem Core<br>LangMem 全栈存储 | 模型只给候选，B 审查来源后提交<br>自行维护提示、适配与质量规则 |
| 事实与就绪 | B 维护元数据和版本<br>正文经 P2，索引写后核验 | 模型直接更新记忆<br>索引写入即宣布可用 | 保存与长期就绪有明确边界<br>维护任务、校验与派生清理 |

这是面向 MVP 的采用路线。Python 领域步骤负责加工顺序，Pydantic 固定数据结构，HTTPX 负责受限模型请求。当前适配器虽使用 LangMemBatchExtraction 等类名，实际 ModelProvider 是自有 HTTPX 调用，不应写成 LangMem 库全栈已经接管。比较 LangMem 的 Core 与全栈路线后，保留结构化候选与来源审核机制，事实、版本、授权及事务提交由 P3 管理。解析采用按类型注册的适配器，pypdf 和 python-docx 是文档依赖。正式聊天模型通过受控端点接入，按中文事实、否定、条件、引用和压缩样本冻结模型版本；此处不虚构已经选定某个具体 LLM。框架比较来自 ADR 与接口适配分析，不是性能排名。 本轮补充比较 Unstructured 通用文档处理路线；当前文档类型优先通过专用解析器接入，复杂版式作为解析规则与失败处理设计，不声称专用解析器质量一定更高。比较依据：https://docs.unstructured.io/open-source/introduction/overview

- Pydantic：https://docs.pydantic.dev/latest/
- HTTPX：https://www.python-httpx.org/
- pypdf：https://pypdf.readthedocs.io/en/stable/
- python-docx：https://python-docx.readthedocs.io/en/latest/
- 参考 LangMem：https://langchain-ai.github.io/langmem/

### Recall：统一编码，分步检索和组包

| 处理模块 | 采用路线 | 比较的技术 / 路线 | 选择理由与代价 |
| --- | --- | --- | --- |
| 共享编码 | BGE small zh v1.5<br>FastEmbed + ONNX Runtime | 远程 Embedding<br>OpenVINO / IPEX 后端 | 先固定可复现的本地编码基线<br>消耗本地算力，换模型需重建索引 |
| 检索与融合 | P3 分段处理 + RRF<br>记忆级聚合、完整组预算 | LlamaIndex<br>Retriever / Query Engine | 业务版本、权限和分组可控<br>自行维护各阶段与适配器 |
| 精排与预算 | 可配置 CrossEncoder<br>tiktoken / 目标模型分词器 | 仅按向量分数排序<br>按字符估算长度 | 精排收益实测，预算按真实分词<br>增加计算；适配目标模型长度限制 |

编码基线选择 BAAI/bge-small-zh-v1.5，经 FastEmbed/ONNX Runtime 本地运行。OpenVINO、IPEX 与远程编码属于比较和后续实测路线，不因存在后端就宣称更快。检索采用 P3 的分段契约和 RRF；LlamaIndex 提供 Retriever、融合和后处理的研读参考，P3 不让通用节点去重或 Query Engine 代替记忆版本、完整冲突组及最终授权。CrossEncoder 按 required/fallback 配置和质量收益启用，不能默认所有请求都已精排。tiktoken 适用于匹配编码的目标模型；其他模型使用其 tokenizer。正式冻结模型、预处理、维度、精度、分词器及版本，并用同一评测集比较质量、时延与资源成本。

- ONNX Runtime：https://onnxruntime.ai/
- CrossEncoder：https://www.sbert.net/
- tiktoken：https://github.com/openai/tiktoken
- 参考 LlamaIndex：https://developers.llamaindex.ai/python/framework/

### Operate 与公共底座：动作可核对，任务可恢复

| 处理模块 | 采用路线 | 比较的技术 / 路线 | 选择理由与代价 |
| --- | --- | --- | --- |
| 内部控制循环 | Python 领域控制器<br>按当前状态判断与核对 | Kubernetes<br>controller-runtime / CRD | 参考 Reconcile，复用 P3 对象<br>无需集群控制面，规则需自行验证 |
| 任务与事件 | SQLite 事务 + 持久 Task<br>Outbox / Inbox 可靠交接 | Temporal 工作流<br>独立队列与数据库 | 业务记录和待办一起提交<br>自行维护租约、重试、幂等与恢复 |
| 授权与观测 | 统一授权检查、版本屏障<br>持久 Trace / 日志、健康探测 | 各模块独立鉴权<br>内存状态 / 外部日志 | 恢复仍能查事实、权限和原动作<br>需明确外部身份映射及监测适配 |

Operate 参考 Kubernetes controller-runtime 的 Reconcile 思路，但采用 Python 领域控制器，不把每条记忆变成 CRD。公共底座使用 SQLite、Task、Outbox/Inbox，在单实例 MVP 中把事实提交和后续交接放入同一事务。外部 P2 操作不属于本地事务，必须单独核对。Temporal 或队列加独立数据库是演进选项，需要迁移任务历史、租约和业务身份；依赖清单包含 Celery/Redis 不等于当前统一主链由 Celery 调度。身份、租户范围、授权和当前版本在发起与返回前复核。多副本、高写并发和跨实例恢复应重新评估存储与调度方案。日志和 Trace 服务诊断，不能替代持久事实。

- 采用 SQLite：https://www.sqlite.org/
- 参考控制器模式：https://github.com/kubernetes-sigs/controller-runtime
- 备选 Temporal：https://docs.temporal.io/

### 接入、P2 与部署：固定协议和运行边界

| 处理模块 | 采用路线 | 比较的技术 / 路线 | 选择理由与代价 |
| --- | --- | --- | --- |
| 应用 / Agent 接入 | FastAPI + Uvicorn<br>统一 HTTP / OpenAPI | Flask / 手写 HTTP<br>多模块分散入口 | 结构化校验、异步接口和统一状态<br>仍需定义身份、超时与幂等语义 |
| P2 数据与动作 | gRPC + Protobuf 客户端<br>对象、向量、关系和动作适配 | 另建 REST 协议<br>绕过 P2 直连存储 | 复用共享协议，保持 P2 责任边界<br>补齐业务字段、错误与结果映射 |
| MVP 运行交付 | 单实例服务 + 持久卷<br>Docker Compose 约定环境 | 多副本 Kubernetes<br>手工散装进程 | 先固定启动、探测、备份与回滚<br>不承诺多副本高可用，需演练恢复 |

应用侧采用统一 FastAPI 入口，由 Uvicorn 运行。P2 侧共享 Protobuf 并生成 gRPC 客户端，具体方法不能绕过业务租户、内容版本、模型空间和原操作查询契约。正文经 P2 对象能力，向量通过 P2 约定的正式路径；SQLiteVectors 是本地替代，Milvus 是适配和独立验证路线，不能未经范围确认替换 P2。关系远程接口需要显式映射。MVP 交付采用约定环境中的单实例与持久卷，以 Compose 固定启动和依赖配置。现有 Compose 冒烟入口与新的统一服务仍应做一致性核对，本方案不把旧脚本存在视为可直接上线。身份提供方按公司入口接入，P3 自己维护业务租户与授权规则。 本轮补充比较 Flask。统一结构校验、异步请求和接口文档采用 FastAPI 路线；这属于工程适配取舍，不是与 Flask 的吞吐实测排名。比较依据：https://flask.palletsprojects.com/en/stable/

## 三、测试设计与验收

### 测试设计原则

- **以业务结果为准**：核对正文、来源、当前版本和权限，不能只检查返回 200。
- **区分状态与完成**：已保存、当前可用、长期就绪分别断言；受理不等于生效。
- **覆盖正常、边界和故障**：在处理前、提交中、返回前改变条件，检查超时、重放与重启。
- **贯穿不可破坏的约束**：旧版 / 删除 / 越权内容不交付；同一副作用不重复发生。
- **分开验证层级**：本地、模拟、真实 P2 分别出结论，缺环境的真实项记为未执行。
- **结果必须能复现**：固定版本、数据、模型与配置，关联请求、任务、动作和复测记录。

### 测试实现：分层复用数据和断言

实施上沿用 pytest、pytest-asyncio、Ruff、Mypy 与 GitHub Actions。相比逐次手工演示和独立临时脚本，统一 fixture、参数化用例和报告更易复现和回归；仍需维护数据与预期。已有 contracts、runtime/flows、integration 目录、StatefulVectorSimulator 和客户端桩是可复用素材。下一步把 Provider 一致性场景抽为公共业务断言，分别传入 local、simulated、real 适配。真实配置缺失时生成明确 not_run 清单，不能借助全局 skip 把发布门槛变绿。现有 CI 工作流不等于这些新增分层门槛已经配置完成。质量和吞吐由专用脚本测量，pytest 负责可重复组织，不能拿单元测试数量替代质量。

| 层级 | 怎样实现 | 保留什么证据 |
| --- | --- | --- |
| 单元 / 契约 | pytest 参数化输入、状态和错误<br>用 fixture 隔离身份、时间与 Provider | 结构 / 版本 / 权限断言<br>错误类型与状态迁移结果 |
| P3 跨模块 | 真实 HTTP 边界、持久任务和临时数据<br>通过公开接口观察，增加进程重启 | 保存到召回的连续业务结果<br>任务 / Trace / 数据恢复关联 |
| 依赖一致性 | 同一数据和业务预期<br>分别接本地、模拟与真实 P2 | 三个环境分别报告<br>适配差异、真实未执行项 |
| 质量 / 运行 | 固定标注集、负载与机器<br>专用评测、压测和持续运行脚本 | 样本级错误、分位延迟、吞吐<br>24h 资源 / 积压 / 未决动作 |

### 测试设计示例：预算更正与删除

准备 tenant-a 与 tenant-b、两个用户和两个会话。第一会话保存预算 20 万，分别观察保存结果、Working 当前可用和长期就绪。只有达到对应就绪状态，第二会话才验证长期召回及来源版本。随后明确更正为 15 万，新召回应使用新值，旧召回结果再次获取也要按当前状态复核。删除后新查询、旧结果重放和迟到任务都不能交付正文。并行插入未授权身份、索引未就绪和提交前撤权等条件。稳定事实提取质量与规则正确性分层验证：先用受控输出验证流程，再用真实模型验证中文含义，不用 Mock 的正确句子证明模型理解正确。

### P2 联调：同样业务预期，核对真实效果

准入包括明确的 P2 联系人、协议与服务版本、可用端点、租户身份、受控数据、重置方法以及已约定动作目标。不要把普通 Object/Vector gRPC 方法与完整业务契约画等号。先完成正文写入到长期召回首链，再扩展更正、删除、关系和真实执行。丢回执要查询原操作，get_projection/目标读回用于核对实际目标，二者不是同一个检查。模拟器的 not_found 不能自动说明无副作用，也不能作为重建动作编号的依据。跨接口连贯性、并发和真实物理介质必须在真实环境补证。任一阻断缺陷由对应 P3 开发或 P2 方修复，对接人维护同一个问题单并跟踪复验。

| 验证阶段 | 执行重点 | 必须观察到什么 |
| --- | --- | --- |
| 接入前：契约一致 | 协议版本、租户、内容 / 模型空间<br>错误、超时、幂等及原操作查询 | 本地与真实适配字段含义一致<br>不支持的能力明确登记 |
| 首条真实链路 | 保存正文、索引写查、长期召回<br>核对实际正文、版本和来源 | 查询得到可验证的当前内容<br>不能只凭写入回执标为就绪 |
| 完整业务与隔离 | 更正、删除、关系变化、动作交接<br>跨租户、共享撤销和旧结果重放 | 旧 / 删除 / 越权内容不交付<br>真实动作可核对，读取路径有效 |
| 故障与恢复 | 写后丢回执、部分写入、读回不符<br>依赖恢复、进程重启、迟到结果 | 保留原操作编号查询与读回<br>不重复副作用，不假报成功 |

### 质量、性能与长稳：先固定测量条件

这些是待验证的目标，不是现有性能结论。质量维度应在测试基线阶段固定样本与评分规则，尤其是数字、否定、条件、引述和来源。P99 核心读写、完整召回端到端时延和语义编码吞吐属于不同测量对象。并发、输入长度、硬件、模型空间和热冷比例都要写进报告，失败与超时请求不能从分母移除。MVP 长稳至少 24 小时，Final 的 72 小时不混入本轮承诺。压缩需要同时达到字节比与质量门槛，模型或性能目标未满足时记录差距并处理，不能默认豁免。

| 验收对象 | 目标 / 判定原则 | 怎样测量 |
| --- | --- | --- |
| 内容与检索质量 | 来源、数字、否定和条件不失真<br>覆盖更正、冲突与负样本 | 冻结标注集与评分规则<br>报告检索命中、事实保真和失败样本 |
| 正文压缩 | 压缩 ≥ 5 倍且质量通过 | 比较同批真实保存字节<br>压缩失败与保真问题单独记录 |
| 当前记忆核心读写 | P99 < 10 ms | 固定硬件、负载、并发与冷热比<br>完整 Recall 时延另测，不混为一项 |
| 有效语义计算 | ≥ 2000 条 / 秒 | 固定模型、输入长度、批次和硬件<br>统计实际计算，不把缓存命中计入 |
| 基础调度 | 规则正确率 100%，错误降层 0 | 按固定规则回放，核对真实目标<br>额外测前后台竞争与恢复 |
| MVP 长稳 | 最终候选连续 ≥ 24 h | 固定真实依赖，记录错误 / 积压 / 资源<br>影响运行的修复后重新计时 |

### 验收标准：按证据逐级进入下一阶段

验收与任务分配分开。这里规定允许前进的证据，不把人员分工当作完成。功能验收包括真实提供方和调用方链路；系统验收包括质量、性能、最终候选至少 24h 长稳及恢复演练。UAT 使用真实候选系统，由业务代表签收，测试通过不能自动代签。缺陷严重度中的 P0/P1 必须清零并复验；P2/P3 一般缺陷按业务接受条件记录，这里的 P2 缺陷等级与 P2 存储模块不同。每份结论登记范围、版本、日期、环境、实际结果、缺陷和复验关联。正式交付资料与运行版本一致，范围未实现或依赖未验不得用模拟结果关闭。

| 验收层级 | 通过条件 | 结论与签收责任 |
| --- | --- | --- |
| 功能与真实集成 | 约定 P0 业务、边界、隔离和恢复通过<br>P2 / 模型 / 身份实际路径有证据 | 对应测试出报告<br>陈凯组织技术验收 |
| 系统验收 | 质量与性能达标，最终候选 ≥ 24h<br>阻断缺陷修复并复测，部署恢复演练通过 | 测试执行，开发修复<br>陈凯确认准入 |
| 业务 UAT | 真实业务必验场景全部通过<br>更正删除、隔离、故障与交付运行可复现 | 业务验收代表签收<br>测试见证并归档 |
| 发布交付 | 服务、配置、模型与证据同版本<br>备份、回滚、监测和运行接手完成 | 陈凯组织发布<br>运行接手人确认接收 |

### 用例实施约定

每个 FR 按“前置状态、输入动作、业务预期、禁止结果、故障插入点、清理、证据”展开。以两个租户、两个用户和两个会话作为最小隔离数据。单元与契约用例使用确定性数据；P3 跨模块用例通过公开边界和真实持久任务验证；模型质量使用标注集；真实 P2 用例独立运行。

Provider 测试目标是复用相同业务断言，分别装配 local、simulated、real 三类适配。现有 tests/contracts/p3、tests/runtime/flows、tests/integration、StatefulVectorSimulator 和客户端桩提供起点；公共断言与环境参数化仍需按本方案实施。这不是已经完整建成的 TC 清单。

快速检查使用 Ruff/Mypy/pytest，每次提交执行。跨模块自动回归持续运行；真实依赖与质量/性能按稳定环境执行；候选版本运行完整回归和至少 24h 长稳。缺少真实环境时列 not_run，发布门槛不能自动通过。报告记录版本、环境、Provider 类型、配置摘要、模型/数据集版本、请求/任务/动作标识、实际结果和复验。

采用工具：pytest（https://docs.pytest.org/en/stable/）、GitHub Actions（https://docs.github.com/en/actions）。

## 四、时间节点与任务分工

### MVP 时间规划：实现、测试和联调并行

沿用 12 月 1 日 MVP 目标。9/30—10/09 固定最小范围、接口、模型和数据口径、测试原则及环境责任，假期按实际出勤安排。10/10—11/06 同步推进 P0 实现与联调，10/16 检查首链阻塞，10/23 交首轮真实闭环。测试设计从第一阶段开始，自动回归贯穿实现、修复和 UAT，质量性能与部署基线从十月同步准备。11/07—13 做系统首验和 24h 长稳，11/14—20 修复并对最终候选复测。11/21—27 业务 UAT 与交接，11/28—12/01 只做发布检查和缓冲。若 P2 晚于前提，继续本地和模拟验证，但重排受影响的真实链路与交付预期，保留验收和修复窗口。

### 关键节点：交付物和退出条件一起固定

设计基线不是花整个十月重建接口，而是用现有契约收敛少量关键差异。10/16 是早期检查点，用来暴露环境和语义缺口；10/23 才是首轮真实闭环证据节点。所有预期都要注明 Provider 和环境类型。11/06 的候选必须具备系统验收条件，不能把首次完整集成压到 11 月下旬。11/20 和 11/27 分别完成技术系统门槛及业务签收。发布缓冲不承接首次联调或首次质量测试。若关键资源晚到，陈凯组织调整计划，不把原目标日期写成已经确认的新承诺。

### 上线交付：发布可运行版本，交接恢复能力

上线流程先固定候选版本、镜像或安装包、配置及模型指纹，再按既定策略排空或保留在途任务并完成可恢复备份。部署后检查 live、ready、依赖与后台工作状态，执行保存、当前读取、长期召回、更正删除的关键业务冒烟，不能只检查页面打开。验证通过后由运行角色接手监测、备份、故障处置和支持联系人。失败则暂停对外切换，回退演练过的版本，并按兼容的数据恢复方案处理，不把未知副作用重新发起。MVP 交付包包含运行服务、配置和接入说明、功能/集成/质量/性能/24h证据、缺陷复验、部署恢复回滚手册及业务签收。后续 Final 的生产扩展和 72h 不混同本次 MVP 完成。

### 时间规划的执行约束

- 9/30—10/09：收敛已有契约、模型与数据口径，设计测试，落实角色和真实环境。假期只按实际出勤核算工时。
- 10/10—11/06：P0 实现、自动回归与 P2 联调并行；10/16 检查首链，10/23 形成首轮真实闭环，质量性能和部署准备同期开展。
- 11/07—11/20：系统首验与修复复测各一周；影响运行的改动后，最终候选重新执行至少 24h。
- 11/21—11/27：UAT、缺陷复验及运行交接。
- 11/28—12/01：发布检查与缓冲，不放入首次联调或首次质量验证。

若真实 P2 在 10/10 尚不能接入，继续本地和模拟任务，建立由对应提供方负责的阻塞项。陈凯依据最早可用时间重排真实首链、候选与交付预期，不压缩系统验收、UAT 和修复窗口。没有 P2 的验证结果不能代替真实 P2 任务关闭。
