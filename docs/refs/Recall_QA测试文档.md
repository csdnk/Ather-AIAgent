# Recall 模块 QA 测试文档

更新日期：2026-10-07。项目：Agent Memory Management / Aether P3。本文件包含人工、API、集成及受控故障测试规程。

测试范围包括当前 Recall 的请求接纳、来源选择、Query 编码、向量候选、Remember 资格核验、精确版本全文、融合与重排、完整关系组的预算、最终提交、结果重取、事件及异步恢复。测试中，Remember 仅用于准备数据，并提供权威资格和正文；Operate 仅用于核对 Recall 事件及热副本对召回的影响。

这些用例依据项目文档中的当前功能规则设计。本地目录没有业务源码、完整 Schema 或可访问的运行接口，执行前需登记目标源码 SHA、镜像 digest、实际配置和接口契约。全部用例尚未执行，状态为`not_run`；用例数量不代表通过率。

本文沿用项目术语：A 是 Recall 编排，B 是 Remember 权威服务，RF 是任务、身份与事务执行框架。candidate 表示候选引用，read 表示读取权威正文，packed 表示结果已提交，delivered 表示结果已交给传输层。

文中的正常成功、空、进行中、降级、失败、未知和失效描述业务含义，具体枚举与 HTTP 码以目标契约为准。规则未明确时，先验证已有的安全要求，并记录待明确项；完整用例仍不能标为`passed`。

## 2. 执行指南

### 2.1 记录版本与环境

| 项目 | 执行前填入 |
|---|---|
| Run ID | 日期加唯一后缀；各用例和变体使用独立后缀 |
| 源码/镜像 | 40 位源码 SHA、镜像 digest、构建映射、目标分支 |
| 后端与隔离 | PG database/schema、Redis namespace/scope 配额、Milvus database/collection、Ceph bucket/prefix、Temporal namespace/deployment/task queue |
| 模型与计量 | BGE 实际权重/hash、用途前缀/tokenizer、维度/归一化/距离、ContextPack tokenizer/渲染模板、reranker 模式/权重/长度上限 |
| 服务策略 | 各来源 Top K、页/块/轮等实际限额、最终包条数/关系计数、来源部分策略、重组限制、http_wait、阶段与总 deadline/heartbeat/retry |
| 接口契约 | 目标/docs 保存请求/结果/Record/job/error Schema；当前 B 与 RF 内部接口映射 |
| 身份与接线 | 当前身份凭据、tenant 启用、scope、auth_epoch/revision；B 资格/正文/关系/最终守卫、实际 Worker 及探针 |
| 控制能力 | 已指定的故障代理/管理接口/阶段屏障/事件只读视图；缺失手段及影响用例 |

集成测试使用真实 PG、Redis、Milvus、Ceph、Temporal 和原生 BGE。PG 优先采用每人独立的 database；同一 database 中的不同 schema 仍可能共享 advisory lock。故障只作用于本次独有资源和连接，不停止共享服务，也不清空共享存储。

分别核对各层健康状态：`/p3/live`是否响应，`/p3/readyz`是否就绪，授权查询`/p3/ready`与`/p3/health`时的依赖状态，Worker 是否实际工作，以及能否完成一条 Recall。新集合尚未建立时的 vectors=unknown 要与业务建集失败区分。探针只读；结构检查通过也不能证明连接或业务可用。

### 2.2 准备数据并提交请求

按[O1](#ref-o1)准备数据，再按[O2](#ref-o2)提交请求。以下请求来自项目文档，1000 只是示例预算；实际预算根据[F9](#ref-f9)的计数结果和[Q01](#ref-q01)确认的合法域确定。

```http
POST /p3/recall
Authorization: Bearer <本例授权凭据>
X-Operation-ID: <本例唯一ID；原意图重试保持不变>
Content-Type: application/json
```

```json
{
  "query": "用户的咖啡加糖习惯是什么？",
  "selection": {"session_id": "本用例真实会话ID"},
  "sources": "working",
  "token_budget": 1000
}
```

按[O3](#ref-o3)轮询原任务，按[O5](#ref-o5)重取原结果，按[O6](#ref-o6)核验阶段和事件。资格变更依[O4](#ref-o4)等待权威回执后再继续；缺少 endpoint 或请求体时，使用负责人提供的当前受控操作。

### 2.3 执行故障与并发场景

在本次独有连接或代理上模拟网络故障：拒绝连接、连接可达但响应慢、半响应、错误结果，以及执行后丢失响应。非法协议输出由严格契约控制面生成，其证据与真实依赖端到端结果分开。CPU 晚到场景使用现有慢推理控制手段；PG 锁只在独有 database 中受控持有，并记录 owner 与释放时点。TLS 测试使用测试配置和证书，不修改共享证书或关闭校验。

并发测试先确认各请求单独执行时正常，再借助屏障交错执行，每次只改变一个关键资格条件。保留原 operation、job 和 recall 的关联，根据持久记录判定结果，不能只看客户端超时或 HTTP 码。

### 2.4 核对结果、保存证据并清理

1. 核对实际身份、selected_sources、精确 Ref/version/hash、完整 rendered_context 及整体 token 数、原 ID、终态和原因。
2. 请求被拒绝、返回空或失败时，检查是否错误生成 Pack、packed 或 delivered。正文可能在后续失败前已成功读取，这类 read 应保留；候选发现和资格核验本身不算正文 read。
3. 并发和恢复场景核对结果与事件的唯一性、late output 的 fence 拒绝，以及资源是否最终回收。健康状态结合实际阶段判断。
4. 先保存原 job、Trace 和故障证据，再释放本例屏障、撤除故障、恢复配置与身份，最后逐对象清理自有数据。不清空整库、整 bucket 或共享存储。无法确认所有权的残留应保留，并记录原因。

证据至少包括脱敏请求与响应、UTC 时间线及上海时区显示、operation/job/recall/trace 关联、实际 backend binding、关键阶段和事务、事件 ID 及计数、原正文与当前正文及 Pack 摘要、源码 SHA 和镜像 digest。普通调用方不能取得受限诊断信息；安全测试使用不含敏感信息的 canary。正文和凭据默认不写入技术日志。

#### [RC-API-01](#ref-rc-api-01) Working 请求端到端验证

<a id="case-rc-api-02"></a>

#### [RC-API-02](#ref-rc-api-02) Query 空值与类型分区

优先级：[P1](#ref-p1)　依据：[Q01](#ref-q01)

**前置与输入**：[F1](#ref-f1)；query 缺失/null/空字符串/纯空白/数字/数组

**预期结果与证据**

query 的类型、必填和 trim 规则以目标 Schema 为判定依据。空白输入行为未定义时记录阻塞，不预设 400/422。拒绝的请求不能提交成功 Pack，也不能让 CPU 无限制运行。

<a id="case-rc-api-03"></a>

#### [RC-API-03](#ref-rc-api-03) Unicode 与多语言 Query 输入

优先级：[P2](#ref-p2)　依据：[R04](#ref-r04)/[R12](#ref-r12)、[S04](#ref-s04)§1、[S05](#ref-s05)真实预算

**前置与输入**：[F1](#ref-f1)；中文、英文、混合、emoji、组合 Unicode、换行、引号查询

**执行步骤**

1. 各变体使用新 ID 提交请求
2. 比对原 query 摘要、模型实际输入和 Pack

**预期结果与证据**

输入不能损坏，也不能在未声明的情况下改变含义；长度按模型 token 计量，不按字节计量。记录语义检索结果，不要求不同语言或归一化形式得到相同排名。

<a id="case-rc-api-04"></a>

#### [RC-API-04](#ref-rc-api-04) token_budget 合法域与极值

优先级：[P1](#ref-p1)　依据：[Q01](#ref-q01)、[S05](#ref-s05)预算

**前置与输入**：Schema 规定预算最小 m/最大 M；[F9](#ref-f9)

**执行步骤**

1. 分别使用 m-1/m/m+1/M-1/M/M+1 及 0/-1/小数/字符串/bool/null/极大整数作为输入
2. 检查组包

**预期结果与证据**

合法取值按 Schema 判断，合法边界用整包计数验证。非法值不能造成溢出或绕过上限。若 m/M 未明确，数值域断言记为 blocked_requirement；1000 只是示例，不能作为上限。

<a id="case-rc-api-05"></a>

#### [RC-API-05](#ref-rc-api-05) sources 缺省和非法枚举

优先级：[P1](#ref-p1)　依据：[Q01](#ref-q01)

**前置与输入**：[F1](#ref-f1)；sources 省略/null/空/未知/大写/数组

**执行步骤**

1. 逐项发请求
2. 记录 selected_sources 与错误

**预期结果与证据**

只接受契约规定的值，并按规定处理缺省值。未知值不能自动改为 auto/both。省略字段和大小写的处理规则须由目标规范确认。

<a id="case-rc-api-06"></a>

#### [RC-API-06](#ref-rc-api-06) selection 结构与空选择

优先级：[P1](#ref-p1)　依据：[Q01](#ref-q01)

**前置与输入**：selection 缺失/空对象/null；合法 session/task；错误字段类型

**执行步骤**

1. 逐项提交
2. 检查可信 scope、auto 选择和候选

**预期结果与证据**

默认值和类型按 Schema 判断。合法的空 selection 也不能扩大授权 scope；session/task 不能作为可信身份。缺少契约时，只验证授权范围不会扩大。

<a id="case-rc-api-07"></a>

#### [RC-API-07](#ref-rc-api-07) 查询和范围字符串注入

优先级：[P0](#ref-p0)　依据：[R01](#ref-r01)/[R03](#ref-r03)、[S01](#ref-s01)selection、[S03](#ref-s03)

**前置与输入**：[F4](#ref-f4)；query 或 selection 合法字符串中含引号、过滤表达式、SQL 样式、换行

**执行步骤**

1. 在隔离数据中发送无害 canary
2. 检查看过滤计划、返回 ID 及状态

**预期结果与证据**

数据按字面处理，不拼接成权限/过滤指令；无越权，无异常数据库动作；错误不泄露 DSN/内部受限 ID。

#### [RC-API-08](#ref-rc-api-08) 客户端伪造内部策略字段

优先级：[P1](#ref-p1)　依据：[Q01](#ref-q01)

**前置与输入**：未知 JSON 字段 tenant_id/K_memory/raw_filter/guard/策略版本

**执行步骤**

1. 分别添加单字段
2. 尝试改已有字段与未知字段组合

**预期结果与证据**

未知字段的拒绝或忽略规则以目标规范为准。无论如何处理，都不能覆盖认证、内部 guard 或服务端策略；客户端不能增加 TopK 或将期限设为无限。

<a id="case-rc-api-09"></a>

#### [RC-API-09](#ref-rc-api-09) 畸形请求与解析失败

优先级：[P1](#ref-p1)　依据：[R13](#ref-r13)、[S04](#ref-s04)§4–5

**前置与输入**：截断 JSON、错误 Content-Type、无请求体、嵌套过深；只用测试端点

**执行步骤**

1. 逐项发送
2. 检查接纳与结果/事件

**预期结果与证据**

已定义的协议错误应有可定位的响应；解析失败不能产生成功 Pack/packed，也不能导致未捕获的崩溃或泄露正文。请求大小和嵌套深度阈值未定义时，只记录观察结果。

#### [RC-API-10](#ref-rc-api-10) 重复 JSON 键与实际输入绑定

**前置与输入**：含重复键 query/sources/token_budget 的原始 JSON 文本

**执行步骤**

1. 交换重复键顺序
2. 比较解析请求与幂等签名

**预期结果与证据**

解析/拒绝遵目标契约；签名绑定实际执行的同一语义，校验值与实际执行值必须一致；重复键政策需确认。

#### [RC-API-11](#ref-rc-api-11) 正式路由和 HTTP 方法

#### [RC-API-12](#ref-rc-api-12) 不存在或非法结果标识符

### 3.2 幂等与接纳（8 条）

<a id="case-rc-ide-01"></a>

#### [RC-IDE-01](#ref-rc-ide-01) 同一 ID、相同请求体的串行重试

优先级：[P0](#ref-p0)　依据：[S01](#ref-s01)持续运行、[S02](#ref-s02)§Recall1

**前置与输入**：[F1](#ref-f1)；同[U01](#ref-u01)、同 operation ID、相同原请求体

**执行步骤**

1. 成功 Recall
2. 串行重发原 POST 两次
3. 比较 job/recall/事件

**预期结果与证据**

重试返回或关联原操作，不产生重复 Pack 或 packed。重取时仍按当前授权检查，幂等不能让原内容永久可读。

<a id="case-rc-ide-02"></a>

#### [RC-IDE-02](#ref-rc-ide-02) 同一 ID 绑定不同请求

优先级：[P0](#ref-p0)　依据：[S04](#ref-s04)§4

**前置与输入**：同 ID，query/selection/sources/预算任一不同

**执行步骤**

1. 原请求在[B0](#ref-b0)或已终态
2. 每个变体重用 ID 改一字段

**预期结果与证据**

签名不一致时，不能继续原执行或另行生成成功结果，也不能篡改原请求状态和正文。具体冲突码以目标 Schema 为准。

<a id="case-rc-ide-03"></a>

#### [RC-IDE-03](#ref-rc-ide-03) 同一 ID、相同请求体的并发接纳

优先级：[P0](#ref-p0)　依据：[S02](#ref-s02)§1、[S07](#ref-s07)§6

**前置与输入**：同 operation ID 原请求在[B0](#ref-b0)

**执行步骤**

1. 两客户端同步 POST 同体
2. 释放[B0](#ref-b0)
3. 轮询双方

**预期结果与证据**

只接纳一个业务意图，并关联唯一结果。请求执行中应查询原 job；并发请求不能生成两个成功 Pack 或两份 packed。

<a id="case-rc-ide-04"></a>

#### [RC-IDE-04](#ref-rc-ide-04) 跨主体同字面操作 ID

优先级：[P0](#ref-p0)　依据：[Q07](#ref-q07)、[R01](#ref-r01)

**前置与输入**：[U01](#ref-u01)与[U04](#ref-u04)或[U02](#ref-u02)用同 operation ID；各有独立[F1](#ref-f1)

**执行步骤**

1. 交错提交相同字面 ID
2. 各取结果

**预期结果与证据**

幂等命名空间按[Q07](#ref-q07)；无论允许独立操作还是冲突，均不得返回另一主体/tenant 的结果、签名或元数据。

<a id="case-rc-ide-05"></a>

#### [RC-IDE-05](#ref-rc-ide-05) 缺失与畸形操作 ID 头

优先级：[P1](#ref-p1)　依据：[Q01](#ref-q01)

**前置与输入**：X-Operation-ID 省略/空/错误格式/重复 header

**执行步骤**

1. 逐项发合法体
2. 检查 Record 和接纳

**预期结果与证据**

ID 是否必填、能否生成，以及重复 header 的处理规则均以目标规范为准，不预设 UUID 格式。有效操作必须有稳定、可追溯的原 ID；拒绝的请求不能留下孤立的成功记录。

<a id="case-rc-ide-06"></a>

#### [RC-IDE-06](#ref-rc-ide-06) 结果提交后响应丢失

优先级：[P0](#ref-p0)　依据：[S02](#ref-s02)横切异常、[S07](#ref-s07)§6

2. 只查询原 job/recall

**预期结果与证据**

### 3.3 权限与范围（15 条）

<a id="case-rc-auth-06"></a>

2. 去掉/改变 selection 分别测试

**预期结果与证据**

<a id="case-rc-auth-07"></a>

#### [RC-AUTH-07](#ref-rc-auth-07) 客户端身份覆盖尝试

不覆盖 Bearer 主体/home_scope，不允许客户端伪造 grant/auth_epoch；是否拒绝未知字段按[Q01](#ref-q01)。

<a id="case-rc-auth-08"></a>

#### [RC-AUTH-08](#ref-rc-auth-08) 索引命中不得授予正文读取权

<a id="case-rc-auth-09"></a>

#### [RC-AUTH-09](#ref-rc-auth-09) 有效共享的可发现性

**执行步骤**

1. 确认有效 grant
2. [U08](#ref-u08) Recall 与 result
3. 同 query 对照无 grant 身份

<a id="case-rc-auth-10"></a>

#### [RC-AUTH-10](#ref-rc-auth-10) 共享撤销后的新旧读取

3. 原 result 重取

<a id="case-rc-auth-11"></a>

#### [RC-AUTH-11](#ref-rc-auth-11) 租户停用后重新启用的 epoch 校验

优先级：[P0](#ref-p0)　依据：[S01](#ref-s01)排障、[S02](#ref-s02)

**前置与输入**：[F12](#ref-f12)；tenant 启用→停用→重启用，身份 epoch 递增

2. 重启用仍持旧凭据

**预期结果与证据**

<a id="case-rc-auth-13"></a>

<a id="case-rc-auth-15"></a>

#### [RC-AUTH-15](#ref-rc-auth-15) 仅权限阻断与正常空区分

### 3.8 RRF 与融合（8 条）

<a id="case-rc-fus-02"></a>

同路重复不增加 A 的分数，也不把 B 从第二个独立名次移到第三个。跨来源时，每路对同一 Ref 最多贡献一次。

Inbox 与消费效果原子提交；原事件重投后确认，但不再次计热。HTTP Recall 成功本身不足以证明事件提交和消费已通过验证。

<a id="case-rc-evt-06"></a>

#### [RC-EVT-06](#ref-rc-evt-06) 跨版本读取与结果重取的事件语义

优先级：[P1](#ref-p1)　依据：[Q10](#ref-q10)、[S02](#ref-s02)/[S04](#ref-s04)

**前置与输入**：同 recall 同 ID 两版本读成功（需合法资格变更）；[F12](#ref-f12)结果重取 GET 多次

**执行步骤**

1. 按批准场景读两版本
2. 重复 GET 已保存结果
3. 观察 read 与 delivery

**预期结果与证据**

同精确版本重复读取去重可判；跨版本热度键及 GET result 新增 read/delivery 的规则按[Q10](#ref-q10)；未明确不自行认定每次计热或永不计热。

<a id="case-rc-evt-07"></a>

#### [RC-EVT-07](#ref-rc-evt-07) 下游不可用 Outbox 积压

优先级：[P1](#ref-p1)　依据：[R17](#ref-r17)、[S02](#ref-s02)横切异常

**前置与输入**：下游 Operate 暂不可达/慢，Recall 已 commit 事实

**执行步骤**

1. 停本例消费者或隔离其连接
2. Recall
3. 恢复投递

**预期结果与证据**

## 4. 关键竞态时间线

这些时间线补充相关用例的具体执行顺序，不另计用例数。异常发生后保留原 operation；时间记录用于判断先后，不用 sleep 安排竞态。

<a id="timeline-t1"></a>

### 4.1 [T1](#ref-t1)：[RC-TX-02](#ref-rc-tx-02) 最终守卫与撤权

1. 在独立 database 准备[F1](#ref-f1)；[U01](#ref-u01)合法，先确认普通 Recall 可命中。
2. 新请求 R 停在[B6](#ref-b6)，记录 guard 采用的对象 revision/auth_epoch 及持有事务/锁。
3. 独立管理客户端尝试撤权并记录其权威提交时刻。如果该写被同事务锁阻塞，应先记录阻塞，不声称撤权已完成。
4. 执行两种可实现顺序：撤权先提交再放行 R；或 R 先提交再撤权。不能在同锁内伪造两者同时已提交。
5. 第一顺序：R 不能提交撤权材料；第二顺序：R 此前提交的 Pack 可保留事实，但撤权后的 result 重取不能泄露。
6. 核对 Pack、终态、Outbox 原子性和条件提交证据；依[Q12](#ref-q12)核验当前 UoW/条件提交证据，不能将 guard 之后的普通无条件写入当安全提交。

<a id="timeline-t2"></a>

### 4.2 [T2](#ref-t2)：[RC-CON-01](#ref-rc-con-01) 搜索后更正且新索引 pending

1. [F5](#ref-f5) v2/g2 Ready，R 返回 v2 命中后停[B2](#ref-b2)；保存 score/Ref/space/hash。
2. B 更正为 v3 并提交，v3 投影暂停在发布前，留下 v2 向量物理残留。
3. 放行 R；查看 qualify/load/final_guard 采用哪个版本与覆盖。
4. 判定无 v2 旧正文、无 v2 分数配 v3 正文；pending 处理按[Q09](#ref-q09)。随后放行 v3 索引，**新 operation**独立请求验证 v3 可查，不重写 R 原结果。

<a id="timeline-t3"></a>

### 4.3 [T3](#ref-t3)：[RC-CON-05](#ref-rc-con-05) PG 锁与心跳

1. 在本例 database 使用现有受控事务持已确认同一 UoW 锁，记录 owner 与锁种类；不得仅锁无关行后称触发 advisory lock。
2. 在授权/页可见性/末端身份复验边界分别运行 MemoryCandidates 搜索；并行记录事件循环 pulse、Activity heartbeat 与本例 health。
3. 持锁 1 秒后受控释放；记录实际持锁时间、等待与最大 pulse gap、剩余 deadline、尝试 ID 和最终 job 状态。
4. 核验本次目标的授权、Ref/Pack 一致性、heartbeat 与原 deadline，不能只看锁释放后是否返回。
5. 再完整执行[RC-E2E-01](#ref-rc-e2e-01)。仅锁诊断成功不能证明完整 Recall 成功；根因须由实际阶段/锁/任务证据确认。

<a id="timeline-t4"></a>

### 4.4 [T4](#ref-t4)：[RC-EVT-05](#ref-rc-evt-05) 消费成功但 ACK 丢失

1. 取得原 read event_id 及下游输入水位，暂停[B8](#ref-b8) ACK。
2. 确认 Inbox+效果已经提交，丢 ACK 并重投同 event_id。
3. 原事件再次确认但同 Ref/版本热度输入只生效一次；packed/delivered 不能补加一次。
4. 原 Recall 记录与 Outbox 交接证据仍可追溯。无法查询 Inbox/水位不得只看页面数字就报 passed。

<a id="timeline-t5"></a>

### 4.5 [T5](#ref-t5)：[RC-ASY-05](#ref-rc-asy-05) 失租 Worker 晚到提交

1. 旧尝试 a1 运行至[B1](#ref-b1)/[B4](#ref-b4)，暂停至租约丢失；记录 lease/revision/fence。
2. 由当前编排授予 a2 新租约，合法完成或因资格变化终止。
3. 放回 a1 旧输出；检查其被拒证据，原 Recall 终态、Pack hash、事件 ID 不变。
4. 若 a1 远端已造成残留，仅 B 当前发布资格决定可召回；不得把残留存在当 a1 有效完成。

<a id="timeline-t6"></a>

### 4.6 [T6](#ref-t6)：[RC-CON-04](#ref-rc-con-04) 组包之后新增冲突成员

1. R 计划 G={[M3](#ref-m3),[M5](#ref-m5)}，记录 relation r1、成员 Ref、临时渲染及 tokens，停[B5](#ref-b5)。
2. B 发布 r2 加入[M6](#ref-m6)；分别使[M6](#ref-m6)合法可读、无权、正文不可用、使整组超预算四变体。
3. 最终守卫必须发现 r2；可重组时补读[M6](#ref-m6)并整体重新计数，不能沿 r1 授权半组。
4. 不可读变体不交半组，按当前规则跳过该组；其他独立可信组可交。公开终态/覆盖按[Q04](#ref-q04)确认，重组停止条件按[Q05](#ref-q05)，不得无限重组。
